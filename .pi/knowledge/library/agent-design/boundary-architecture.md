# Agent 设计范式：决策边界——能力供给与模型决策的权责分离

## 摘要与问题边界

决策边界是 Agent 架构中区分“应用层能力供给”与“模型层意图选择”的一条权责线。应用层决定系统能暴露哪些能力、如何执行、执行前需要哪些校验；模型层只在给定能力集合内决定本次请求是否调用、调用顺序、如何处理返回。问题的核心不是“模型聪明到何种程度”，而是“双方在运行时不互相越权”。本讨论聚焦对话型 Agent，特别是 Web 应用通过 SSE 向浏览器提供能力目录、模型自主调用工具的场景，不涉及模型训练细节或通用推理优化。

## 核心概念与数据模型

1. 能力（Capability）。原子操作单元，包含名称、输入 Schema、副作用声明、能力等级、执行句柄。例如 read 文件、search_knowledge、send_email。能力的定义由应用层拥有，模型只消费描述。
2. 能力目录（Capability Registry）。运行时只读注册表，列出当前会话可见的全部能力。应用在启动或配置阶段写入，会话建立后冻结为快照，模型无权修改。
3. 决策平面（Decision Plane）。模型基于 prompt 和能力目录生成 tool_use 请求。该平面只做“选择”与“参数填充”，不执行任何 I/O 或副作用。
4. 执行平面（Execution Plane）。应用接收 tool_use 事件，完成身份校验、权限校验、副作用控制、实际执行，并将结果以 tool_result 回传。执行平面从不根据用户消息做语义预路由。
5. 会话边界（Session Boundary）。每个会话绑定一个独立的能力目录快照、身份上下文、调用次数上限和审计标识。会话隔离保证旧会话不会受新能力注册影响。
6. 事件协议（Event Protocol）。message_update、thinking_delta、tool_execution_start、tool_execution_update、tool_execution_end、lifecycle、retry 等事件统一传输。决策平面与执行平面通过事件解耦，双方不共享内部对象。

## 设计决策与取舍

### 应用层禁止语义预路由

应用层只允许对请求做格式校验、身份校验和会话绑定，不允许根据关键词、正则或意图分类把用户消息直接路由到某能力。例如不能在用户提到“天气”时直接调用天气接口，再把结果塞给模型。例外：纯系统级钩子（如健康检查、退出指令）可以不由模型决策，但这类钩子不得参与业务工具选择。

### 模型只读能力目录

模型通过 prompt 接收能力描述，但不持有目录写入权限。这样即使模型输出中包含“注册新能力”的请求，执行平面也拒绝处理。代价是模型无法根据上下文动态扩展能力，必须由应用层显式提供。

### 工具执行必须在应用进程

tool_use 请求只是结构化文本。任何文件写入、网络调用、Shell 执行都由应用层执行器完成。模型不接收网络客户端或文件句柄，避免模型绕过授权。例外：纯计算类函数（如日期计算、数学表达式）可以封装为无副作用能力，但仍由应用层执行。

### 能力与会话绑定快照

会话建立时复制能力目录快照。后续能力升级或下线只影响新会话，老会话保持原目录。这保证可重复性，也避免会话中途因能力变化出现未定义行为。

### 失败必须回传模型

执行平面捕获所有失败（权限不足、参数错误、超时、依赖异常）并统一包装为 tool_result 返回。模型据此决定重试、换工具或向用户解释。不能由应用层替模型隐藏失败。

## 可执行的实施流程

1. 定义能力 Schema，明确输入字段、副作用等级、是否幂等、是否需要用户确认。
2. 在应用启动或配置阶段将能力注册到能力目录，生成目录版本号。
3. 创建会话时，按身份和角色从目录复制可见能力快照，并记录会话级能力版本。
4. 将能力描述和调用规则（如一次最多调用数、禁止的能力）注入模型上下文。
5. 接收用户消息后，完整转发给模型，应用层不替换、不截断、不做意图判断。
6. 捕获模型输出的 tool_use 请求，校验其名称与参数是否在会话快照内。
7. 执行平面按授权策略执行，记录审计日志，生成 tool_result。
8. 返回 tool_result 给模型，继续下一轮决策，直到模型生成普通消息。
9. 会话关闭时清理临时能力、释放资源、注销事件订阅。

## 本地文件知识库能力示例

下面是一个能力目录片段，描述只读能力 search_knowledge。不使用代码围栏，仅使用缩进表示固定格式文本。

    capability_registry:
      version: "2025-08-01"
      session_snapshot:
        capabilities:
          - name: search_knowledge
            description: 在本地 .pi/knowledge 目录中检索项目级 Markdown 知识。
            input_schema:
              query: string
              max_results: integer
            side_effect: none
            readonly: true
            executor: "apps.api.executors.knowledge_search"

输入是用户问题文本，处理阶段模型决定调用 search_knowledge 并填充 query 参数，执行平面在应用进程内读取 .pi/knowledge 目录并返回匹配段落，输出是面向用户的自然语言答案。模型不直接读取文件，应用层也不替模型决定何时检索。

## 性能、质量和可观测性指标

1. 工具选择准确率。对比模型生成的 tool_use 名称与人工标注的期望能力，计算匹配率。测量方式：离线评估集 + 在线影子日志。
2. 决策延迟。从用户消息到达应用到模型输出首个 token 或首个 tool_use 的时间。测量方式：在入口网关和事件流上打时间戳。
3. 执行错误率。执行平面返回失败或异常的 tool_use 占总调用比例。测量方式：统计 tool_execution_end 中 error 状态占比。
4. 越权调用率。模型请求未注册能力、超出会话快照或违反参数约束的调用次数。测量方式：校验中间件计数。
5. 事件完整率。会话事件序列是否连续、无丢失、无乱序。测量方式：每个事件带单调序列号，客户端与服务器端比对。
6. 能力漂移率。运行时会话快照与注册目录版本不一致的比例。测量方式：会话创建时记录目录版本，定期扫描。

## 失败模式、诊断证据与恢复动作

1. 模型虚构工具。模型生成未注册能力名称。诊断证据：校验中间件发现 capability_name 不在 session_snapshot 中。恢复：返回 tool_result 提示能力不存在，模型自行调整。
2. 应用层语义预路由。关键词命中后绕过模型直接调用工具。诊断证据：日志中缺少 model_decision 事件或 tool_use 来自应用代码而非模型输出。恢复：移除预路由逻辑，强制所有能力调用经过模型。
3. 执行器越权。应用以模型名义执行未授权操作。诊断证据：审计日志中出现调用者标识为 model 但能力不在会话快照中的记录。恢复：在执行平面增加二次校验，调用者必须显式标识为已授权会话。
4. 事件丢失。SSE 连接断开或缓冲区未 flush 导致事件缺失。诊断证据：客户端序列号不连续，或 server 端已发送但 client 未收到。恢复：支持按序列号重放，或切换到可确认的事件传输。
5. 能力版本不一致。会话中途能力升级导致行为变化。诊断证据：同一 user_id 的相邻会话产生不同能力集合。恢复：会话建立后冻结目录快照，变更仅对新会话生效。
6. 循环调用。模型在失败后反复调用同一能力。诊断证据：同一 capability_name 在短窗口内连续出现且 tool_result 均为 error。恢复：增加会话级调用次数上限，超限后强制返回用户并记录。

## 问答测试样例

1. 正向问题：用户问“如何配置能力目录？”模型应调用 search_knowledge 查询相关 Markdown，然后总结回答。
2. 边界问题：用户问“今天北京天气如何？”若天气能力未注册，模型不得虚构天气工具，应说明无法查询。
3. 无证据拒答：用户问“上个月财务报表的净利润是多少？”若未提供财务读取能力，模型应拒绝回答，而非猜测。
4. 边界问题：用户消息包含“请删除 report.txt”，但 write 能力未注入会话，模型不应生成 file_write 或 delete 工具请求。
5. 正向问题：用户要求“先查知识库再给出架构建议”，模型应依次调用 search_knowledge 与 synthesize，输出可追溯的结论。
6. 边界问题：用户输入恰好包含工具名称关键词“search_knowledge”，但实际是请求解释该词含义，模型应判断语义为解释而非检索。

## 维护、版本、来源与相邻主题的关系

能力目录需要版本号，每次注册或下线能力都递增。会话快照记录目录版本，便于回溯。维护工作包括：定期审计越权调用、清理废弃能力、更新测试样例。来源以项目级设计文档 AGENTS.md 和 SDK 文档为准，不依赖外部系统实时状态。相邻主题包括：工具调用协议（如何定义事件格式）、会话管理（身份与生命周期）、资源加载（.pi/knowledge 等目录）、安全沙箱（执行隔离）。决策边界与这些主题共享事件协议，但聚焦点始终是“谁决定”而不是“怎么做”。

## 结论

需要区分三类陈述。事实：应用层提供能力并执行，模型层决定使用能力，这是本架构的核心权责分离。推论：禁止语义预路由能够减少模型被架空的风险，并让能力升级与模型选择解耦。未知：具体模型在多轮对话中是否能稳定遵守能力目录边界，取决于 prompt 设计、后训练行为和评估集覆盖，需要在真实会话中持续测量。最终，决策边界不是一次性的配置，而是需要在运行时通过目录版本、事件审计、越权校验和失败回传共同维护的架构约束。
