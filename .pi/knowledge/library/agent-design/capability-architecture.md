# 能力注入：面向任务边界的最小能力契约

## 摘要与问题边界

能力注入是一种将外部工具与权限以显式契约形式绑定到单次 Agent 会话的设计范式。其核心约束是：Agent 在任意时刻只能调用当前任务声明过的能力集合，禁止持有无限扩展的工具箱。问题边界限定在会话层的能力发现、校验、撤销与审计，而非底层模型训练或通用推理优化。本视角面向负责系统边界、安全半径和长期演进的架构设计者，要求先确立接口契约与责任归属，再选择具体实现技术。

本范式不解决模型本身的幻觉问题，也不替代传统的身份认证与授权系统。它强调的是“能力在正确的时间以最小的集合存在”。当任务切换、用户离开或异常触发时，已注入的能力必须能够被回收，避免会话泄露为持久权限。

## 核心概念与数据模型

1. **能力声明（Capability Declaration）**：一段不可变描述，包含能力标识、版本、输入模式、副作用等级、资源作用域和过期条件。每个能力声明必须由可信来源签名。

2. **能力上下文（Capability Context）**：一次会话运行时的能力视图，是声明集合在特定任务下的投影。上下文具有生命周期，与任务标识、用户身份、时间窗口强绑定。

3. **注入器（Injector）**：负责将能力上下文转换为 Agent 可调用的工具实例的组件。注入器本身不执行业务逻辑，只负责装配、校验和拦截。

4. **能力契约（Capability Contract）**：Agent 与工具之间的双向约束，既约束 Agent 只能调用已注入能力，也约束工具只能访问被声明的资源范围。

5. **沙箱边界（Sandbox Boundary）**：能力运行的最小隔离单元。高风险能力必须运行在独立进程、容器或受限运行时中，低风险能力可共享进程但受调用拦截器控制。

6. **撤销令牌（Revocation Token）**：一个可在运行时触发能力回收的句柄。持有撤销令牌的监控组件可在超时、越界或异常时立即缩小能力上下文。

7. **审计轨迹（Audit Trail）**：记录每次能力注入、调用、失败、回收事件的只追加日志，用于事后追踪和策略优化。

## 设计决策与取舍

### 显式注入优于默认全集
默认加载全部工具会导致调用面不可控，增加误用和攻击面。显式注入要求每个任务在启动时声明所需能力，未声明能力即使已安装也不可访问。取舍是启动阶段需要多一次配置，但换来运行时更小的爆炸半径。

### 静态契约优于动态发现
运行时动态发现工具会破坏版本一致性和审计能力。能力声明应在任务编排阶段完成校验并锁定版本。动态发现仅允许在受控的白名单扩展点发生，且需重新走注入流程。

### 副作用分级优于统一权限
将能力按副作用分为只读、本地写、远程写、不可逆写四个等级，不同等级对应不同的沙箱策略和二次确认要求。统一权限会让低风险能力继承过高的执行半径。

### 短期会话优于长期持有
能力上下文不应长期驻留在 Agent 实例中。任务结束后应立即回收。长期持有能力会让会话成为事实上的特权通道，违背最小能力原则。

### 注入器与执行器分离
注入器负责能力装配，执行器负责实际调用。两者分离后，可以独立升级策略引擎和执行运行时，避免策略逻辑混入业务实现。代价是增加一层调用开销，通常控制在毫秒级。

## 可执行的实施流程

1. **梳理现有工具集合**，为每个工具生成能力声明草案，明确输入输出模式、副作用等级和资源依赖。
2. **定义能力签名规范**，选择 JSON Schema 或 TypeScript 类型作为声明格式，并确定签名密钥和校验算法。
3. **建立能力仓库**，将声明文件纳入版本控制，每次变更触发版本号升级和回归测试。
4. **实现注入器接口**，接收任务描述、用户身份、环境上下文，输出能力上下文和撤销令牌。
5. **在会话启动流程中接入注入器**，在 Agent 获得模型访问权之前完成能力装配。
6. **部署调用拦截器**，在每次工具调用前检查目标能力是否在当前上下文有效，校验参数是否超出声明范围。
7. **配置沙箱策略**，对高风险能力启用独立进程或容器，对低风险能力使用进程内拦截。
8. **建立撤销与回收机制**，实现超时回收、任务完成回收、异常触发回收三种路径。
9. **接入审计日志**，记录注入、调用、越界尝试、撤销事件，并支持按任务标识查询。
10. **编写契约测试**，为每个能力声明配套正向用例、边界用例和异常用例，确保实现与声明一致。
11. **在 CI 流水线中校验能力漂移**，禁止未声明的新工具直接投入生产环境。
12. **定期评审能力使用热力图**，根据调用频率和失败模式调整最小能力集合。

## TypeScript 示例：本地文件知识库能力注入

```typescript
interface FileReadCapability {
  kind: 'file:read';
  scope: { rootDir: string; allowedExtensions: string[] };
  maxFilesPerQuery: number;
}

interface Injector {
  inject(task: TaskSpec, principal: Principal): CapabilityContext;
}

const task: TaskSpec = {
  id: 'research-pi-docs',
  requiredCapabilities: [
    { kind: 'file:read', scope: { rootDir: '/data/kb', allowedExtensions: ['.md'] }, maxFilesPerQuery: 5 }
  ],
  ttlSeconds: 300
};

const ctx = injector.inject(task, user);
// Agent 只能读取 /data/kb 下扩展名为 .md 的文件，每次最多 5 个。
```

输入为任务描述、用户身份和环境配置；处理阶段由注入器校验声明签名、计算资源作用域、装配拦截器；输出为能力上下文与撤销令牌。运行时若 Agent 请求读取 `/etc/passwd`，拦截器依据 `scope.rootDir` 拒绝并记录越界事件。

## 性能、质量和可观测性指标

1. **能力注入延迟**：从任务启动到上下文就绪的时间，目标 P99 小于 50 毫秒，可在注入器入口和出口打桩测量。
2. **运行时拦截开销**：单次工具调用的额外校验耗时，目标平均值小于 5 毫秒，通过 A/B 对比关闭拦截器前后的延迟获得。
3. **越界尝试率**：单位时间内被拦截的非法调用次数除以总调用次数，应低于 0.1%，并通过日志聚合面板追踪。
4. **能力回收成功率**：任务结束或异常触发后，相关能力上下文被正确清理的比例，目标为 100%，通过会话生命周期钩子验证。
5. **声明漂移率**：生产环境中出现未在仓库声明即被调用的能力次数，目标为零，通过审计日志与仓库清单交叉核对。
6. **误拦截率**：合法调用被错误拦截的比例，通过人工复核每日 Top 10 拦截事件估算。

## 失败模式与恢复动作

1. **注入器配置漂移**
   - 诊断证据：审计日志出现调用成功但仓库声明未覆盖的能力标识。
   - 恢复动作：立即将该能力标记为未授权，回滚最近部署，并强制所有会话重新注入。

2. **沙箱逃逸**
   - 诊断证据：工具进程访问了声明作用域之外的文件句柄或网络地址。
   - 恢复动作：终止该进程，回收对应撤销令牌，审查沙箱策略并升级隔离级别。

3. **撤销令牌失效**
   - 诊断证据：会话超时后仍能观察到该会话标识的调用记录。
   - 恢复动作：检查撤销调度器状态，必要时强制刷新会话注册表，并补写审计事件。

4. **过度注入**
   - 诊断证据：任务平均持有能力数显著高于理论最小值。
   - 恢复动作：按任务模板拆分能力集合，引入注入前评审检查清单。

5. **能力声明版本冲突**
   - 诊断证据：同一能力标识存在多个签名版本，调用结果不一致。
   - 恢复动作：冻结旧版本声明，强制客户端升级，并在注入器中加入版本互斥校验。

## 问答测试样例

1. 正向问题：当前任务需要读取本地 Markdown 知识库，应注入哪些能力？
   - 答案：注入 `file:read`，限定根目录为知识库路径，扩展名为 `.md`，并设置单次查询文件上限。

2. 正向问题：能力注入与工具注册有何区别？
   - 答案：工具注册是静态安装，能力注入是运行时按任务投影；未注入的工具即使已注册也不可调用。

3. 边界问题：任务运行过程中需要新增一个能力怎么办？
   - 答案：必须暂停当前 Agent 执行，触发重新注入流程，更新能力上下文和撤销令牌，并记录变更原因。

4. 边界问题：同一个能力能否同时授予读写两种副作用等级？
   - 答案：不能。能力声明应拆分为 `file:read` 与 `file:write` 两个独立声明，分别注入并分别审计。

5. 无证据拒答：能否允许 Agent 自动发现并使用未声明工具？
   - 答案：不能。没有显式声明和签名的工具调用必须被拦截，动态发现属于受控扩展点而非常态。

6. 无证据拒答：模型本身是否受能力注入约束？
   - 答案：能力注入约束工具调用层，不约束模型内部推理。若模型生成调用未注入工具的意图，拦截器负责拒绝。

## 维护、版本、来源与相邻主题

能力声明文件应采用语义化版本管理，重大变更提升主版本号，扩展字段提升次版本号，修正描述提升修订号。所有声明需记录来源系统、负责人和上次评审日期。相邻主题包括访问控制、沙箱隔离、工具注册中心、提示词工程和 Agent 会话管理。能力注入位于这些主题之间，向上承接权限策略，向下驱动工具装配，向左约束提示词中可调用的能力集合，向右为审计和合规提供数据。

## 结论

事实：能力注入要求 Agent 在单次任务中只持有已声明的最小能力集合，并通过注入器、拦截器和撤销令牌实现运行时约束。推论：将能力声明版本化、注入器与执行器分离、按副作用分级，可以显著降低误用和攻击面，同时提升系统的可审计性。未知：在超长上下文或多 Agent 协作链中，能力上下文的最优传递与回收策略仍需结合具体负载验证；不同模型对能力描述格式的解析一致性也存在待测空间。设计时应优先固化接口契约和责任边界，再根据实测数据选择实现技术。
