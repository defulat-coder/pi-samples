# 能力注入：为 Agent 配置最小可用工具集的验证与运维实践

标签：Agent 设计范式、能力注入、最小工具集、可观测性、运维

能力注入不是静态的“工具白名单”，而是在每次会话或每次对话轮次中，按任务需求把最小可用能力集合绑定到 Agent 运行时的机制。这里的“能力”不仅包括可调用工具，还包括可读取的资源路径、可访问的知识库分片以及输出模式约束。本文从验证与运维视角出发，只讨论运行时的能力集合如何确定、如何生效、如何观测；不讨论模型选型、提示词撰写、业务授权或沙箱隔离本身。核心问题是：如果给 Agent 的工具集过大，会产生决策噪声、延迟抖动和级联故障；如果切得太小，则任务因能力缺失而失败。验证与运维的目标是把这两种风险都变成可度量、可回放、可恢复的证据。

## 核心概念或数据模型

1. **能力清单（Capability Manifest）**：一份显式声明的、版本化的能力集合，包含工具签名、参数模式、资源通配符、知识库命名空间和可用输出格式。清单必须可以离线校验，在会话中途不能被偷偷替换。
2. **任务能力闭包（Task Capability Closure）**：针对单个用户请求，从目标出发反向推导出的最小能力集合，包含直接工具、其依赖的读取权限以及所需的上下文知识库。闭包不考虑“可能有用”的工具。
3. **注入点（Injection Point）**：能力清单生效的时刻，通常发生在 `createAgentSession()` 或每次 turn 的边界。注入点之后，当前轮次的能力集合应保持只读，除非通过显式的 scope transition 重新注入。
4. **最小工具集（MTS，Minimal Tool Set）**：在验证套件上满足成功概率阈值且延迟分位稳定的工具子集。MTS 不是“越少越好”，而是“在可接受误差内不再减少”。
5. **能力依赖图（CDG，Capability Dependency Graph）**：有向图，节点是工具、资源、知识库分片，边表示调用或读取关系。CDG 用于发现隐藏依赖、循环引用和被遗漏的间接权限。
6. **能力审计日志（Capability Audit Log）**：按时间顺序记录每个 turn 实际生效的能力集合、注入版本、来源哈希和生效时长。审计日志是故障回放和责任界定的唯一可信来源。

## 设计决策与取舍

### 1. 工具数量与决策准确率
每增加一个工具，模型需要在更多候选中做选择，错误调用概率上升。经验上，当候选工具超过 7 个时，无关工具调用率会快速增加；但不同模型和任务的拐点不同。运维中应以 A/B 测试为准，而不是套用固定上限。

### 2. 动态注入与静态策略
动态按任务注入能把攻击面和误调用面降到最低，但注入本身带来延迟，并增加策略服务的故障点。静态策略简单可靠，却容易把不相关工具留在会话里。建议热路径采用预生成的角色模板，冷路径再按请求细化。

### 3. 知识库可见范围
只开放任务所需的知识分片可以减少幻觉引用，但过度分片会让检索路径变长，且分片边界可能切在语义连贯处。应记录每次检索命中的分片标识，用于事后核对“答案是否来自授权范围”。

### 4. 缓存能力声明与实时发现
缓存能力声明可降低注入延迟，但缓存过期策略必须比业务变更周期短。实时发现能拿到最新工具，却依赖发现服务可用性。建议缓存 TTL 设为业务发布间隔的一半，并在发布时主动失效缓存。

### 5. 失败回退：放宽还是保持最小
当任务因缺少能力失败时，立即放宽到完整工具集可能恢复任务，但会引入噪音并掩盖清单缺陷。运维上应先把失败样本加入验证集，再决定是否把缺失能力加入 MTS，而不是在运行时无限制回退。

## 可执行的实施流程

1. 梳理全部工具、资源和知识库，建立 CDG。
2. 为每个业务任务编写成功标准和失败标准示例，形成验证套件。
3. 使用验证套件离线枚举能力子集，找出满足成功阈值的最小工具集。
4. 把 MTS 与任务类型映射，生成角色级能力模板并版本化。
5. 在 `createAgentSession()` 时按任务类型注入对应模板，并记录审计日志。
6. 在每次 turn 边界检查能力集合是否被意外修改；若被修改则标记为异常。
7. 部署注入延迟、工具调用分布、任务完成率等指标，并设置告警。
8. 每轮迭代用新失败的会话补充验证套件，重新计算 MTS，更新模板和文档。

## 代码示例

下面是一个贴近 TypeScript/Web/本地文件知识库的 YAML 能力清单片段。

```yaml
capability_manifest:
  version: "2025-06-10.3"
  scope: summarize_api_changes
  tools:
    - name: search_knowledge
      params:
        namespaces: [".pi/knowledge", "docs/adr"]
        max_results: 5
    - name: read_file
      params:
        allowed_paths: ["docs/**", "apps/api/**"]
        deny_patterns: ["**/*.env", "**/node_modules/**"]
  output_schema:
    type: object
    properties:
      summary: { type: string }
  audit:
    source_hash: "a1b2c3"
    injected_at: "2025-06-10T09:12:00Z"
```

输入是任务分类结果（`summarize_api_changes`）和项目 `cwd`；处理流程是策略服务按 scope 查表，把 `search_knowledge` 和 `read_file` 绑定到 `AgentSession`；输出是 Agent 实际接收到的能力对象，后续任何越界调用都应被拦截并记日志。

## 性能、质量和可观测性指标

1. **注入延迟**：从任务分类完成到能力对象就绪的耗时，用 p50/p99 表示，目标 p99 < 20ms。
2. **工具调用分布**：每个 turn 实际调用工具的次数和种类，用于发现“僵尸工具”。
3. **无关工具调用率**：模型调用了清单内但与任务无关的工具的比例，通过人工标注 5% 样本估算。
4. **越界访问次数**：试图访问清单外资源或工具的调用次数，由拦截层统计。
5. **任务完成率与失败归因**：按任务类型统计成功、因能力缺失失败、因模型错误失败三类比例。
6. **恢复时间**：从“能力注入异常”告警到会话被重建或降级的时间。

## 失败模式

1. **过度注入（Over-injection）**：清单包含多余工具。诊断证据：无关工具调用率 > 10%，p99 决策延迟上升。恢复：收紧模板，灰度验证后全量发布。
2. **注入不足（Under-injection）**：缺少必要工具。诊断证据：任务完成率下降，审计日志出现 `tool_not_found` 或 `capability_denied`。恢复：把失败样本加入验证集，补充工具后重新计算 MTS。
3. **能力漂移**：会话中途能力集合被热更新。诊断证据：同一 session 的相邻 turn 调用到了本不应存在的工具。恢复：禁止运行时修改，改为 turn 结束后重新创建会话。
4. **清单版本错位**：生产环境使用了旧版清单。诊断证据：`source_hash` 与最新发布不一致，越界访问增多。恢复：主动失效缓存，强制重新注入。
5. **注入点竞争**：`createAgentSession` 与策略服务并发导致部分工具丢失。诊断证据：部分会话缺少工具，其他会话正常，日志出现部分成功注入。恢复：给注入过程加幂等键和原子校验。

## 问答测试样例

1. **正向**：用户要求“列出 apps/api 最近新增的接口”。Agent 应调用 `read_file` 扫描 `apps/api` 路由文件。判断：清单包含 `read_file` 且路径匹配。
2. **正向**：用户要求“解释能力注入的目标”。Agent 应调用 `search_knowledge` 在 `.pi/knowledge` 中检索。判断：命中授权命名空间。
3. **边界**：用户请求涉及 `packages/contracts`，但清单只开放了 `apps/api`。Agent 不应读取，而是说明“当前会话没有该目录读取能力”。
4. **边界**：工具返回结果为空，Agent 不应擅自切换到未授权工具重试。
5. **无证据拒答**：当审计日志显示没有相关能力命中时，Agent 不应声称“我已经读取了文件”。
6. **无证据拒答**：当任务分类器无法识别请求类型时，应拒绝注入并返回“无法确定所需能力集合”，而不是使用默认全量工具。

## 维护、版本、来源和与相邻主题的关系

能力清单应随代码一起版本控制，版本号包含日期和迭代号，如 `2025-06-10.3`。来源包括项目 `AGENTS.md`、`.pi/skills` 和 `.pi/prompts`。每次变更需同步更新验证套件和审计日志解析文档。

能力注入与相邻主题的关系：它依赖访问控制作为底层执行层，但不同于授权；它影响提示词工程，因为工具描述是提示词的一部分；它为 Agent 编排提供可组合单元；与可观测性交叉，因为审计日志是链路追踪的前置数据。不要把能力注入和模型微调、RAG 检索策略混为一谈。

## 结论

**事实**：能力注入可以通过显式清单把运行时工具集限制在任务所需最小范围，并通过审计日志记录每一次注入。

**推论**：在验证套件上迭代 MTS，能够同时降低无关工具调用率和因能力缺失导致的失败率。

**未知**：不同模型对工具数量增加的敏感度差异、长期运行会话中能力衰减或漂移的量化规律、以及在多 Agent 协作场景下跨会话能力传递的最小安全边界，仍需要更多生产数据来验证。
