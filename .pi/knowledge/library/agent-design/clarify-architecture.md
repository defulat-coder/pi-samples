# 澄清问题：Agent 设计中的最小有价值澄清机制

## 摘要与问题边界

在 Agent 与用户的单次交互中，输入往往是不完整的自然语言请求、局部上下文或含糊的目标描述。澄清问题机制负责在信息不足以安全推进时，提出数量最少、区分度最高、最贴近真实意图的追问，而不是依赖模型内部先验进行猜测。本文讨论的是“该不该问、问什么、如何收敛”的结构层，而非答案生成、工具执行或检索排序本身。边界内：意图缺口检测、候选假设管理、问题价值评估、用户反馈解析与收敛判定。边界外：下游执行器、外部 API 调用、多模态理解。核心原则是：宁可中断一次，也不要在错误假设上连续执行。

## 核心概念与数据模型

1. 意图缺口（Intent Gap）：当前可观察上下文与可安全执行目标之间的最小信息差集合，表示为缺失键（missing keys）和歧义值（ambiguous values）两种形态。
2. 候选假设空间（Candidate Hypothesis Space）：基于当前上下文可合理推断出的全部目标解释，每个假设包含触发条件、约束集合、预期输出类型和置信度。
3. 澄清问题（Clarification Question）：为压缩假设空间而设计的请求，必须具备可回答性、可验证性和非诱导性，不能预设答案。
4. 信息价值密度（Information Value Density）：某个澄清问题能够将候选假设空间压缩的期望比例，优先选择高区分度、低开销的问题。
5. 约束边界（Constraint Boundary）：硬边界（必须满足，如权限、格式、预算）和软边界（偏好，如风格、详细程度）的分离，避免把偏好缺失误判为阻塞。
6. 确认与消除（Confirmation & Elimination）：用户反馈后，对假设空间进行确认、排除或细化，更新置信度并重新计算缺口。
7. 反馈环（Feedback Loop）：澄清结果回流到意图模型，形成会话级状态机，支持多轮收敛和回退。

## 设计决策与取舍

### 主动澄清与默认执行的边界
系统不能对所有缺口都问，否则交互负担爆炸；也不能完全依赖默认策略，否则会在关键歧义上猜测。决策规则是：当最优假设与次优假设的置信度差低于阈值，且两者会导致不同输出路径时，必须触发澄清；若差距高于阈值但最优假设仍违反硬边界，则同样触发澄清。

### 问题数量与覆盖范围
一次最多提出 N 个问题，N 由接口契约限定。优先选择“一个问题消除多个假设”的覆盖性问题，而不是罗列多个独立问题。若问题之间存在依赖关系，则拆分为顺序澄清。

### 确定性阈值
阈值不是全局常量，而是按主题域、工具风险等级和用户历史动态调整的。高风险操作（如删除、写入、外部调用）阈值更低；低风险只读查询阈值更高。阈值必须显式可配置，不能隐藏在模型提示中。

### 澄清会话状态管理
会话状态必须与会话身份绑定，但不应无限累积。采用栈式结构：当前澄清帧、已确认约束、待消除假设、历史问题记录。过期策略是：当会话超过 T 分钟或用户主动重置时，清理假设空间但保留已确认的硬边界。

### 工具与模型职责边界
澄清策略器（Clarification Strategist）只负责生成问题和解析反馈，不直接调用执行工具；执行器只接收已收敛意图。两者之间通过“澄清完成信号”分隔，确保模型不会在澄清过程中误触副作用。

## 可执行实施流程

1. 解析输入：将原始请求转换为结构化意图草图，提取已知实体、动作和约束。
2. 检测意图缺口：识别缺失键、歧义值、冲突约束和上下文断层。
3. 生成候选假设：基于领域知识和已知上下文，枚举所有合理目标解释，并赋予初始置信度。
4. 计算信息价值：对每个候选问题，评估其在期望意义上能消除多少假设。
5. 选择最优问题：按信息价值、用户认知成本、回答成本排序，选择前 N 个。
6. 生成问题表述：将内部问题转化为自然语言，避免诱导、隐藏假设，并提供选项。
7. 等待并解析反馈：将用户回答映射回假设空间的确认、排除或细化。
8. 收敛判定：检查是否只剩一个满足硬边界的假设，或是否需要新一轮澄清。
9. 输出已确认意图：向下游执行器交付结构化意图，附带约束快照和来源标注。
10. 记录日志：保存问题、反馈、假设变化、决策依据，用于后续审计和优化。

## TypeScript 接口与本地文件知识库示例

以下定义一个本地 Markdown 知识库场景下的澄清策略接口：

```typescript
interface ClarificationIntent {
  action: 'clarify';
  requestId: string;
  missingKeys: Array<{ key: string; reason: string }>;
  candidateHypotheses: Array<{
    id: string;
    interpretation: string;
    confidence: number;
    hardViolations: string[];
  }>;
  questions: Array<{
    id: string;
    text: string;
    expectedType: 'single_choice' | 'boolean' | 'text';
    options?: string[];
    targets: string[]; // hypothesis IDs this question splits
    valueDensity: number;
  }>;
}

interface UserFeedback {
  questionId: string;
  answer: string | string[];
}

function resolveAfterFeedback(
  intent: ClarificationIntent,
  feedback: UserFeedback
): { confirmed: string[]; eliminated: string[]; nextGap: string | null } {
  const answered = intent.questions.find(q => q.id === feedback.questionId);
  if (!answered) return { confirmed: [], eliminated: [], nextGap: 'unknown_question' };
  // 根据回答映射到假设空间
  const confirmed = answered.targets.filter(t => matchesAnswer(t, feedback.answer));
  const eliminated = answered.targets.filter(t => !matchesAnswer(t, feedback.answer));
  return { confirmed, eliminated, nextGap: null };
}
```

输入：一段模糊请求，如“帮我整理文档”。处理：系统检测到 action 和目标路径缺失，生成“整理”可能指重命名、归类、摘要或删除四个假设，并选择两个问题覆盖最多假设。输出：澄清意图对象，包含候选假设、问题和价值密度，等待用户反馈后更新假设空间。

## 性能、质量和可观测性指标

1. 澄清命中率：用户回答后能够消除至少一个候选假设的问题比例，通过反馈解析日志计算。
2. 平均交互轮数：从首次请求到意图收敛的平均轮数，按主题域和请求类型分桶统计。
3. 误拒率：系统因信息不足拒绝回答，但用户后续表明原请求其实可执行的比例，从会话回退日志中提取。
4. 问题质量评分：由用户是否修改答案、是否额外追问、是否选择“以上都不是”构成复合指标。
5. 收敛时间：从首次输入到澄清完成的时间中位数，受问题数量和用户等待时间影响。
6. 猜测回滚率：未澄清直接执行后被用户纠正或撤销的次数，监控该指标可发现阈值设置过松。

## 失败模式

1. 过度澄清：对可执行请求仍提出多个问题。诊断证据：历史类似请求 95% 以上原句即可执行，但当前会话触发澄清。恢复：提高该模式阈值，或引入“常见请求白名单”。
2. 澄清不足：在高风险歧义上未提问。诊断证据：执行后被用户纠正的频次上升。恢复：降低高风险操作阈值，并在候选假设差异小时强制澄清。
3. 问题表述歧义：用户无法判断问题在问什么。诊断证据：问题复选率、文本重述率升高。恢复：对问题生成器增加可读性校验和反例测试。
4. 假设错误生成：候选假设包含不存在的目标解释。诊断证据：用户回答“以上都不是”的比例高。恢复：收紧假设生成范围，引入领域约束过滤。
5. 上下文丢失：多轮澄清后遗漏早期已确认约束。诊断证据：最终输出违反已确认边界。恢复：在会话状态栈中固化硬边界，并在每轮重新注入上下文。
6. 价值误判：选择的问题区分度低。诊断证据：多轮问题回答后假设空间压缩缓慢。恢复：重新评估信息价值函数，引入假设熵减计算。

## 问答测试样例

1. 正向问题：用户输入“把这个文件处理一下”。系统应识别“处理”歧义，询问“你是指重命名、移动、复制、删除还是生成摘要？”。
2. 正向问题：用户输入“导出报告”。系统应澄清“报告的时间范围、输出格式和包含哪些数据源？”。
3. 边界问题：用户输入“帮我删除旧的备份”。系统应确认“旧的判定标准是什么？以及是否包含云端同步副本？”。
4. 边界问题：用户输入“发邮件给团队”。系统应澄清“团队的精确定义、邮件主题和是否需要附件。”。
5. 无证据拒答：用户仅输入“优化它”，但当前没有任何文件或上下文被选中。系统应回答“我看不到当前被优化的对象，请先提供文件或描述具体目标。”。
6. 无证据拒答：用户输入“修复那个 bug”，但系统未检索到任何错误日志或相关代码。系统应回答“没有定位到具体 bug 的上下文，请提供报错信息、复现步骤或相关文件路径。”。

## 维护、版本、来源与相邻主题关系

维护：澄清策略、阈值和领域约束应版本化，与提示模板和知识库文件同步发布。每次更新后运行问答测试样例回归，确保行为一致。

版本：当前设计基于本地 TypeScript 项目架构，接口在 `packages/contracts` 中定义，实现在 `packages/pi-agent` 中。阈值参数通过环境变量或配置文件注入，不应写入模型提示。

来源：与相邻主题“意图识别”“工具选择”“会话管理”的关系是：意图识别输出意图草图，澄清问题模块精化意图，收敛后交付工具选择模块。会话管理负责状态生命周期，但不应参与澄清策略判断。

## 结论

事实：澄清问题机制是 Agent 意图收敛的结构层，必须显式区分硬边界与软偏好，且不能由模型自行猜测高风险动作。推论：通过候选假设空间、信息价值密度和会话状态栈，可以在工程上实现最小有价值澄清，并把它作为可替换接口与执行器隔离。未知：用户长期认知成本与系统交互轮数之间的最优权衡，仍需通过 A/B 测试和真实会话日志进一步量化；不同文化或专业背景用户对“诱导性问题”的敏感度也可能影响问题生成策略。
