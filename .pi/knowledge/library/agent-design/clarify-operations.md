# Agent 设计范式：信息不足时以最少澄清获取可验证答案

标签：#clarification #agent-design #observability #type-safe-intent #ops-validation #fallback-boundary

## 摘要与问题边界

当用户输入缺少关键参数、指代不明或超出当前上下文可验证范围时，Agent 常见两种失效路径：依赖内部先验猜测，或用固定模板反复追问。本范式将“澄清问题”定义为受控熵减：只在确定性缺口能被可验证信息填补时才提问，且每次提问的期望收益应高于继续执行或调用工具。目标读者是负责性能、稳定性与故障恢复的工程师，因此所有设计点都围绕成功、失败、延迟、容量与恢复证据展开，避免只记录一次成功请求。

问题边界限定为：用户意图可解析但信息不足；系统能测量“缺什么”与“问什么”；不存在可验证证据时，系统必须拒答并说明空白。

## 核心概念与数据模型

1. 请求向量 RequestVector：用户消息、会话状态、本地文件片段、已填充与未填充槽位组成的不可变快照。澄清必须基于该快照，而非模型记忆。

2. 确定性缺口 CertaintyGap：对未填充槽位计算熵分或置信分。仅当熵分超过阈值且存在可获取证据时，才触发澄清。

3. 候选澄清集合 CandidateSet：按信息增益、预期工具调用减少量、用户认知成本排序的可能问题集合，容量通常不超过三个。

4. 澄清价值函数 ClarificationValue：预期错误下降率除以（预期往返延迟 + 用户回答成本）。低于 0.1 时不提问，改为执行可回退动作或拒答。

5. 证据类型标签 EvidenceType：区分“本地文件可验证”“运行时日志可验证”“必须用户提供”“无法验证”。问题只能针对必须用户提供的缺额。

6. 观测记录 ClarificationTrace：包含 trace_id、触发原因、候选排序、回填结果、最终判定以及延迟与容量指标。

7. 恢复锚点 RecoveryAnchor：发起澄清前固化会话状态版本号；若用户回复导致漂移或工具链失败，可回滚并重新评估。

## 设计决策与取舍

### 何时停止澄清并执行

当未填充槽位不影响下一动作安全性时，允许带缺省占位符执行，并在输出中声明假设。涉及写操作或外部调用的路径禁止缺省，必须完成澄清。

### 单轮多问还是逐轮追问

单轮多问减少往返但增加认知负荷；逐轮追问提高精度但增加延迟。本地文件知识库场景建议最多同时提出两个互斥选项，且每个选项可独立回答。

### 确定性阈值与业务容忍度

阈值不能是全局常数。查询类任务置信分 0.7 可接受；生成配置或删除类任务需达到 0.95。阈值应随操作破坏力单调递增，并在配置中可审计。

### 预定义槽位还是开放语义

预定义槽位便于度量和缓存，但会漏掉长尾意图；开放语义覆盖新场景却难以计算信息增益。推荐混合策略：核心路径用强类型槽位，边缘意图允许开放式问题但限制单次澄清。

### 日志保留与隐私边界

澄清日志保留问题文本、用户回复的槽位值和判定结果，不保留敏感文件内容。保留周期默认 30 天，失败诊断时可临时提升采样率。

## 可执行的实施流程

1. 网关层解析用户消息，生成 RequestVector 并注入会话 ID 与版本号。
2. 检索本地文件知识库，填充可自动验证槽位，标记剩余未填充槽位。
3. 对每个未填充槽位计算确定性缺口，输出熵分与证据类型。
4. 若所有缺口低于阈值，进入执行路径；若存在无法验证缺口，进入拒答路径。
5. 对需要用户补全的缺口，生成候选澄清集合并运行价值函数排序。
6. 选择价值最高的一个或两个问题，附加假设声明与可验证边界后返回用户。
7. 用户回复后再次生成 RequestVector，回填槽位，并记录 ClarificationTrace。
8. 若回填导致新缺口或触发失败模式，加载 RecoveryAnchor 回滚并重新评估。
9. 最终执行动作，并将成功、失败、延迟、容量与恢复指标写入可观测性后端。

## 示例：本地文件知识库的澄清请求

输入为一个 JSON 对象：用户消息是“把那份报告改成正式版”，系统已检索到当前目录存在 report-draft.md 与 report-final.md，但缺少“覆盖目标”与“生效分支”两个槽位。处理逻辑识别“正式版”对应 report-final.md 可由本地文件验证，而“是否覆盖”和“目标分支”因涉及写风险必须用户提供。系统生成两个选项：是否覆盖 report-final.md？目标分支是 main 还是当前分支？输出附带声明：60 秒内未回复则放弃操作并保留原文件。

输入：{user: "把那份报告改成正式版", cwd: "/repo", files: ["report-draft.md","report-final.md"], missing: ["overwrite_target","target_branch"]}

处理：检索文件确认 report-final.md 存在，标记两个缺额均为 must_ask_user；生成两个单选选项，计算 ClarificationValue 为 0.42，大于阈值 0.1，发起提问。

输出：{action: "clarify", questions: [{slot:"overwrite_target",options:["覆盖 report-final.md","另存为新文件"]},{slot:"target_branch",options:["main","当前分支"]}], timeout: 60, recovery_anchor: "v3"}

## 性能、质量与可观测性指标

1. 澄清触发率：每百次请求进入澄清路径的次数，通过网关计数器测量。异常波动意味着槽位设计或检索质量退化。
2. 单次澄清往返延迟：从返回问题到收到回复的 P50/P99，由会话管理器记录。P99 超过 60 秒应缩短超时或拆分问题。
3. 回填成功率：回复后槽位正确解析并进入执行路径的比例。低于 85% 提示候选集合或解析器缺陷。
4. 误触发执行率：本应先澄清却直接执行并导致失败的比例，用 RecoveryAnchor 触发次数除以总执行次数计算。
5. 澄清后最终任务成功率：从首次消息到最终动作完成且未触发失败模式的比例。
6. 平均候选集合大小：反映意图拆解粒度，应保持在 1.2 到 2.0 之间。

## 失败模式与恢复动作

1. 模型幻觉式澄清：问题包含未在 missing 集合中的槽位。恢复：丢弃该问题，回滚到 RecoveryAnchor，并对该模型版本提升采样率。
2. 用户回复语义漂移：回复与问题无关，导致新槽位被错误填充。证据：回填后 RequestVector 与上一轮的语义相似度低于阈值。恢复：重新生成澄清并提示用户按选项回答。
3. 高价值问题排序失败：价值函数低估关键问题，导致先问次要问题。证据：后续因主要缺额再次澄清。恢复：将本次 trace 标记为负样本并调整权重。
4. 超时未回复：用户在 timeout 内无响应。证据：会话状态停留在 waiting_clarification 超过阈值。恢复：释放锁、标记任务为 cancelled，并保留 RecoveryAnchor。
5. 候选集合过大导致用户放弃：证据：返回超过三个选项后任务完成率骤降。恢复：裁剪候选集并对边缘意图启用开放性问题。
6. 缓存过期导致可验证槽位误标为 must_ask_user：证据：本地文件索引时间戳早于请求时间。恢复：刷新索引后重新填充，不发起澄清。

## 问答测试样例

1. 正向：用户输入“把 /repo/report-draft.md 改为正式版并覆盖原文件，目标分支 main”。两个槽位均被显式填充，系统直接执行。
2. 正向：用户输入“把报告改成正式版”，文件存在 report-final.md。系统问“是否覆盖 report-final.md？目标分支是 main 还是当前分支？”。
3. 边界：用户输入“把报告改成正式版”，目录下无 report 文件。系统拒答，说明未找到匹配文件。
4. 边界：用户输入“把所有草稿改成正式版”，匹配到三个文件。系统列出候选文件并询问是否全部处理，不依次猜测。
5. 无证据拒答：用户输入“删掉那个旧的”。缺少文件证据且无历史上下文，系统回复请提供路径或选择列表项。
6. 无证据拒答：用户输入“优化一下配置”，目录下存在多个配置文件。系统返回候选列表并要求选择，不随机挑选。

## 维护、版本、来源与相邻主题的关系

本范式与意图识别、槽位填充、工具调用链和可观测性体系相邻。意图识别负责映射结构意图；澄清问题只处理映射后的缺额。槽位填充提供未填充集合；本范式决定哪些值得问。工具调用链提供可验证证据；澄清不应替代工具调用。可观测性体系记录 ClarificationTrace。

版本管理：RequestVector 模式、EvidenceType 枚举和 ClarificationValue 阈值作为配置 schema 纳入版本控制。每次修改阈值或排序权重必须附带 A/B 测试的触发率与回填成功率对比。

来源：所有设计来自本地 TypeScript/Web/本地文件知识库项目的可验证需求，未引用未经验证的外部系统。术语 ClarificationTrace、RecoveryAnchor 为项目自定义。

## 结论

事实：澄清问题是受控熵减动作；RequestVector、CertaintyGap、CandidateSet、ClarificationValue、EvidenceType、ClarificationTrace 和 RecoveryAnchor 构成可观测数据模型；涉及写操作或外部调用的路径必须完成澄清。

推论：在本地文件知识库场景中，优先填充本地可验证槽位、仅询问必须用户决定的缺额并固化 RecoveryAnchor，可在延迟可控前提下显著降低误操作率。

未知：不同用户群体对“最少且有价值”的认知成本差异；长会话历史上下文对熵分权重的最优值；异步消息场景下超时策略对完成率的影响，均需后续 A/B 测试和故障复盘验证。
