# 上下文预算：Agent 系统的资源边界与可替换分配策略

## 摘要与问题边界

上下文预算是 Agent 推理调用前必须满足的一项跨层不变量：单次输入中，系统提示、工具说明、检索片段与历史消息所占用的 token 总量不得超过上限。它不同于速率限制，也不同于输出 token 上限；它约束的是“进入模型之前”的上下文体积。核心责任边界如下：运行时 allocator 负责制定分区策略并执行预留；模型层只提供 tokenizer 与最终 token 计数；工具注册表只返回描述文本的 token 长度；检索存储只保证片段按相关性排序；会话管理器只负责历史消息的裁剪与压缩。各组件通过可替换接口协作，因此预算策略可以独立演进，而不必重写模型调用或业务逻辑。

## 核心概念与数据模型

1. 总预算（TotalCap）：由部署配置决定，通常等于模型上下文窗口减去安全余量。它是一次调用的硬上限。
2. 预留分区：系统提示（SystemReserve）、工具说明（ToolsReserve）、检索片段（RetrievalReserve）、历史消息（HistoryReserve）和输出头空间（OutputHeadroom）。分区大小是策略，不是模型参数。
3. 计费单位：优先使用目标模型的 tokenizer 返回的 token 数；本地知识库片段可先用字符数做近似代理，但必须在入模前通过 tokenizer 校准。
4. 历史状态：历史不仅包含用户与助手的可见文本，还包含工具调用消息、工具结果、元数据和错误信息。
5. 可替换接口：BudgetProvider 接收上下文（会话标识、模型名、工具集、检索结果、历史消息），输出 Budget 对象；实现可以从固定分区切换到动态池，而消费方代码不变。
6. 优先级队列：每个上下文单元带有优先级标签。系统提示与当前轮必需的工具结果通常不可裁剪；旧历史与低分检索片段进入候选淘汰队列。

## 设计决策与取舍

### 固定分区 vs 动态池
固定分区使资源占用可预测，便于在资源受限环境做静态预算；缺点是检索旺盛时会浪费历史空间，或历史过长时挤占检索空间。动态池按当前轮意图重新分配，可以提升利用率，但会导致相同请求出现不同上下文组成，调试成本更高。

### 工具描述的精确度与体积
越详细的工具说明能提升模型调用准确率，但会直接吃掉预算。如果一次性注册全部工具，可能导致 ToolsReserve 超过可用空间。推荐做法是在注册时区分“常驻工具”与“按需加载工具”，并通过意图分类器选择子集送入模型。

### 检索片段密度与数量
多片段能降低幻觉，但每个片段都包含标题、路径和正文，token 开销高。应把检索预算拆为“片段数上限”与“片段总 token 上限”两个约束，避免单个过长文档垄断预算。

### 长历史修剪策略
直接截断保留最新若干轮，语义损失最小但会丢失早期承诺；摘要化能保留长期意图，但会丢失具体参数和引用。建议实现三级策略：完整保留、滑动窗口、摘要化，并按轮数阈值自动降级。

### 输出头空间预留
如果输入占满 TotalCap，模型将没有足够空间生成答案。OutputHeadroom 必须作为输入预算的一部分预留，不能等输出阶段再协商。当检索结果临时变大时，应优先压缩历史而非输出空间。

## 可执行的实施流程

1. 定义 BudgetProvider 接口，包含 resolveBudget(ctx) 与 actualize(ctx) 两个方法。
2. 接入模型 tokenizer，建立字符数到 token 数的转换系数，并每季度用真实语料校准。
3. 在配置中声明各分区占比，默认建议 System 10%、Tools 15%、Retrieval 25%、History 40%、OutputHeadroom 10%。
4. 系统提示加载时立即计算 token 数，若超出 SystemReserve 则启动失败。
5. 工具注册表在初始化时汇总所有工具说明的 token 数，若超过 ToolsReserve 则标记为需要动态选择。
6. 检索模块在返回片段前先按相关性排序，再按预算截断，最后加入来源路径与版本号。
7. 会话管理器维护历史消息的原始副本与 trimmed 副本，trimmed 副本用于入模。
8. 在每次模型调用前执行预算检查：total = system + tools + retrieval + history + outputHeadroom；若超过 TotalCap，则触发降级路径。
9. 将各组件占用写入结构化日志，包含会话 ID、模型版本、分区名与 token 数。
10. 允许按会话覆盖分区比例，但必须在审计日志中记录，并限制覆盖范围。

## 示例：本地文件知识库的预算配置

下面是一个以 TypeScript/Web 本地文件知识库为背景的紧凑配置示意：

budget:
  totalCap: 32000
  model: local-32k
  reserves:
    system: 1800
    tools: 4200
    retrieval: 8000
    history: 15000
    outputHeadroom: 3000
  components:
    - type: system
      source: .pi/prompts/system.md
      tokens: 1720
    - type: tools
      list: [search_knowledge, read_file]
      tokens: 3980
    - type: retrieval
      chunks:
        - {id: c1, path: docs/adr/0001.md, tokens: 980, score: 0.91}
        - {id: c2, path: docs/pi-agent-learning.md, tokens: 1450, score: 0.85}
      selectedTotal: 2430
    - type: history
      turns: 8
      tokens: 14600
    - type: outputHeadroom
      tokens: 3000

输入：会话上下文、候选检索片段、完整历史、已注册工具列表。处理：BudgetProvider 按分区比例计算，先保留系统与工具，再按相关性挑选检索片段，最后压缩历史至剩余空间。输出：一个符合 TotalCap 的上下文包，包含各组件实际占用与来源追溯。

## 性能、质量与可观测性指标

1. 组件级 token 利用率：分别测量 system、tools、retrieval、history、outputHeadroom 的实际占用与预留之比，通过每次推理前的预算日志计算。
2. 裁剪率：统计被截断或摘要化的历史轮数、被淘汰的检索片段数，用于评估上下文损失。
3. 检索产出率：实际进入上下文的片段数与候选片段数之比，反映预算对知识召回的限制。
4. 预算组装延迟：从接收请求到完成预算计算与上下文压缩的耗时，应在 50 ms 以内。
5. 预算违规率：每万次请求中未能在模型调用前降至 TotalCap 以内的次数，目标为零。
6. 上下文漂移指数：通过对比用户原始问题与最终入模上下文的语义相似度，估计压缩造成的信息丢失。

## 失败模式、诊断证据与恢复动作

1. 系统提示超限：启动日志显示 system tokens > SystemReserve；恢复动作为拆分提示、将静态说明移入外部文档，或增大 SystemReserve。
2. 工具注册表膨胀：ToolsReserve 被全部占满，历史轮数被压缩至下限；证据是工具说明 token 数接近 ToolsReserve；恢复动作为引入动态工具选择，只注册与当前意图相关的工具。
3. 检索片段回灌：多个片段内容重复或单片段过长，导致 retrieval 占用超过预留；证据是 selectedTotal > RetrievalReserve；恢复动作为对片段去重并实施单片段 token 上限。
4. 历史压缩滞后：会话轮数增长后，history 持续占用增加，最终触发模型端 token 超限错误；证据是 API 返回 context length exceeded；恢复动作为降低窗口阈值、提前启用摘要化。
5. 字符代理漂移：使用字符数估算时，实际 tokenizer 计数比估算高 10% 以上；证据是 budget 日志中的 estimated vs actual 差异；恢复动作为校准字符/token 系数，或改用本地 tokenizer 精确计数。
6. 跨会话预算泄漏：多租户部署中，某会话的历史或检索片段被错误地计入另一会话；证据是会话 ID 与 token 统计不匹配；恢复动作为每次调用前清空 allocator 状态并校验会话边界。

## 问答测试样例

1. 正向问题：当前 totalCap 为 32000，系统提示 1800 token、工具 4000 token、检索 8000 token、预留输出 3000 token，历史最多可保留多少 token？答案：15200 token。
2. 正向问题：为什么输出头空间也计入输入预算？答案：因为模型总上下文窗口是输入与输出共享的，必须提前预留生成空间。
3. 边界问题：如果系统提示本身为 2000 token，而 SystemReserve 只有 1800，应优先启动失败还是自动借用历史空间？答案：架构上应启动失败，因为系统提示变更不频繁，借用会隐藏配置错误。
4. 边界问题：检索片段相关性第 5 名刚好 1500 token，而剩余检索预算只有 800 token，应如何处理？答案：丢弃该片段，并记录裁剪原因，不应借用输出空间。
5. 无证据拒答：当前预算策略能否保证模型不幻觉？答案：无法保证；预算只控制上下文体积，不直接控制内容准确性。
6. 无证据拒答：是否所有模型都应使用相同的分区比例？答案：不能确定；比例取决于任务分布、工具数量与历史长度，应通过观测数据迭代。

## 维护、版本、来源与相邻主题

上下文预算策略需要独立版本号，并与模型 tokenizer 版本、系统提示版本、工具注册表版本同时记录。每次调整分区比例，都应升级策略版本并保留旧策略用于回滚。检索片段必须携带来源路径、生成时间或版本标识，以便在预算裁剪后仍能追溯。该主题与以下相邻主题紧密相关：RAG 召回策略决定检索片段候选池；会话管理决定历史消息的保存与压缩；提示工程决定系统提示体积；工具路由决定需要注入哪些工具说明；可观测性系统决定如何采集预算日志；模型运行时决定 tokenizer 与上下文窗口上限。

## 结论

事实：上下文预算是进入模型前的总 token 上限，必须涵盖系统提示、工具说明、检索片段和历史消息；各组件应通过 BudgetProvider 这类可替换接口协作。推论：固定分区适合早期确定性部署，动态池适合高吞吐但调试成本更高；工具与检索是预算消耗增长最快的两个部分，应优先实施动态选择和片段截断。未知：具体任务下最优分区比例仍需通过实测确定；多模态输入（图像、音频）对上下文预算的换算方式不在当前文本范围，需要另行定义。
