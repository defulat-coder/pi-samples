# 证据回答：在Agent响应中保留可验证来源的工程设计

## 摘要与问题边界

证据回答要求Agent生成的每个事实性主张都必须绑定到可复查的原始材料，例如本地文件、数据库记录、API工具返回或执行日志。该范式的目标不是阻止模型生成，而是让运维工程师在事后能够回答三个问题：这个结果引用了什么？引用当时是否有效？失效后如何重建？

并非所有查询都适合证据回答。创意写作、开放式头脑风暴、纯数学推导或用户授权的主观建议可以不绑定外部证据。当查询涉及系统状态、配置值、代码库结构、运行时指标、历史操作或合规声明时，才强制启用。混淆边界会导致两种失败：把主观输出硬套来源，或在需要审计时丢失来源。

## 核心概念与数据模型

1. 证据单元（Evidence Unit）：一次可独立验证的最小引用块，包含来源标识符、获取时间戳、内容哈希、原始片段和访问路径。对文件，路径是文件绝对路径与行号范围；对数据库，是表名、主键和字段名；对工具，是工具名、调用参数和返回摘要。

2. 来源签名（Source Signature）：对证据来源的规范化描述，避免模型用不同措辞指向同一来源。签名包括协议、定位符、版本和读取权限。运维通过签名统一检索，而不是依赖模型对文件名的自由描述。

3. 检索上下文（Retrieval Context）：Agent在生成前实际获取到的原始上下文集合。它与最终提示词分离存储，因为提示词可能被截断或改写，而检索上下文保留完整输入。

4. 回答主张（Claim）：Agent输出中需要证据支撑的具体命题。每个主张必须对应一个或多个证据单元。如果主张无法对应，则进入“无证据”分支。

5. 证据链（Evidence Chain）：从用户问题到检索查询、到来源读取、到主张生成、再到响应交付的完整链路。每一步都记录事件ID和时间戳，支持事后回放。

6. 回退证据（Fallback Evidence）：当首选来源不可用时，Agent使用替代来源并明确标注。例如，数据库主节点故障时读取只读副本，并在响应中声明副本延迟。

## 设计决策与取舍

1. 同步取证还是异步取证。同步模式在生成前等待所有证据返回，延迟可预测，但高并发时来源易被拖垮。异步模式允许先返回部分结果，后台补充证据，但增加了客户端状态管理。选择取决于来源P99延迟：若低于响应时间预算的30%，可同步；否则必须异步并标注“证据待补齐”。

2. 完整引用还是摘要引用。完整引用把原始片段嵌入响应，便于直接核对，但占用token并可能泄露敏感字段。摘要引用只给定位符，需二次查询。内部运维用完整引用，外部用户用摘要引用，通过权限策略自动切换。

3. 单源验证还是多源融合。多源一致时可信度最高；冲突时必须有裁决策略。建议设定优先级表而非让模型自行判断，例如：数据库实时记录 > 文件快照 > 工具缓存。模型仅负责报告冲突，裁决由策略引擎执行。

4. 客户端可见还是服务端内部证据。暴露证据会增加网络负载和安全风险，但能提高用户信任。关键配置、密钥路径和中间调试信息应保留在服务端日志，只有脱敏后的定位符和摘要才允许下发。

5. 缓存命中与证据新鲜度。缓存能显著降低来源读取压力，但过期策略必须显式配置。文件系统可监听变更事件，数据库可依赖版本号或时间戳。任何来自缓存的证据都应标记“缓存时间”和“最大可接受陈旧时间”。

## 可执行的实施流程

1. 建立证据来源清单，列出所有可能被引用的文件目录、数据库表、API工具、执行命令和环境变量，并为每个来源分配稳定签名。

2. 为每个来源实现只读连接器，封装读取、分页、超时和重试逻辑。连接器返回原始字节或结构化数据，不预先解释内容。

3. 定义统一的证据元数据Schema，包含source_id、retrieval_time、content_hash、byte_range、row_count、cache_ttl、permission_level等字段。

4. 在提示词中注入证据约束，要求模型在生成事实性主张时，每个主张后必须紧跟引用标识，无法引用时输出“NO_EVIDENCE”。

5. 生成后运行证据对齐校验，检查模型引用是否真实存在于检索上下文中，哈希是否匹配，行号范围是否越界。

6. 将取证过程作为结构化事件流输出到可观测系统，包括检索开始、来源命中、来源失败、缓存命中、模型引用生成、对齐校验通过或失败。

7. 实现来源降级策略：主来源失败时切换到副本，副本延迟过高时切换到缓存，所有切换写入响应元数据并触发告警。

8. 建立响应回放机制，保存问题、检索上下文、生成结果、证据链和来源签名，保留周期不少于系统变更窗口的两倍。

## 性能、质量和可观测性指标

1. 证据获取P99延迟：从发起检索到收到原始数据的耗时。在连接器中记录start_time和end_time，按来源维度聚合。异常阈值设定为响应时间预算的50%。

2. 证据对齐率：生成后通过校验的主张数量占总主张数量的比例。低于95%时触发模型输出质量告警。

3. 证据缺失率：模型输出“NO_EVIDENCE”或引用不存在来源的比例。需区分“合理无证据”与“缺陷无证据”。

4. 端到端响应时间：从用户请求到最终流结束的总耗时。该指标必须与证据获取延迟分开，以便判断瓶颈在模型生成还是来源读取。

5. 缓存命中率与陈旧度：命中缓存的证据占比，以及命中时证据距离原始写入的时间差。运维需同时追踪两者，避免只追求命中而忽视新鲜度。

## 失败模式、诊断证据与恢复动作

1. 来源服务不可用。诊断证据：连接器连续超时、DNS解析失败或TCP连接拒绝。恢复：切换到备用来源，返回降级证据，并标记响应为“证据来源降级”。若所有来源不可用，返回无证据拒绝而非编造答案。

2. 证据过期。诊断证据：原始文件或数据库记录在生成后发生变更，content_hash与响应记录不一致。恢复：回放时重新读取最新来源，对比生成时刻快照，判断是数据演进还是输出错误。

3. 模型幻觉引用。诊断证据：对齐校验发现引用ID不存在，或行号范围与检索上下文不匹配。恢复：拒绝该主张，提示模型重新生成，并加强引用格式约束。

4. 权限拒绝导致证据不完整。诊断证据：读取器返回部分字段缺失或403错误，但模型仍基于不完整数据生成结论。恢复：为每个证据单元标记权限级别，并在字段缺失时要求补充来源或降级为无证据。

5. 并发读取导致证据不一致。诊断证据：同一响应中多个来源时间戳差异超过可接受窗口。恢复：为相关来源实施事务性快照或读取时间锚点，确保所有证据围绕同一时刻获取。

## 问答测试样例

1. 正向问题：pnpm-lock.yaml 中 Pi Coding Agent 的版本号是多少？期望回答：0.83.0，并引用文件路径和字节范围。

2. 正向问题：api 目录的职责边界是什么？期望回答：引用AGENTS.md中apps/api段落，说明其负责请求验证、会话身份和SSE/JSON传输。

3. 边界问题：比较两个不同时间点数据库记录的差异。期望回答：若系统未保存历史快照，必须声明无法提供差异证据，而非虚构差异。

4. 边界问题：未来一个季度的容量规划。期望回答：若知识库中没有规划文档，输出NO_EVIDENCE，并说明超出当前可验证范围。

5. 无证据拒答条件：用户询问pi内部实现细节，但.pi目录未被授权访问。期望：拒绝引用未授权来源，说明无法提供证据。

6. 无证据拒答条件：用户要求评价同事代码质量。期望：该问题属主观判断，无统一证据标准，应拒答或声明为个人观点。

## 维护、版本、来源和与相邻主题的关系

维护：证据Schema变更属于破坏性变更，需要版本化。为evidence_unit、source_signature和chain_id分别维护版本号，并在回放时携带旧版本读取器。

版本：知识库文章、配置文件和Agent代码应使用相同版本控制策略。当来源文件升级或数据库Schema变更时，必须同步更新来源签名和连接器，否则历史响应将无法对齐。

来源：本文基于项目级设计描述，未调用外部系统。所引用文件路径和示例数据均来自当前项目结构：AGENTS.md、pnpm-lock.yaml、package.json、apps/api、packages/pi-agent。

相邻主题：证据回答与“检索增强生成（RAG）”相关，但RAG关注检索质量，证据回答关注引用可验证性；与“工具调用”相关，但工具调用强调动作执行，证据回答强调结果溯源；与“可观测性”相邻，因为证据链本身就是结构化日志；与“权限与沙箱”相邻，因为读取来源必须受能力边界约束；与“会话管理”相邻，因为证据链需要绑定会话生命周期。

## 结论

事实：证据回答强制事实性主张与可验证来源绑定；来源签名、证据单元和证据链是工程设计中的可复用结构；来源不可用、过期、幻觉引用、权限拒绝和并发不一致是已被识别的失败模式。

推论：在运维场景下，同步证据更适合低延迟来源，异步证据适合高吞吐但可接受延迟的场景；缓存能提升性能但必须以新鲜度指标为代价；模型引用格式约束可显著降低幻觉引用概率。

未知：不同来源之间的冲突裁决策略是否能在所有业务域中统一，仍需根据具体项目数据验证；长上下文模型是否会削弱证据单元精度，尚无定论；在极端并发下，跨文件、数据库和API的多源一致性保证成本仍需实测。
