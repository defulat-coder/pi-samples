# Agent Loop：模型-行动-结果闭环的架构责任与可替换接口

## 摘要与问题边界

Agent Loop 是 Agent 运行时把“观察上下文、选择行动、接收结果、继续下一轮”串成连续回合的最小控制结构。它不承担用户意图预分类，也不负责工具内部业务实现；它的核心责任是维护一条可追加的上下文序列，让模型每轮决定下一步动作，接收执行结果，再决定继续、终止或回退。本文从架构视角界定 Agent Loop 与模型运行时、工具注册、持久化、安全策略等模块的接口边界，再讨论控制流、状态机、错误恢复与可替换性，最后给出可直接落地的实施流程、指标与失败模式。

## 核心概念与数据模型

1. 上下文切片（Context Slice）：每轮追加到工作记忆的最小单元，包含角色、动作请求、工具输出、元数据与版本戳。它必须不可变，历史切片不修改，只能通过新增切片或摘要切片覆盖语义。

2. 动作签名（Action Signature）：模型可调用的动作集合，由名称、参数模式、Capability、副作用级别和超时组成。Loop 只识别签名，不解析业务语义；签名由 Tool Registry 启动时注入。

3. 执行结果（Result）：工具或环境返回的结构化数据，含成功标志、输出载荷、错误码、耗时、来源标识。结果必须能序列化进上下文切片，成为下一轮观察。

4. 回合（Turn）：从模型生成动作请求到结果写回上下文的一次迭代。一个会话由多个 Turn 组成，每个 Turn 有单调递增序号，同一回合可包含多个并行动作请求。

5. 终止条件（Termination Condition）：定义何时停止循环的判定函数，例如最大回合数、显式结束动作、token 预算耗尽、用户中断、安全策略命中或连续无效动作阈值。

6. 观察窗口（Observation Window）：受上下文长度限制时，决定哪些切片进入模型输入的策略。策略可最新优先、摘要压缩、分层检索或关键切片锁定，但必须在循环外部可配置，不能写死在控制器中。

## 设计决策与取舍

### 控制流所有权归运行时

Agent Loop 必须由运行时持有控制流，而不是由模型自行驱动。循环决定何时调用模型、工具与结束。若模型直接输出新请求而不经校验，会破坏安全边界，也可能导致失控。

### 同步执行与异步执行

单回合内工具调用可同步等待或异步派发。同步实现简单、顺序清晰，但长工具阻塞循环；异步支持并发，却需结果队列与顺序还原。若 P90 延迟超过 500 毫秒，优先采用异步。

### 状态持久化粒度

按 Turn 持久化可完整恢复，但写入压力大；按会话快照减少 I/O，却会在崩溃时丢失最近动作。推荐混合策略：每次动作结果写回上下文时追加日志，会话元数据只在边界切换或用户触发时写快照。

### 错误恢复策略

模型可能输出无效参数或触发超时。恢复分两层：运行层把错误封装成标准 Result 写回上下文；策略层决定是否重试、降级或终止。运行层错误不应直接抛给用户，除非策略层明确放行。

### 可替换接口而非具体实现

Loop 不应依赖具体模型或工具。应抽象出 ModelRuntime、ToolRegistry、ContextStore 接口。替换者遵守契约即可在不改控制逻辑的情况下切换模型、工具或持久化后端。

## 可执行的实施流程

1. 定义 `Turn` 和 `ContextSlice` 的不可变数据结构，明确版本戳、角色标记和追加规则。
2. 建立 `Capability` 与 `ActionSignature` 注册机制，为每个工具声明名称、参数模式、副作用级别和超时。
3. 实现 `ContextStore` 接口，支持追加切片、读取观察窗口、按会话回滚和生成摘要切片。
4. 实现 `ModelRuntime` 接口，统一输入格式、流式输出解析、动作提取和 token 计数返回。
5. 编写循环控制器：检查终止条件 → 组装观察窗口 → 调用模型 → 解析动作 → 校验权限与参数 → 执行工具 → 封装结果 → 追加上下文 → 回到起点。
6. 引入错误转换层，把工具异常、网络超时、参数校验失败映射为标准 Result 结构。
7. 接入可观测性：记录每轮 latency、输入输出 token、工具调用次数、错误码、终止原因和上下文切片数量。
8. 在集成测试中构造最小会话：用 mock 模型返回固定动作，用 mock 工具返回固定结果，验证多轮后上下文顺序、窗口策略和终止条件生效。

## 代码示例：本地文件知识库的 YAML 动作签名与处理

以下示例描述一个无写权限的 `search_knowledge` 动作：

    tool: search_knowledge
    signature:
      name: search_knowledge
      parameters:
        query: { type: string, maxLength: 256 }
        limit: { type: integer, default: 5, minimum: 0, maximum: 10 }
      sideEffect: none
      capability: read
    input:
      turn: 3
      action: search_knowledge
      arguments: { query: "Agent Loop 的上下文窗口策略", limit: 3 }
    process:
      - validate_signature
      - check_capability_read
      - LocalFileKnowledgeBase.search
      - rank_by_relevance
      - truncate_to_limit
    output:
      success: true
      source: local_file_kb
      items:
        - title: "Agent Loop 观察窗口"
          excerpt: "Observation Window 决定哪些上下文切片被送进模型..."
      turn: 3

输入：模型在第三轮输出 `search_knowledge` 动作，参数包含查询字符串与返回条数。处理：运行时从 `ToolRegistry` 查找签名，校验 `query` 为字符串、`limit` 为 0 到 10 的整数；调用本地文件知识库读取 `.pi/knowledge` 目录，按相关度排序并截取前三条。输出：结果以 JSON 写回上下文，包含 `success`、`source`、`items` 与当前 `turn`，成为下一轮观察。

## 性能、质量和可观测性指标

1. 每轮延迟：从模型输出到结果写回上下文的时间。在循环控制器内记录 `turn_start` 和 `turn_end` 时间戳，统计 P50、P90、P99。
2. 上下文命中效率：观察窗口保留的切片中被后续模型引用的比例。通过模型输出中的引用标记或动作相关性近似测量。
3. 工具错误率：每百轮出现无效参数、未注册工具或超时的次数。按错误码聚合，区分运行层错误与策略层拒绝。
4. 会话完成率：会话在达到目标前正常终止的比例。区分用户取消、策略命中、模型错误、循环耗尽和异常退出。
5. Token 利用率：每轮输入 token 与有效信息增益之比，定义为输出动作价值评分除以输入 token 数，用于评估窗口策略是否引入冗余。

## 失败模式、诊断证据与恢复动作

1. 循环震荡：模型反复调用同一工具，无法收敛。诊断证据：连续三轮动作名称相同、参数相似、上下文未显著变化。恢复：触发去重启发式，提示模型已尝试结果，或强制终止。
2. 工具权限逃逸：模型请求超越声明能力的动作。诊断证据：Capability 与注册时不符，或请求被策略层拦截。恢复：拒绝动作并把拒绝结果写回上下文，不暴露内部权限细节。
3. 上下文窗口溢出：输入超出模型最大长度。诊断证据：token 计数超过阈值。恢复：启动观察窗口压缩策略，如丢弃最早非关键切片、生成摘要替换，或切换更大上下文模型。
4. 持久化损坏：追加日志中出现无法解析的切片。诊断证据：读取会话时反序列化失败。恢复：跳过损坏切片并记录偏移量，或从上一个快照回滚。
5. 结果顺序错乱：异步工具结果未按请求顺序返回。诊断证据：结果中的 turn 与请求不匹配。恢复：在结果队列中按 turn 序号排序，缺失结果等待超时后标记为 timeout 并写回上下文。

## 问答测试样例

1. 正向：Agent Loop 每轮需要完成哪三个关键步骤？答案：模型观察上下文并输出动作；运行时校验并执行动作；将结果追加回上下文。
2. 正向：为什么动作签名要声明副作用级别？答案：让运行时在不解析语义的情况下判断是否需要用户确认、审计或沙箱隔离。
3. 边界：如果模型要求调用未注册工具，循环应如何处理？答案：返回标准 Result，标记 `success: false`、错误码 `tool_not_found`，并追加到上下文，不中断会话。
4. 边界：当 token 预算耗尽时，终止条件是否必须立即生效？答案：不一定，策略可允许先压缩上下文再尝试一轮；若压缩后仍超出，则终止。
5. 无证据：Agent Loop 是否保证模型不会 hallucinate 工具结果？答案：无法保证。运行时只校验格式与权限，不验证内容真实性。
6. 无证据：循环是否适用于实时流式音视频响应？答案：本文未讨论实时音视频场景；若延迟要求低于单轮平均耗时，需额外引入流式分片与快速响应通道，不能直接从本文推导。

## 维护、版本、来源与相邻主题的关系

Agent Loop 的架构契约应使用语义化版本管理。`Turn`、`ContextSlice` 和 `ActionSignature` 的字段变更属于破坏性变更，需要主版本升级；新增可选字段属于次版本升级。本文内容来源于项目内部架构约定，如 `packages/pi-agent` 的会话控制实现与 `packages/contracts` 的 DTO 定义。相邻主题包括：Agent 安全沙箱（负责执行隔离）、工具注册与发现（负责 Capability 注入）、记忆与检索（负责长期上下文压缩）、模型运行时（负责生成与 token 计算）。Agent Loop 位于这些模块的交汇处，但不应侵入它们的具体实现。

## 结论

事实：Agent Loop 是“观察上下文、选择动作、执行并接收结果、继续下一轮”的连续迭代控制结构；它依赖不可变的上下文切片、动作签名和终止条件，并通过可替换接口与模型、工具和持久化解耦。

推论：把循环控制流与模型、工具、持久化解耦，可以显著提升系统的可测试性、可替换性和长期演进能力；错误恢复应分层，运行层只负责封装，策略层负责决策。

未知：在多 Agent 协作、强化学习反馈循环或极低延迟实时交互中，Agent Loop 的最优回合长度、错误恢复策略与上下文压缩方法仍缺乏统一结论，需要结合具体业务场景持续验证。
