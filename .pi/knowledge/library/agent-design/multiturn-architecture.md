# 多轮对话上下文合并：架构视角下的状态化推理协议

多轮对话的核心困难不是“记住前面说了什么”，而是如何在每一轮把前一轮已确认的事实、用户给出的修正、以及从本地知识库新检索到的证据，合并成一个自洽且可审计的上下文。本文从架构视角界定这一合并过程的责任边界、可替换接口与演进路径，目标读者是负责 Agent 边界和长期演进的系统设计者。

问题边界限定在单次会话内部。它处理三类输入：上一轮的已确认事实、用户本轮的显式修正或补充、以及从本地文件知识库检索到的新证据。它不处理跨会话长期记忆、情感建模、多模态原生编码，也不假设模型参数知识具备可验证性。

## 核心概念与数据模型

1. **事实断言 FactAssertion**。一个结构化记录，包含 `claim`（命题文本）、`confidence`（取值 0 到 1）、`sourceTurn`（来源轮次编号）、`provenance`（证据引用列表）。它不是自由文本，而是必须能被后续合并算子解析和覆盖的原子单元。

2. **修正指令 CorrectionDirective**。用户显式用于覆盖或撤销既有事实的指令，例如“刚才的身高改成 175”或“忽略第三点”。它必须带有 `targetId` 指向被修正的事实，否则只能作为新证据等待人工确认。

3. **证据片段 EvidenceFragment**。从本地文件知识库检索出的原始块，包含 `content`、`filePath`、`chunkId`、`retrievalScore`。证据不直接等同于事实，需要经过置信度校准后才能进入状态。

4. **上下文窗口 ContextWindow**。一个可替换策略接口，定义哪些历史事实、证据和修正被保留在活跃上下文中。它的实现可以是滑动窗口、摘要压缩或基于相关性的选择性保留，但接口本身只暴露 `select(state, query) -> slice`。

5. **会话状态 SessionState**。结构化的状态对象，包含 `turns`、`facts`、`corrections`、`evidenceLog`、`mergeVersion`。它与“消息列表”不同：消息列表是通信记录，会话状态是推理 substrate。

6. **合并算子 MergeOperator**。确定性函数 `merge(prevState, correction, newEvidence) -> nextState`。它负责解决冲突、维护版本、生成变更日志，并在冲突无法仲裁时标记人工审查。

7. **来源追溯链 ProvenanceChain**。每一次状态变更都必须记录父版本、变更原因、责任人（用户 / 检索器 / 合并算子）。它是可观测性和回滚的基础。

## 设计决策与取舍

**状态模型还是消息模型**。消息模型实现简单，把历史消息直接拼进 prompt；但它把合并责任推给语言模型，导致结果不可重复、难以审计。状态模型把合并显式化，代价是增加 schema 演进和序列化成本。对于需要长期演进和多 Agent 协作的系统，状态模型更可取。

**显式合并还是隐式推理**。显式合并由代码规则执行，可预测但可能遗漏语义 nuances；隐式推理让模型自己处理，灵活但黑盒。建议采用“显式合并为主，模型重述为辅”：合并算子输出结构化状态，语言模型仅负责把状态重述为自然语言回复。

**本地知识库作为证据源还是依赖模型参数知识**。本地文件知识库提供可验证、可引用、可版本化的证据；模型参数知识无法引用，容易产生幻觉。所有进入会话状态的事实必须有 `provenance` 指向本地证据或用户显式声明。

**截断策略：滑动窗口、摘要压缩还是选择性保留**。滑动窗口最简单，但会丢失跨轮关键事实；摘要压缩节省 token，但引入二次信息损失；选择性保留根据当前查询动态召回历史事实，实现复杂但精度最高。建议把 `ContextWindow` 设计为接口，默认使用选择性保留，同时允许按会话配置切换。

**同步阻塞还是异步增量更新**。同步阻塞保证每轮回复前状态已一致，适合强一致性场景；异步增量允许在后台合并检索结果，适合高吞吐但容忍短暂不一致的场景。接口层面应暴露 `mergeSync` 和 `enqueueMerge` 两种语义，由调用方选择。

**用户修正的权威性 versus 模型推断的置信度**。用户修正无条件覆盖同标识的事实；模型推断的置信度仅用于排序和拒答阈值，不能直接覆盖用户修正。这是安全边界，防止模型“合理化”地撤销用户输入。

## 可执行的实施流程

1. 定义 `SessionState` 与 `MergeOperator` 的 TypeScript 接口，明确字段、版本号和不可变更新语义。
2. 实现事实提取器，从每轮用户输入和助手回复中抽取候选 `FactAssertion`。
3. 实现修正解析器，识别否定词、指代和目标标识，生成 `CorrectionDirective`；无法解析时转人工审查队列。
4. 集成本地文件知识库检索，返回带分数和来源路径的 `EvidenceFragment`。
5. 实现确定性合并算子，规则包括：用户修正覆盖同标识事实；新证据按置信度排序；冲突事实进入待仲裁状态。
6. 配置 `ContextWindow` 策略，确保关键事实即使被截断也能通过选择性保留机制召回。
7. 建立来源追溯链，每次状态变更写入父版本哈希、变更原因和责任人。
8. 接入观测系统，记录合并延迟、冲突率、回滚事件和上下文命中率。
9. 编写回归测试套件，覆盖正向合并、边界冲突和无证据拒答场景。

## TypeScript 示例

输入：`prevState` 包含上一轮确认的事实“项目使用 pnpm”；用户本轮输入“改为 npm”；新证据是从 `package.json` 检索出的 `"packageManager": "pnpm@10.30.3"`。

处理：`CorrectionParser` 生成 `CorrectionDirective`，目标为事实 id `pkg-manager`，新值为 `npm`。`EvidenceFragment` 提供反证据。`MergeOperator` 执行规则：用户修正权威性高于证据，因此事实被更新为 `npm`，但 `provenance` 保留证据引用并标记 `userOverride: true`，置信度降至 `0.6` 以提示后续轮次可再确认。

输出：`nextState` 包含更新后的事实、版本号递增、变更日志记录“用户覆盖：pkg-manager npm（证据建议 pnpm）”。助手回复时重述该状态，提示用户本地文件仍显示 pnpm，以促成下一轮澄清。

```typescript
interface FactAssertion {
  id: string;
  claim: string;
  confidence: number;
  sourceTurn: number;
  provenance: string[];
  userOverride?: boolean;
}

type MergeResult = {
  state: SessionState;
  changelog: string[];
  conflicts: string[];
};
```

## 性能、质量和可观测性指标

1. **上下文命中率**：当前轮成功从状态而非仅依赖 prompt 历史召回的关键事实比例。测量方式：对测试集标记关键事实，检查其是否出现在 `ContextWindow.select` 结果中。

2. **修正响应延迟**：从接收用户输入到生成 `CorrectionDirective` 并更新状态的中位耗时。应低于 200ms（本地组件）或低于 1s（含检索）。

3. **事实漂移率**：用户在后续轮次中再次否定同一件事的频率。高漂移率说明合并算子或重述层未能稳定状态。

4. **证据召回率**：本地知识库中真正相关的证据片段被检索并进入状态的比例。通过人工标注的 ground truth 计算。

5. **合并冲突率**：每百轮中进入 `conflicts` 队列需要人工或模型仲裁的次数。目标低于 5%，否则说明 schema 或规则不足。

6. **回滚成功率**：在检测到错误合并后，通过来源追溯链回滚到上一有效版本并成功恢复一致性的比例。应接近 100%。

## 失败模式

1. **修正被新证据覆盖**。诊断证据：状态日志显示 `CorrectionDirective` 后紧跟 `EvidenceFragment` 又把事实改回旧值。恢复动作：在合并算子中把用户修正标记为 sticky，任何证据在 N 轮内不得覆盖，除非用户再次确认。

2. **证据幻觉**。诊断证据：`EvidenceFragment.filePath` 指向不存在的文件或 chunkId 无法校验。恢复动作：在检索层加入文件存在性校验，并在状态中把不可验证证据的置信度置 0。

3. **上下文截断丢失关键事实**。诊断证据：关键事实 `id` 出现在历史但不在当前 `ContextWindow.select` 结果中，导致模型重复询问。恢复动作：对标记为 `sticky` 或用户修正过的事实强制保留，无论 token 预算。

4. **合并顺序依赖错误**。诊断证据：同样输入按不同顺序调用合并算子得到不同状态。恢复动作：合并算子必须满足结合律近似，或把多来源输入先排序再合并；单元测试应覆盖顺序交换。

5. **轮次间来源断裂**。诊断证据：状态中存在事实但 `provenance` 为空，无法回滚或审计。恢复动作：在类型层把 `provenance` 设为非空数组，缺失时拒绝写入状态。

## 问答测试样例

1. 正向问题：用户先说“部署到 Vercel”，后说“改成 Netlify”。期望状态中的部署目标事实被更新为 Netlify，且变更日志包含来源轮次。

2. 正向问题：用户询问“pnpm 版本是多少”，系统从 `package.json` 检索出 `pnpm@10.30.3`。期望回复引用文件路径并给出准确版本。

3. 边界问题：用户说“不对，我指的是测试环境不是生产环境”。期望系统解析指代，仅更新环境相关事实，不触碰无关事实。

4. 边界问题：用户输入“删掉刚才所有关于数据库的设定”。期望系统生成批量修正指令，将数据库相关事实标记为撤销，而不是真正删除以保留审计。

5. 无证据拒答：用户问“这个项目的 CEO 是谁”，本地知识库没有任何人员信息。期望系统不基于模型参数知识回答，而是明确说明无证据并询问用户是否补充。

6. 无证据拒答：用户说“其实我们是 Go 项目”，但本地文件全是 TypeScript。期望系统把该声明作为低置信度用户断言记录，并提示与本地证据冲突请确认。

## 维护、版本、来源与相邻主题

会话状态的 schema 变更必须带版本号，旧版本数据通过迁移函数升级。合并算子的规则变更应写入 `CHANGELOG`，并在测试集中新增对应失败模式用例。与相邻主题的关系：多轮对话上下文合并依赖检索增强生成提供证据，依赖工具调用执行具体动作，依赖对话状态管理维护持久会话；它又向上支撑任务规划，因为稳定的事实层是计划修正的前提。

## 结论

事实层面：多轮对话的上下文合并可以显式建模为状态转换，由可替换的 `MergeOperator` 和 `ContextWindow` 接口驱动。推论层面：把用户修正置于最高权威性、把本地证据作为可验证来源、把来源追溯作为审计基础，是长期演进中降低幻觉和回归风险的关键设计。未知层面：在超长会话中如何平衡状态膨胀与召回精度，以及如何让合并算子在语义层面比规则层面更鲁棒，仍是需要结合具体领域数据迭代验证的开放问题。
