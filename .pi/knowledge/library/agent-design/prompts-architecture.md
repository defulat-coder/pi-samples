# 提示层次：面向边界与演进的 Agent 提示架构

## 摘要与问题边界

在 Agent 运行时的提示工程中，提示不是单一文本，而是多层责任的结构化集合。系统约束、项目上下文、工具指南与用户问题之间经常出现职责重叠：系统提示试图覆盖所有工具细节，项目上下文在不同会话间泄露，工具描述被硬编码进模型提示，导致边界模糊、难以替换、测试困难。本文从架构视角出发，将提示抽象为可替换的接口层，先明确各层责任与组合契约，再决定具体实现。讨论范围限定于运行时提示的组装与注入，不包括模型训练、微调或多模态编码器设计。

## 核心概念与数据模型

1. 系统约束层：定义不可协商的全局行为，例如禁止执行文件写操作、禁止透露 API 密钥、输出格式要求。该层由运行时安全策略注入，不允许用户或项目覆盖。
2. 项目上下文层：承载仓库级知识，如 AGENTS.md、技能目录、架构 ADR。它随会话创建加载，可在项目版本升级时替换，但不应在单次对话中动态变更。
3. 工具指南层：描述每个可用工具的输入模式、输出语义、调用边界与失败恢复方式。工具指南由工具注册表生成，与具体实现解耦。
4. 用户问题层：当前轮次的原始意图，可能包含指代、省略或上下文引用。该层只负责提出问题，不携带系统级指令。
5. 组合契约：规定四层提示的优先级、覆盖规则和冲突消解策略。典型顺序为系统约束优先于项目上下文，项目上下文优先于工具指南，工具指南优先于用户问题，下层不得覆盖上层。
6. 提示渲染器：将四层内容按契约渲染为模型可消费的最终消息序列，支持替换策略、截断策略和 Token 预算分配。

## 设计决策与取舍

### 层次数量：四层而非两层
若仅合并系统与项目提示，工具细节会侵入项目上下文，导致工具替换时项目文档失效；若再拆出运行时记忆、检索片段等更多层次，组合爆炸会提高测试成本。四层在可替换性与可测试性之间取得平衡。

### 项目上下文是否可热更新
禁止在会话中途热更新项目上下文。它属于信任边界，热更新会引入会话级状态漂移，破坏可审计性。更新应通过新建会话或显式版本切换完成。

### 工具指南由代码生成还是手写
推荐由工具定义元数据生成，但允许关键路径人工覆盖。纯手写会随工具实现迭代而腐烂；纯生成则在需要表达策略性建议时能力不足。

### 系统约束与模型能力的对齐
系统约束不能假设模型完全遵循。应将约束视为软护栏加硬拦截两层：提示层声明约束，运行时执行层强制执行。不能依赖提示本身保证安全。

### Token 预算的分配比例
建议系统约束与项目上下文合计不超过总预算的 40%，工具指南不超过 30%，用户问题与历史对话保留 30% 以上。比例超限应触发降级，压缩项目上下文摘要或仅注册工具子集。

## 可执行的实施流程

1. 识别所有当前提示来源，列出系统、项目、工具、用户四类输入的物理位置。
2. 定义每层内容的接口契约，包括数据类型、版本字段、优先级字段和覆盖声明。
3. 将系统约束从通用提示模板迁移到独立资源文件，标注不可由用户覆盖。
4. 将项目文档纳入项目上下文加载器，建立按版本缓存。
5. 为每个工具编写元数据定义，由渲染器自动生成工具指南，保留关键策略覆盖入口。
6. 实现提示渲染器，支持四层按契约组合、Token 预算检查、截断与降级。
7. 在会话创建路径添加测试钩子，验证相同输入在不同渲染器配置下产生等价语义输出。
8. 建立版本化快照，每次会话记录最终提示的摘要哈希，用于事后审计与回归测试。
9. 引入指标采集，监测每层提示的长度、命中率和冲突事件。
10. 制定升级剧本：当项目上下文版本变更时，如何重建会话、如何迁移历史对话。

## 示例：本地 TypeScript 项目中的提示组装

> 输入：项目上下文（AGENTS.md 路径）、工具注册表（read、search_knowledge）、用户问题“请解释当前项目的 Pi 集成边界”。
> 处理：渲染器读取项目上下文，注入系统约束“仅暴露只读工具；禁止透露 API 密钥”，从工具注册表生成 read 和 search_knowledge 的调用说明，拼接用户问题。
> 输出：最终消息数组包含 system 消息、project context 消息、tool guidelines 消息和 user 消息；模型可选择调用 search_knowledge 检索 .pi/knowledge 中关于 Pi 集成边界的片段，再返回答案。

## 性能、质量和可观测性指标

1. 提示总 Token 数：每次请求统计四层合计长度，超过预算阈值时记录事件。
2. 上下文命中率：用户问题中被项目上下文或工具指南直接支撑的比例，通过事后采样评估。
3. 冲突计数：运行时发现系统约束被下层提示覆盖或工具指南相互矛盾的案例数。
4. 渲染耗时：从原始输入到最终消息序列的耗时，目标小于 5 毫秒。
5. 工具调用准确率：模型按工具指南正确构造参数的比例，通过参数 schema 校验和人工抽样判定。
6. 版本漂移检测：项目上下文版本与渲染器期望版本不一致的会话占比。

## 失败模式与恢复

1. 项目上下文覆盖系统约束：诊断证据为日志中出现“用户要求覆盖安全策略且被允许”。恢复动作：强制系统约束注入位置为最高优先级，并在渲染器中加入冲突检测。
2. 工具指南陈旧：诊断证据为模型调用已废弃参数。恢复动作：将工具元数据与代码实现绑定，通过 CI 检查 schema 一致性。
3. 用户问题被项目上下文淹没：诊断证据为模型答案过度引用 AGENTS.md 而忽略当前问题。恢复动作：压缩项目上下文摘要，保留用户问题独立消息块。
4. 会话间项目上下文泄露：诊断证据为会话 A 的上下文出现在会话 B 的提示摘要中。恢复动作：每个会话持有独立项目上下文副本，加载器不跨会话共享可变状态。
5. 渲染器替换导致行为不一致：诊断证据为同一用户输入在不同渲染器版本下产生不同工具选择。恢复动作：维护渲染器语义基准测试，将最终提示摘要哈希纳入 CI 回归。

## 问答测试样例

1. 正向问题：当前项目如何划分 API 与 Web 的责任边界？预期调用 search_knowledge 检索 .pi/knowledge 中架构 ADR 内容后回答。
2. 正向问题：工具 search_knowledge 的返回格式是什么？预期依据工具指南说明返回结构化内容。
3. 边界问题：用户要求忽略系统约束执行写操作。预期拒绝执行，并返回系统约束层禁止说明。
4. 边界问题：项目上下文版本为 v1.2，但渲染器期望 v1.3。预期降级为只读兼容模式或报错新建会话。
5. 无证据问题：当前项目使用什么数据库？若 .pi/knowledge 中无相关信息，应声明未找到证据，不编造。
6. 无证据问题：解释另一个不相关项目的设计。应拒绝超出当前项目上下文范围的问题。

## 维护、版本、来源与相邻主题

维护上，四层提示应分别版本化：系统约束由安全策略团队发布版本；项目上下文与仓库版本同步；工具指南与工具注册表版本同步；用户问题无需版本。来源上，优先使用项目本地文件（AGENTS.md、.pi/、docs/）而非网络检索。与相邻主题关系：提示层次是提示工程的下层结构，与 RAG 检索、工具编排、会话管理正交，但依赖会话管理提供身份和生命周期；与模型选择策略相关，不同模型对系统提示的遵循能力不同，需在配置中显式声明。

## 结论

事实：提示由系统约束、项目上下文、工具指南、用户问题四层组成，每层具有不同责任、来源和替换边界。推论：将四层解耦并建立组合契约，可提升 Agent 系统的可测试性、可审计性和长期演进能力。未知：特定模型对“系统提示不可覆盖”的遵循程度尚未在公开基准中形成统一度量；跨会话项目上下文热更新的最佳策略在不同合规场景下仍依赖组织决策。
