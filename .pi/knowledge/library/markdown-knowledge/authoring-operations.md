# Markdown 知识库文章编写的验证与运维规范

## 摘要与问题边界

本文面向需要观察系统性能、稳定性与故障恢复路径的工程师，定义单篇 Markdown 知识文章的生产规范。核心问题不是“如何写得好看”，而是“如何写出一篇可被检索、可被验证、可被恢复的文章”。范围限定在单篇文章内部：读者契约、问题边界、事实来源、可检索正文结构、可执行示例、可观测证据、失败恢复记录。不讨论知识库全局架构、权限模型、向量检索算法或模型生成策略。前提假设是读者已掌握 Markdown 基础语法，并熟悉 TypeScript/Web 项目的本地文件结构与 pnpm 工作流。

## 核心概念与数据模型

1. 读者契约。每篇文章必须在 H1 之后立即声明目标读者、先备知识和阅读目标。未声明读者契约的文章，在检索排序中应被视为低置信度；若被 Agent 引用，应触发“读者未确认”警告。
2. 问题边界。通过显式的“范围内”与“范围外”两段列表框定主题。边界外的内容即使相关也不得展开，只能以“参见”链接指向其他文章。边界变更属于破坏性更新。
3. 事实来源分级。一级来源是项目内可直接验证的代码、日志、配置文件或 CI 输出；二级来源是官方文档、已发布的 ADR 或版本锁定后的外部页面；三级来源是个人经验、社区讨论或临时笔记。引用处必须标注级别和路径。
4. 可检索正文。H2 标题对应核心概念，H3 标题对应实施细节，固定术语在同一篇文章中保持词形一致。避免在同一段落用多个别名指代同一组件，除非在术语定义段集中列出同义词映射。
5. 验证证据。每个关键论断应附带可复现证据：命令、输出片段、日志采样、监控截图路径或单元测试结果。证据必须包含采集时间、环境版本和采集人标识。没有证据的论断应标记为推论或待验证。
6. 恢复记录。恢复步骤必须独立于主流程编写，包含触发条件、降级模式、回退命令和验证命令。仅记录成功请求的文章不满足运维视角要求。

## 设计决策与取舍

### 标题层级与检索召回的取舍
层级过深会削弱检索器对段落的召回能力，层级过浅则导致主题混杂。本规范限定单篇文章使用 H1 一个、H2 不超过六个、H3 作为最细标题；超过三级的细分使用有序列表。例外：术语表和失败模式表可以使用 H2 下的表格，但不允许使用 H4。

### 原子化文章与专题聚合的取舍
单篇文章应只回答一个可验证问题。跨主题内容通过“参见”链接关联，而不是在同一篇中展开。这种取舍增加了链接维护成本，但降低了单篇文章版本漂移时的影响面。例外：故障恢复步骤若完全依赖某架构设计，可在同一篇文章中以 H2 分隔。

### 内联示例与外部引用的取舍
关键命令和配置必须内联展示，避免运行时被外部链接失效阻断。外部引用仅作为二级来源补充，并标注获取日期和本地快照路径。取舍代价是文章体积增大，但换来了离线可执行性。

### 版本锁定与活文档的取舍
运维类文章倾向于版本锁定：明确声明适用的软件版本、配置文件格式版本和依赖包版本。活文档模式适用于接口频繁变化的开发阶段，但需通过 CI 每日校验示例有效性。本规范默认采用版本锁定，仅在标题中标注版本范围。

### 自动化校验与人工复核的取舍
结构性约束由 CI 自动校验，包括标题唯一性、来源标注完整率、代码块语言标识和清单 schema 有效性；事实正确性、边界合理性和证据真实性由人工复核。自动校验不能替代事实核查，只能阻止明显不符合schema 的内容进入主分支。

## 可执行的实施流程

1. 在 H1 标题正下方写入读者契约段，明确角色、先备知识和阅读目标。
2. 编写摘要与问题边界，用两段列表分别写出“范围内”和“范围外”。
3. 列出文章将引用的全部来源，并为每个来源分配一级、二级或三级分级。
4. 用 H2 组织核心概念，每个概念下至少包含一个可验证的论断或示例。
5. 用 H3 展开设计决策，每个决策说明取舍理由、适用边界和例外条件。
6. 嵌入 YAML、JSON 或代码示例，说明输入、处理、输出，并标注运行环境版本。
7. 在关键论断后插入验证证据，包括命令、输出、时间戳和环境标识。
8. 在文章末尾独立编写失败模式与恢复记录，区分已知失败、未知异常和观测不足场景。
9. 定义可观测指标及其测量方式，说明采集频率和告警阈值。
10. 提交前执行项目级校验脚本，检查标题唯一性、来源存在性、死链和过期证据。

## 性能、质量和可观测性指标

1. 检索召回率。在固定查询集合下，目标文章被召回的比率。测量方式：使用项目检索器对 20 个常见运维查询执行测试，记录命中次数，目标值不低于 0.85。
2. 事实可验证率。标注为一级或二级来源的论断数量占总论断数量的比例。通过正则匹配来源标记自动计算，目标值不低于 0.80。
3. 死链比例。外部 URI 在 30 天内返回非 200 状态码或本地快照丢失的比例。CI 每周扫描一次，目标值为 0。
4. 示例可执行率。内联命令或脚本在目标环境中成功运行的比例。集成测试每日采样执行，目标值不低于 0.90。
5. 平均恢复时间。从文章记录的失败模式触发到按恢复步骤完成恢复的时间。由故障复盘时人工记录，目标值依据故障等级分别设定。

## 失败模式、诊断证据与恢复动作

1. 边界模糊导致误用。诊断证据：读者在讨论区反复提问“这篇文章是否涵盖 X”，或 Agent 在边界外场景引用本文。恢复动作：在边界段写入“不涵盖 X”，添加“参见”链接，并升级文章次版本号。
2. 来源失效。诊断证据：CI 扫描显示 URI 返回 404，或本地文件 checksum 与清单不一致。恢复动作：更新为新的快照路径或归档页面，在来源条目中标注失效时间和替代来源。
3. 示例命令过期。诊断证据：集成测试报告命令返回非预期输出，或环境版本已超出声明范围。恢复动作：按当前环境重写示例，更新证据时间戳，并调整文章版本范围。
4. 标题无法被检索。诊断证据：常见查询无法召回目标文章，检索日志显示标题与查询词差异过大。恢复动作：在 H2/H3 和同义词定义段补充检索关键词，但不得为 SEO 堆砌无关术语。
5. 恢复步骤缺失。诊断证据：故障复盘显示工程师未按文章操作，或文章只有成功路径。恢复动作：补充独立“失败模式与恢复”小节，明确降级路径、回退命令和验证命令。

2. 正向问题：为什么每篇运维文章必须为关键论断添加证据？期望回答说明证据用于可复现性、故障复盘和版本漂移校验。

4. 边界问题：一篇文章是否可以同时详细描述架构设计和故障恢复？期望回答指出应拆分为两篇文章并通过“参见”链接关联，除非恢复步骤完全依赖该架构。

## 维护、版本、来源与相邻主题

维护：每篇文章纳入 Git 版本控制，与代码仓库同步发布。重大边界调整升级主版本号，示例更新升级次版本号，错字修正升级修订号。

版本：文章顶部标注适用版本，例如“适用于 `@earendil-works/pi-coding-agent@0.83.0` 及以上”。依赖版本变更时，必须重新执行示例和验证命令，并更新证据时间戳。

来源：事实来源优先使用项目内部文件，如 AGENTS.md、docs/adr、配置文件、CI 输出。外部来源必须标注获取日期和本地归档快照；无法归档的外部来源至少记录访问时间。

相邻主题：与“提示词模板编写”相邻，区别在于模板侧重模型输入构造，本文侧重知识文章的结构化与可验证；与“技能开发”相邻，区别在于技能包含可执行工具与运行时注册，本文聚焦静态知识文档。与“知识库检索优化”相邻，但后者属于系统工程，不在单篇文章范围内。

## 结论

事实：Markdown 知识文章的检索效果依赖标题、术语和正文结构的显式设计；运维视角要求同时记录成功路径、失败模式、延迟影响、容量边界和恢复证据。

推论：通过 YAML 元数据清单和 CI 自动校验，可以提高文章的可维护性和可验证率；将恢复记录独立成段有助于缩短故障复盘时间。但这些措施无法保证读者一定按文章执行。

未知：不同检索器对同义词和层级结构的召回差异尚未量化；读者实际执行恢复步骤的成功率缺乏大规模观测数据；本规范对超长专题文章的适用性仍需更多项目实践验证。
