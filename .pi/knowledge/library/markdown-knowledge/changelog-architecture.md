# 变更记录：Markdown 知识库中的责任边界与可替换接口

在 Markdown 知识库中，"变更记录"不是版本控制系统提交日志的替代品，也不是审计追踪的简化版。它的核心目标是让内容读者在消费事实时，能够判断：这条事实在何时成立、由谁基于何种依据改变、改变的边界范围是多大。从架构视角看，变更记录是一套责任声明机制，它连接知识生产者、知识单元、时间锚点和来源证据，使读者可以在不深入仓库历史的情况下，对事实的当前有效性和历史沿革做出可信判断。

## 摘要与问题边界

变更记录解决的是"知识衰减"问题：随着项目演进，Markdown 文件中的断言、配置说明、依赖约束、接口约定会逐渐与真实系统偏离。读者无法仅凭当前文本判断某句话是昨日刚确认，还是三年前遗留的假设。变更记录通过显式标注关键事实的变更事件，降低读者的认知负担。

其边界必须明确限定。变更记录不负责：
- 记录每一次文件保存或格式化操作；
- 证明作者的真实身份或法律签名；
- 替代 Git 等版本控制系统进行全文差异比对；
- 追踪非语义内容的修改，如标点、排版、目录结构调整。

它负责的是：当事实发生变化时，保留"旧事实为什么被撤销、新事实凭什么成立、谁对此负责"的最小可验证信息。

## 核心概念与数据模型

变更记录的数据模型应围绕"事实"而非"文件"设计。一个最小可替换接口至少包含以下实体：

1. **事实断言（Assertion）**：知识库中可独立判断真假的陈述，如"本服务依赖 Node.js 20"或"启动命令为 `pnpm dev`"。一个 Markdown 段落可能包含多个断言，每个断言应有唯一标识或稳定锚点。

2. **变更事件（ChangeEvent）**：一次导致事实状态发生转移的操作。变更事件必须包含事件类型，如 `create`（首次确立）、`update`（修订）、`deprecate`（标记废弃）、`retract`（撤回）、`confirm`（重新确认无变更）。

3. **作者身份（AuthorIdentity）**：对变更承担解释责任的实体。粒度可以是个人、角色、工具流水线或外部系统。作者身份必须可解析，但不必等同于 Git 提交者；例如，一次由 CI 工具根据监控告警自动更新的阈值，其作者身份应记录为工具角色，同时保留触发该工具的人类或规则引用。

4. **时间锚点（TemporalAnchor）**：变更记录至少需要两个时间戳：记录时间（条目写入知识库的时间）和语义生效时间（该变更对读者产生约束力的时间）。两者不一致时，必须给出原因，如"提前发布未来生效的接口约定"。

5. **变更范围（ChangeScope）**：明确变更影响的事实边界。范围可以是段落、断言标识、文件、目录或跨文件主题标签。范围定义过宽会导致读者无法定位影响；过窄则增加维护成本。

6. **来源引用（ProvenanceReference）**：支持新事实的依据，如设计文档编号、会议纪要、测试结果、外部 API 文档 URL、Git 提交哈希。来源引用必须可验证，即读者能够根据引用找到原始证据，而非仅看到"据某次会议讨论"这类无法回溯的说明。

7. **置信度标签（ConfidenceLabel）**：作者对变更后事实稳定程度的声明。可选等级如 `experimental`（实验性）、`stabilized`（已稳定）、`committed`（已承诺）、`legacy`（遗留，待迁移）。置信度随时间可能下降，因此需要 `confirm` 事件重新评估。

8. **可替换接口（ReplaceableInterface）**：变更记录的存储、渲染、验证应通过接口隔离。例如，存储层接口支持 Git 历史解析、数据库表、前端 YAML 头元数据等多种实现；渲染层接口决定如何在 Markdown 阅读界面中呈现变更徽章或时间线。

## 设计决策与取舍

**集中式记录与分布式记录的取舍**
集中式记录将所有变更事件存储在单一索引或数据库中，便于查询和全局一致性校验，但增加了中心化故障点和写入复杂度。分布式记录将变更信息嵌入每个 Markdown 文件头部或段落附近，降低了单点依赖，但跨文件查询时需要聚合，且容易出现同一事件在多个文件中被重复或矛盾描述。推荐采用混合模式：文件内保留最小变更摘要，全局索引由构建时聚合生成，索引只读，不成为写入瓶颈。

**显式注释与隐式元数据的取舍**
显式注释将变更记录直接写在 Markdown 正文中，例如段落后跟 `[updated: 2024-11-03 by runtime-team]`。优点是读者无需切换视图即可看到，缺点是污染正文、增加冗余。隐式元数据将变更事件放在文件头 YAML、外部 JSONL 或数据库中，优点是正文干净，缺点是读者可能忽略。建议对关键事实使用行内显式徽章，对常规更新使用文件级元数据，并通过渲染层统一决定是否展开。

**提交时间与语义生效时间的取舍**
Git 提交时间精确但经常不等于事实生效时间。若知识库描述的是未来将要执行的迁移计划，提交时间可能早于生效时间数月。若记录时间被误读为生效时间，读者会提前采取行动。因此数据模型必须支持两者分离，并在缺失时默认显示"记录时间，生效时间未声明"。

**作者粒度：个人、角色还是工具的取舍**
将作者绑定到个人邮箱会带来隐私和离职后不可解析的问题；绑定到角色如 `@architecture-team` 更稳定，但需要角色目录维护映射关系；绑定到工具如 `ci-release-bot` 可以自动化，但需要保留工具配置版本以便回溯。推荐将作者身份设计为可解析标识符，由身份注册表决定该标识符当前指向个人、团队或自动化系统。

**版本控制与变更记录的关系**
Git 已经提供了全文差异和提交者信息，为什么还要单独变更记录？因为 Git 的粒度是文件或行，而知识读者的粒度是"事实"。一次 Git 提交可能同时修改十个事实，其中九个是排版修正，一个是关键约束变更。变更记录让关键约束的变更从噪音中显式浮现，而不是要求读者自行比对差异。

## 可执行的实施流程

1. **识别知识单元**：梳理知识库中哪些断言对读者决策有长期影响。优先覆盖接口约定、依赖版本、命令路径、环境配置、权限要求、排障步骤。

2. **定义变更事件类型**：建立项目级事件类型枚举，如 `create`、`update`、`deprecate`、`retract`、`confirm`。禁止随意新增类型，避免渲染和查询逻辑碎片化。

3. **设计作者身份注册表**：创建身份映射文件，如 `.pi/identities.json`，将 `@platform-team` 映射为当前成员和角色邮箱。CI 工具身份必须记录版本和配置路径。

4. **建立时间锚点规范**：规定所有变更记录必须包含 `recorded_at`；若涉及未来生效，必须显式声明 `effective_at` 和 `reason_for_effective_date`。

5. **实现记录存储接口**：在存储层定义 `ChangeLogStore` 接口，支持 `append`、`queryByAssertion`、`queryByTimeRange`、`validateConsistency`。初期可用文件系统 YAML 实现，后期可替换为数据库或版本控制解析器。

6. **集成渲染管线**：在阅读界面中增加变更徽章渲染层。徽章显示最近一次变更类型、时间、作者；点击后展开时间线。渲染层必须从存储接口读取，不得直接解析文件。

7. **建立验证机制**：在构建或提交前运行校验脚本，检查变更记录是否包含空作者、时间锚点是否倒置（生效时间早于记录时间且无原因）、来源引用是否指向不存在的文件或链接。

8. **监控与回滚**：部署后观测变更记录覆盖率、未解析作者数量、悬垂来源引用数量。当发现错误记录时，使用 `retract` 事件撤销，并追加 `update` 或 `create` 事件提供修正，禁止直接删除历史条目。

## 示例：本地文件知识库的变更记录

以下是一个基于 TypeScript 类型与本地 YAML 的示例。输入是 Markdown 文件和与之配套的变更记录 YAML；处理由 `ChangeLogStore` 接口完成；输出是读者看到的渲染结果。

```yaml
# .pi/changelog/dependency-node.yaml
assertion_id: "svc-runtime-node-version"
scope:
  file: "docs/runtime.md"
  anchor: "#runtime-node-version"
events:
  - type: create
    recorded_at: "2023-08-10T09:00:00Z"
    effective_at: "2023-08-10T09:00:00Z"
    author: "@platform-team"
    confidence: stabilized
    reason: "Node 18 成为组织默认 LTS"
    sources:
      - type: adr
        ref: "docs/adr/0012-default-node-version.md"
  - type: update
    recorded_at: "2024-11-03T14:22:00Z"
    effective_at: "2024-12-01T00:00:00Z"
    author: "ci-release-bot@1.4.0"
    confidence: committed
    reason: "Node 20 在监控集群完成两周灰度，无异常"
    sources:
      - type: git
        ref: "commit 7a8f9c2"
      - type: dashboard
        ref: "https://monitor.example.com/grafana/d/canary-node-20"
  - type: confirm
    recorded_at: "2025-03-15T10:00:00Z"
    effective_at: "2025-03-15T10:00:00Z"
    author: "@runtime-team"
    confidence: committed
    reason: "季度审查确认 Node 20 约束仍然有效"
```

输入包括：断言标识、范围、事件序列、作者、时间锚点、来源引用、置信度。处理阶段，`ChangeLogStore` 读取该 YAML，校验 `effective_at` 不早于 `recorded_at`（除非声明原因），校验 `sources` 中引用的文件或链接是否可达，并将事件按时间排序。输出阶段，渲染层在 `docs/runtime.md` 的对应锚点附近生成徽章：当前有效约束为 `Node 20`，最近变更于 2024-11-03 由 `ci-release-bot@1.4.0` 提交，2024-12-01 生效，依据为灰度监控和 Git 提交。读者点击徽章可展开完整时间线。

## 性能、质量和可观测性指标

1. **变更覆盖率**：对关键事实断言有多少比例附带了至少一个变更事件。测量方式：通过断言解析器扫描 Markdown 锚点，与变更记录索引比对，计算覆盖比例。目标值不低于 90%。

2. **时间锚点一致性**：生效时间早于记录时间且未声明原因的记录数量。测量方式：校验脚本扫描所有变更 YAML，统计异常事件。目标值为 0。

3. **作者身份解析率**：变更记录中作者标识符能够在身份注册表中找到有效映射的比例。测量方式：定期运行 `identities.resolve()` 检查未解析标识。目标值 100%。

4. **悬垂来源引用**：指向已删除文件、失效链接或已撤销 ADR 的来源引用数量。测量方式：构建阶段爬取所有 `sources[].ref`，记录 404 或文件不存在错误。目标值 0。

5. **渲染延迟**：在阅读界面加载知识单元时，从调用 `ChangeLogStore.queryByAssertion()` 到徽章渲染完成的 P95 延迟。测量方式：在 Web 前端或 API 中加入计时埋点。目标 P95 低于 50 毫秒。

## 失败模式

**作者身份丢失**
诊断证据：变更记录中作者标识符无法解析，显示为 `unknown` 或已离职个人的邮箱。恢复动作：在身份注册表中添加指向团队的别名，或在变更记录中追加 `update` 事件更正作者，同时保留原始事件作为历史。

**时间锚点漂移**
诊断证据：读者在 2024-10 看到一条标记为"2024-12-01 生效"的约束，但系统已经在 2024-11 强制执行。原因可能是生效时间填写错误。恢复动作：追加 `retract` 事件撤销错误时间锚点，再追加 `update` 事件使用正确生效时间，并在 `reason` 中说明修正原因。

**变更范围过宽**
诊断证据：一次 `update` 事件的范围覆盖整个文件，但读者发现文件中只有一句断言发生变化。恢复动作：拆分事件，将范围细化到具体断言锚点，并补充被遗漏的变更条目。

**来源断裂**
诊断证据：来源引用指向的 ADR 或监控面板已被删除或迁移。恢复动作：将失效引用标记为 `stale_source`，追加新的 `confirm` 或 `update` 事件并引用新的证据；若无法找到新证据，则将置信度降至 `experimental` 并提示读者。

**记录腐烂**
诊断证据：知识单元长期仅有 `create` 事件，无 `confirm` 事件，事实可能已经与真实系统不一致。恢复动作：建立定期审查流程，对超过六个月未确认的关键断言触发审查任务，由责任人执行 `confirm`、`update` 或 `deprecate`。

## 问答测试样例

**正向问题**
1. 问：当前 `docs/runtime.md` 中 Node.js 版本约束是什么？何时生效？依据是什么？答：Node 20，2024-12-01 生效，依据是 `commit 7a8f9c2` 和两周灰度监控面板。
2. 问：`@platform-team` 在 2023 年建立该约束时引用了哪份 ADR？答：`docs/adr/0012-default-node-version.md`。

**边界问题**
3. 问：为什么 2024-11-03 的 `update` 事件生效时间是 2024-12-01 而不是记录时间？答：因为存在灰度窗口，必须等旧集群全部迁移后新约束才生效。
4. 问：如果一条变更记录的作者字段填写的是 `ci-release-bot@1.4.0`，谁对变更内容负责？答：工具负责执行，但工具配置和触发规则由 `@runtime-team` 维护，责任归属应查看身份注册表中的映射关系。

**无证据时的拒答条件**
5. 问：这条约束是由哪次会议决定的？如果变更记录中没有引用会议纪要，应回答：无法确定，变更记录中未提供会议来源，不能推断。
6. 问：Node 18 的约束是在哪一天被撤销的？如果记录中只有 `update` 事件说明 Node 20 生效，没有单独的 `retract` 事件，应回答：记录中未显式声明撤销事件，只能推断旧约束在 2024-12-01 新约束生效时失效，不能给出精确撤销时间。

## 维护、版本、来源与相邻主题关系

变更记录的维护周期应短于知识库正文的大规模重构周期。推荐每次变更事实时同步更新记录，而不是在文档重写后再统一补录。

版本策略上，变更记录本身应使用与知识库相同的版本控制系统，但不应依赖 Git 元数据作为唯一来源。将变更记录作为 YAML 或 JSON 文件纳入版本控制，可以享受 diff、回滚、分支合并的能力，同时通过渲染层实现知识读者友好的展示。

来源管理方面，变更记录应引用项目内稳定的标识，如 ADR 编号、测试报告路径、监控面板 URL，而非临时的聊天消息或私有笔记。如果来源必须引用外部系统，应至少保留截图哈希或归档链接，以防外部链接失效。

相邻主题包括：
- **版本控制**：提供全文差异和提交者信息，但粒度是文件，不是事实。
- **审计日志**：关注操作合规性和责任追究，通常由基础设施层维护，而非知识读者。
- **引用管理**：管理知识单元之间的依赖和引用关系，变更记录则管理这些引用随时间的变化。
- **知识生命周期管理**：决定何时创建、废弃、归档知识单元，变更记录为其提供时间维度的证据。

## 结论

**事实**：变更记录必须让内容读者知道关键事实在何时、为什么、由谁改变。它至少应包含事实断言、变更事件、作者身份、时间锚点、变更范围、来源引用和置信度标签。存储与渲染应通过可替换接口隔离。

**推论**：采用文件内最小记录与构建时全局索引结合的混合模式，能够在不引入中心化写入瓶颈的前提下，为读者提供一致的时间线视图。将记录时间、语义生效时间和作者身份解析问题显式建模，可以显著降低时间锚点漂移和身份丢失类缺陷。

**未知**：在多大程度上，自动化工具（如 CI 机器人、大模型辅助摘要）生成的变更记录能够被读者信任，仍然取决于项目对作者身份注册表和来源引用验证的严格程度。变更记录本身无法保证事实正确，只能提高事实沿革的可追溯性；最终判断仍需读者结合外部证据和自身上下文完成。
