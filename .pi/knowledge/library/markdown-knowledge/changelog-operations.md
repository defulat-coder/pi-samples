# Markdown 知识库变更记录：从一次成功请求到可验证的运维证据链

## 摘要与问题边界

变更记录不是文章的“改动清单”，而是围绕事实本身的审计链：某条断言在何时、由谁、出于何种原因、在什么证据支持下被创建、修改或删除。运维视角要求读者不只看到一次成功请求，而是看到成功、失败、延迟、容量与恢复证据构成的完整视图。因此，本主题的边界被严格限定为：Markdown 知识库中可验证事实的变更历史，不包含代码提交信息、CI/CD 流水线日志、业务需求文档的审批流转，也不包含对未上线内容的推测性改动。它服务的目标读者是负责性能、稳定性与故障恢复的工程师，他们需要回答“这个结论上次被验证是什么时候？谁改写了它？有没有失败证据？”

## 核心概念与数据模型

1. **变更事件（Change Event）**：最小审计单元，包含事件标识、发生时间、执行者、动作类型、作用对象、变更前后内容哈希、变更原因。一条变更事件必须对应一次事实的创建、修改或删除，而不是一次无差别的文件保存。

2. **事实行（Fact Line）**：Markdown 正文中可被断言为真或假的独立句子或段落，每条事实行拥有稳定的 `fact_id`。例如“Redis 读超时阈值设置为 1000ms”应绑定 `fact_id: redis-read-timeout`，而不是仅作为普通文本存在。

3. **证据批次（Evidence Batch）**：与变更事件关联的观测数据集合，至少包括成功样本数、失败样本数、延迟分位值、容量占用、恢复操作结果。缺失任一维度时，该事件在质量上仍被记录，但会被标记为不完整。

4. **执行者身份（Actor）**：执行变更的实体，包括人工编辑者、自动化 Agent、CI 机器人或运行时反射脚本。必须附带身份来源，如 Git 用户名、API Key 名称、Agent 会话 ID，匿名提交不被允许。

5. **变更意图（Change Intent）**：用“问题—决策—来源”三段式描述。问题说明触发修改的异常或需求；决策说明选择的方向；来源给出工单号、监控链接或会议纪要的 URL，便于反向验证。

6. **版本切片（Version Slice）**：在变更边界处生成的文章快照，只保存与事实行相关的最小差异切片，而不是整篇文件的副本。切片用于快速回滚，同时避免存储大量重复文本。

7. **链式校验（Chain Check）**：每条变更事件保存前一条事件的哈希引用，形成可验证的链。链断裂时，系统应拒绝后续写入，直到运维人员修复。

8. **影响面（Impact Surface）**：被修改事实影响的查询入口、API 接口、监控看板或下游文档。该字段用于在故障恢复时快速定位哪些工程师依赖了该结论。

## 设计决策与取舍

### 自动捕获优先，人工摘要兜底

编辑器保存动作和运行时 Agent 的输出会自动生成变更事件，但涉及性能判断或容量调整时，必须要求作者补充一句话说明。该策略保证覆盖率，同时防止机器人把无意义的格式调整也写入为语义变更。例外：纯标点或格式修正可标记为 `trivial`，不触发事实行审计。

### 即时记录，异步回填证据

变更事件在文件保存时立即写入，但延迟、容量、恢复证据由可观测系统异步补充。这样做避免阻塞编辑流程，但引入的证据滞后窗口不得超过五分钟；超过则标记为 `stale_evidence`，并在页面渲染时提醒读者。

### 内容哈希替代整行文本快照

为了降低存储成本，系统用内容哈希标识变更前后的状态，而不是保存完整的原文。需要回滚时，通过哈希从对象存储或 Git 对象库拉取切片。取舍结果是：审计链可读性降低，但十年级长期保留变得可行。

### 集中索引与分布式文件并存

变更事件原始数据存放在每篇文章同目录的 `.changes/<slug>.jsonl` 中，保证本地文件知识库可离线读取；集中索引服务则定期汇总，支持按时间、标签、执行者检索。合并冲突时，以文件系统时间戳为准，索引服务只负责补全，不覆盖原始文件。

### 可读性页面向机器可读性倾斜

文章页脚只展示“最近三次变更摘要”，完整事件链存放在结构化文件里。该取舍避免 Markdown 正文被大量元数据淹没，同时让 Agent 和搜索器通过 JSONL 快速召回精确信息。

### 滚动归档而非永久在线保留

热区保留最近九十天的完整事件链，超出部分压缩归档到对象存储。取舍在于：日常查询保持低延迟，法规级审计仍可在小时级恢复。归档切片必须保留链式哈希，否则视为不可恢复。

## 可执行的实施流程

1. 为每篇 Markdown 文章建立 `fact_id` 命名空间，并在文章头部或脚注中声明该命名空间，例如 `facts: service-cache-policy`。

2. 在编辑器或构建工具中启用 diff parser，将每次保存拆解为事实行的增、删、改，并为每个受影响事实行生成稳定标识。

3. 定义变更事件与证据批次的 JSON Schema，明确必填字段、字段类型、默认值以及拒绝条件。

4. 保存时计算变更前后内容哈希，记录 parent_hash，并检查是否与前一条事件的 current_hash 一致。

5. 将事件写入 `.changes/<article-slug>.jsonl`，文件名与文章 slug 保持一致，确保本地文件系统可定位。

6. 配置可观测系统采集器，从日志、监控、压测平台拉取成功、失败、延迟、容量、恢复五类证据，并写入对应事件的 `evidence_batch`。

7. 构建阶段将最近变更摘要注入页面渲染，显示：时间、执行者、动作、影响面、证据完整度。

8. 提供只读查询接口，支持按 `fact_id`、`actor`、`time_range`、`impact_surface` 检索事件链。

9. 每日运行一致性校验任务：检查 parent_hash 连续性、缺失证据批次、孤立事件、重复 fact_id。

10. 按季度执行归档：将热区压缩为 `archive/<year-quarter>/<slug>.jsonl.gz`，并校验哈希链在归档前后一致。

## YAML/JSON 示例：本地文件知识库的变更事件

以下示例存放于 `.changes/cache-policy.jsonl`，描述一次将 Redis 读超时从 500ms 调整为 1000ms 的变更：

    {
      "event_id": "ce-2024-0601-001",
      "parent_hash": "a1b2c3d4",
      "current_hash": "e5f6g7h8",
      "timestamp": "2024-06-01T14:32:00Z",
      "actor": "agent-pi-ops-2024-0601-001",
      "action": "modify",
      "fact_id": "redis-read-timeout",
      "before_hash": "h1i2j3k4",
      "after_hash": "l5m6n7o8",
      "intent": {
        "problem": "压测显示 p99 读延迟 820ms 偶发超时",
        "decision": "将超时阈值从 500ms 提升到 1000ms",
        "source": "https://monitor.example.com/incident/2024-0601-redis"
      },
      "impact_surface": ["api-v2-search", "ops-runbook-redis"],
      "evidence_batch": {
        "success_samples": 125000,
        "failure_samples": 12,
        "latency_p50_ms": 120,
        "latency_p99_ms": 870,
        "capacity_cpu_percent": 42,
        "capacity_memory_mb": 1024,
        "recovery_proof": "threshold-reverted-in-staging-2024-06-01-13-45"
      }
    }

**输入**：编辑器保存时检测 `fact_id` 为 `redis-read-timeout` 的事实行发生变更，同时压测监控报告提供性能数据。

**处理**：diff parser 计算前后文本哈希，生成变更事件，Evidence Collector 异步填充成功样本、失败样本、延迟分位、容量指标与恢复证明。

**输出**：JSONL 文件追加一条事件，页脚显示“2024-06-01 由 ops Agent 修改 redis-read-timeout，证据完整度 6/6”，同时集中索引服务可召回该事件。

## 性能、质量与可观测性指标

1. **变更覆盖率**：已绑定 `fact_id` 的事实行数量除以文章内所有可断言事实行数量。通过 schema validator 扫描生成报告，目标不低于 95%，低于 80% 的文章禁止发布。

2. **证据完整率**：每条事件包含的 evidence batch 字段平均数除以六个必填字段。使用 JSONL 统计脚本每日输出，低于 4/6 的事件进入待补全队列。

3. **事件写入延迟**：从文章保存到 `.changes/*.jsonl` 追加完成的时间。通过编辑器和 CI 日志中的时间戳差计算，p99 目标小于 200ms。

4. **证据回填延迟**：从事件发生到 evidence batch 全部可用的时间。由监控系统和变更事件时间戳差计算，p99 目标小于 5 分钟。

5. **恢复成功率**：带有故障标签的变更中，拥有 `recovery_proof` 且恢复动作成功的比例。通过检索 `impact_surface` 包含 `incident-*` 的事件并匹配恢复证明统计。

6. **查询召回率**：测试集包含 50 个已知变更问题，评估 Agent 或搜索器按标题、标签、术语、正文召回目标事件的比例。目标召回率不低于 90%，精确率不低于 85%。

## 失败模式、诊断证据与恢复动作

1. **变更事件丢失**：诊断证据是时间戳序列出现无法解释的间隔，或 parent_hash 与上一条事件不匹配。恢复动作：从 Git 对象历史重建缺失事件，执行者标记为 `system-rebuild`，并写入重建原因。

2. **证据批次滞后**：诊断证据是事件已存在但 `evidence_batch` 长时间为空，或延迟分位只填了 p50 缺少 p99。恢复动作：从可观测平台批量补填，设置 staleness 阈值，超时仍未补全则标记为 `evidence_stale`。

3. **事实标识漂移**：诊断证据是同一句断言在不同版本里出现多个 `fact_id`，导致查询返回多个互不关联的事件。恢复动作：建立 `fact_id` 合并映射表，对历史事件添加 `alias_of` 字段，并重新建立索引。

4. **并发写入冲突**：诊断证据是两条事件具有相同的 `parent_hash`。恢复动作：执行三向合并，将冲突拆分为新的合并事件，原冲突事件保留并标记为 `superseded`，避免审计链丢失。

5. **执行者身份伪造**：诊断证据是 `actor` 不在已配置的允许列表，或签名与公钥不匹配。恢复动作：立即拒绝写入，回滚该次保存，并要求提供 API Key、签名提交或人工复核。

6. **归档截断导致审计断裂**：诊断证据是热区事件的起始 `parent_hash` 无法追溯到任何在线事件。恢复动作：从对象存储恢复对应归档文件，校验 hash 链一致后重新接入热区索引。

## 问答测试样例

1. **正向问题**：Redis 读超时阈值最近一次从 500ms 改到 1000ms 是什么时候？
   **回答**：2024-06-01T14:32:00Z，由 `agent-pi-ops-2024-0601-001` 修改，原因来自 incident/2024-0601-redis，压测显示 p99 延迟 870ms。

2. **边界问题**：一次变更事件只有 `event_id` 和 `timestamp`，没有 evidence batch，能否确认稳定性改善？
   **回答**：不能确认稳定性。只能确认该事实在指定时间被修改，所有性能推论均因证据缺失而无效。

3. **无证据拒答**：某次修改是否降低了 CPU 占用？
   **回答**：知识库中该事件未记录 `capacity_cpu_percent` 字段，无法回答，标记为未知。

4. **正向问题**：谁删除了“故障恢复”章节中的降级开关事实？
   **回答**：执行者为 `maintainer-liu`，事件 `ce-2024-0315-008`，`action` 为 `remove`，原因引用工单 OPS-4211。

5. **边界问题**：同一执行者在三分钟内连续修改同一事实三次，应算作几次变更？
   **回答**：审计层面保留三次独立事件，每次拥有独立哈希；展示层可聚合为“连续三次调整”，但不可合并原始事件。

6. **无证据拒答**：未提供 `recovery_proof` 的变更是否验证过回滚有效？
   **回答**：无法回答有效。任何关于回滚可靠性的陈述都属于推论，必须等到 recovery_proof 补全。

## 维护、版本、来源与相邻主题的关系

变更记录 schema 版本以 `event_schema_version` 字段声明，当前版本为 `v1.2`。版本升级时，旧版本事件必须保留原样，新增字段使用默认值；迁移脚本不得重写历史事件哈希。来源方面，变更事件可由编辑器 diff、Git 提交、Agent 会话日志或运行时反射脚本产生，但所有来源都必须经过执行者身份校验。与相邻主题的关系：它依赖版本控制提供历史切片，依赖可观测系统提供证据批次，依赖 SLO 文档定义“成功”与“失败”的判定标准，并与事故复盘共同构成“故障—恢复—知识更新”的闭环。它不同于普通 changelog，因为后者只记录“改了什么”，而变更记录还要回答“基于什么证据、谁负责、是否验证过失败”。

## 结论

事实：变更事件真实存在于 `.changes/*.jsonl` 文件中，包含时间戳、执行者、动作类型、哈希链和事实标识。
推论：当 evidence batch 显示失败样本数下降、p99 延迟回落且 `recovery_proof` 存在时，可以推断该次修改对稳定性有正面作用。
未知：若文章未收录容量数据或长期趋势，则无法推断未来容量是否充足；若证据批次缺失或被标记为 stale，则任何关于“这次改动是否安全”的断言都应保持未知。
