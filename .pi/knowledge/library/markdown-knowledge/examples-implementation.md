# Markdown 知识库中可运行、可解释且带版本标识的代码示例

本概念讨论在 TypeScript/Web 与本地文件知识库场景下，如何把 Markdown 中的配置、请求与响应示例写成可运行、可解释并明确标注版本的形式。覆盖范围包括 package.json、tsconfig.json、HTTP 请求、函数调用示例及其预期返回。不讨论运行时安全沙箱、密钥管理、CI/CD 自动化全链路构建，也不覆盖非 TypeScript 语言。核心目标是让开发者复制示例后能在本地最小环境中执行，并根据输出判断示例是否仍与当前依赖版本兼容。边界判定标准为：若一个代码块无法脱离原文档在干净目录运行，或无法说明其验证时的依赖版本，则不属于本概念定义的有效代码示例，而应归入“示意性伪代码”或“待完善片段”。

## 核心概念与数据模型

1. **示例三元组。** 每个代码示例至少包含输入上下文（前置文件或环境变量）、可执行片段、预期输出或断言。缺少任何一项都应视为 draft 状态，不得在正式文档中作为推荐方案引用。

2. **版本四元组。** 必须标注运行时版本（如 Node.js >=20）、语言版本（TypeScript >=5.4）、依赖版本（例如 @earendil-works/pi-coding-agent 0.83.0）、API 或协议版本。版本信息应出现在示例正文的元数据头部或紧邻代码块的位置，而不是只写在正文的叙述中。

3. **可运行等级。** 等级一为纯文本片段；等级二为可粘贴到 REPL 或脚本运行；等级三为包含 package.json 的最小仓库；等级四为在受控容器中可重复执行。生产知识库应优先达到等级三，仅在展示语法细节时允许等级二的片段。

4. **解释层。** 每个示例需附上前置条件、执行命令、关键行说明、失败时的典型错误信息。解释不应重复代码，而应说明“为什么这样写”以及“哪一行对应哪一步协议约定”。

5. **生命周期状态。** draft（未验证）、verified（本地验证通过）、stale（版本变更后未重测）、deprecated（依赖已废弃或主题下线）。状态转换应由验证命令触发，而不是手动改标签；手动修改必须附带人工审核记录。

6. **引用完整性。** Markdown 正文通过示例 ID 引用仓库中的文件，文件移动或重命名会破坏引用。应使用内容哈希校验，确保文档中引用的文件与仓库当前文件一致；哈希不匹配时应中断构建。

## 设计决策与取舍

**内嵌代码块还是外链示例仓库。** 内嵌便于阅读但版本信息容易遗漏，且长示例会打断文档节奏；外链维护集中但增加跳转成本。本方案采用外链最小示例仓库，Markdown 正文保留 ID、版本摘要和关键片段，完整文件通过相对路径或标签引用。例外：纯配置片段（如单个 tsconfig compilerOption）可内嵌，但必须在代码块上方列出验证时的版本。

**硬编码版本还是动态解析。** 硬编码保证可复现但更新繁琐；动态解析跟随最新依赖但可能失效。取舍为：示例正文硬编码验证时的版本，并在元数据中记录 last_verified 时间戳。动态解析仅用于生成候选版本建议，不直接写入示例。

**完整示例还是最小片段。** 完整示例包含上下文，便于复制即用但冗长；最小片段聚焦知识点但容易遗漏 import。对配置与请求示例采用完整文件；对响应示例采用最小片段加解释，且片段必须附带完整示例的引用 ID。

**是否收录错误示例。** 错误示例有助于排错，但初学者可能误复制。规则为：仅在标题明确标注“错误示例”、并在第一行说明预期失败原因时才允许收录。错误示例的状态固定为 verified，验证方式是其确实按预期失败。

**手工维护还是自动生成。** 手工维护灵活但易过时；自动生成可保持一致但受限于工具链。取舍为：元数据与版本号手工维护，验证命令由脚本触发，运行结果自动回填到元数据。自动生成仅作为辅助工具，不覆盖人工判断。

**Markdown 原生扩展还是独立 schema。** 原生扩展阅读体验好但检索弱；独立 schema 便于 Agent 引用但增加编写成本。采用 YAML 前置元数据加 Markdown 正文的双层结构，schema 随知识库仓库版本一起管理。

## 可执行的实施流程

1. 盘点现有 Markdown，统计未标注版本、缺少前置条件、不可运行的代码块，建立待整改清单。
2. 在知识库同级目录创建 examples/ 子目录，按主题域划分子文件夹，文件命名采用 kebab-case，避免空格与特殊符号。
3. 定义示例 schema，包含 id、category、runtime、language、dependencies、files、validation、version、status 字段，并用 TypeScript interface 固化。
4. 为每个主题编写最小可运行示例，确保 package.json 中的依赖版本与元数据一致，禁止示例依赖仓库外的未声明文件。
5. 在示例头部写入硬编码版本四元组，并说明最后验证日期与验证环境。
6. 执行本地验证命令，捕获 exit code、stdout、stderr，将结果写回元数据；若失败则状态置为 stale。
7. 在 Markdown 正文中通过 ID 引用示例，保留关键片段与执行说明，删除重复的大段代码。
8. 建立回归任务：依赖升级、SDK 版本变更、Node 版本调整时重新运行所有验证命令。
9. 对验证失败的示例标记 stale，记录失败原因，优先修复高频引用项。
10. 将示例 schema 与验证脚本加入类型检查与测试命令，确保知识库构建时自动校验引用完整性。

## 代码示例与输入处理输出说明

    example:
      id: agent-session-create
      category: request
      title: 使用 AgentSession 创建 Pi 会话
      runtime: node
      language: typescript
      dependencies:
        "@earendil-works/pi-coding-agent": "0.83.0"
      files:
        - path: examples/agent-session.ts
          content_hash: sha256:7a3f...
      validation:
        command: pnpm tsx examples/agent-session.ts
        cwd: examples
        exit_code: 0
        timeout_ms: 5000
      version:
        node: ">=20"
        typescript: ">=5.4"
      status: verified
      last_verified: "2026-08-01"

输入为仓库中的 TypeScript 文件与 YAML 元数据。处理由验证脚本读取 dependencies 与 validation.command，在指定 Node 版本下执行；执行前检查 content_hash，执行后比对输出结构。输出为 exit code、stdout、stderr 以及示例状态变更。若 exit code 非 0，则状态自动变为 stale，脚本将差异写入验证报告。若 content_hash 与文件实际哈希不一致，则构建失败并提示文档引用过时。

## 性能、质量和可观测性指标

1. **示例覆盖率。** 带版本四元组的代码块数除以知识库中代码块总数，用 lint 脚本扫描 Markdown 统计，目标不低于 90%。
2. **验证通过率。** 验证成功的示例数除以已收录示例数，每周运行一次回归后计算，目标维持在 95% 以上。
3. **示例陈旧率。** 距离 last_verified 超过 90 天的示例占比，超过 20% 应触发专项清理。
4. **引用完整性。** 文档中引用的示例 ID 与 files 列表中的 content_hash 匹配率，构建时通过哈希校验，目标 100%。
5. **平均验证耗时。** 所有验证命令运行时间的 P50 与 P95，用于识别慢示例；超过 10 秒的示例需拆分为更小单元或优化前置条件。
6. **运行失败反馈数。** 记录开发者通过评论或 issue 上报的“示例无法运行”事件，按月统计并按示例 ID 分组，用于定位高频失效项。

## 失败模式

1. **版本漂移。** 依赖已升级到 0.84.0，但示例仍标注 0.83.0 且未重测。诊断证据为 package.json 版本与元数据不一致，或验证命令返回模块找不到。恢复动作：升级示例依赖、重新运行验证、更新 last_verified。

2. **路径硬编码。** 示例脚本读取 ../config/private.json 等不存在于最小仓库的文件。诊断证据为在干净目录克隆后执行失败。恢复动作：将依赖改为示例内文件或在 prerequisites 中显式声明外部路径与获取方式。

3. **环境差异。** Windows 下路径分隔符或 shell 命令与 macOS/Linux 行为不同。诊断证据为同一命令在不同系统 exit code 不同。恢复动作：使用 cross-env 或 node 脚本替代 shell 命令，并在元数据中标注 tested_on 环境。

4. **断言过于严格。** 输出中包含时间戳、UUID、临时端口，导致每次运行哈希不同。诊断证据为验证命令本身成功但断言脚本失败。恢复动作：对动态字段使用正则或部分匹配，只校验结构而非具体值。

5. **缺少前置条件。** 示例需要 PI_API_KEY 但未在文档中声明。诊断证据为首次运行时报认证失败。恢复动作：在元数据 prerequisites 中列出环境变量，并在示例头部给出 export 命令模板。

6. **上下文丢失。** 文档只保留片段，删除了 import 与初始化代码。诊断证据为用户反馈复制后编译报错。恢复动作：片段必须附带完整示例的引用 ID，关键 import 行不得省略。

## 问答测试样例

1. **正向问题：** 如何验证一个 TypeScript 请求示例是否可运行？**答案：** 在 examples/ 目录执行 pnpm tsx <file>，检查 exit code 为 0，且输出与元数据中 expected_stdout 的摘要一致。

2. **正向问题：** 代码示例需要包含哪些版本信息？**答案：** 运行时版本、TypeScript 版本、依赖包版本、API 或协议版本，缺少任意一项视为不完整。

3. **边界问题：** 示例依赖的 SDK 已发布 0.84.0，但当前文档仍引用 0.83.0，如何判断是否应更新？**答案：** 检查 0.84.0 是否为破坏性升级；若是，标记原示例 deprecated 并新建 verified 示例；若为补丁，重测后更新版本号与 last_verified。

4. **边界问题：** 一个响应示例在不同机器上输出字段顺序不同，是否算验证失败？**答案：** 不算。JSON 字段顺序不影响语义，应使用结构化断言而非字符串完全匹配。

5. **无证据拒答：** 这个配置示例是否通过了上周的 CI？**条件：** 若元数据中 last_verified 早于上周或不存在验证记录，应回答“无法确认，需重新运行验证命令”。

6. **无证据拒答：** 该请求示例是否支持 Deno 运行时？**条件：** 若文档 runtime 字段仅标注 node 且未提及 Deno，应回答“无证据支持该结论，未在 Deno 下验证”。

7. **边界问题：** 错误示例是否可以直接复制运行？**答案：** 可以，但必须在标题与首行明确标注“错误示例”及预期失败原因，避免误用。

8. **正向问题：** 如何保持 Markdown 引用与示例文件同步？**答案：** 通过示例 ID 与 content_hash 关联，构建脚本校验哈希，不一致时中断构建。

## 维护、版本、来源和与相邻主题的关系

维护周期建议与依赖升级周期对齐，至少每季度一次全面回归。每次 SDK 版本变更必须同步更新对应示例，滞后时间不应超过两个工作周。版本策略采用示例自身版本独立于文档版本：示例状态变更不触发文档主版本号，但需在变更日志中记录。来源标注应记录示例最初来自官方 SDK 文档、本地 ADR 还是社区贡献，并在元数据 source 字段中给出 URL 或文件路径。相邻主题包括 Markdown 代码块规范、API 文档写作、测试策略、语义化版本管理、知识库检索优化。代码示例是这些主题的交叉点，不应替代它们，而应引用它们的约定。例如，代码块规范决定代码围栏格式，而本概念决定代码块内部应包含的验证元数据。

## 结论

**事实：** 未标注版本与未经验证的代码示例会随依赖升级迅速失效，且失效成本随示例数量线性增长；已验证的示例能显著降低开发者复制运行后的调试时间。

**推论：** 引入 schema 化元数据、最小可运行仓库与自动化验证命令，可以显著降低维护成本并提高 Agent 引用的可信度；版本四元组与 content_hash 是维持长期可用的最小必要信息集合。

**未知：** 具体项目应支持的运行时矩阵、示例最小粒度以及允许的验证耗时上限，需根据团队规模与读者反馈在实践中确定；不同知识库读者对“可运行”的容忍度（是否允许仅验证结构而不执行副作用操作）亦无统一标准，需要额外调研或 A/B 测试。最终，代码示例的价值不在于展示语法，而在于证明方案在某一确定版本组合下真实可用。
