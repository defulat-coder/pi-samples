# FAQ 组织：把真实问题、边界答案与拒答条件封装为可复用问答单元

## 摘要与问题边界

FAQ 组织不是简单地把常见问题和答案堆在一起。它的核心责任是：把来自真实场景的问题、经过边界检查的答案，以及没有证据时必须拒绝回答的条件，封装成可复用、可检索、可演进的问答单元。这个视角面向负责知识库边界和长期演进的设计者。

问题边界包括三类。第一类是输入边界：哪些问题来自真实用户，哪些来自推测；问题是否包含触发环境、版本号、前置条件。第二类是答案边界：答案在什么时候成立，在什么配置或版本下失效，是否有需要前置阅读的知识点。第三类是拒答边界：当证据不足、版本过旧、或问题超出当前知识库覆盖范围时，问答单元必须给出拒绝条件，而不是编造答案。

## 核心概念与数据模型

一个可复用问答单元至少包含以下六个组成部分。

1. **问题表述集合**。同一个真实问题可能有多种问法，例如“如何启动本地服务”和“pnpm dev 报错怎么办”。单元需要保存经过验证的自然语言变体，而不是只保留一个标准问题。

2. **触发上下文**。记录问题出现的场景，包括命令、版本、运行时、依赖、文件路径。没有触发上下文的问题很难判定答案是否适用。

3. **答案内容块**。答案必须区分事实陈述、操作步骤、风险提示。事实陈述需要有来源或验证路径；操作步骤需要可执行；风险提示需要说明失败后的回退动作。

4. **边界条件声明**。明确答案失效的条件，例如“仅适用于 pnpm 10.30.3 及以上版本”“不适用于 Windows 环境”“需要 Node.js 20 以上”。边界条件必须可验证。

5. **拒答条件与话术**。当问题缺少必要上下文、证据不在知识库范围内、或答案已过期时，单元必须输出标准化的拒绝话术，并指引用户补充信息。

6. **元数据与来源链**。包括作者、最后验证时间、验证命令或测试用例编号、来源文件路径、相关问答单元标识。元数据用于版本演进和召回排序。

## 设计决策与取舍

### 单元粒度：一个问题一个单元，还是一类问题一个单元

如果一个问题横跨多个命令或概念，拆成多个单元更利于精确召回；但过度拆分会导致维护成本上升。建议按“可独立完成的最小闭环”划分，例如“启动本地服务”与“启动后端口冲突排查”分成两个单元，因为它们的触发上下文和恢复动作不同。

### 答案是写死的文本，还是模板加参数

写死文本可预测性强，适合稳定流程；模板加参数可以复用结构，但增加了渲染层复杂度。对于操作步骤，推荐模板化；对于风险提示，推荐写死文本以避免歧义。

### 拒答条件是显式配置，还是运行时推断

显式配置的拒答条件可审计、可测试，但需要人工维护；运行时推断依赖模型能力，结果不稳定。关键边界必须显式配置，例如版本不兼容；模糊边界可以交给运行时推断，但要在元数据中记录推断依据。

### 召回以标题为主，还是以问题表述集合为主

标题适合人类浏览，问题表述集合适合语义检索。两者不可互相替代。推荐在构建索引时，把问题变体、关键词、边界术语都纳入召回字段，但答案正文不直接参与语义排序，避免长答案稀释相关性。

### 版本演进采用替换还是追加

替换方式保持单元数量稳定，但会丢失历史答案；追加方式保留完整历史，但会增加检索噪音。推荐主索引只保留当前有效版本，历史版本存入归档路径，并通过来源链关联。

## 可执行的实施流程

1. 收集真实问题。从对话日志、工单、社区讨论中提取高频问题，过滤掉一次性或无法复现的问题。

2. 标注触发上下文。为每个问题补充环境、版本、命令、错误现象，形成最小可复现描述。

3. 编写初始答案。区分事实、操作、风险三类内容，并为每个事实标注来源。

4. 定义边界条件。列出答案成立的必要条件和失效条件，例如操作系统、运行时版本、依赖范围。

5. 制定拒答规则。明确缺少哪些上下文时必须拒绝回答，并准备标准话术。

6. 设计元数据结构。确定来源链、验证命令、最后验证时间、相关单元等字段。

7. 构建索引与检索接口。把问题变体、标题、关键词、边界术语加入索引，设置召回权重。

8. 编写测试样例。覆盖正向问题、边界问题和无证据拒答问题，确保单元行为可验证。

9. 集成到发布流程。每次知识库更新时，运行测试样例并检查元数据 freshness。

10. 定期审查与归档。每季度检查边界条件是否仍然成立，把失效单元迁移到归档路径并更新来源链。

## 本地文件知识库的 YAML 示例与输入处理输出

以下是一个贴近本地 Markdown 知识库和 TypeScript 处理流程的 YAML 示例。

```yaml
id: faq-003
title: 本地开发服务启动异常
questions:
  - "pnpm dev 无法启动"
  - "本地 Web 服务启动失败"
  - "api 和 web 端口被占用"
context:
  package_manager: pnpm
  version: ">=10.30.3"
  node: ">=20"
  os: [macOS, Linux]
answer:
  facts:
    - "pnpm dev 会同时启动 apps/api 和 apps/web"
  steps:
    - "先运行 pnpm install 确保依赖同步"
    - "再运行 pnpm dev"
  risks:
    - "如果 3000 或 4000 端口被占用，服务会报错退出"
boundaries:
  valid_when: ["pnpm-lock.yaml 存在", "Node.js 版本 >= 20"]
  invalid_when: ["Windows 环境未经验证", "Node.js < 18"]
refusal:
  - condition: "未提供 package_manager"
    response: "请说明你使用的包管理器，以便判断启动命令是否正确。"
metadata:
  source: "AGENTS.md"
  verified_at: "2026-08-01"
  verify_command: "pnpm dev"
  related: ["faq-001", "faq-002"]
```

输入是用户消息，例如“pnpm dev 启动失败”。处理阶段，检索器先在 questions 和 title 中召回候选单元，再检查 context 和 boundaries 是否匹配当前环境。如果匹配失败，比如用户在 Windows 上提问，系统输出 refusal 中对应的话术；如果匹配成功，则按 answer 中的 facts、steps、risks 组合输出。输出不是原始 YAML，而是结构化的回答片段，便于前端渲染。

## 性能、质量和可观测性指标

1. **召回命中率**。衡量用户问题是否在 top-k 候选中命中正确单元。通过已标注的测试集计算，推荐 k=3 时命中率不低于 85%。

2. **边界误触发率**。统计因边界条件判断错误导致的错误回答比例。可通过边界测试样例自动执行，目标低于 5%。

3. **拒答准确率**。无证据问题的拒答率。人工抽检 100 条无答案问题，正确拒答应高于 90%。

4. **元数据 freshness**。计算已验证时间与当前时间的差距，超过 90 天的单元需要重新验证。可通过 CI 扫描元数据实现。

5. **答案引用完整率**。检查每个事实是否都关联到来源或验证命令。通过静态分析工具统计，目标 100%。

## 失败模式、诊断证据与恢复动作

1. **问题表述遗漏**。用户用了新问法，但单元没有收录，导致召回失败。诊断证据是 top-k 候选相似度低且无命中。恢复动作是补充问题变体并重新索引。

2. **边界条件过期**。运行时已升级，但单元仍声明旧版本限制，导致正确回答被拒。诊断证据是 verify_command 在新环境通过但单元标记 invalid。恢复动作是更新 boundaries 和 verified_at。

3. **拒答条件过度触发**。缺少次要上下文就拒绝回答，影响用户体验。诊断证据是大量用户反馈“问题没解决但系统让我补充信息”。恢复动作是放宽非关键字段的拒答要求。

4. **相关单元未关联**。用户问题需要多个单元组合回答，但元数据缺少 related 链接。诊断证据是单次回答后用户继续追问同一主题的子问题。恢复动作是补充 related 字段并优化组合输出策略。

5. **来源链断裂**。答案中的事实没有对应来源，后续无法验证。诊断证据是 metadata.source 为空或指向已删除文件。恢复动作是追溯到原始文档或测试用例，重建来源链。

## 问答测试样例

1. **正向问题**：“pnpm dev 会启动哪些服务？”预期输出应包含 apps/api 和 apps/web，并引用 AGENTS.md。

2. **正向问题**：“本地开发需要什么 Node.js 版本？”预期输出应声明 Node.js 20 以上，并给出检查命令。

3. **边界问题**：“Windows 上能跑 pnpm dev 吗？”预期输出应说明 Windows 环境未经验证，并建议补充信息或参考其他单元。

4. **边界问题**：“Node.js 18 能运行吗？”预期输出应引用 boundaries.invalid_when，明确说明不支持，并解释原因。

5. **无证据拒答**：“为什么我的 API 返回 502？”如果知识库没有相关单元，应拒绝回答并请求错误日志、请求路径和环境版本。

6. **无证据拒答**：“这个项目的部署流程是什么？”如果部署流程不在当前知识库覆盖范围内，应说明超出范围并指向可能的文档入口。

## 维护、版本、来源与相邻主题

维护工作分为三层。内容层由领域负责人定期验证答案，确保事实和命令仍然有效。结构层由知识库维护者管理单元 ID、相关链接和索引配置。工具层由工程师负责检索接口、测试运行器和 CI 集成。

版本策略采用时间戳加来源链。每个问答单元记录 verified_at 和 source，失效单元不直接删除，而是移动到 archive/ 目录，并在主单元 metadata 中保留 archived_ref。这样既能保证当前索引简洁，又能保留演进历史。

来源管理要求每个事实都可追溯到项目文档、测试命令或经验证的操作记录。不允许使用未经验证的社区回答作为唯一来源。

相邻主题包括：Markdown 知识写作、检索增强生成、提示词模板管理、会话上下文管理。FAQ 组织与前者的区别在于它以“问题—答案—边界”三元组为核心数据模型，而不是以文档章节或会话轮次为核心。

## 结论

事实层面，FAQ 组织需要显式的问题表述集合、触发上下文、答案内容块、边界条件、拒答条件和元数据六个组成部分。推论层面，把拒答条件显式写入单元比依赖模型自行推断更稳定，尤其适合长期演进的知识库。未知层面，不同模型对边界语义的理解差异尚未被充分量化，问答单元的最优粒度也会随着领域复杂度变化而变化，因此需要通过可观测指标持续校准。
