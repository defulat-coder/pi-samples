# Markdown 知识库中的 FAQ 组织：面向验证与运维的可复用问答单元

## 摘要与问题边界

FAQ 组织不是把常见问题罗列成问答列表，而是把真实事件、边界答案和拒答条件封装成可复用的问答单元。每个单元必须携带可验证证据，能够回答“什么情况下成立、什么情况下不成立、没有证据时如何回绝”。本视角面向需要观察性能、稳定性和故障恢复的工程师，因此重点关注一次成功请求之外的状态：失败路径、延迟分布、容量阈值和恢复证据。适用范围限定在由本地 Markdown 文件、TypeScript/Web 服务或 Agent 知识库承载的运维知识；不包含产品路线图、法律合规条款或未经验证的假设。

## 核心概念与数据模型

1. **问题主干（Question Stem）**：用户可能提问的规范表述，包含唯一标识符、同义词集合和分类标签。同一现象的不同口语化表达应映射到同一个主干，避免检索时因措辞差异而漏召。
2. **答案实体（Answer Entity）**：针对问题主干的正式回答，由主路径、边界说明和已知异常三部分组成。答案必须标注最后验证时间、验证方式以及失效条件。
3. **证据链（Evidence Chain）**：支撑答案的可观测材料，包括日志路径、Trace ID、指标查询语句、截图或命令输出。证据链需记录来源、采集时间和置信度，过期证据应触发重验。
4. **边界条件（Boundary Conditions）**：答案成立的前提，例如软件版本区间、配置开关、容量上限、地域或实例角色。边界条件用显式谓词表示，便于运行时判断答案是否适用。
5. **拒答条件（Refusal Conditions）**：当证据不足、问题超出范围、输入过于模糊或与已知事实冲突时，单元应明确拒绝生成答案，而不是给出猜测。拒答必须返回原因和可进一步提供的信息。
6. **运维元数据（Operational Metadata）**：记录严重等级、错误预算影响、关联恢复动作、负责人和版本哈希。运维元数据用于在故障期间快速排序答案优先级。
7. **问答单元（QCell）**：由问题主干、答案实体、证据链、边界条件、拒答条件和运维元数据组成的最小可复用单元，对应本地知识库中的一个 Markdown 文件及其前置元数据。

## 设计决策与取舍

### 原子化单元与主题聚合

每个 QCell 只对应一个可观测故障或一个明确的操作问题。聚合多个现象会提高阅读效率，但会降低检索精度；原子化虽然维护成本更高，却能让 Agent 在回答时精确定位边界。取舍原则是：当两个现象需要不同的恢复动作或证据集时，必须拆分为独立单元。

### 精确边界与过度防御

答案必须附带边界条件，但不能因边界过多而始终拒答。需要为每个证据条目设置置信度阈值：高于阈值则给出带边界说明的答案；低于阈值则拒答并提示补充材料。过度防御会导致召回率下降，过度宽松则会产生错误答案。

### 版本锁定与持续刷新

答案与代码、配置、基础设施版本绑定。版本锁定可以明确适用范围，减少“旧答案应用到新环境”的风险；但如果不建立刷新机制，答案会迅速过期。建议将 `last_validated` 时间与版本哈希写入元数据，并在 CI 中根据源文件变更触发重验。

### 结构化元数据与正文叙述

QCell 使用 YAML 前置元数据承载机器可解析的字段，正文 Markdown 保留给人阅读的操作细节。若全部结构化，作者负担重且可读性差；若全用自然语言，检索和边界判断又不可靠。采用“元数据控制召回、正文承载过程”的混合方案。

### 集中审核与分布式提交

运维团队集中审核可以保证边界和证据质量，但会拖慢更新速度；允许一线工程师直接提交能快速沉淀现场经验，却容易引入未经核实的结论。折中方案是：一线工程师提交 draft 状态单元，运维负责人审核后标记为 stable；只有 stable 单元才会被检索器召回。

### 运行时拒答与静态修正

运行时拒答能在查询端保护用户，但频繁拒答会影响体验；静态修正则在入库前解决问题。应将运行时拒答作为最后防线，平时通过定期回放真实问题、比对指标来修正单元内容。

## 可执行的实施流程

1. **收集真实问题**：从工单、On-Call 记录、 incident channel、监控告警注释中提取真实提问，记录原始上下文和发生时间。
2. **提取可观测证据**：为每个问题 attach 日志片段、Prometheus/Metrics 查询、分布式 Trace、配置文件快照或命令输出，标注来源路径和采集时间。
3. **编写问题主干**：将口语化提问抽象为规范表述，列出同义词和反义词样例，确保检索覆盖多种输入。
4. **撰写答案实体**：写出主恢复路径、边界说明和已知异常，避免使用“通常”“可能”等无法验证的词汇。
5. **定义边界与拒答条件**：用版本、配置、容量等谓词表达适用边界；列出证据缺失、范围外、模糊、冲突四类拒答触发条件。
6. **创建 QCell 文件**：在知识库目录生成 Markdown 文件，前置 YAML 元数据，正文写入操作细节和证据引用。
7. **本地索引与召回测试**：使用关键词、标签和嵌入向量分别测试，验证正向问题能召回、边界问题能提示限制、无关问题能被拒答。
8. **部署到服务并接入监控**：将知识库挂载到 Agent 或 Web 服务，记录检索延迟、答案生成时间、拒答率和证据点击率。
9. **定期重验与回放**：每月抽取近期 incident 复现问题，对比知识库答案与现场实际结果，更新失效单元。
10. **变更联动与版本管理**：在源代码或配置仓库变更时，通过 CI 检查受影响的 QCell 是否需要重验或退役。

## 本地文件知识库示例

```yaml
id: qcell-api-timeout-2024-001
status: stable
question_stem: "为什么上传大文件时 API 返回 504？"
aliases:
  - "文件上传超时"
  - "大文件上传 Gateway Timeout"
tags: [api, upload, timeout, nginx, typescript]
boundary:
  - service: upload-api
    version_range: ">=2.3.0 <2.5.0"
    nginx_client_max_body_size: "<= 100MB"
    network: "内网或 VPN"
evidence:
  - type: trace
    source: "/logs/traces/upload-trace-2024-06-11.json"
    query: "trace_id=abc123 and duration > 30s"
    confidence: high
    collected_at: "2024-06-11T09:23:00Z"
answer:
  main: "Nginx 默认 proxy_read_timeout 30s，后端处理大文件超过阈值时返回 504。调整 location /upload 的 proxy_read_timeout 至 120s 并开启分片上传。"
  boundaries: "仅适用于通过 Nginx 代理的 upload-api 2.3.x-2.4.x；直接访问后端端口或 2.5.0 以后使用流式接口时原因不同。"
  known_exceptions:
    - "若后端返回 413，则原因为 client_max_body_size 限制，而非 proxy_read_timeout。"
refusal:
  - "未提供版本号、代理层或文件大小时，要求补充环境信息。"
  - "trace 中无 upload-api 跨度时，说明证据不足，不给出确定结论。"
operations:
  severity: P2
  recovery_action: "/runbooks/upload-timeout-recovery.md"
  owner: sre-upload
  last_validated: "2024-09-20T14:00:00Z"
  source_commit: "a1b2c3d"
```

输入是一段用户查询“上传大文件 504”以及当前服务版本、代理层等上下文。处理阶段检索器根据问题主干和同义词召回本单元，边界引擎检查版本、代理层和证据是否存在；若匹配则组合答案、边界说明和恢复动作。输出是面向工程师的答复：主因、适用边界、例外情况和下一步操作链接，并在证据不足时返回拒答提示。

## 性能、质量与可观测性指标

1. **检索延迟 P95/P99**：从用户提问到召回 Top-K 单元的时间。测量方式是记录检索器入口和出口的时间戳，按请求维度聚合；目标 P95 低于 200ms。
2. **答案覆盖率**：真实问题中至少召回一个 stable 单元的比例。通过每月回放 incident 工单抽样计算，目标覆盖率高于 85%。
3. **拒答准确率**：拒答请求中确实属于证据不足或范围外的比例。人工抽检拒答样本，结合原始工单判断；目标误判率低于 5%。
4. **证据新鲜度**：stable 单元 `last_validated` 距今天数的分布。使用元数据扫描，超过 90 天的单元标记为待重验。
5. **恢复动作点击率**：答案中包含的恢复动作链接被点击的比例。通过 Web 前端事件日志统计，低点击率提示答案可操作性不足。
6. **错误答案导致的重复工单率**：用户获得答案后仍再次提交工单的比例。结合 FAQ 调用日志与工单系统计算，用于发现边界缺失或答案过时的单元。

## 失败模式、诊断证据与恢复动作

1. **答案过期**：代码升级后答案仍引用旧版本配置。诊断证据是 `last_validated` 早于最近一次发布，或现场指标与答案描述不符。恢复动作是标记单元为 stale，重新采集证据并更新边界条件。
2. **边界未命中**：用户环境与答案边界不一致，导致正确单元被误用。诊断证据是答案被召回但用户后续反馈“按步骤操作无效”。恢复动作是在元数据中补充更严格的边界谓词，并增加拒答提示。
3. **虚假拒答**：证据其实存在，但检索器或边界引擎未识别。诊断证据是拒答日志中出现高频问题但对应单元未被召回。恢复动作是扩展同义词、调整阈值或修复索引。
4. **证据链接失效**：引用的日志、Trace 或 Runbook 路径已删除或权限变更。诊断证据是访问证据返回 404 或无权限。恢复动作是更新证据来源或改为内联关键片段。
5. **答案与指标冲突**：同一问题出现多个 QCell，结论互相矛盾。诊断证据是不同问题主干返回相反恢复动作。恢复动作是合并单元、明确分支条件，并指定一个负责人裁决。
6. **检索超时或索引膨胀**：知识库增长后查询延迟上升。诊断证据是 P99 检索延迟持续超过阈值。恢复动作是分片索引、压缩向量、归档退役单元或引入缓存。

## 问答测试样例

1. **正向问题**：用户问“上传大文件时 API 返回 504 怎么办？”并提供 upload-api 2.4.1、Nginx 代理、文件 80MB。期望返回调整 proxy_read_timeout 和开启分片上传的答案。
2. **边界问题**：用户问同样问题，但版本为 2.5.0 且使用流式接口。期望答案说明该版本原因不同，要求补充 trace，不直接套用旧结论。
3. **无证据拒答**：用户只问“上传超时”，未提供版本、代理层、文件大小和 trace。期望返回拒答，提示需要补充环境信息。
4. **范围外问题**：用户问“为什么前端页面样式错乱？”该问题与上传超时无关。期望返回范围外拒答，并建议查看前端知识库分类。
5. **冲突证据拒答**：用户提供了 upload-api 2.4.1 但 trace 显示 413 错误码。期望单元检测已知例外，拒答“504 超时”结论并引导用户检查 client_max_body_size。
6. **模糊输入**：用户问“服务又挂了”。期望拒答并要求具体现象、错误码、时间范围和影响面。
7. **容量边界**：用户问 504 问题但文件大小为 500MB，超过 nginx_client_max_body_size 100MB 边界。期望答案附带容量边界说明，指出需调整 Nginx 体积极限或改用对象存储直传。

## 维护、版本、来源与相邻主题关系

QCell 文件建议存放在 `.pi/knowledge/faq/` 或项目约定的 Markdown 知识库目录中，文件名采用 `qcell-{主题}-{序号}.md` 格式。每个单元必须保留 `source_commit` 和 `last_validated`，便于在 Git 历史中追溯答案来源。维护周期分为日常、周度和月度：日常由一线工程师在 incident 闭环时提交 draft；周度由 SRE 审核 stable 单元；月度执行回放重验和证据链接健康检查。

版本管理上，答案与代码、配置同版本演进。当上游服务发布新版本时，CI 应扫描 tags 中受影响的单元，强制更新或降级状态。来源方面，优先使用可观测证据，其次是经评审的 incident postmortem；不接受匿名聊天截图或未复现的传闻。

FAQ 组织与相邻主题的关系如下：与 Runbook 的关系是，FAQ 回答“为什么会这样”，Runbook 回答“具体怎么修”，FAQ 可链接到 Runbook；与 Alert Rule 的关系是，告警应引用相关 QCell ID，方便 On-Call 工程师快速定位；与 SLO/Error Budget 的关系是，QCell 的运维元数据可帮助评估某类故障对错误预算的影响；与 Skills 的关系是，Agent Skill 可封装检索逻辑，但知识内容仍由 Markdown QCell 承载；与 Prompt Template 的关系是，模板负责格式化输出，QCell 负责提供事实和边界。

## 结论

事实：FAQ 组织必须由真实问题驱动，每个可复用问答单元应包含问题主干、答案实体、证据链、边界条件、拒答条件和运维元数据；本地 Markdown 与 YAML 前置元数据的混合格式兼顾人类阅读和机器召回；性能、质量和可观测性指标可以量化检索延迟、覆盖率和证据新鲜度。

推论：将答案与版本、配置和证据绑定，并建立定期重验机制，能够显著降低“旧答案应用到新环境”的风险；运行时拒答是保护用户体验的最后防线，长期质量依赖静态修正和持续回放。

未知：不同业务场景下最优的重验周期、拒答阈值和召回 Top-K 数量需要结合实际工单量和错误预算进一步实验；多语言、多 Agent 共享同一 FAQ 时的一致性和权限模型也未在本文中完全验证。
