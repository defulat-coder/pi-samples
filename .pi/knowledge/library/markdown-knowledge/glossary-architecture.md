# 术语表：知识库中的歧义消减接口

## 摘要与问题边界

术语表不是词汇清单，而是对知识库中“同一含义的多种表达”进行规范化映射的接口层。它解决的问题边界限定在：检索器面对用户查询时，因同义词、缩写、领域行话或跨团队命名差异而产生的匹配歧义。超出此边界的问题——如实体关系推理、语义相似度计算、多语言翻译——应由其他模块承担，术语表只提供“术语→规范定义”的确定性映射，不做概率推断。

术语表的责任边界包含三条规则：第一，只收录在项目中真实出现的表达；第二，每个规范条目必须对应一个可验证的上下文来源；第三，术语表本身不提供自然语言理解能力，只向检索器和 Agent 提供扩展查询信号。

## 核心概念与数据模型

1. **规范词条（Canonical Entry）**：术语表的唯一主键，采用项目选定的语言形式，例如“会话管理器”。规范词条必须对应一段明确的定义文本，并在知识库中至少有一个出处锚点。

2. **表达变体（Variant）**：包括同义词、缩写、旧称、拼写变体及口语化写法。变体不独立存在，必须挂载到规范词条下，并标注变体类型，如 `synonym`、`abbreviation`、`deprecated`。

3. **出处锚点（Source Anchor）**：指向文档、代码注释或配置文件的持久化引用，例如 `docs/pi-agent-learning.md#L42`。出处锚点保证定义可被复核，也是词条可信度的判断依据。

4. **领域标签（Domain Tag）**：限制词条生效范围的分类，如 `api`、`web`、`agent-runtime`。标签使同一名称在不同上下文下可映射到不同规范定义。

5. **歧义标记（Ambiguity Flag）**：当一个变体在多个领域中指向不同规范词条时，标记为歧义，并附带消歧提示。歧义标记触发检索器请求补充上下文，而不是自行猜测。

6. **版本戳（Version Stamp）**：每个词条的生效版本和废弃版本。版本戳支持渐进式迁移，避免旧文档中的术语被误读为当前语义。

## 设计决策与取舍

### 1. 中心化存储与分布式维护的平衡

术语表采用单一可解析文件作为事实来源，便于版本控制和全文检索；但词条的增删改由各领域文档所有者通过 pull request 提交，避免中心团队成为瓶颈。取舍点在于：存储集中，治理分散。

### 2. 严格匹配优先于语义相似

术语表接口优先返回严格匹配结果，只有在严格匹配失败时才允许检索器降级到语义相似。这一决策降低了幻觉风险，代价是要求维护者完整枚举常见变体。

### 3. 变体类型的显式标注

将缩写与废弃写法分别标注，而不是混为一谈。这影响下游行为：缩写可安全地扩展查询，废弃写法应附带迁移提示，歧义变体必须暂停并请求澄清。

### 4. 领域标签的二义性控制

允许同一名称在不同领域拥有不同定义，但限制同一词条在同一领域内只能有一个主键。这一边界防止了“无限消歧”，同时承认了跨团队命名的客观差异。

### 5. 机器可解析与人可阅读的格式

采用结构化文本格式（如 JSON）存储术语表，但要求每个字段都有注释说明。机器可解析保证检索器稳定消费；人可阅读保证评审者能在代码审查中直接校验。

## 可执行的实施流程

1. 梳理现有文档和代码中反复出现但不统一的术语，记录其出现位置和上下文。
2. 确定每个术语的规范写法，优先选择代码中实际使用的标识符或文档标题中的主名称。
3. 为每个规范词条编写 30 至 100 字的定义，并标注至少一个出处锚点。
4. 枚举所有观察到的变体，按类型标注为 `synonym`、`abbreviation`、`deprecated` 或 `ambiguity`。
5. 为每个词条分配领域标签，若存在跨领域冲突，则拆分为多个带标签的条目。
6. 选择或设计术语表文件格式，约定字段名称、必填项和校验规则。
7. 在构建流程中加入校验脚本，检查主键唯一、变体不悬空、出处锚点可解析、版本戳格式合法。
8. 将术语表接入检索器扩展查询路径，记录每次扩展的触发词、目标词条和命中领域，以便后续审计。

## 输入、处理与输出示例

以下是一个面向 TypeScript/Web/本地文件知识库的 JSON 示例，展示了术语表如何被检索器消费：

```json
{
  "glossary": {
    "version": "2024.06",
    "entries": [
      {
        "canonical": "会话管理器",
        "definition": "负责创建、维护和销毁 Pi Agent 会话的运行时组件，对应 SessionManager 接口。",
        "domain": "agent-runtime",
        "variants": [
          { "form": "SessionManager", "type": "synonym" },
          { "form": "session manager", "type": "synonym" },
          { "form": "SM", "type": "abbreviation", "requiresContext": true }
        ],
        "sources": ["packages/pi-agent/src/session.ts#L12"],
        "since": "2024.03"
      },
      {
        "canonical": "会话管理器",
        "definition": "Web 应用中维护用户登录状态的浏览器端存储逻辑。",
        "domain": "web",
        "variants": [
          { "form": "session manager", "type": "synonym" }
        ],
        "sources": ["apps/web/src/auth/store.ts#L8"],
        "since": "2024.01",
        "ambiguityFlag": {
          "sharedVariant": "session manager",
          "disambiguationHint": "请补充上下文：agent-runtime 或 web"
        }
      }
    ]
  }
}
```

输入：检索器接收到查询“session manager 的职责是什么”。处理：检索器先匹配变体，发现该表达同时命中 `agent-runtime` 和 `web` 两个领域，且带有歧义标记，因此不直接返回结果，而是附加消歧提示。输出：Agent 收到“该术语在 agent-runtime 与 web 两个领域有不同定义，请指定上下文”的提示。

## 性能、质量与可观测性指标

1. **术语命中率**：查询中触发术语表扩展的占比。通过检索日志统计，目标区间为 15% 至 35%，过低说明收录不足，过高说明词条过度泛化。
2. **歧义拦截率**：被歧义标记拦截并请求澄清的查询比例。应维持在 5% 以下，超过则表明领域拆分或变体标注需要优化。
3. **出处锚点有效率**：术语表引用的文件路径与行号在代码库中仍有效的比例。通过构建期检查测量，应保持在 100%。
4. **扩展查询精确率**：使用术语表扩展后，检索结果与期望文档的相关度。采用人工抽样评估，目标 ≥ 85%。
5. **版本迁移完整率**：带 `deprecated` 或 `since` 标记的词条在相关文档中已完成同步更新的比例。通过文档扫描工具测量，目标 ≥ 90%。

## 失败模式与恢复

1. **同义循环**：变体 A 指向规范 B，而 B 的变体又包含 A。诊断证据：校验脚本报告循环依赖。恢复：删除冗余变体，或引入弃用标记。
2. **幽灵术语**：词条存在但对应出处锚点已失效。诊断证据：构建期检查失败，报告文件不存在或行号偏移。恢复：更新锚点或删除词条。
3. **过度扩展**：缩写“SM”被无差别扩展为“会话管理器”，导致与“状态机”查询混淆。诊断证据：歧义拦截率突增。恢复：为该缩写添加 `requiresContext` 或拆分到具体领域。
4. **领域泄漏**：web 领域的术语定义出现在 agent 检索结果中。诊断证据：跨领域扩展日志异常。恢复：收紧领域标签过滤规则，或拆分共享变体。
5. **版本漂移**：旧文档中的“会话管理器”仍被解释为当前语义，而当前语义已改变。诊断证据：扩展查询精确率下降。恢复：为旧义项添加 `until` 版本戳，并提示读者查阅历史版本。

## 问答测试样例

1. 正向问题：“SM 在 agent-runtime 中是什么？” 预期回答：指“会话管理器”，并给出对应定义与出处。
2. 正向问题：“session manager 在 Web 应用中的定义是什么？” 预期回答：指浏览器端用户登录状态存储逻辑。
3. 边界问题：“session manager 是什么？” 无领域上下文。预期：拒答并提示歧义，请求补充 agent-runtime 或 web。
4. 边界问题：“SessionManager 与 session manager 是否相同？” 预期：取决于领域，agent-runtime 中相同，web 中可能不同。
5. 无证据问题：“Pi Agent 是否支持 Redis 会话存储？” 术语表未收录 Redis 相关定义。预期：基于知识库正文回答，不得引用术语表虚构义项。
6. 无证据问题：“术语表中是否存在‘运行时’的定义？” 若不存在，预期：明确回答“术语表未收录该词条”，并给出可验证的查询方式。

## 维护、版本、来源与相邻关系

维护责任：技术作者负责新增和修订定义；构建流程负责结构校验；检索器维护者负责接入与扩展逻辑。版本策略：术语表文件版本与项目主版本解耦，采用独立日历版本，便于文档和代码独立演进。来源管理：每个词条必须保留至少一个可追踪的出处锚点，优先选择文档和源码而非会议记录或口头约定。

与相邻主题的关系：术语表位于“知识库结构”与“检索增强”之间。它不同于“本体/知识图谱”——不表达实体关系；也不同于“FAQ”——不直接回答用户问题；还不同于“写作规范”——不规定风格，只规定映射。术语表与“标签体系”互补：标签用于分类，术语表用于消歧。

## 结论

事实：术语表是知识库中降低同义词、缩写和领域词歧义的确定性映射接口；它必须依赖出处锚点和领域标签才能稳定运行。

推论：若将术语表设计为严格匹配优先、语义相似为辅的接口，可显著降低 Agent 在缺少上下文时产生错误扩展的概率；版本戳和歧义标记是长期演进不可或缺的机制。

未知：不同检索器对变体扩展的召回阈值应如何设定；多语言术语表的优先级策略应如何与中文规范主键共存；术语表规模扩大到数千条时，校验脚本的性能拐点具体位于何处。这些需要结合项目实际查询日志进一步验证。
