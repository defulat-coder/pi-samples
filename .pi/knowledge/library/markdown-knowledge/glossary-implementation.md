# 实现 Markdown 知识库术语表：同义词、缩写与领域词统一

## 摘要与问题边界

术语表的作用是把知识库中反复出现的同义词、缩写和领域词收敛到同一个定义。实现视角下，它不是简单的“名词解释列表”，而是一个输入 Markdown 源文件、输出规范化引用记录的管道。输入包括术语条目、别名、缩写、领域标签和来源；输出是查询时可以返回的规范词、定义、歧义提示与来源追踪。本方案面向把术语表落地为 TypeScript 服务的开发者，重点在写入前的验证、索引构建、查询解析与生命周期维护，而不是让大模型在运行时随意猜测词义。

## 核心概念与数据模型

1. **规范词（Canonical Term）**：每个概念的唯一稳定标识。它在存储中通常是一个小写、去标点的字符串，但保留一个 `display` 字段用于渲染。例如规范词 `server-side-rendering` 的显示名称为 `Server-Side Rendering`。

2. **别名（Alias）**：与规范词等价的自然语言变体。别名可以是“服务端渲染”“SSR”，也可以是拼写差异“SS Rendering”。别名本身不是独立条目，必须指向一个规范词。

3. **缩写（Abbreviation）**：一类特殊的别名。它必须有 `expansion` 字段说明全称，并且可以带 `domain` 字段处理歧义。同一个缩写“API”在 Web 领域与医药领域应指向不同规范词。

4. **领域标签（Domain Tag）**：用于隔离同形异义词。每个条目至少有一个主领域，可选次级领域。查询时如果没有给出上下文，系统必须返回候选列表而不是强制选其一。

5. **定义条目（Definition Entry）**：最小的可发布单元，包含规范词、别名列表、缩写列表、定义正文、示例、来源文件路径、版本戳、弃用状态与替代词。它对应 TypeScript 接口 `GlossaryEntry`。

6. **索引记录（Index Record）**：查询时真正使用的数据结构。它在构建阶段把规范词、别名、缩写拆成词干或 n-gram，记录命中位置、来源路径和权重，并预先计算别名闭包，避免运行时递归。

## 设计决策与取舍

### 规范化策略：小写为主，显示与匹配分离
实现时把匹配键统一小写并去除多余空格与标点，但保留原始大小写用于页面展示。这会导致“Node.js”和“node.js”等价，但“ID”与“Id”也会等价，属于可接受的工程折中。若对大小写敏感的业务词，可在条目中显式声明大小写敏感标志。

### 别名解析：离线计算闭包，运行时直接查表
同义词关系可以设计为在线递归查询，也可离线计算传递闭包。选择离线闭包，优点是把查询复杂度降为 O(1)，缺点是新增条目后必须重新构建索引。折中方案是增量 diff：只重建受影响的连通分量。

### 歧义处理：返回候选列表，不替调用方做决定
当缩写“API”同时命中多个领域时，直接返回最可能的结果会引入静默错误。因此查询接口返回 `{ candidates, confidence }` 结构，让调用方根据上下文再选择。代价是调用方代码需要多写一层分支，但换来可审计的决策链路。

### 存储格式：YAML 用于作者，JSON 用于运行时
Markdown 中嵌入 YAML 适合人类编写，但解析慢且容易出错。构建管道把 YAML 验证后编译成 JSON 索引文件，运行时只加载 JSON。这样写入校验与读取性能分离，也方便在 CI 中做版本比对。

### 更新策略：增量索引 + 定期全量重建
日常编辑通过 diff 更新索引；每周或每次 schema 升级时触发全量重建。全量重建可以检测增量阶段遗漏的循环引用和跨文件冲突，增量阶段保证开发反馈速度。

## 可执行的实施流程

1. 定义 TypeScript 类型与 JSON Schema，明确字段必填、类型与枚举值。
2. 在 `.pi/glossary/` 或项目约定目录中创建 YAML 源文件，每个文件对应一个领域或一个主题包。
3. 运行验证脚本：检查必填字段、唯一规范词、无循环别名、缩写不空、来源路径存在。
4. 对别名和缩写做规范化处理，生成匹配键。
5. 计算同义词传递闭包，并生成反向映射 `alias -> canonical` 和 `abbreviation -> canonical`。
6. 将条目序列化为 JSON 索引，写入构建产物目录，附带校验和文件。
7. 在 Web/API 中暴露查询接口，接受 `term`、`domain`、`context` 参数，返回候选列表或单条结果。
8. 在 Markdown 渲染管线中接入术语表：遇到候选词时自动添加链接或提示气泡，并记录未命中词。
9. 配置 CI：每次提交都运行验证与索引构建，失败时阻止合并。
10. 部署可观测性：记录索引构建耗时、查询延迟、未命中率和歧义返回率。
11. 建立弃用流程：弃用条目保留至少一个版本，通过替代词重定向，并在日志中告警旧引用。
12. 定期人工审查：每月抽样检查未命中词和歧义查询，补充缺失条目。

## 输入、处理与输出示例

下面是一个贴近本地 Markdown 知识库的源文件与构建产物片段。

```yaml
# glossary/web-rendering.yaml
- canonical: server-side-rendering
  display: Server-Side Rendering
  domain: [web, frontend]
  aliases:
    - 服务端渲染
    - SSR
  abbreviations:
    - short: SSR
      expansion: Server-Side Rendering
  definition: 在服务器端完成页面初始 HTML 生成，再返回给浏览器渲染的技术。
  examples:
    - 框架 A 使用 SSR 缩短首屏时间。
  source: docs/architecture/rendering.md
  version: 1.2.0
  deprecated: false
```

构建脚本将其解析为：

```json
{
  "canonical": "server-side-rendering",
  "display": "Server-Side Rendering",
  "domain": ["web", "frontend"],
  "matchKeys": ["server-side-rendering", "server-side rendering", "ssr", "服务端渲染"],
  "definition": "在服务器端完成页面初始 HTML 生成，再返回给浏览器渲染的技术。",
  "source": "docs/architecture/rendering.md",
  "version": "1.2.0"
}
```

输入是 YAML 源文件与 Markdown 正文；处理阶段完成规范化、去重、计算闭包和生成匹配键；输出是 JSON 索引和可被查询接口消费的候选列表。

## 性能、质量与可观测性指标

1. **索引构建耗时**：测量全量重建与增量 diff 的耗时，目标在千级条目下小于 5 秒。
2. **查询延迟 p99**：在 API 层统计 `resolveTerm` 的 p99 响应时间，目标小于 20 毫秒。
3. **覆盖率**：统计正文中被术语表识别为已知词的比例，按每周维度报告增长或下降。
4. **歧义返回率**：返回候选列表大于 1 的查询占比，高于 15% 时提示需要拆分领域或补充别名。
5. **验证错误率**：每次 CI 中 schema 或约束失败的次数，归零是合并的必要条件。
6. **弃用引用残留率**：扫描 still 引用已弃用术语的 Markdown 文件数，定期归零。

## 失败模式、诊断证据与恢复动作

1. **重复规范词**：两个 YAML 文件定义了相同 `canonical`。诊断证据是验证报告列出冲突路径；恢复动作是合并条目或给其中一个添加领域前缀。
2. **循环别名**：A 的别名指向 B，B 的别名又指向 A。诊断证据是图算法检测到的环；恢复动作是打断最弱边，要求至少一个节点必须是规范词。
3. **缩写歧义**：同一缩写命中多个不同定义。诊断证据是查询返回的 `candidates.length > 1`；恢复动作是在查询处补充 `domain` 参数，或在缩写定义中标记更精确的领域。
4. **定义漂移**：Markdown 中的定义文字被修改，但 `version` 未升级。诊断证据是构建阶段比较条目哈希与索引哈希不一致；恢复动作是拒绝提交，要求作者更新版本或撤销改动。
5. **来源文件丢失**：条目的 `source` 字段指向的 Markdown 文件不存在。诊断证据是文件系统检查失败；恢复动作是修正路径或删除失效条目。
6. **未命中高频词**：某词在正文中频繁出现但不在索引中。诊断证据是覆盖率低且未命中日志重复；恢复动作是补充条目或加入同义词。

## 问答测试样例

1. **正向**：用户问“SSR 是什么？”系统返回 `server-side-rendering`，并给出 Web 领域定义。
2. **正向**：用户问“服务端渲染和 SSR 是同一个概念吗？”系统返回“是”，并列出共同规范词。
3. **边界**：用户问“API 在医药领域指什么？”系统返回 `active-pharmaceutical-ingredient`，并提示 Web 领域还有另一个候选。
4. **边界**：用户用大小写混合 `sSr` 查询，系统经规范化后仍命中 `server-side-rendering`。
5. **边界**：用户问已弃用术语“旧渲染方案”，系统返回条目并附带 `deprecated: true` 与替代词。
6. **拒答**：用户问“TBD 是什么？”索引中无定义、无别名、无缩写，系统返回“无证据，无法确定”，不编造定义。

## 维护、版本、来源与相邻主题的关系

术语表本身应使用语义化版本管理 schema，例如 `1.0.0` 表示稳定字段，`2.0.0` 表示破坏性字段变更。每个条目独立维护 `version` 字段，记录定义内容的变更。来源字段必须指向真实 Markdown 文件路径，便于在代码库中追踪。

术语表与相邻主题的关系：它依赖**Markdown 解析与 AST 处理**来提取正文中的候选词；它输出结果给**搜索索引**和**问答检索器**；它与**知识图谱**互补，术语表聚焦“词到定义”，知识图谱聚焦“概念到关系”；它与**标签/分类体系**共享 `domain` 字段，但标签体系更宽，术语表更精确。

## 结论

- **事实**：术语表由规范词、别名、缩写、定义与来源字段构成；构建过程包括验证、规范化、闭包计算与索引生成；查询返回单条结果或候选列表。
- **推论**：在 TypeScript 服务中，把 YAML 作为作者源、JSON 作为运行时索引，可以在人类可读性与查询性能之间取得平衡；增量 diff 加定期全量重建能兼顾反馈速度与一致性。
- **未知**：具体项目中同义词网络的实际密度、缩写歧义的真实分布、以及用户查询与正文用词的差异，需要上线后通过未命中日志和歧义率来验证，不能预先假设。
