# Markdown 知识库术语表：面向运维验证的统一语义协议

在运维工程师的日常工作中，性能告警、稳定性事件和故障恢复很少由单次成功请求证明。一个术语可能在日志、监控面板、聊天和文档中以全称、缩写、旧称或口语反复出现。如果知识库不把这些形式绑定到同一个权威定义，检索器会按字面切分，导致同类问题散落在不同片段中，Agent 引用时也会给出相互矛盾的说法。术语表不是普通词典，它是在指定知识库范围内强制生效的语义契约：为同义词、缩写和领域词提供统一定义，并记录验证证据、失败边界与恢复动作。

本主题的问题边界限定在 Markdown 文件构成的本地知识库中，目标是通过结构化术语数据降低查询歧义。它不解决跨语言翻译、语义推理或事实正确性审查；也不替代代码命名规范、版本控制或变更审批流程。术语表的价值最终要通过可观测性验证：不同关键词搜索同一故障时，应返回一致的召回集合。

## 核心概念与数据模型

1. 主术语条目：知识库中的权威名称，具有唯一标识符，如 `oom`。定义必须包含可验证边界，例如“特指进程因可用内存不足被操作系统或运行时终止，不包括磁盘空间耗尽、文件句柄泄漏或线程死锁”。

2. 同义词：指向主术语的等效或近似表达，需标注等价类型。精确等价如“内存溢出”映射到 `oom`；近似等价如“内存吃紧”仅允许描述现象，不能用于归因结论。

3. 缩写与全称：记录缩写、全称、大小写敏感性和可独立使用性。例如 `k8s` 可单独使用，但 `lb` 在首次出现时建议补充“负载均衡”。

4. 领域上下文：同一术语在不同子系统中含义可能不同。`gc` 在运行时团队指垃圾回收，在基础设施团队中可能指全局配置。每个定义必须绑定领域标签，否则检索器默认返回通用定义并提示补充上下文。

5. 证据来源：每个定义必须附带可追溯的来源，如 `/docs/adr/0002-memory-policy.md` 或 `/runbooks/recovery-oom.md`。没有来源的条目状态只能为 `draft`，不得进入 `active`。

6. 状态与版本：术语条目具有 `draft`、`active`、`deprecated` 或 `removed` 状态。任何状态变更需记录语义化版本，并通过 git diff 保留历史。

7. 冲突词与反推荐词：明确列出不应使用的表达及其原因。例如“爆内存”不推荐用于正式文档，仅作为口语记录保留在冲突词中。

8. 使用示例：给出在 Markdown 正文中正确使用术语的示例片段，帮助作者和检索器对齐边界。

## 设计决策与取舍

集中维护与本地覆盖：项目维护一个主术语表文件，如 `.pi/glossary.yml`，所有 Markdown 文档默认遵循该表。允许单个文档声明局部覆盖，但覆盖条目必须显式标注，且不能改动全局主术语条目。

强匹配与弱相关：检索阶段先执行强匹配，将同义词映射到主术语；若查询无精确命中，再允许弱相关语义扩展。强匹配保证一致性，弱相关承担召回风险。关键运维术语优先使用强匹配。

单定义与多态定义：一个术语允许存在多个领域定义，但每个定义必须绑定 `domain` 标签。如果上下文缺失，默认返回通用定义，并提示用户补充领域信息。

人工审核与自动抽取：高频运维术语必须由人工审核确认；自动 NLP 工具可以生成候选条目，但候选状态为 `draft`，不能直接生效。自动抽取的缩写必须人工验证是否存在冲突。

只读引用与动态改写：Agent 在引用术语时只能读取术语表中的定义，不能根据上下文自行改写或省略边界。这能防止定义在传播过程中漂移。

版本锁定与最新版本：知识库文档在引用术语时建议采用版本锁定。对于稳定术语使用主术语 ID 即可；对于边界快速演进的术语，应引用具体版本号，避免复现结果不一致。

## 可执行的实施流程

1. 扫描现有 Markdown 文件，使用词频统计和缩写检测脚本提取高频技术词、缩写和疑似同义词。

2. 由 SRE 与可观测性负责人对候选词进行分类，区分同义词、缩写、产品名、历史称谓和误用表达。

3. 为每个候选术语编写定义，明确边界、例外和可验证证据，并指定来源文件路径。

4. 组织评审会议，重点审查与失败、延迟、容量和恢复相关的术语，确保定义与运行手册一致。

5. 将审定后的术语写入主术语表文件，使用结构化格式，并为每个条目添加来源与状态字段。

6. 在 Markdown 文档中首次出现术语时进行统一标记，避免混用旧称、缩写和全称。

7. 构建查询召回测试集，覆盖同义词、缩写和领域上下文，验证检索器是否返回一致结果。

8. 在 CI 中集成术语漂移检测，检查新增的未定义高频词或已弃用术语的引用。

9. 部署后持续观察术语解析模块的延迟、命中率和错误引用日志。

10. 每次变更术语表时生成语义化版本，并更新相邻文档的变更日志。

## 本地文件知识库示例

以下是一个贴近 TypeScript/Web 本地文件知识库的术语表 YAML 片段，采用缩进代码格式：

    glossary:
      version: "1.4.0"
      terms:
        - id: "oom"
          primary: "OOM"
          definition: "进程因可用内存不足被系统或运行时终止，不包括磁盘空间耗尽或文件句柄泄漏。"
          domain: "infrastructure"
          status: "active"
          evidence: "/runbooks/recovery-oom.md"
          synonyms:
            - term: "内存溢出"
              type: "exact"
            - term: "内存不足"
              type: "approximate"
              note: "仅描述现象，不能用于归因"
          conflicts:
            - term: "爆内存"
              reason: "口语化，不用于正式文档"
        - id: "k8s"
          primary: "Kubernetes"
          definition: "用于容器编排的开放平台，本知识库中不指代个人 Kubernetes 配置。"
          domain: "platform"
          status: "active"
          evidence: "/docs/infrastructure/k8s-intro.md"
          synonyms:
            - term: "K8s"
              type: "exact"
            - term: "kube"
              type: "approximate"
              note: "通常指客户端工具或社区简称"

输入：工程师在 Web 搜索框或 Agent 对话中键入“内存溢出”“OOM”“out of memory”或“爆内存”。处理：术语解析模块加载 `glossary.yml`，根据 `synonyms` 和 `conflicts` 将命中表达映射到主术语 `oom`，并对冲突词给出警告。输出：检索器返回所有以 `oom` 为主术语索引的 Markdown 片段，Agent 引用时输出统一定义，并附带证据来源。

## 性能、质量与可观测性指标

术语覆盖率：定义为已收录的运维高频术语数除以需收录的候选术语总数。每周通过词频脚本运行一次，目标不低于 90%。

同义词映射准确率：在人工标注的测试集上，同义词查询返回正确主术语的比例。每月抽样 100 条，目标不低于 95%。

召回一致性：同一概念三种不同说法返回的文档集合的 Jaccard 相似系数。目标不低于 0.85，低于 0.7 视为异常。

术语漂移率：观测周期内新增未定义高频词数量占文档总量的比例。用于判断知识库是否出现新术语潮流。

术语解析延迟：术语解析模块的 P95 响应时间。在本地文件知识库中应低于 10 毫秒；若通过 Web API 暴露，应低于 50 毫秒。

错误引用率：Agent 输出或生成文档中使用了非推荐术语或冲突词的次数。通过正则扫描和人工复审测量。

## 失败模式、诊断证据与恢复动作

同义词循环映射：A 映射到 B，B 映射到 C，C 又映射回 A。诊断证据是术语解析图出现环。恢复动作：运行拓扑检测脚本，找到最小环并打破，通常移除最不常用的别名。

缩写冲突：同一缩写对应多个全称，例如 `lb` 可能指负载均衡或负载均衡器。诊断证据是查询返回混合领域的文档。恢复动作：为缩写绑定默认领域，并在其他领域强制使用全称或带上下文的形式。

术语漂移：文档作者引入新表达但未更新术语表。诊断证据是 CI 漂移检测出现未命中高频词。恢复动作：补充定义、标记来源，并将旧表达设置为弃用或冲突。

版本不匹配：文档引用了旧版本术语定义，导致新定义与旧文档冲突。诊断证据是同一术语在不同文档中出现矛盾的边界描述。恢复动作：统一升级到最新版本，或在引用处锁定历史版本并标注。

领域上下文误判：未提供上下文时，检索器返回了错误领域的定义。诊断证据是用户反馈“这个定义不适合当前场景”。恢复动作：在查询接口中强制要求领域参数，或提示用户补充上下文。

术语表未加载：检索器或 Agent 未读取术语表文件，导致直接字面匹配。诊断证据是查询“OOM”和“内存溢出”返回的文档集合差异显著。恢复动作：检查文件路径、加载日志和缓存状态，确保术语表在启动时被正确加载。

## 问答测试样例

正向问题：什么是 OOM？期望回答：OOM 是进程因可用内存不足被终止的事件，在本知识库中不包括磁盘空间不足，证据来源为 `/runbooks/recovery-oom.md`。

正向问题：Kubernetes 和 K8s 是否等价？期望回答：等价，K8s 是 Kubernetes 的精确缩写，均指向平台容器编排概念。

边界问题：OOM 在 JVM 应用和容器环境中是否完全相同？期望回答：不完全相同。JVM 中 OOM 通常指 Java 堆或元空间溢出；容器环境中 OOM 可能由 cgroup 内存限制触发。两者共享“内存不足被终止”的核心语义，但具体证据和恢复动作需要领域上下文。

边界问题：fallback 和 degrade 是否是同义词？期望回答：不是。degrade 是主动降低服务能力；fallback 是降级后采用的备选路径。二者经常同时出现，但不能互换。

无证据拒答：如果知识库未定义“热更新”，用户问“什么是热更新？”应拒绝给出定义，仅说明当前术语表未收录该术语，并建议提交定义请求。

无证据拒答：当用户用“上次大促的内存问题”这种模糊指代查询时，若术语表未将“大促”绑定到具体事件，应拒绝归因，仅提示用户提供具体日期或事件名称。

## 维护、版本、来源与相邻主题关系

术语表由 SRE 和平台工程团队共同维护，变更需通过 Pull Request 并经过至少一名相关领域负责人审批。每条术语必须标注来源文件路径，来源可以是架构决策记录、运行手册、监控配置或事后复盘文档。

版本采用语义化版本号。补丁号用于修正拼写或补充示例；小版本号用于新增术语或同义词；主版本号用于删除术语或改变核心定义。每次版本变更应同步更新 `.pi/glossary.yml` 的 `version` 字段和项目变更日志。

术语表与相邻主题紧密耦合：与“Markdown 命名规范”共同约束作者用词；与“检索索引”共同决定召回策略；与“文档版本控制”保证术语定义可回滚；与“变更日志”记录语义变更；与“运维运行手册”提供定义背后的证据和恢复动作。

## 结论

事实：术语表通过结构化主术语、同义词、缩写和领域上下文，降低了 Markdown 知识库中的查询歧义。每条术语必须绑定来源、状态和版本，才能被检索器和 Agent 安全引用。

推论：在运维验证视角下，统一语义后，故障检索的召回一致性会提升，Agent 生成内容的可引用性也会提高，但提升幅度取决于现有文档的术语混乱程度。

未知：术语表对自然语言理解能力的具体贡献边界尚不明确；在多领域上下文中实现最佳匹配所需的算法与维护成本比例仍需项目持续度量；长期来看，自动化抽取与人工审核的最优组合比例也需要根据实际漂移率不断调整。
