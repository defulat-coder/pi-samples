# 标题层级：面向 Markdown 知识库的 H1-H3 结构契约

## 摘要与问题边界

在 Markdown 知识库中，标题层级不仅是排版问题，而是结构契约。如果作者把 H1 当作“主标题”，H2 当作“章节”，H3 当作“小节”，那么检索器、导航器、Agent 都可以依赖这套层级进行摘要、分块和跳转。如果层级随意跳跃、H1 重复或把 H4 当作结构节点，则所有下游组件都会把错误当成语义来消费。本文讨论的责任边界是：作者负责用 H1-H3 表达稳定语义；工具负责校验、生成 slug、切分 chunk 和导航；渲染器负责把这套结构映射到 HTML 或终端界面。渲染样式可以替换，但 H1-H3 的语义契约不可替换。

## 核心概念与数据模型

1. **文档根节点**：一篇知识文章必须有且仅有一个 H1，它作为该文档的根标识。根节点的文本对应文档主题，H1 的 slug 作为 URL 锚点和检索主键的一部分。
2. **章节（Section）**：H1 打开文档，H2 打开主题域，H3 打开子主题或操作步骤。每个标题行生成一个章节节点，节点之间形成父子关系。
3. **层级递增规则**：标题层级只能逐级加一，禁止从 H1 直接跳到 H3，也禁止 H3 之后回到 H1。相邻层级差必须等于 1，不允许出现 H2 接 H4。
4. **slug 与锚点**：每个 H1-H3 标题通过文本生成稳定的 slug，用于 URL 锚点、TOC 和向量检索路径。slug 生成策略可替换，但同一文档内必须唯一。
5. **分块单元（Chunk）**：H2 及其下属的 H3 与正文构成一个最小语义块；H3 也可以单独成块，但不应把 H4 当作独立块边界。
6. **导航索引（TOC）**：TOC 只从 H1-H3 派生，H4 及更深的内容不进入导航树，只作为正文内部的视觉辅助。
7. **可替换接口**：校验器、渲染器、分块器和 slug 生成器可以替换，但它们必须都消费同一套 H1-H3 抽象语法树。

## 设计决策与取舍

### 限制在 H3 的深度

把结构契约限制到 H3，而不是允许 H4-H6，是为了保证检索召回率和导航简洁性。H4 及以下通常用于操作说明中的子步骤、参数列表或例外说明，这些内容的语义不稳定，容易变成“伪结构”。允许它们进入结构树会导致 TOC 膨胀、chunk 边界过细。代价是：少数复杂主题需要把深层内容拆成多篇文档或用列表、加粗段落来组织。

### 单 H1 契约

强制单 H1 消除了文档主题的歧义。多 H1 通常来自拼接多篇旧文档，或作者把 H1 当作“页面标题”和“文章标题”混用。工具在检测到多 H1 时应拒绝构建或发出阻断级错误，而不是自动合并，因为合并会改变语义。

### 标题编号由工具注入

文档原文中不强制手写“1. 引言”这类编号。编号由渲染器或导航组件根据 H1-H3 树动态注入。这样作者修改结构时编号自动重排，避免编号与层级脱节。例外：法律条文、标准规范等需要固定编号的知识库可以保留手写的编号，但工具不参与校验。

### slug 冲突的消解

当两个 H3 标题文本相同，直接生成的 slug 会冲突。项目级策略是：在冲突 slug 后追加父级路径前缀，例如 `h2-title--h3-title`。如果冲突发生在 H1 之间，则视为文档错误，必须修改标题，而不是靠算法消歧。

### H4 及以下内容的降级策略

H4 不进入结构树，但在渲染时仍然按标题样式显示。分块器把 H4 视作其所属 H3 正文的一部分，而不是新 chunk 的起点。如果一篇文档出现超过三次 H4，工具应告警，提示作者考虑拆分 H3。

## 可执行的实施流程

1. 在知识库根目录定义 `pi-heading-policy.yml`，声明允许层级为 `[1, 2, 3]`，要求单 H1，最大层级跳跃为 1。
2. 在构建流水线中引入 Markdown AST 解析器，把标题节点抽象为 `{level, text, slug, line}`。
3. 校验每个文档：检查 H1 数量是否等于 1；检查相邻标题层级差是否等于 1。
4. 生成 slug：对 H1-H3 使用统一 slug 算法，例如 GitHub 风格的空格转连字符、移除标点。
5. 校验 slug 唯一性：在文档内出现重复时，按父级路径前缀进行修正；无法修正时报错。
6. 构建章节树：把 H1 作为根，H2 作为子节点，H3 作为 H2 的叶子节点。
7. 生成分块：以 H2 为粗粒度 chunk，以 H3 为细粒度 chunk，每个 chunk 保留从 H1 到自身的标题路径。
8. 生成 TOC：只输出 H1-H3 节点，绑定 slug 锚点。
9. 写入向量数据库：每个 chunk 的元数据包含 `doc_slug`、`h2_slug`、`h3_slug` 和行号范围。
10. 在本地 dev 和 CI 中运行校验；失败时阻断发布，而不是仅打印警告。

## 输入、处理与输出示例

以 TypeScript 配置对象为例：

 HeadingPolicy: { allowedLevels: [1, 2, 3]; requireSingleH1: true; maxLevelJump: 1; slugStrategy: "github"; h4AsBody: true }

输入是一篇 Markdown 文件，例如包含一个 H1、两个 H2 和若干 H3。处理时，校验器先检查层级是否跳跃；分块器把每个 H2 或 H3 下的正文与代码示例组成 chunk；slug 生成器为每个标题生成稳定标识。输出包括：一份通过校验的 AST、一个只含 H1-H3 的 TOC JSON、一组带标题路径的 chunk 记录，以及渲染时使用的锚点映射。

## 性能、质量与可观测性指标

1. **TOC 生成耗时**：对单篇 5000 行文档测量 AST 到 TOC 的耗时，目标低于 20 毫秒。
2. **标题违规率**：每 100 次构建中因层级跳跃、H1 缺失或重复导致失败的文档数。
3. **chunk 召回命中率**：用固定问题集测试，期望命中 chunk 的标题路径中包含正确答案，使用 MRR 或 Top-3 准确率评估。
4. **平均标题路径深度**：统计 H1-H2-H3 的平均深度，如果深度持续向 H3 倾斜，提示主题拆分不足。
5. **构建阻断次数**：按周统计因标题违规被 CI 拒绝的合并请求数，用于判断作者培训效果。
6. **Agent 引用准确率**：在 Agent 回答中检查其引用的 H1-H3 锚点是否确实存在且与正文一致。

## 失败模式与恢复

1. **H1 缺失**：诊断证据是 AST 中没有 level 1 节点；恢复动作是拒绝构建，要求作者补 H1。
2. **H1 重复**：诊断证据是 AST 中存在两个 level 1 节点；恢复动作是停止合并，要求拆分文档或降其中一个为 H2。
3. **层级跳跃**：诊断证据是相邻标题层级差大于 1，例如 H1 后接 H3；恢复动作是阻断构建，作者需插入 H2 或把 H3 降级。
4. **slug 冲突**：诊断证据是不同标题生成相同 slug；恢复动作是工具用父级路径前缀修正，无法修正时提示作者改标题。
5. **H4 被误当作结构节点**：诊断证据是 TOC 或 chunk 边界中出现 level 4；恢复动作是把 H4 降级为正文，并在构建报告里告警。
6. **标题与正文内容不符**：诊断证据是 Agent 引用 H3 后发现正文未涉及该主题；恢复动作是标记为低质量 chunk，通知作者重写标题或正文。

## 问答测试样例

1. **正向问题**：H2 标题“实施流程”下有哪些步骤？**预期**：Agent 按 H3 顺序列出八到十步，并引用每个 H3 的 slug。
2. **正向问题**：这篇文档的主旨是什么？**预期**：Agent 直接引用 H1 文本，并说明 H2 下的主要主题域。
3. **边界问题**：H4 标题是否出现在导航中？**预期**：Agent 回答 H4 不进入 TOC，但如果正文中有 H4 内容，仍可检索到。
4. **边界问题**：如果一篇文档有两个 H1，应如何判断主题？**预期**：Agent 拒绝给出唯一主题，并说明这是违反单 H1 契约的错误。
5. **无证据拒答**：请解释“数据血缘”在这篇文档中的作用。**预期**：Agent 在 H1-H3 中未找到该术语，回答“本文未涉及该主题”，不编造。
6. **无证据拒答**：请列出所有 H3 标题的 slug 生成策略。**预期**：Agent 只引用文档中明确出现的策略，不扩展说明未定义的算法。

## 维护、版本、来源与相邻主题

本契约的版本与 Markdown 解析器、slug 库和向量分块器同步升级。当解析器升级后，必须重新跑一遍历史文档的校验，因为新的 AST 规则可能暴露旧文档中的层级跳跃。相邻主题包括：YAML frontmatter（负责元数据，不参与结构层级）、标签系统（横向分类，与标题层级无关但互补）、内部链接（依赖 slug 锚点）、块级代码示例（在 chunk 中作为正文内容，不影响标题层级）、以及分块策略（把标题结构转化为检索单元）。本文来源为项目级设计文档，不依赖外部系统；所有可验证细节均可通过 `pi-heading-policy.yml` 和构建流水线的 AST 输出复现。

## 结论

**事实**：H1 是文档根节点，H2 是主题域，H3 是子主题或操作步骤；H4 及以下不进入结构树；单 H1 和逐级递增是必须执行的硬规则。

**推论**：在多数 TypeScript/Web/本地文件知识库中，H1-H3 结构足以支撑摘要、分块和导航；把 H4 降级为正文能显著提升 chunk 稳定性。

**未知**：对于高度嵌套的 API 文档或法律规范，H3 是否足够仍需按项目用例测试；slug 在非 ASCII 标题中的稳定性取决于具体 slug 算法，需要单独验证。
