# 政策说明的架构化写作：适用范围、例外与解释边界的确定性设计

## 摘要与问题边界

政策说明是知识库中承载约束力的文档类型，其目标不是提供操作教程，而是划定哪些行为、哪些对象、哪些场景必须被纳入规则管辖。与其他说明性文档不同，政策说明必须回答四个不可回避的问题：适用主体是谁、例外条件如何被触发、最终审批人是谁、以及哪些解释路径被明确禁止。架构视角下的政策说明写作，要求将这四个问题先抽象为稳定的概念接口与责任边界，再选择具体的 Markdown 结构、校验工具或审批工作流。

在 TypeScript/Web 与本地文件知识库环境中，政策说明通常以 `.pi/policy/`、`AGENTS.md` 或 `docs/governance/` 下的 Markdown 文件存在。它们被检索器召回、被 Agent 引用，并可能在 CI 中被校验。因此，政策说明必须同时满足人类可读、机器可定位和语义可验证三重目标。本文围绕政策说明的架构模型展开，重点讨论如何通过明确适用范围、例外条款、审批人链与解释边界，避免政策在传播过程中被稀释或误读。

## 核心概念与数据模型

政策说明的知识结构可分解为以下七个可验证的实体：

1. **政策主体（Policy Subject）**：被规则约束的对象。在 Agent 知识库中，主体可以是具体角色（如 `api-developer`、`web-ui-maintainer`）、代码模块（如 `packages/pi-agent`）、或流程节点（如 `deploy-pipeline`）。主体必须在正文中以可标识的术语列出，不能仅靠标题暗示。

2. **适用范围表达式（Scope Expression）**：描述政策在何种条件下生效。应使用“当……时”“凡涉及……”等可转换为布尔判断的句式，避免“一般”“通常”等模糊副词。适用范围可以被编码为 frontmatter 中的 `scope` 字段，便于检索器按标签召回。

3. **例外条款（Exception Clause）**：明确哪些情况不受政策约束。每个例外必须包含触发条件、临时替代规则、以及谁有权确认该例外成立。例外不能写为“除非另有说明”这类空泛表述。

4. **审批人链（Approver Chain）**：记录政策的起草人、审核人与最终批准人。批准人必须是可标识的个体或角色，而不是“团队”或“相关人员”。审批人链用于追溯政策效力的来源。

5. **解释空间禁令（Interpretation Ban）**：列出不允许的解读方向。例如“本政策不得以‘默认允许’反向推导”“不得将‘建议’提升为‘强制’”。禁令条目是政策说明区别于普通指南的核心特征。

6. **版本与来源（Version & Provenance）**：包含政策版本号、生效日期、修订记录和来源引用。版本号应遵循语义化版本，修订记录至少说明“变更内容、变更原因、变更审批人”。

7. **相邻政策引用（Adjacent Policy Reference）**：指向与本政策互斥、互补或继承关系的其他政策文件。引用必须给出文件路径或稳定标识符，避免使用“参见安全策略”这类无法定位的描述。

## 设计决策与取舍

### 精确性优先于灵活性

政策说明不是设计草案，不允许用“建议”“推荐”替代“必须”“禁止”。在架构上，这意味着所有约束条款应优先使用 RFC 2119 风格的强制词汇，或在项目约定中定义等价词汇表。代价是政策文档需要更频繁地修订，但收益是 Agent 与检索器可以基于关键词进行高置信度召回。

### 人类可读与机器可解析的分离

 Markdown 正文保持自然语言，供人类阅读；frontmatter 或关联的 YAML 元数据承载结构化字段，供检索器与校验脚本使用。分离的代价是维护两份信息，需要 CI 检查二者一致性。收益是避免在正文中塞入过多机器语法，破坏可读性。

### 审批人实名化而非角色泛化

最终批准人应指向具体角色或个体，例如 `security-lead@project` 或 `tech-architect-x`。泛化表述如“由相关负责人审批”会导致解释空间无限扩大。架构上，审批人可替换为身份系统中的实际标识符，但接口必须是确定的。

### 静态声明为主、动态评估为辅

适用范围与例外尽量在文档中静态声明，而非在运行时由 Agent 自行判断。动态评估保留给明确的上下文条件，例如“当运行环境为 production 时”。静态声明便于版本控制和审计，动态评估需要配套的运行时证据。

### 本地来源优先、外部引用可替换

政策说明应优先引用本地文件或项目内部约定。外部引用必须附带访问日期与镜像路径，防止外部链接失效后政策失效。在架构上，外部来源被视为可替换的依赖，需要本地缓存或摘要。

## 可执行的实施流程

1. 识别政策意图：明确本政策要约束的具体风险或边界，避免写成原则宣言。
2. 定义政策主体：列出所有被约束的角色、模块或流程，给出可索引的标识。
3. 编写适用范围表达式：使用可布尔化的条件句，覆盖正常场景与常见边界场景。
4. 枚举例外条款：为每个例外写明触发条件、替代规则与确认人，禁止开放式例外。
5. 确定审批人链：指定起草人、审核人与最终批准人，记录审批日期。
6. 写入解释空间禁令：明确列出哪些解读方向被禁止，使用“不得”“禁止”等强制词汇。
7. 建立相邻政策引用：链接到相关文件，说明关系类型（互补、互斥、继承）。
8. 配置校验与召回测试：在 CI 中检查 frontmatter 完整性、术语一致性与问答召回率。

## 本地文件知识库示例：政策说明元数据与正文

以下是一个贴近 TypeScript/Web 知识库场景的 YAML 与 Markdown 组合示例。输入为项目根目录下的 `.pi/policy/agent-tool-allowlist.yaml` 与 `agent-tool-allowlist.md`。

```yaml
policy_id: POL-003
title: Agent 工具白名单政策
version: 1.2.0
effective_date: 2025-06-01
subjects:
  - role: api-developer
  - role: agent-runtime-maintainer
  - module: packages/pi-agent
scope:
  - when: 任何代码或配置向 Agent 注册工具时
  - when: 任何文档向 Agent 描述可用工具时
exceptions:
  - id: EXC-003A
    condition: 本地开发沙箱中临时调试
    fallback: 仍须记录于 debug.log
    confirmed_by: devops-lead@project
approvers:
  - drafter: security-lead@project
  - reviewer: tech-architect@project
  - approver: project-steward@project
interpretation_bans:
  - "不得以‘未明确禁止’推断某工具被允许"
  - "不得将只读工具的说明扩展为写权限"
  - "不得将本政策应用于非 Agent 会话的外部脚本"
adjacent_policies:
  - id: POL-001
    relation: complementary
    path: .pi/policy/project-trust.md
  - id: POL-002
    relation: superseded
    path: .pi/policy/legacy-tool-guide.md
```

```markdown
# Agent 工具白名单政策

本政策适用于所有向 Agent 注册或描述工具的代码与文档。任何工具的引入必须在白名单内明确列出，并标注读写能力。例外仅在本地开发沙箱中临时调试时成立，且必须由 devops-lead@project 确认并记录于 debug.log。

禁止以下解释：不得因本政策未提及某工具而推断该工具可用；不得将只读工具的说明扩展为写权限；不得将本政策应用于非 Agent 会话的外部脚本。
```

处理过程：检索器读取 `policy_id` 与 `subjects` 建立索引；Agent 在会话中收到工具相关查询时，按 `scope` 召回；CI 脚本校验 `approvers` 是否存在、版本是否递增、`interpretation_bans` 是否在正文中复现。输出为：召回列表、一致性报告、以及 Agent 引用时使用的政策摘要。

## 性能、质量与可观测性指标

1. **召回命中率**：在问答测试中，政策相关查询应被正确召回的概率。测量方法：构造 50 条覆盖主体、范围、例外与禁令的查询，统计 top-3 召回中包含正确政策的比例。

2. **范围表达式可布尔化率**：适用范围中能被解析为条件判断的条款占比。测量方法：人工或脚本检查每条范围句是否包含明确的主语、谓语与触发条件。

3. **例外条款完整率**：每个例外是否包含条件、替代规则与确认人。测量方法：统计 `exceptions` 列表中缺失字段的比例。

4. **审批人链可解析率**：`approvers` 字段是否包含有效标识符。测量方法：脚本校验标识符是否匹配项目成员列表或角色注册表。

5. **解释禁令一致性**：frontmatter 中的 `interpretation_bans` 是否在正文逐条复现。测量方法：文本比对或关键词匹配，允许同义改写，但不允许遗漏。

## 失败模式、诊断证据与恢复动作

1. **范围漂移**：政策标题为工具白名单，但正文大量讨论通用安全原则。诊断证据：正文关键词与 `scope` 字段的 Jaccard 相似度低于 0.3。恢复动作：删除无关内容，或将泛化内容迁移至相邻政策。

2. **例外无限扩大**：例外条款使用“等其他特殊情况”等开放式表述。诊断证据：`exceptions` 中存在未指定 `condition` 或 `confirmed_by` 的条目。恢复动作：将开放式例外拆分为具体条目，或明确写入“未列出的情况不适用例外”。

3. **审批人失效**：`approver` 指向已离职或角色已撤销的个体。诊断证据：标识符在项目成员列表中不存在超过 90 天。恢复动作：更新审批人链，重新审批当前版本。

4. **禁令被正文弱化**：frontmatter 中写入“禁止”，正文中使用“不建议”。诊断证据：情绪极性检测或强制词汇一致性检查失败。恢复动作：统一使用强制词汇，并重新走审批流程。

5. **相邻引用断裂**：引用的政策文件路径变更或删除。诊断证据：CI 中 `path` 字段对应的文件不存在。恢复动作：更新路径、移除引用或重构相邻政策。

## 问答测试样例

1. 正向问题：当 Agent 注册一个新的写工具时，应遵循哪条政策？期望召回 `POL-003`。

2. 边界问题：在本地开发沙箱中临时调试只读工具，是否需要记录日志？期望回答：是，必须记录于 debug.log，且由 devops-lead@project 确认。

3. 边界问题：本政策是否适用于非 Agent 会话的外部脚本？期望回答：不适用，解释空间禁令第三条明确排除。

4. 无证据拒答：如果某工具未被白名单提及，是否可以默认允许？期望回答：不能，必须以政策文本为依据，禁止以“未明确禁止”反向推断。

5. 无证据拒答：如果 devops-lead 未确认，本地调试例外是否自动成立？期望回答：不成立，例外确认人是必要条件。

6. 边界问题：当本政策与 `POL-001` 冲突时如何处理？期望回答：应参考 `adjacent_policies` 中的关系字段，本例中为互补，需同时满足二者。

## 维护、版本、来源与相邻主题关系

政策说明应纳入版本控制，与代码同仓管理。每次修订必须升级语义化版本，并在修订记录中说明变更原因。来源优先使用本地文件或项目内部决议；外部标准引用需附带镜像或摘要。相邻主题包括：项目信任模型（`project-trust`）、技能与提示词管理（`skills`）、工具注册规范（`tool-definition`）。政策说明与这些主题的关系通常是：政策说明定义约束边界，工具规范定义实现细节，信任模型提供执行语境。

## 结论

事实：政策说明是知识库中承载约束力的文档，必须包含适用范围、例外条款、审批人链与解释空间禁令。推论：通过 frontmatter 与正文分离、审批人实名化、解释禁令一致性检查，可以显著降低政策在传播与引用过程中的失真风险。未知：不同 Agent 运行时对强制词汇与解释禁令的理解深度存在差异，当前尚无统一标准衡量 Agent 是否会严格遵守写入的政策约束，需要持续通过问答测试与审计日志验证。
