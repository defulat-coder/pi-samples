# Markdown 运行手册的架构化写作

## 摘要与问题边界

运行手册（runbook）在 Markdown 知识库中不是静态操作说明，也不是事件复盘或产品需求文档，而是一组可被检索、引用并按顺序执行的恢复流程。它的问题边界只包含：触发条件的结构化描述、可重复的诊断步骤、幂等的恢复动作，以及可验证的恢复证据。部署脚本、凭证管理、人员值班表、SLO 定义、事故复盘等超出边界的内容应通过链接引用相邻主题，而不写入运行手册正文。

## 核心概念与数据模型

1. 触发事件（Trigger Event）。每个运行手册只对应一个主要触发事件，包含症状、严重程度、来源系统和环境指纹（如 Node 版本、包管理器、工作目录）。触发事件必须能被客观证据复述，不能依赖“系统感觉变慢”这类主观描述。

2. 运行手册单元（Runbook Unit）。每个单元对应一个独立的 Markdown 文件，具备稳定 URI（文件路径 + slug），标题可重命名但 URI 不变。单元是版本控制、全文检索和权限管理的最小粒度。

3. 流程步骤（Procedure Step）。步骤是有序列表中的原子项，包含动作类型（检查、命令、配置、等待）、超时时间、期望输出和失败后的回退分支编号。步骤默认串行，仅在显式标记为并行时才允许并发。

4. 诊断证据（Diagnostic Evidence）。任何判断都必须绑定可观测产物：日志片段、命令返回码、文件哈希、指标阈值或 API 响应字段。证据是步骤是否通过的唯一依据。

5. 恢复动作（Recovery Action）。恢复动作必须满足幂等性和可逆性，执行前声明前置条件，执行后声明后置条件。若无法回退，必须标记为“破坏性步骤”并触发人工确认，不能由 Agent 自动执行。

6. 验证门（Validation Gate）。验证门不是“看起来正常”，而是一组可自动比对的断言。例如 `pnpm typecheck` 返回 0，且产物目录存在、文件哈希与上次成功构建一致。

7. 接口契约（Interface Contract）。运行手册不直接调用 shell，而是引用能力受限的工具名（如 `read`、`search_knowledge`）。具体实现由 API 层注入，手册只描述输入参数和预期结果，保证实现可替换。

## 设计决策与取舍

### 文件优先于数据库

本地 Markdown 文件作为唯一事实源，索引仅用于加速检索。优点是可 Git 版本化、Diff 审查、离线编辑；缺点是语义召回需要额外索引。数量超过数百本时可引入数据库缓存，但 Markdown 文件仍保留为最终权威来源。

### 稳定 URI 优先于标题

标题可随产品演进重命名，URI 由目录结构和 slug 决定。引用时使用 URI 而非标题，避免同名不同文。移动文件会破坏引用，因此目录结构应受 ADR 约束，变更需搜索替换。

### 一触发一手册

每个运行手册只解决一个主要触发事件。多症状场景通过“相关手册”链接组合，不把所有步骤塞进同一文件，使检索更精确、变更影响范围更小。

### 命令式步骤与声明式元数据分离

Markdown 正文保存命令式执行顺序，文件头或 YAML 元数据保存声明式信息。Agent 先读元数据做路由，再按需加载正文，降低上下文消耗，也便于外部工具批量校验。

### 工具抽象边界

运行手册引用工具名而非具体命令，例如用 `read` 读取 `pnpm-lock.yaml`。工具实现可在本地、CI、测试中替换，代价是作者必须学习项目约定的工具集合和参数 schema。

## 可执行实施流程

1. 捕获触发事件：记录症状、来源、环境指纹和初始证据，形成结构化事件记录。
2. 检索候选手册：通过标题、标签、术语和摘要向量匹配候选运行手册，返回得分最高的 3 个并附带匹配理由。
3. 确认环境上下文：注入当前工作目录、Node 版本、包管理器、已加载技能和可用工具列表。
4. 加载并校验手册：检查必填元数据（触发条件、步骤、验证门）和内部链接完整性。
5. 按顺序执行步骤：每个步骤先检查前置条件，再执行动作，收集标准输出、返回码和文件变更。
6. 通过验证门：将实际输出与期望输出比对，输出差异作为下一轮诊断的证据。
7. 失败时进入回退或升级：若步骤失败且存在回退分支则执行；否则标记为需人工介入，并记录已尝试动作和当前状态。
8. 归档执行记录：保存输入事件、执行路径、验证证据和最终状态，用于后续复盘和模型微调。

## 示例：本地 TypeScript 类型检查失败的运行手册

以下 YAML 描述了一个运行手册的输入、处理与输出。输入为触发事件；处理为按序步骤；输出为验证证据。

```yaml
uri: runbooks/ts-typecheck-failure.md
trigger:
  symptom: "pnpm typecheck 返回非零退出码"
  severity: P1
  env_fingerprint:
    node: ">=20"
    package_manager: pnpm
    cwd: /repo
steps:
  - id: S1
    action: read
    target: tsconfig.json
    expected: "strict: true 存在"
    timeout: 5s
  - id: S2
    action: shell
    command: "pnpm tsc --noEmit"
    expected_exit_code: 0
    timeout: 120s
    rollback: S3
  - id: S3
    action: shell
    command: "git checkout -- tsconfig.json"
    destructive: false
validation:
  - assertion: "S2 exit_code == 0"
  - assertion: "dist/types 目录未缺失"
output:
  evidence:
    - path: tsconfig.json
      hash: sha256:abc123
    - exit_code: 0
      command: "pnpm tsc --noEmit"
```

在此示例中，输入是触发事件的结构化字段；处理是 `read` 与 `shell` 的串行步骤，失败时回退到 S3；输出是退出码和文件哈希，用于证明恢复真实发生。

## 性能、质量与可观测性指标

1. 检索召回率（Recall@3）。测量相关手册是否落在前 3 个候选中，通过人工标注的查询-手册对计算，目标值不低于 0.85。

2. 步骤首次通过率。统计执行中首次即通过验证门的步骤比例。低于阈值说明前置条件或期望输出描述不清，需要重写。

3. 平均恢复时间（MTTR）。从触发事件到所有验证门通过的时间差，按小时分桶观察趋势。异常峰值往往对应某一步骤超时配置不合理。

4. 误触发率。记录手册被选中但最终症状不匹配的事件数，用于发现标题或标签歧义。高误触发率意味着触发条件过于宽泛。

5. 证据覆盖率。检查每个步骤是否都声明了期望输出和可观测证据，缺失证据的步骤需打回重写，覆盖率目标为 100%。

6. 回退执行率。统计进入 rollback 分支的频率，过高说明前置检查不足或环境漂移严重。

## 失败模式、诊断证据与恢复动作

1. 环境指纹过期。诊断证据：手册要求 Node 18，但当前环境为 Node 20，命令行为发生变化。恢复动作：更新 env_fingerprint，新增版本条件分支，必要时要求人工确认。

2. 触发条件歧义。诊断证据：同一标题“构建失败”被类型检查和打包失败同时命中，导致选择错误手册。恢复动作：拆分手册，在触发条件中加入更具体的错误码或日志片段。

3. 缺少回退分支。诊断证据：某非只读步骤失败后运行手册直接终止，无 rollback 字段。恢复动作：为所有非只读步骤补充幂等回退，或显式标记为需升级。

4. 工具输出格式漂移。诊断证据：期望输出是 JSON 字段 `errorCount`，实际工具改为 `errors.length`，断言失败。恢复动作：在接口契约中声明 schema 版本，运行前校验并随工具升级同步更新手册。

5. 循环引用。诊断证据：手册 A 的“相关手册”指向 B，B 又指回 A，Agent 检索时反复横跳。恢复动作：构建引用图并拒绝有向环，强制相关手册形成 DAG。

## 问答测试样例

1. 正向问题：当 `pnpm typecheck` 失败时，运行手册首先读取哪个文件？ 答案：`tsconfig.json`，依据是示例中 S1 的 target 字段。

2. 正向问题：验证门要求什么退出码？ 答案：0，来自 validation 中的 `S2 exit_code == 0`。

3. 边界问题：若 S2 超时，系统会执行哪一步？ 答案：S3；若 S3 失败则升级到人。

4. 边界问题：当前 Node 版本为 22，而手册 env_fingerprint 要求 Node 20，是否直接执行？ 答案：不能，应触发环境不匹配分支或要求人工确认。

5. 无证据拒答：用户只问“为什么我的应用很慢”，未提供日志或指标，能否进入恢复流程？ 答案：不能。缺少诊断证据，运行手册无法被选择。

6. 无证据拒答：用户给出 `npm run build` 失败，但未说明返回码和 Node 版本，应如何回应？ 答案：要求补充返回码、package manager、Node 版本和 cwd，再匹配运行手册。

## 维护、版本、来源与相邻主题关系

运行手册应随代码一起版本化，Git 提交信息使用 `[runbook]` 前缀。重大变更更新 `last_reviewed` 和 `tested_with`，并在 `docs/adr/` 记录目录结构决策。来源包括线上事件、CI 失败记录、代码审查重复问题以及运行会话反馈。

与相邻主题的关系：运行手册引用故障排查指南以获取背景知识，引用部署脚本以执行环境变更，引用事件响应流程以决定何时升级到人。运行手册本身不应包含这些主题的具体内容，只保留入口链接和触发条件匹配规则。

## 结论

事实：运行手册是将触发条件、诊断步骤、恢复动作和验证证据写成顺序流程的 Markdown 单元，并通过工具抽象与实现解耦。推论：采用文件优先、稳定 URI、一触发一手册和命令式/声明式分离，能够让本地 TypeScript/Web 知识库长期保持可检索、可审查和可执行。未知：不同团队对手册粒度、破坏性自动步骤和 Agent 执行权限的接受度存在差异，需结合组织的信任边界、合规和审计策略进一步验证。
