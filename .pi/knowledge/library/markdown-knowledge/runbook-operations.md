# Markdown 运行手册：把触发、诊断、恢复、验证写成可执行的顺序流程

## 摘要与问题边界

运行手册不是系统说明文档，也不是故障复盘记录。它的核心任务是把一类可重复的异常场景压缩成一条可执行的顺序流程：在什么触发条件下开始、按什么顺序诊断、执行什么恢复动作、用什么证据验证结果。本文档面向需要观察性能、稳定性和故障恢复的工程师，要求每一步都附带可验证的边界与例外说明。超出范围的内容包括：事故沟通模板、根因分析报告、容量规划脚本、代码实现细节。

## 核心概念与数据模型

1. **触发条件**：必须是可观测事件或指标阈值，不能只写“系统慢”。例如“连续 5 分钟内 `http_request_duration_seconds:p95` 大于 500ms，且错误率高于 0.1%”。触发条件要注明数据来源、采样窗口、严重级别和抑制规则。
2. **诊断步骤**：按依赖关系排序，前一步的输出是后一步的输入。每一步必须写明预期输出、异常判断标准和超时时间。例如“`kubectl top pod` 返回的 CPU 使用率若超过 80% 则进入恢复分支，否则继续收集日志”。
3. **恢复动作**：包括主动作、回滚动作和幂等性声明。若动作可能影响持久数据或下游服务，必须标明爆炸半径和人工确认点。
4. **验证证据**：不能只看一次成功请求。必须记录成功证据、失败证据、延迟证据、容量证据和恢复时间证据。验证窗口通常不小于异常窗口的 1.5 倍。
5. **手册元数据**：包含 `runbook_id`、`version`、`owner`、`last_verified`、`environment`、`related_alerts`、`tags`。缺少元数据的手册无法被检索器可靠召回，也不适合 Agent 引用。
6. **决策节点**：流程中的分支点。每个分支必须给出明确判定条件，并记录实际选择的支路与理由。避免使用“视情况而定”这类不可执行描述。
7. **执行记录**：每次执行后留下的只读日志，包括时间戳、执行者、命令输出、判定结果和偏差说明。这些记录是后续更新手册的事实来源。

## 设计决策与取舍

### 顺序流程优先于纯分支图

运行手册以顺序流程为主，只在关键位置插入决策节点。原因是工程师在高压下更容易按顺序执行，但完全线性的流程会掩盖边界分支。取舍规则：当某个分支包含超过 3 个步骤或跨系统操作时，应拆成独立的子手册，并在主手册中引用。

### 证据密度与执行速度的平衡

收集证据会延长恢复时间，但证据不足会导致误判。约定：触发后 2 分钟内必须完成“触发是否真实”的验证；进入恢复动作前必须至少确认两类证据；验证阶段必须覆盖全部五类证据。不能因为追求速度跳过关键判定。

### 自动化与人工判定

已知模式、低爆炸半径的恢复动作可以自动化，但涉及数据删除、费用激增、跨服务变更时必须保留人工确认。自动化执行前后仍要记录日志，人工判定节点必须写明“如果满足 X 条件则继续，否则升级到 Y 渠道”。

### 版本控制与可读性

运行手册使用 Markdown 并纳入 Git 管理。为了保持 diff 可读，优先使用列表和短段落，避免大表格。当涉及多组命令输出时，使用独立小节而不是嵌套表格。版本号遵循 `major.minor.patch`：重大结构调整升级 major，环境适配升级 minor，错别字和输出样例更新升级 patch。

### 一册多环境还是环境隔离

推荐同一 `runbook_id` 通过变量替换覆盖多个环境，例如用 `{{ environment }}` 替换命名空间。但每个环境必须有独立的“最后验证日期”和已知差异清单。如果环境间命令差异超过 20%，则强制拆分手册，防止环境漂移造成误操作。

### 告警与手册的关联关系

告警应直接关联运行手册，但手册本身必须能独立执行。如果告警系统或指标平台不可用，工程师仍能从本地知识库和命令行获取足够信息。因此手册正文中不得只写“查看 Grafana 面板”，必须给出等价命令和输出样例。

## 可执行的实施流程

1. 收到告警或人工报告后，先确认触发条件是否真实：检查指标来源、采样窗口、基线阈值，排除误报和已抑制事件。
2. 确认执行环境就绪：权限、工具版本、VPN、凭证和访问入口。若环境不可用，记录为“前置条件不满足”并升级。
3. 采集基线证据：记录当前时间、受影响范围、服务版本、容量快照。这些证据将用于验证阶段的对比。
4. 按顺序执行诊断步骤，每步记录输出和耗时。若某步超时或返回异常，立即进入该步骤的例外分支。
5. 在决策节点对比证据与判定条件，选择分支，记录选择理由。如果证据不足，不得进入恢复动作。
6. 执行恢复动作，记录命令、参数、响应和副作用。若动作失败，按回滚方案执行；若回滚也失败，触发升级。
7. 进入验证阶段：依次检查成功证据、失败证据、延迟证据、容量证据和恢复时间证据。每项都给出量化阈值。
8. 若验证未全部通过，重复诊断或执行回滚，不能仅凭主观判断关闭事件。
9. 事件关闭后，在手册末尾追加执行记录：开始时间、结束时间、触发真实性、主要偏差、是否需要更新手册。
10. 定期演练：每季度至少执行一次非生产环境演练，验证命令和阈值是否仍然有效，演练结果同样作为版本更新依据。

## 贴近本地文件知识库的 JSON 示例

    {
      "runbook_id": "web-api-latency-spike",
      "version": "1.2.0",
      "environment": "prod",
      "trigger": {
        "source": "prometheus",
        "metric": "http_request_duration_seconds:p95",
        "threshold": "0.5s",
        "duration": "5m"
      },
      "diagnosis": [
        {
          "step": 1,
          "command": "kubectl top pod -l app=api",
          "evidence": "cpu/memory per pod"
        },
        {
          "step": 2,
          "command": "kubectl logs -l app=api --since=10m | grep -i timeout",
          "evidence": "timeout log count"
        }
      ],
      "recovery": {
        "action": "kubectl rollout restart deployment/api",
        "rollback": "kubectl rollout undo deployment/api"
      },
      "verification": [
        {
          "metric": "p95_latency",
          "operator": "<",
          "target": "0.5s",
          "samples": 10,
          "duration": "3m"
        },
        {
          "metric": "error_rate",
          "operator": "<",
          "target": "0.1%",
          "samples": 5
        },
        {
          "metric": "cpu_utilization",
          "operator": "<",
          "target": "80%"
        }
      ]
    }

**输入**：上述 JSON 存储在本地知识库 `runbooks/web-api-latency-spike.json` 中，由 TypeScript 服务通过 `fs.readFileSync` 读取并解析。Agent 检索时根据 `runbook_id` 和 `tags` 召回，并注入当前会话的 `environment` 变量。

**处理**：解析后，先校验触发条件是否满足；若满足，则按 `diagnosis` 顺序执行，每一步把命令输出写入执行日志。决策节点依据输出选择分支，再执行 `recovery.action`。执行结束后，用 `verification` 中的阈值和采样数判断恢复是否成立。

**输出**：生成一条执行记录，包括 `trigger_confirmed`、`diagnosis_results`、`recovery_action`、`verification_passed`、`total_duration`。若任一验证项未通过，输出 `rollback_recommended: true` 并附带失败证据。

## 性能、质量与可观测性指标

| 指标 | 测量方法 | 边界说明 |
|---|---|---|
| 触发到开始响应时间 | 告警时间戳与运行手册第一条执行记录时间戳之差 | 生产环境应 ≤ 5 分钟 |
| 诊断步骤平均耗时 | 每步开始与结束时间戳之差，按 runbook 聚合 | 单步超过 SLA 时标记为例外 |
| 恢复动作成功率 | 验证全部通过且无需回滚的执行次数 / 总执行次数 | 目标 ≥ 95%，低于 90% 触发手册审查 |
| 验证覆盖率 | 实际收集证据类型数 / 要求证据类型数 | 必须等于 5/5，否则视为未恢复 |
| 手册误操作率 | 因执行手册直接导致的二次故障数 / 手册执行次数 | 目标 < 1% |
| 平均恢复时间 | 触发确认到验证全部通过的时间跨度 | 按严重程度分档，P1 目标 < 30 分钟 |

## 失败模式、诊断证据与恢复动作

| 失败模式 | 诊断证据 | 恢复动作 |
|---|---|---|
| 触发条件误报 | 告警触发，但基线指标健康、无相关日志 | 调整阈值或窗口，增加抑制规则，重新标注触发条件 |
| 诊断步骤卡住 | 命令超过超时时间无返回，或返回非预期格式 | 强制超时后切换备选命令，若仍失败则升级 |
| 恢复动作部分成功 | 部分实例恢复，错误率仍高于阈值 | 针对剩余实例重复动作，检查依赖服务，必要时回滚 |
| 验证证据不足 | 仅一次成功请求或单一指标正常 | 扩展采样窗口，检查多个节点和多条指标，记录“证据不足” |
| 环境漂移导致命令失效 | 命令输出格式变更、字段缺失或参数弃用 | 固定工具版本为临时措施，更新手册并升 patch 或 minor |
| 权限缺失 | 执行返回 403 或 Unauthorized | 切换服务账号，使用应急凭证，更新权限清单 |

## 问答测试样例

**Q1**：收到 P95 延迟告警，第一步应该做什么？
**A1**：先确认触发条件真实性：检查指标来源、采样窗口、阈值和基线，排除误报后再进入诊断。

**Q2**：如果只有一个请求返回 200，是否可以认为服务已恢复？
**A2**：不能。必须至少采集成功证据、失败证据、延迟证据、容量证据和恢复时间证据，且采样覆盖多个实例和时间窗口。

**Q3**：手册中的命令已弃用，执行时返回“unknown flag”，怎么办？
**A3**：立即停止执行，记录实际输出与手册预期的差异，切换到备选命令，事后更新手册版本。

**Q4**：验证阶段部分指标通过、部分未通过，但主观感觉“已经好了”，可以关闭事件吗？
**A4**：不可以。未通过指标意味着恢复未成立，应回滚或继续诊断，直到所有验证项满足阈值。

**Q5**：告警系统不可用，无法获取指标，还能执行手册吗？
**A5**：如果手册提供了等价命令行证据，可以执行；若没有可验证证据，应拒绝盲目操作，记录“无证据”并升级。

**Q6**：运行手册没有覆盖当前现象，是否可以用最相似的手册替代？
**A6**：不能套用。应记录未知场景，触发新增手册流程，并升级给更高级别值班人员。

**Q7**：恢复动作可能影响下游支付服务，如何决策？
**A7**：先评估爆炸半径；若可能导致数据丢失或资金损失，必须引入人工确认；否则执行动作并严格验证。

## 维护、版本、来源与相邻主题

维护周期：每季度至少演练一次；每次重大变更、重大故障或环境升级后，必须审查相关手册；所有权按服务维度划分，(owner) 字段不能为空。

版本策略：采用语义化版本。`major` 表示结构或流程变更；`minor` 表示环境适配或新增分支；`patch` 表示样例更新、阈值微调和错别字。每次更新都要在 `CHANGELOG` 中说明触发原因和验证结果。

来源：运行手册的主要来源包括告警规则、SLO 定义、历史事故复盘、架构变更文档和代码仓库中的依赖清单。禁止从二手传闻或未验证的聊天记录中构建触发条件。

相邻主题关系：README 描述“系统是什么”；FAQ 回答“用户常见问题”；运行手册回答“在可观测异常下如何恢复”。架构决策记录（ADR）解释“为什么这样设计”，而运行手册解释“出现问题时如何操作”。事故指挥官手册关注沟通与协调，运行手册关注技术操作。三者可以互相引用，但不应合并。

## 结论

**事实**：运行手册由触发条件、诊断步骤、恢复动作、验证证据四部分组成；缺少任一部分，手册都无法被可靠执行；验证必须覆盖成功、失败、延迟、容量和恢复时间五类证据。

**推论**：结构化的顺序流程和强制验证能缩短真实恢复时间，并降低“只看一次成功请求”导致的虚假恢复风险。版本控制和定期演练能显著减少因环境漂移造成的手册失效。

**未知**：当前没有统一证据表明最优验证采样数和窗口长度；完全自动化与保留人工确认之间的最佳平衡点因组织而异；运行手册在复杂分布式系统中的长期维护成本与收益仍需结合具体场景持续度量。
