# Markdown 表格表达：把字段、决策、状态与对比从段落中抽离出来

## 摘要与问题边界

在知识库写作中，长段落擅长描述因果、背景与叙事，但容易把关键事实压进句子中间。当 Agent 或读者需要快速确认字段、判断状态、比较方案时，段落不是最优容器。表格表达的核心职责是把具备“行-列”正交结构的事实从 prose 中抽出来，使同一维度下的取值能够对齐扫描。

本主题的问题边界限于：在 Markdown 为主的本地文件知识库中，如何用表格承载字段、决策、状态与对比四类信息，并保证这些表格可被人工阅读、可被工具解析、可在版本演进中保持语义稳定。不讨论：表格的可视化样式、富文本编辑器实现、复杂嵌套关系的数据库建模、把表格当作代码执行载体。

关键判断：只有当一组事实共享同一组维度，并且每个单元格可以单独作为答案被引用时，才值得用表格承载。否则，应保留段落或使用列表、示例代码等其他结构。

## 核心概念与数据模型

1. 字段行（Field Row）：把实体属性拆成“属性名、取值类型、约束、来源”等列。每一行代表一个可独立验证的事实。例如 API 设计中的字段表，一行即一个属性定义。
2. 决策表（Decision Table）：用条件、规则、优先级、结果四列描述分支。它把“如果 A 则 B”的多个段落压缩成可逐行检查的矩阵，减少遗漏。
3. 状态矩阵（State Matrix）：行是实体，列是状态或事件，单元格填写合法转换或副作用。它避免状态机规则散落在多处段落中。
4. 对比表（Comparison Table）：行是候选方案，列是评估维度。单元格必须给出可验证的取值或评分，而不是主观口号。
5. 表头即接口（Header as Interface）：表头名称、顺序、对齐方式构成了表的公开契约。下游解析器依赖表头定位字段，因此表头一旦确定，应视为接口变更。
6. 表间引用（Table Cross-Reference）：表格不应是孤岛。每张大表应通过锚点或命名与段落、代码示例、清单建立关联，例如“字段定义详见表 3-1”。
7. 可解析单元（Parseable Cell）：每个单元格的内容应能被工具按列语义处理。例如枚举值用逗号分隔，引用值用统一标识符，避免混合自然语言与代码片段。

## 设计决策与取舍

### 1. 表格优先还是段落优先

优先使用表格的场景：同一实体有 3 个以上同构属性、存在多个互斥方案需横向对比、状态转换规则有 2 个以上维度。优先保留段落的场景：历史背景、设计动机、因果关系、一次性例外说明。边界判断：当读者为了回答“X 支持哪些取值”需要在段落中跳读 5 次以上时，应改为表格。

### 2. 列名稳定性与可读性

列名应使用英文标识符或中英混合的固定术语，避免口语化同义词。可读性不应以牺牲解析稳定性为代价。例如“是否必填”和“必填”不应在不同表中交替出现。取舍：一旦下游工具解析过该表，修改列名必须同步更新解析器或提供映射表。

### 3. 单一表与多表拆分

单表适合维度固定、行数不超过 20 的场景。超过 20 行或列数超过 6 时，应拆分为子表，并通过表头分组或链接保持语义。例外：决策表允许列多但行少，因为每一行是一个完整规则。

### 4. 手动维护与程序化生成

表格初始由作者手动编写，确保语义准确。当表格反映的数据源是频繁变动的运行时信息（如错误码列表、版本矩阵）时，应使用脚本从单一事实源生成，并在 CI 中校验“生成结果与 Markdown 文件一致”。

### 5. 表格与 YAML/JSON 的单一事实来源

如果同一份知识同时出现在表格和 YAML/JSON 配置中，必须指定其中一方为源。通常做法：静态设计约束以 Markdown 表格为源，运行时配置以 YAML 为源，CI 检查两者一致性。不允许两者独立修改而不同步。

## 可执行的实施流程

1. 梳理当前文档中适合表格化的段落，标记字段、决策、状态、对比四类候选。
2. 为每一张候选表定义主键列和维度列，主键列应能唯一标识一行。
3. 选择表类型：字段表、决策表、状态矩阵或对比表，并确定表头。
4. 在 Markdown 中先写出最小表，确保表头、分隔线、数据行对齐。
5. 用锚点（如 `<a name="tbl-field-def"></a>`）或标题 ID 为表格建立可引用位置。
6. 在段落中显式引用表格，避免“如下表所示”这类无法定位的表述。
7. 编写解析器单元测试，验证表头顺序、必填列、枚举值范围。
8. 在 CI 中加入表格 lint 规则：检查表头是否变更、必填单元格是否为空、是否存在跨表同义列名。
9. 将表格变更纳入版本控制记录，并在每次 PR 中说明“新增/删除/修改列”。
10. 发布前检查渲染效果，确保在 Web 和编辑器中横向可读。

## 示例：本地文件知识库中的表格表达

输入：一篇 Markdown 文件中的字段定义表。

    | 字段 | 类型 | 必填 | 取值范围 | 来源 |
    |------|------|------|----------|------|
    | id | string | 是 | 本地唯一标识 | 文件系统 |
    | status | enum | 是 | draft, published, archived | 业务规则 |
    | lastModified | ISO 8601 | 否 | 时间字符串 | 编辑器元数据 |

处理：项目中的 `markdownTableToRecords` 函数按行切分，去掉第二根分隔线，将 `|` 分割后的单元格按表头映射为对象数组。同时校验 `status` 列必须只包含枚举值。

输出：JSON 对象。

    {
      "tableId": "tbl-file-metadata",
      "headers": ["字段", "类型", "必填", "取值范围", "来源"],
      "rows": [
        { "字段": "id", "类型": "string", "必填": "是", "取值范围": "本地唯一标识", "来源": "文件系统" },
        { "字段": "status", "类型": "enum", "必填": "是", "取值范围": ["draft", "published", "archived"], "来源": "业务规则" }
      ]
    }

该示例说明：表格为输入，解析器为处理边界，JSON 为可被检索器和 Agent 消费的输出。

## 性能、质量、可观测性指标

1. 表格覆盖度：统计文档中“可被表格化但仍在段落中”的事实数，目标每月下降。测量方式：维护一组测试查询，若答案藏在段落而非表，则记一次遗漏。
2. 表头一致性：跨文档同义列名数量。目标值为 0。测量方式：解析所有表头，聚类相似度高于 0.85 的列名对。
3. 解析成功率：自动化工具能够无警告解析的表格比例。目标 > 98%。测量方式：CI 运行 `parseAllTables` 并记录失败表。
4. 检索召回率：针对表格内容的标准问答，前 3 个检索结果命中目标表的比例。目标 > 90%。测量方式：使用固定测试集运行 `search_knowledge`。
5. 语义漂移率：版本之间表头或主键列发生无说明变更的次数。目标每季度 < 1 次。测量方式：对比相邻版本 Markdown 的 AST 表头差异。
6. 渲染可读性：在 1280px 宽度下无需横向滚动即可完整显示的表格比例。目标 > 95%。

## 失败模式

1. 表头漂移：下游解析器期望列“必填”，作者改为“是否必填”，导致工具失败。诊断证据：解析测试报错 `Missing required column: 必填`。恢复：统一列名，并在解析器中维护别名映射，优先选择标准列名。
2. 事实重复与冲突：段落与表格对同一字段给出不同取值。诊断证据：单元测试断言失败或 QA 测试结果不一致。恢复：以表格为单一事实来源重写段落，或显式说明例外。
3. 过度细化：表格行数超过 50 行且频繁变更，维护成本高于收益。诊断证据：连续 3 次 PR 仅修改表格。恢复：拆分子表或改为从数据源生成。
4. 列名歧义：不同主题使用同名列但语义不同，例如“状态”在文档 A 表示生命周期，在文档 B 表示运行状态。诊断证据：检索结果把无关表召回。恢复：命名空间化列名，如“文档状态”、“任务状态”。
5. 合并冲突破坏结构：Git 合并时破坏 Markdown 表格的对齐线，导致渲染错位。诊断证据：Markdown 渲染器显示表格错乱，或 lint 失败。恢复：引入合并前格式化钩子，强制对表格执行统一格式化。
6. 大表在 Web 渲染时横向溢出：列数过多导致移动端无法阅读。诊断证据：渲染可读性指标低于阈值。恢复：拆分为可折叠子表或提供横向滚动提示。

## 问答测试样例

1. 正向：请问 `status` 字段的取值范围是什么？证据：示例表格中的取值范围列给出 `draft, published, archived`。答案应列出这三个值。
2. 正向：决策表中“用户未登录且访问公开资源”的结果是什么？证据：决策表对应行。答案应给出准确结果。
3. 边界：当表格未列出 `deleted` 状态时，是否意味着该状态不存在？答案：仅表示当前文档未将 `deleted` 纳入取值范围；若存在其他权威来源，应引用该来源，不可臆断。
4. 边界：字段表中的“必填”是否对草稿文件也生效？若表格未说明阶段例外，则拒答：表格未提供阶段相关证据，请查看状态矩阵或业务规则。
5. 无证据拒答：表格是否支持嵌套子表？若正文中未提及，应回答：当前知识库未提供关于嵌套子表的设计信息，无法判断。
6. 无证据拒答：对比表中方案 A 的维护成本如何？若表格只有“性能”和“兼容性”列，没有“维护成本”列，应回答：表格未包含维护成本维度，无法从给定文档得出。

## 维护、版本、来源与相邻主题

维护责任：知识作者负责表格语义准确；API/工具团队负责解析器与 lint 规则；前端负责渲染适配。版本策略：表格结构变更遵循破坏性变更标记；新增列视为非破坏性，删除列或修改列名视为破坏性，必须更新解析器与测试。来源：表格内容应引用可验证的来源，如代码类型定义、设计文档、会议纪要，避免引用外部链接作为唯一来源。相邻主题：与“Markdown 列表表达”相邻，列表适合顺序、层级与 todo；与“搜索知识”相邻，表格为搜索提供结构化段落；与“提示模板”相邻，表格可被注入为少样本示例；与“版本控制”相邻，表格是 diff 敏感对象。

## 结论

事实：Markdown 表格能够有效承载字段、决策、状态与对比四类正交信息；表头构成解析契约；同一事实不应在段落和表格中独立维护。

推论：当表格行数超过 20 或列数超过 6 时，拆表或程序化生成通常比单表维护成本更低；检索器和 Agent 对表格的召回准确率高于同等信息的 prose 段落。

未知：不同渲染器对表格对齐、换行、特殊字符的处理差异是否会影响解析器一致性；超长表格在移动端的最佳交互形态；在表格中表达多语言术语时，检索器应以哪种语言为索引主键。
