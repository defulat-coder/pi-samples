# 在 TypeScript 知识库中用 Markdown 表格表达字段、决策、状态与对比

## 摘要与问题边界

本文面向需要把方案落成 TypeScript 代码的开发者，描述在本地 Markdown 知识库中如何用表格表达字段、决策、状态与对比。输入是仓库中的 `.md` 文件；输出是类型化的记录数组、验证报告和可检索索引；错误通过行号回指到源文件。问题边界限定为：只处理 GitHub-Flavored-Markdown 风格、由 `|` 分隔的表格，不支持合并单元格、HTML 表格或 Mermaid 图表。目标是让关键事实以结构化行列形式存在，而不是 buried 在长段落中。

## 核心概念与数据模型

1. **表头契约（Header Contract）**：表格第一行是列名集合，决定列顺序；列名必须非空，重复列名在解析阶段直接报错，不隐式合并。
2. **分隔行（Delimiter Row）**：第二行只能由 `---`、`:---`、`:---:`、`---:` 四种对齐标记组成，用于分隔表头与数据，并携带列对齐语义。
3. **行实体（Row Entity）**：从第三行起每行是一个元组，单元格数量必须等于表头列数；缺失单元格用空字符串占位，禁止用 `<br>` 拆分单元格。
4. **列类型（Column Type）**：通过 `.pi/schemas/table-types.yaml` 或相邻说明声明，如 `status: enum(adopted | trial | rejected)`，在 TypeScript 阶段生成字面量联合类型。
5. **对齐语义（Alignment Semantics）**：`:---` 表示左对齐，`:---:` 表示居中，`---:` 表示右对齐；右对齐是数值列的提示，但解析时不强制类型转换。
6. **关系索引（Relation Index）**：每行默认以第一列作为隐式主键，用于与列表、段落或其他表格建立交叉引用；重复主键视为数据冲突。
7. **错误生命周期（Error Lifecycle）**：语法错误、列数错误、类型错误、主键冲突、引用缺失按阶段收集进 `ValidationResult`，而不是直接抛出异常。

## 设计决策与取舍

### 严格表头还是容错解析

优先严格表头。如果表头缺少分隔行或分隔行不符合对齐模式，直接标记为 `MISSING_DELIMITER_ROW` 语法错误，不降级为普通文本。优点是结果可复现、类型声明可精确生成；缺点是手写时偶尔忘记分隔行会报错。容错仅允许表头前后存在空列和多余空格，CI 中关闭宽松模式。

### 单表多主题还是一表一主题

强制一表一主题。一个表格只表达一种实体：字段、决策、状态或对比。混合主题会导致列类型不一致，搜索召回率下降。边界例外：当需要横向比较多个方案时，使用“对比矩阵”，每行是一个方案，每列是一个评估维度，这仍被视为单一“对比”主题。

### 纯文本表格还是 AST 持久化

Markdown 源文件保留纯文本，便于版本控制和人工编辑；解析后写入索引或缓存时保存带行列坐标的 AST，便于错误回指和后续定位。代价是写入阶段多一次序列化，但消费端获得统一的 `TableNode` 结构。

### 列对齐的语义是否参与验证

对齐标记只作为 lint 提示，不参与强类型验证。右对齐列中写字符串不会阻断解析，但会产生 `ALIGNMENT_TYPE_HINT` 警告。原因是：对齐反映作者意图，不应因格式错误阻止数据消费；同时保留提示，方便 Code Review 时发现类型与格式不一致。

### 表格与列表混排的策略

表格承载紧凑事实，列表承载展开解释。表格正下方可跟一个无序列表，为每行提供详细说明，列表项通过锚点或主键值与行对应。不允许在表格中间插入段落，否则行连续性被破坏，解析器会停止在该表格。

## 可执行的实施流程

1. **输入收集**：读取 `.md` 文件，按段落边界扫描，识别以 `|` 开头且至少包含一个分隔行的段落为候选表格。
2. **词法切分**：按行切分，以 `|` 为分隔符，去掉首尾空单元格，保留转义 `\|` 为普通单元格内容。
3. **表头规范化**：移除列名首尾空格，统一大小写规则；若项目配置 `caseSensitiveHeaders` 为真，则保留原样，否则转换为小写。
4. **分隔行验证**：检查第二行是否全部为合法对齐标记；否则生成语法错误并停止该表格解析。
5. **结构验证**：逐行比较单元格数量与列数；不一致行生成 `ColumnMismatchError`，包含行号和期望列数。
6. **类型推断与绑定**：根据表头名称或 `.pi/schemas/table-types.yaml` 将单元格映射到 TypeScript 类型；枚举值不在声明集合中时报错。
7. **行级校验**：校验第一列主键是否唯一、必填列是否为空、引用列是否指向已知文件或锚点。
8. **索引与转换**：把有效表格转换为 JSON 数组，写入索引；生成 TypeScript 类型声明到 `packages/contracts/src/tables/`；返回包含错误和统计的 `ValidationResult`。

## 代码示例：本地文件决策表

以下示例来自 `.pi/decisions/auth-method.md`，展示输入、处理与输出。

输入：

    | 决策项 | 候选方案 | 状态 | 影响范围 | 验证脚本 |
    |---|---|---|---|---|
    | 认证协议 | OIDC | 已采纳 | packages/auth | test/auth/oidc.spec.ts |
    | 会话存储 | Redis | 试验中 | apps/api | test/api/session.spec.ts |

处理：解析器先确认表头有五个非空列，分隔行全为 `---`，然后按行切分。`状态` 列通过 `.pi/schemas/table-types.yaml` 声明为枚举 `adopted | trial | rejected`，因此把“已采纳”映射为 `adopted`，把“试验中”映射为 `trial`。

输出：

    interface DecisionRow {
      item: string;
      candidate: string;
      status: 'adopted' | 'trial' | 'rejected';
      scope: string;
      verification: string;
    }

    const decisions: DecisionRow[] = [
      { item: '认证协议', candidate: 'OIDC', status: 'adopted', scope: 'packages/auth', verification: 'test/auth/oidc.spec.ts' },
      { item: '会话存储', candidate: 'Redis', status: 'trial', scope: 'apps/api', verification: 'test/api/session.spec.ts' }
    ];

## 性能、质量和可观测性指标

1. **解析耗时**：对单文件内所有表格解析计时，目标中位数小于 10 毫秒；在 `pnpm test` 中通过 `performance.now()` 测量。
2. **表头一致率**：统计版本 diff 中表头是否发生未声明变更；目标小于 5% 的表格在补丁中发生表头变更。
3. **验证错误率**：每百行中语法、类型、主键错误数；CI 目标为 0。
4. **搜索召回率**：给定字段名，检索是否能召回包含该字段的表格；通过固定查询集和单元测试测量。
5. **渲染一致性**：同一份源文件在 Web 列表与 API 返回中单元格数量一致；通过 diff 行数与列数断言。
6. **类型覆盖率**：已声明类型的列占所有列的比例；核心表目标达到 100%。

## 失败模式

### 表头缺少分隔行

诊断证据：解析器找不到第二行对齐分隔行，错误码 `MISSING_DELIMITER_ROW`。恢复动作：在表头下方插入 `|---|---|---|`，并重新运行 `pnpm typecheck`。

### 列数不一致

诊断证据：某行单元格数与表头列数不符，错误包含行号与期望列数。恢复动作：检查该行是否漏写 `|` 或在单元格中使用了未转义的 `|`。

### 重复主键行

诊断证据：第一列值重复，错误码 `DUPLICATE_PRIMARY_KEY`。恢复动作：合并两行、删除重复行，或把主键改为复合主键。

### 对齐标记与数据类型冲突

诊断证据：数值列未右对齐，产生 lint 警告 `ALIGNMENT_TYPE_HINT`。恢复动作：若数据确实是数值，改为 `---:`；若是字符串，保持 `---` 并忽略警告。

### 表格外混入解释性长段落

诊断证据：表格与说明段落之间出现未通过列表锚点关联的长段落，导致搜索召回时相关说明无法与行绑定。恢复动作：把长段落改为表格下方的列表项，并在列表项中引用行主键。

## 问答测试样例

1. 正向问题：状态为“已采纳”的决策项有哪些？
   答案：认证协议。证据是 `.pi/decisions/auth-method.md` 第二行 `status` 单元格。

2. 正向问题：会话存储的验证脚本路径是什么？
   答案：`test/api/session.spec.ts`。可直接从表格最后一列读取。

3. 边界问题：如果一行缺少 `状态` 值，解析器是否允许？
   答案：不允许，必填列为空会触发 `REQUIRED_CELL_EMPTY`，除非模式声明该列可空。

4. 边界问题：表格中能否使用合并单元格？
   答案：不能，项目边界明确排除合并单元格；出现 `>` 或 `<` 标记会按普通文本处理。

5. 无证据拒答：这些决策是谁在何时做出的？
   答案：无法回答，表格本身没有记录作者和决策时间；需查询相邻段落或版本历史。

6. 无证据拒答：当前表格是否覆盖了所有微服务的认证方案？
   答案：无法回答，表格只列出文件内出现的方案，未声明全局完备性。

## 维护、版本、来源和与相邻主题的关系

维护：表格模式变更必须同步更新 `.pi/schemas/table-types.yaml` 和 `packages/contracts/src/tables/` 类型声明；CI 中运行 `pnpm typecheck` 防止漂移。废弃的表头列应保留至少一个版本，并在 ADR 中记录迁移路径。

版本：知识库表格按 Markdown 文件版本管理；类型声明与模式文件版本号遵循仓库语义化版本；重大表头变更需走 ADR 流程。

来源：字段、状态和对比数据来自项目代码、设计评审会议纪要和测试用例；来源引用以验证脚本路径或文档锚点形式写入表格。

相邻关系：与 `frontmatter` 主题共享模式声明入口；与 `列表表达` 主题形成主从关系，表格承载事实，列表承载解释；与 `Mermaid 图表` 主题互不替代，图表用于时序和依赖，表格用于字段和状态。

## 结论

事实：Markdown 表格由表头、分隔行和行实体组成，是表达字段、决策、状态和对比的紧凑结构；TypeScript 消费端需要显式表头契约、类型绑定和主键唯一性。

推论：把关键事实从长段落迁移到表格后，搜索召回、类型校验和测试覆盖都会提升，前提是项目强制实施一表一主题和严格分隔行。

未知：不同 Markdown 方言对嵌套表格、HTML 转义和任务列表的支持差异，尚未在本项目边界内验证；超大型表格（千行以上）对解析性能和索引存储的影响仍待实测。
