# OKF 知识治理中的格式迁移：以身份与引用稳定性为中心的架构方法

## 摘要与问题边界

格式迁移在 OKF 知识治理中的核心任务，是把概念记录从旧字段或旧目录搬迁到新结构，同时保证全局标识、引用闭包和内容语义不因结构变化而断裂。它不是一次性的文件拷贝，也不是一次 schema 升级发布会，而是一组受控的、可回滚的、留下审计痕迹的身份图变换。

本主题的范围严格限定在三件事：标识（ID）如何跨格式保持唯一与可解析；引用（reference）如何在字段或目录变化后仍然指向正确的目标；内容语义（content semantics）如何在字段拆分、合并、重命名或类型转换后不发生隐性漂移。它不负责运行时的渲染策略、权限继承、搜索相关性调优，也不承诺新 schema 在用户体验上必然优于旧 schema。所有输入被视为旧知识库快照、字段映射规则、命名空间表和语义等价断言；输出则是新目录、映射日志、变更清单和回滚包。迁移一旦进入执行阶段，旧目录必须被冻结为只读，直到验收完成并正式切换写入点。

## 核心概念与数据模型

1. **Concept Record（概念记录）**。每条知识的最小迁移单元，包含全局唯一 URI 形式的 `id`、面向 URL 的 `canonical slug`、多语言 `label map`、语义类型标签，以及覆盖全部可迁移字段的 `content fingerprint`。ID 在格式迁移中通常保持不变，除非出现命名空间冲突或隐私泄露等例外。

2. **Field Slot（字段槽位）**。描述一个字段在旧 schema 和新 schema 中的地址，包括点分路径、数据类型、基数（单值/数组/映射）、可重复语言标签和默认值来源。Field Slot 不承载语义判断，只承载位置与结构信息。

3. **Reference Edge（引用边）**。由 `source id`、`target id`、`relation kind`、`provenance pointer` 和 `is_required` 布尔值组成。它记录了“谁引用了谁、以什么关系、从哪条旧字段产生”。迁移后，source 和 target 的 ID 必须仍然解析成功，relation kind 的语义保持不变。

4. **Namespace Mapping（命名空间映射）**。旧命名空间前缀到新命名空间前缀的转换表，附带生效版本戳和冲突裁决策略。它解决的是 URI 中域或路径前缀的变化，不替代字段级映射。

5. **Semantic Equivalence Assertion，SEA（语义等价断言）**。对旧字段值与新字段值是否语义等价的判定记录，包含判定者、判定时间、置信度和判定依据。任何 1:N、N:1、类型转换或默认值填充都必须有 SEA；纯 1:1 同类型同语名字段可由规则自动生成低置信度 SEA，但须经审核。

6. **Migration Delta（迁移增量）**。单条记录的迁移原子记录，包括旧内容的指纹、新内容的指纹、操作类型（keep / map / split / merge / deprecate）、受影响的引用边集合，以及指向回滚包中原始文件副本的 `rollback token`。

## 设计决策与取舍

### ID 稳定性优先于目录结构优雅

目录路径和文件组织可以重新设计，ID 必须尽量保留。ID 是引用闭包的关键锚点；一旦 ID 改变，所有外部引用、书签、深层链接和缓存键都会失效。只有在旧 ID 违反新命名空间规则、发生全局冲突，或包含需要脱敏的隐私信息时，才允许重新分配 ID，并必须在 `redirect_map.json` 中建立旧 ID 到新 ID 的永久重定向。

### 字段映射显式表优于自动推断

自动推断只适用于类型相同、语义标签相同、基数相同的 1:1 字段。任何涉及拆分、合并、单位转换、markdown 到结构化块的转换，都必须写入字段映射表并由 SEA 覆盖。禁止依赖默认值“看起来一样”的隐式映射，因为同样的字符串在不同 schema 下可能代表不同的人名、标签或计算值。

### 引用重写成两阶段

第一阶段只读地收集整个知识库的引用闭包，检测悬空引用、循环引用和孤儿节点；第二阶段才按拓扑顺序重写引用并写入新目录。第一阶段失败不得进入第二阶段，避免产生半成品的引用图。循环引用按节点 ID 字典序打破循环，确保每个节点的引用边都被处理且不会无限递归。

### 内容语义校验用结构指纹而非字符串相等

标题、正文、元数据分别计算结构指纹，忽略空白、字段顺序和缩进差异，但不允许改变 prose 语义或丢失可翻译字符串。例如，把 `article.body.markdown` 转成 `concept.content.blocks[]` 后，正文指纹必须一致；如果迁移器错误地去掉了脚注或代码块，指纹校验会立即失败。

### 回滚包与正迁包必须原子交付

迁移脚本同时产出 `forward bundle` 和 `rollback bundle`。验收通过前，旧目录保持主写入点；验收通过后，才切换写入点并封存旧目录。回滚包必须包含所有被修改文件的原始字节、原始时间戳和原始权限，缺一不可，否则无法在法律或合规层面证明迁移的可逆性。

## 可执行的实施流程

1. **冻结旧目录写入**。通过文件系统只读标记或版本控制分支锁，禁止旧知识库再接受新提交，确保快照一致性。

2. **导出旧知识库快照**。保留原始字节顺序、文件时间戳和目录结构，快照本身不提前做任何规范化处理。

3. **加载并验证 schema 与命名空间表**。检查目标 schema 版本、字段槽位定义、命名空间前缀是否冲突，若有冲突先返回配置错误。

4. **构建概念图与引用闭包**。读取所有 Concept Record，解析 Reference Edge，标记悬空引用、孤儿节点和循环引用。

5. **生成字段映射草案**。列出 1:1、1:N、N:1、删除字段和新增字段，并对非 1:1 字段打上待审核标记。

6. **人工或规则审核 SEA**。对任何非 1:1 映射、类型转换或默认值填充签署语义等价断言，低置信度断言必须经第二人复核。

7. **执行两阶段迁移**。第一阶段预演生成 delta 报告；第二阶段在确认无异常后写入新目录并重写引用。

8. **运行语义校验**。对比旧内容与新内容的结构指纹，验证引用闭包完整性，确认无悬空引用。

9. **生成映射日志、回滚包和变更清单**。所有输出放入版本控制，并与迁移任务单关联。

10. **验收与切换写入点**。在维护窗口确认未处理 delta 为空后，才将主写入点切换到新目录，并封存旧目录为只读归档。

## 贴近 TypeScript / Web / 本地文件知识库的示例

下面的迁移清单描述了一个本地 Markdown 知识库从旧格式 `legacy.docs/v2` 迁移到 `okf.kg/v3` 的配置：

    migration_id: okf-kg-fmt-2025-q3
    source_namespace: legacy.docs/v2
    target_namespace: okf.kg/v3
    id_policy:
      stable: true
      redirect_on_conflict: true
    field_map:
      - legacy_path: article.meta.author_name
        target_path: concept.authors[].name
        sea:
          confidence: 1.0
          judge: schema-committee
      - legacy_path: article.body.markdown
        target_path: concept.content.blocks[]
        sea:
          confidence: 0.85
          judge: parser-v3
    reference_rewrite:
      - relation: cites
        old_prefix: legacy.docs/v2
        new_prefix: okf.kg/v3
    output_artifacts:
      - new_tree/
      - delta_log.jsonl
      - rollback_bundle.tar
      - redirect_map.json

**输入**：旧目录 `legacy-docs/` 中包含 Markdown 文件与 YAML 前置元数据，文件间通过相对路径和 `cites:` 列表相互引用。
**处理**：迁移器读取每篇文章，把 `article.meta.author_name` 映射到 `concept.authors[].name`，把正文 Markdown 解析成结构化块数组，同时把 `cites` 关系里的旧前缀全部替换为新前缀，但保留目标 ID 的本地部分。
**输出**：`new_tree/` 存放新格式文件；`delta_log.jsonl` 记录每条记录的操作类型与指纹；`rollback_bundle.tar` 保存所有原始文件；`redirect_map.json` 保存 ID 重定向表，供 Web 路由或反向链接服务使用。

## 性能、质量与可观测性指标

1. **引用闭包损失率**。迁移后，所有新目录中的引用边必须能在概念图中解析到目标节点。通过图遍历脚本测量，目标为 0%。

2. **字段未映射率**。旧字段值未进入任何新字段且未在映射表中声明删除的比例。从 `delta_log.jsonl` 统计，目标为 0%。

3. **SEA 低置信度占比**。置信度低于 1.0 的断言数量除以总断言数量。若超过 5%，必须暂停迁移并补充人工审核。

4. **端到端迁移耗时**。从快照导出到验收完成的时间，按文件数或记录数标准化，用于评估工具链效率。

5. **回滚包完整性**。通过校验和验证 `rollback_bundle.tar` 是否包含所有被修改文件的原始字节。缺失任何文件即视为失败。

6. **语义漂移率**。在相同快照上重复执行迁移，比较两次输出的结构指纹一致率。低于 100% 说明迁移器存在非幂等或随机行为。

## 失败模式、诊断证据与恢复动作

1. **命名空间冲突**。两个旧 ID 映射到同一个新 ID。诊断证据：`delta_log.jsonl` 中出现 `duplicate_target_id` 记录。恢复动作：启用 `redirect_on_conflict`，对其中一个旧 ID 分配新 ID 并在 `redirect_map.json` 中保留永久重定向。

2. **悬空引用**。引用边指向的目标不存在于快照中。诊断证据：第一阶段引用闭包报告中 `unresolved_refs` 非空。恢复动作：要么在旧知识库中补充缺失目标，要么把该引用降级为 `deprecated stub`，不能让它在新目录中默默失效。

3. **字段隐式丢失**。旧字段未出现在映射表且无删除声明。诊断证据：`unmapped_fields` 报告非空。恢复动作：补充字段映射和 SEA，或显式声明该字段被弃用。

4. **内容语义改变**。迁移后结构指纹与旧内容不一致。诊断证据：`semantic_check` 阶段出现 `fingerprint mismatch`。恢复动作：立即使用回滚包还原，修正转换器后重新迁移，不得在指纹不一致时切换写入点。

5. **写入点提前切换**。验收未完成就有人把新目录切为主写。诊断证据：旧目录出现新写入，但 `delta_log.jsonl` 未包含对应记录。恢复动作：立即冻结新旧两个目录，重新从快照执行完整迁移，废弃已被污染的增量写入。

6. **循环引用导致重写死锁**。虽然已按拓扑顺序处理，但自定义 relation kind 的处理脚本若双向引用可能死锁。诊断证据：第二阶段日志长时间无进展且 CPU 空转。恢复动作：杀死进程，回到第一阶段重新分析 relation kind 的处理顺序，必要时手动指定打破循环的入口节点。

## 问答测试样例

1. **正向**：旧字段 `article.meta.author_name` 迁移后位于哪里？
   答：`concept.authors[].name`。依据是字段映射表和置信度为 1.0 的 SEA，判定者为 schema-committee。

2. **正向**：外部系统保存的旧链接在迁移后会失效吗？
   答：不会。ID 保持稳定；若发生重分配，旧 ID 会进入 `redirect_map.json` 永久指向新 ID。

3. **边界**：如果旧 ID 中包含作者真实姓名拼音，是否仍必须保留？
   答：不必保留原始字符串。这是 ID 稳定的例外，应重新分配 ID 并在重定向表中记录旧 ID 到新 ID 的映射。

4. **边界**：`article.body.markdown` 被拆成结构化块数组后，如何证明语义等价？
   答：需要 SEA 且置信度为 0.85，由 parser-v3 判定；若置信度低于 1.0，必须经人工复核。

5. **边界**：A 引用 B，B 引用 A，如何处理？
   答：两阶段迁移：先收集闭包，再按节点 ID 字典序重写引用边，避免循环导致无限递归。

6. **无证据拒答**：新 schema 是否比旧 schema 更适合知识库长期发展？
   答：无法从格式迁移规范中得出该结论。schema 优劣取决于使用场景、查询模式和组织约束，不在本主题证据范围内。

## 维护、版本、来源与相邻主题的关系

迁移规范本身应使用语义化版本管理，例如 `okf-kg-fmt-2025-q3`。旧目录封存后版本锁定，任何后续修正都必须通过新的迁移任务单执行，不允许直接修改归档。字段映射规则、SEA 记录和解析器版本号应存入版本控制系统，与代码变更一起审查。

来源证据包括：旧 schema 文档、人工签署的 SEA、自动解析器的版本与输出日志、以及迁移前后的结构指纹报告。格式迁移与以下相邻主题有明确边界：schema 演化负责定义新结构；内容校验负责判断内容是否正确；引用解析负责运行时把 ID 转成资源；访问控制负责谁能读写；全文检索负责索引与排名。格式迁移只保证身份、引用和内容语义稳定，不替代上述主题。

## 结论

**事实**：ID 和引用闭包是格式迁移中不可破坏的契约；任何非 1:1 字段映射都必须由显式 SEA 覆盖；回滚包必须原子交付且完整无缺。

**推论**：在负责任的架构视角下，显式字段映射与结构化指纹校验比依赖自动推断更能降低长期演进中的语义漂移风险；两阶段引用重写是处理循环引用和悬空引用的可靠模式。

**未知**：不同内容类型（代码片段、自然语言段落、结构化数据表）的最优指纹粒度尚无统一结论；LLM 辅助语义等价判定在真实知识库中的误报率、漏报率及其对 SEA 置信度的影响，仍需在项目实施后通过真实数据持续测量。
