# OKF 知识治理发布流程：从作者草稿到线上切换的架构设计

在 OKF（Object-Knowledge-Flow）兼容的知识治理体系中，发布流程负责把离散的作者产物转化为可被检索器与 Agent 安全引用的线上知识。本文档只讨论从草稿提交到线上切换的治理边界，不涉及创作工具的选择、实时协作协议或运行时搜索的排序算法。

## 摘要与问题边界

本流程的核心问题是：如何在作者、系统与治理者之间划分责任，使得一次发布可以在任意阶段被暂停、审计或回滚。起点是作者完成草稿并更新发布清单；终点是线上指针原子切换到新的索引产物。范围外的事项包括：未提交的本地编辑、运行时查询权限、模型生成内容的事实核查。读者应当先关注接口、责任与不变量，再决定具体使用哪一家向量数据库、CI 平台或缓存方案。

## 核心概念与数据模型

1. **Draft（草稿）**：作者产出的最小发布单元，包含 `draftId`、`sourcePath`、`authors`、`contentDigest`、`lineage` 与 `status`。草稿一旦进入流程即视为不可变，后续修改必须产生新的 `revision`，旧版本保留用于审计。
2. **Manifest（发布清单）**：一份声明式文件，描述本次发布包含哪些 Draft、依赖关系、期望产物、验证器列表与签名。它把“有哪些内容”与“怎么处理”分开，使处理逻辑可以替换而不影响内容组织。
3. **Validation Verdict（验证裁决）**：验证器输出的结构化结果，包括 `schemaCheck`、`linkCheck`、`provenanceCheck`、`policyCheck` 四类结论，以及失败证据和置信度。验证裁决是进入下一阶段的前置条件。
4. **Index Artifact（索引产物）**：编译阶段生成的产物，例如倒排表、向量嵌入、术语路由表、段文件清单。产物必须能通过 `contentDigest` 与来源 Draft 重新关联，确保可复现。
5. **Staging Pointer（预发布指针）**：指向一组已编译索引产物的引用，用于隔离预发布环境。只有授权审查者与自动化测试可以访问该指针，避免未经验证的内容影响线上服务。
6. **Production Pointer（线上指针）**：控制线上服务读取哪一组索引产物。切换操作通过原子更新该指针完成；旧指针被保留，作为回滚的备用目标。
7. **Audit Ledger（审计记录）**：追加式日志，记录每个阶段的事件、执行者、输入摘要、输出指针与耗时。审计记录是唯一的权威来源，不能由后续阶段覆盖。

## 设计决策与取舍

### 阶段式交付而非连续流
选择把流程切分为明确的四个阶段，而不是让作者提交后立即触发索引更新。每阶段产生签名的产物，便于定位问题与并行审查。代价是整体延迟增加，通常需要分钟级而非秒级。

### 清单驱动而非文件隐式约定
系统只处理清单中声明的 Draft，未声明的本地文件即使存在也被忽略。这避免了“目录扫描”带来的漂移风险，但要求作者维护清单，并增加了格式校验。

### 中央编排与可替换校验器
流程由中央发布控制器编排，但每个校验器通过标准接口接入。只要接口契约不变，本地文件校验、外部 API 校验或基于规则引擎的校验都可以互换。这种设计要求所有校验器返回统一格式的裁决，禁止私自绕过审计。

### 索引编译与线上切换分离
编译阶段在 Staging 完成，只有验证通过的产物才允许进入切换。这样切换动作本身只更新指针，不产生新的计算风险。代价是需要额外存储空间保存多份索引产物。

### 指针切换与来源一致性
每次切换必须记录旧指针、新指针、对应产物摘要和批准事件。如果切换失败，系统必须回退到旧指针，而不是停留在中间状态。这要求底层存储提供原子写或至少版本化配置能力。

## 可执行的实施流程

1. 作者在工作分支中完成 Draft，并更新发布清单中的条目、依赖与验证器声明。
2. 合并请求触发 Ingestion Job，读取清单并解析所有声明的依赖是否存在。
3. 系统将 Draft 与依赖物化到 Staging 存储，计算每个文件的内容指纹，生成内容清单。
4. 验证器执行四类检查，输出结构化裁决；任何一类失败都会进入阻塞态，除非获得策展人显式覆盖。
5. 验证通过后，索引编译器读取内容清单，生成倒排索引、向量嵌入等产物，并写入 Staging 指针。
6. 预发布环境加载 Staging 指针，运行烟雾测试、搜索质量回归与权限验证。
7. 策展人审查审计记录、测试结果与差异报告，批准进入线上切换。
8. 发布控制器原子更新 Production Pointer，保留旧指针，触发缓存失效，并写入切换事件到审计记录。

## 示例：本地文件知识库的发布清单

    schemaVersion: "okf-release/v1.2"
    releaseId: "release-2025-06-14-docs"
    sourceRoot: "./knowledge/drafts"
    outputs:
      indexPath: "./dist/knowledge-index.json"
      manifestPath: "./dist/release-manifest.json"
    entries:
      - draftId: "draft-ts-patterns"
        path: "typescript/patterns.md"
        authors: ["wei"]
        dependencies: ["draft-base-types"]
        validators: ["schema-md", "link-check"]
        embeddings: true
      - draftId: "draft-base-types"
        path: "typescript/base-types.md"
        authors: ["wei"]
        dependencies: []
        validators: ["schema-md"]
        embeddings: false
    promotion:
      pointer: "./dist/production-pointer.json"
      rollbackWindow: "24h"

**输入**：`sourceRoot` 下的 Markdown 草稿文件与上述清单。
**处理**：发布管道按清单解析 Draft、验证依赖、执行声明的校验器、编译索引产物。
**输出**：`dist` 目录下的 `knowledge-index.json`、`release-manifest.json` 与 `production-pointer.json`，线上服务通过指针读取最终产物。

## 性能、质量与可观测性指标

1. **阶段时延**：Ingestion、Validation、Compile、Switch 各阶段的 p50 与 p99，由 CI 步骤时间戳与审计记录计算。
2. **验证误报率**：人工覆盖的验证失败数除以总验证失败数，从审计记录中的 `override` 事件统计。
3. **索引新鲜度**：发布清单被批准到 Production Pointer 切换完成的时间差，目标值通常低于 10 分钟。
4. **搜索质量回归**：在 Staging 上对比生产索引的 NDCG@10 或召回率，若下降超过阈值则阻断切换。
5. **切换成功率**：成功切换次数除以总切换次数，失败包括指针冲突、缓存失效超时或健康检查未通过。
6. **回滚耗时**：从触发回滚到旧指针重新生效的时间，通过缓存命中率与旧版本内容请求恢复比例验证。

## 失败模式、诊断证据与恢复动作

1. **清单缺失必填字段**
   证据：Ingestion Job 返回 schema 错误，指出缺失字段与位置。
   恢复：拒绝提交，通知作者补充清单，不进入后续阶段。

2. **交叉引用失效**
   证据：`link-check` 输出死链列表、源文件路径与依赖 Draft 状态。
   恢复：默认阻断；若目标 Draft 已列入 pending 发布计划，可标记为条件通过，但需策展人批准。

3. **索引编译资源耗尽**
   证据：编译器内存曲线突增、进程退出码 137、产物文件未完整生成。
   恢复：降低嵌入批次大小、拆分批处理清单或增加资源配额，并重新触发编译。

4. **预发布预览与预期不一致**
   证据：烟雾测试输出差异报告，或 NDCG 低于阈值。
   恢复：冻结切换，回退 Staging 指针，由策展人定位内容差异或测试数据漂移。

5. **切换指针并发冲突**
   证据：Promoter 发现当前指针版本与预期不一致，或乐观锁失败。
   恢复：将切换操作串行化到队列中，失败后重新读取最新审计事件并重新评估。

6. **线上缓存未失效**
   证据：切换后旧版本内容仍被服务，缓存命中日志中的版本号滞后。
   恢复：主动触发缓存刷新，并在切换步骤中增加幂等失效调用与回退超时。

## 问答测试样例

1. **正向**：发布流程的主要阶段是什么？
   答案：作者草稿、验证、索引编译、线上切换。

2. **正向**：发布清单在流程中起什么作用？
   答案：声明待发布内容、依赖、验证器与预期产物，解耦内容存储与处理逻辑。

3. **边界**：如果 Draft 缺少依赖，验证阶段如何处理？
   答案：默认阻塞，除非清单中显式声明该依赖为 pending 并附带策展人批准。

4. **边界**：是否可以跳过验证直接编译索引？
   答案：不可以；但可以缩小验证范围，例如只对变更文件执行增量检查，结果仍须进入审计。

5. **无证据**：该流程应该使用哪家向量数据库？
   答案：未知；设计只定义了 Index Artifact 接口，具体后端需根据项目基础设施选择，不应推断。

6. **无证据**：生产系统能支撑多少并发查询？
   答案：无给定数据；这取决于运行时索引实现与部署规模，无法从发布流程本身得出。

## 维护、版本、来源与相邻主题

- **版本**：清单 schema 采用语义化版本，主版本变更意味着发布流程不兼容，需同步升级校验器与编译器。
- **来源**：每个产物保留来源指针，包括 `sourceRoot`、`commit`、`draftId` 与 `contentDigest`，支持从线上结果回溯到原始草稿。
- **维护**：审计日志定期归档，旧索引产物按保留策略清理；Production Pointer 保留至少两个历史版本，确保可回滚。
- **相邻主题**：与“作者创作”相邻，但本流程不约束创作工具；与“运行时搜索”相邻，但只输出索引；与“访问控制”相邻，预发布环境的可见性由授权子系统负责；与“知识验证策略”相邻，验证规则由治理层制定，发布流程只提供执行框架。

## 结论

- **事实**：发布流程被明确划分为作者草稿、验证、索引编译、线上切换四个阶段；通过清单、审计记录和指针切换实现可替换性与可回滚性。
- **推论**：将索引编译与线上切换分离，能够降低线上变更风险，并允许不同验证器和索引后端在统一接口下互换。
- **未知**：具体索引格式、向量后端实现、缓存失效协议以及并发切换的锁机制，需依据目标基础设施进一步确定。
