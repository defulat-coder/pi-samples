# BM25 排序：RAG 候选片段的架构化评分接口

## 摘要与问题边界

BM25 是一种基于词项重叠的概率检索排序函数，用于在检索增强生成（RAG）流程中为候选片段打分。它解决的核心问题是：给定一条查询和一组已分块的文档片段，如何按照查询词项在片段中的出现频率、稀有程度和字段重要性，生成一个可解释、可替换、可回测的排序结果。本文的边界限定在候选片段的评分接口与索引架构，不讨论语义检索、查询改写或生成模型的后处理。BM25 不是意图理解模型，不能自动处理同义词、拼写错误或跨语言查询；这些能力应通过上游分析器或下游重排器实现。

## 核心概念与数据模型

1. **候选片段（chunk）**：排序的基本单元，通常对应本地 Markdown、JSON 或 TypeScript 源码中的一段连续文本。每个 chunk 拥有稳定标识 `chunkId` 和若干可配置字段。
2. **字段（field）**：如 `title`、`body`、`tags`、`filepath`。字段权重在查询时注入，用于体现不同字段的语义优先级；权重是配置项，不是模型学习结果。
3. **词项（term）**：由分析器对字段文本切分、归一化后的最小索引单位。同一字段的 term 可能保留位置信息，但 BM25 本身只需要词频。
4. **词频（tf）**：某个 term 在指定字段的某个 chunk 中出现的次数。高频不线性加分，而是通过饱和函数限制影响力。
5. **文档频率（df）与逆文档频率（idf）**：df 是包含该 term 的 chunk 总数；idf 衡量词项区分度，常用形式为 `log((N - df + 0.5) / (df + 0.5) + 1)`，其中 N 为索引中 chunk 总数。
6. **字段长度归一化**：使用字段平均长度 `avgfl` 对长字段进行惩罚、对短字段进行奖励，控制参数为 `b`（0 表示不归一化，1 表示完全归一化）。
7. **BM25 饱和度参数 `k1`**：限制词频对得分的边际增益，避免某个 term 重复出现导致排序被单一词项垄断。
8. **得分聚合**：查询总分为所有查询词项在加权字段上的 BM25 得分之和。跨字段实现可以是独立求和，也可以采用 BM25F 式字段内聚合，取决于索引设计。
9. **不可变索引段（segment）**：本地文件知识库建议按快照生成只读索引段，便于并发查询、版本回滚和可重复测试。

## 设计决策与取舍

### 将 BM25 隐藏在可替换的 Scorer 接口之后
定义接口 `score(queryTerms, posting, stats) -> number`，使 BM25 与索引存储、倒排表格式解耦。这样未来可以用向量评分器或学习排序模型替换，而无需改动检索管线。取舍：接口抽象会引入一次函数调用开销，在极端低延迟场景可内联。

### 字段权重由配置决定，不通过查询日志在线训练
在本地文件知识库场景，训练数据稀缺且结果可解释性要求高，字段权重应作为显式配置维护。优势是稳定、可审计；劣势是无法自动适应用户行为。例外：当 A/B 实验需要临时调整时，可通过请求级覆盖参数生效，但必须在日志中标记。

### `k1` 与 `b` 采用全局默认值，按字段可覆盖
默认 `k1 = 1.2`、`b = 0.75` 对多数文本有效。若 `body` 字段长度方差远大于 `title`，可为 `body` 单独设置更小的 `b`，降低长文档惩罚。全局策略降低调参面；按字段策略提升异构字段场景的 recall，但增加回归测试成本。

### 两段式检索：BM25 粗排 + 可选重排器
BM25 负责高效召回 top-K，随后可由稠密向量或交叉编码器重排。取舍：重排提升质量但增加延迟；若 API 的 P95 目标低于 100ms，应关闭重排或限制重排候选数。边界是 BM25 与重排器的接口必须统一为 `(chunkId, score, snippet)` 列表。

### IDF 更新策略选择全量重算
本地知识库规模有限，建议每次快照构建时全量重算 IDF，保证分数一致性。增量更新虽然更快，但会导致新旧 chunk 的 IDF 基准不一致，引起不可复现的排序。例外：索引大于十万 chunk 且写入频繁时，可改用定期全量重建 + 查询时局部平滑。

## 可执行的实施流程

1. 定义 chunk schema，明确 `title`、`body`、`tags` 等字段及其分析器。
2. 实现字段级分析器：统一 Unicode 归一化、大小写折叠、分词和停用词处理。
3. 构建倒排索引：对每个字段记录 `(term -> chunkId -> tf, fieldLength)` 的 posting 列表。
4. 计算全局统计量：每个字段的 `N`、`avgfl`、term 的 `df`。
5. 实现 BM25 评分函数，默认 `k1 = 1.2`、`b = 0.75`，支持按字段覆盖。
6. 配置字段权重映射，例如 `title: 3.0`、`body: 1.0`、`tags: 1.5`。
7. 暴露检索接口 `search(query, filters, topK)`，返回带高亮片段的候选列表。
8. 与可选重排器集成：BM25 输出 top-K 作为重排器输入，重排器输出最终顺序。
9. 接入可观测性：记录查询延迟、term 覆盖率、得分分布、索引版本号。
10. 建立版本与回滚机制：每个快照绑定分析器配置哈希和全局统计量，支持按版本查询。

## 输入、处理与输出示例

以下是一个贴近 TypeScript/Web/本地文件知识库的 JSON 请求与响应示意。

请求：

```json
{
  "query": "BM25 字段权重 配置",
  "topK": 5,
  "fields": { "title": 3.0, "body": 1.0, "tags": 1.5 },
  "filters": { "source": "docs" }
}
```

处理过程：分析器将查询切分为 `["bm25", "字段", "权重", "配置"]`，统计每个 term 在候选 chunk 各字段中的 tf，结合字段长度与 avgfl 计算 BM25 子分，再乘以字段权重并求和。

响应片段：

```json
{
  "results": [
    {
      "chunkId": "docs/ranking.md#3",
      "score": 18.42,
      "fields": { "title": 12.3, "body": 6.12 },
      "snippet": "...BM25 字段权重通过请求级配置注入..."
    }
  ],
  "indexVersion": "2026-08-01T12:00:00Z"
}
```

## 性能、质量与可观测性指标

1. **查询 P95 延迟**：从 API 收到请求到返回 top-K 结果的时间。测量时应排除网络传输，使用本地索引加载。
2. **Recall@K**：在人工标注的相关集合中，BM25 top-K 覆盖的相关 chunk 比例。K 通常取 5 或 10。
3. **NDCG@K**：利用分级相关性（0–3 分）评估排序质量，能反映高相关项是否排在前面。
4. **索引新鲜度滞后**：源文件最新修改时间与当前服务索引版本时间之差。对于本地知识库，建议不超过 5 分钟。
5. **Term 覆盖率**：查询中出现在索引里的词项比例。持续低于 80% 说明分析器或分词策略有问题。
6. **分数可重复性**：相同查询在相同索引版本上重复 10 次，得分标准差应为 0；若不为 0，检查浮点聚合与排序比较器。

## 失败模式、诊断证据与恢复动作

1. **稀有词 IDF 爆炸**：某个术语仅出现在极少数 chunk，导致这些 chunk 得分异常高。诊断证据为得分分布中出现离群峰值。恢复动作：对 IDF 设置上限或引入平滑。
2. **字段权重失衡**：`title` 权重过大，导致标题含查询词的弱相关 chunk 排在正文高度相关 chunk 之上。诊断证据是 top-10 全部来自 title 字段。恢复动作：降低 title 权重或加入字段级上限。
3. **长度归一化过度惩罚短片段**：短代码注释或命令行片段虽然精确匹配，却因长度归一化得分偏低。诊断证据是短 chunk 的 BM25 子分显著低于预期。恢复动作：对短字段调低 `b` 或关闭该字段归一化。
4. **查询与索引分析器不一致**：查询被切分为不同词项，导致明明存在的文档无法召回。诊断证据是 term 覆盖率低且手动检查索引存在该词。恢复动作：统一分析器流水线，并在 CI 中增加分析器一致性测试。
5. **索引版本滞后**：本地文件已修改，但检索结果仍返回旧内容。诊断证据是 `chunkId` 对应文件哈希与索引记录不一致。恢复动作：建立文件变更监听器或定时快照重建。
6. **浮点排序不稳定**：多线程或多分片聚合时，相同得分但不同 `chunkId` 的返回顺序随机。诊断证据是重复查询顺序变化。恢复动作：使用稳定排序，以 `chunkId` 作为最终 tie-breaker。
7. **停用词策略漂移**：查询端移除停用词而索引端保留，或反之，导致相关文档漏召回。诊断证据是查询与索引的 token 数量不一致。恢复动作：将停用词表纳入索引版本元数据。

## 问答测试样例

1. **正向问题**：BM25 的 k1 参数有什么作用？
   期望：返回解释词频饱和度并给出默认值的文档。接受条件为 top-3 结果包含 `k1` 与 `tf` 关系说明。

2. **正向问题**：如何为 title 字段设置更高权重？
   期望：返回字段权重配置示例。接受条件为结果中包含可验证的 JSON 字段权重映射。

3. **边界问题**：如果一个查询词在所有 chunk 中都出现，BM25 会怎么处理？
   期望：答案指出 IDF 接近 0，该词对排序贡献极小。若知识库未覆盖 IDF 公式，应明确说明无证据。

4. **边界问题**：短片段与长片段得分相同时如何确定顺序？
   期望：答案说明 tie-breaker 策略（如按 chunkId 稳定排序）。若未定义，应拒绝猜测。

5. **无证据拒答**：BM25 是否支持在线学习字段权重？
   拒答条件：若知识库未声明在线学习能力，应回答“当前设计不支持”，而非给出训练方法。

6. **无证据拒答**：BM25 与 dense retrieval 哪个更好？
   拒答条件：若知识库未包含两者对比实验，应回答“无法从现有材料得出一般性结论”，不可虚构评估结果。

## 维护、版本、来源与相邻主题

维护重点包括：保持分析器配置与索引版本绑定，任何分词、停用词、归一化变更都必须触发新版本构建；将 `k1`、`b`、字段权重纳入版本控制，并附带变更说明；每次发布前运行问答回归测试，确保正向用例 recall 不下降。

版本策略采用单调递增的构建号或 ISO 时间戳索引版本，API 响应中携带 `indexVersion`，便于排查时复现结果。来源以 Robertson 等人的 Okapi BM25 论文与 Lucene、Tantivy 的实现文档为参考。

相邻主题包括：文本分词与归一化、倒排索引存储格式、向量检索与稠密重排器、Learning to Rank、索引增量更新与快照管理。BM25 与这些主题的关系是：它作为可替换评分器位于检索管线的打分层，通过清晰接口与上游分析器和下游重排器协作。

## 结论

**事实**：BM25 依赖词频、逆文档频率、字段长度归一化和字段权重对候选片段排序；其公式和 `k1`、`b` 参数有公开定义；字段权重是配置项。

**推论**：在本地文件知识库 RAG 系统中，将 BM25 封装在可替换 Scorer 接口之后、采用两段式检索、统一分析器流水线，可以在可解释性与扩展性之间取得平衡；这些推论来自工程实践假设，仍需在具体数据集上验证。

**未知**：当前仓库未提供针对本地知识库的最优 `k1`、`b` 与字段权重组合；也未证明 BM25 粗排加稠密重排一定优于纯 BM25 或纯向量检索。最优参数应通过标注数据和 A/B 实验确定，而非预设。
