# BM25 排序：词频、逆文档频率与字段权重的 TypeScript 实现

## 摘要与问题边界

BM25 排序是在检索增强生成（RAG）中把候选片段按查询相关性排序的稀疏检索方法。本文只讨论**文档片段级别**的 BM25 实现：输入是一个查询字符串和一组已经切分好的片段，输出是按得分降序排列的片段 ID 列表。覆盖的内容包括词频（TF）、逆文档频率（IDF）、字段权重、长度归一化和倒排索引的工程实现；不讨论语义向量检索、神经网络重排、查询扩展、中文分词器的训练，也不讨论分布式索引或实时增量更新。目标是在 Node.js 或 Deno 环境下，用 TypeScript 写出一个可直接运行的排序函数。

## 核心概念与数据模型

1. **片段（Fragment）**：检索的最小单位，结构为 `{ id: string; fields: Record<string, string>; meta?: object }`。一个 Markdown 文件可以拆成多个片段，但排序只针对片段，不针对原始文件。

2. **字段（Field）**：每个片段下的可检索文本槽位，例如 `title`、`body`、`tags`。每个字段独立计算词频和长度，字段之间通过权重相乘来体现重要性。

3. **词项（Term）与词频（TF）**：词项由分词器输出，通常为规范化后的小写字符串。字段级词频 `tf(t, f)` 表示词项 `t` 在片段字段 `f` 中出现的次数。词频不跨字段累加。

4. **逆文档频率（IDF）**：对词项 `t`，`idf(t) = log((N - df(t) + 0.5) / (df(t) + 0.5))`，其中 `N` 为片段总数，`df(t)` 为包含该词项的片段字段数。IDF 在索引构建时一次性计算，查询时只读。

5. **字段长度与平均长度**：字段 `f` 的长度 `|f|` 为该字段经分词后得到的词项个数；`avgdl(f)` 为所有片段该字段长度的平均值。长度只统计有效词项，不计停用词或标点。

6. **倒排索引（Posting List）**：对每个字段维护 `Map<term, Array<{ fragmentId, tf }>>`，查询时通过交集或并集取出候选片段，避免全量扫描。

7. **排序得分（Score）**：对查询 `Q` 中每个词项 `t` 和字段 `f`，片段 `D` 的得分为 `score(D, Q) = Σ_f boost(f) · Σ_{t∈Q} idf(t) · tf(t,f)·(k1+1) / (tf(t,f) + k1·(1 - b + b·|f|/avgdl(f)))`。`k1` 控制词频饱和度，默认 `1.2`；`b` 控制长度惩罚，默认 `0.75`。

## 设计决策与取舍

### 分词策略：确定性正则 vs 语言分词器
选择基于正则 `/[a-z0-9]+(?:[-_.][a-z0-9]+)*/g` 的 ASCII 分词。它把连字符、下划线、点号保留在词项内，适合代码、配置文件和英文技术文档；缺点是中文无法按字切分。若知识库以中文为主，必须把分词器接口抽象成 `Tokenizer`，在实现层替换为jieba或自研分词，BM25 核心不变。

### IDF 变体：标准 BM25 公式
采用 Robertson 标准 BM25 的 IDF，并对结果做下限截断到 `1e-6`。当词项出现在超过半数片段时，原始 IDF 会接近 0 甚至为负；截断后可避免常见词拉低总分。不采用 BM25+ 的长度归一化下界，因为本地文件知识库片段长度差异通常可控。

### 字段权重的乘法模型
字段权重 `boost(f)` 作为整个字段得分的外部乘数。例如 `title=3.0`、`body=1.0`、`tags=2.0`。乘法模型实现简单，但字段权重会放大 IDF 差异；如果某个字段极短，高权重容易导致该字段出现少量匹配就压制长字段。恢复手段是引入字段长度先验或二阶段重排。

### 字段隔离的长度归一化
每个字段单独计算 `avgdl` 和 `b`，而不是把全部字段合并成一个大文本。标题字段通常只有 5～15 个词，正文字段可达 100～300 词；合并归一会让标题词频被严重稀释。字段隔离的代价是索引元数据体积增加，约等于字段数量倍的统计量。

### 索引构建时机：启动时全量构建
本地文件知识库在进程启动时扫描目录、切分片段、构建倒排索引并写入内存 Map。这样查询延迟稳定，代价是启动时间与文件数量成正比。如果文件超过 10 万，应改为读取预序列化的索引文件，并把索引构建脚本独立到 CI 流程。

## 可执行的实施流程

1. 定义片段接口与字段配置，要求每个片段至少有一个非空字段，字段名必须在白名单内。

2. 实现分词器，输入字符串输出 `Term[]`，对每一个词项做 Unicode 规范化（NFKC）、小写转换、去除首尾空白，返回数组长度记为字段长度。

3. 扫描全部片段，对每个字段分别统计 `tf` 并累加 `df`。使用两层 Map：`field -> term -> Set<fragmentId>`，同时记录字段长度总和。

4. 计算 `N` 与每个字段的 `avgdl`，将 `df` 转换为 IDF 表，字段级独立存储。

5. 把 `Set<fragmentId>` 转为紧凑的倒排列表 `Array<{ id, tf }>`，并按 `id` 排序以便后续交集/并集操作。

6. 提供查询入口，先校验查询字符串非空且长度不超过 512 字符，再校验 `k1>0`、`0<=b<=1`、字段权重非负数。

7. 对查询分词，按每个字段的倒排索引取出含任一查询词项的候选片段，合并去重。

8. 对每个候选片段，按公式累加所有字段、所有查询词项的得分；若某字段不含该词项，则该项贡献为 0。

9. 按得分降序排序，返回前 `k` 个结果；当得分相同按 `id` 字典序稳定，保证可重复测试。

10. 暴露可观测埋点：查询耗时、命中片段数、IDF 为下限的词项比例、零结果查询比例，并定期把这些指标写入日志。

## 输入、处理、输出示例

以下是一个贴近本地文件知识库的配置与索引片段，说明数据如何在 BM25 函数中流动。

    # bm25.config.yaml
    fields:
      title:  { boost: 3.0, k1: 1.2, b: 0.75 }
      body:   { boost: 1.0, k1: 1.2, b: 0.75 }
      tags:   { boost: 2.0, k1: 1.2, b: 0.75 }
    tokenizer: ascii_word
    idf_floor: 0.000001

    // index.fragment.0.json
    {
      "id": "install-pnpm",
      "fields": {
        "title": "install pnpm",
        "body": "Install pnpm via corepack. corepack enable and corepack prepare.",
        "tags": "package-manager setup"
      }
    }

    // search("corepack pnpm", { topK: 5 })
    // 输入：查询字符串 "corepack pnpm"，字段配置见 YAML，片段集包含 install-ppnpm 等。
    // 处理：分词得到 ["corepack","pnpm"]；标题命中 "pnpm"，正文命中 "corepack" 两次和 "pnpm" 一次；
    //       标签未命中。计算每个字段的 BM25 得分并乘以 boost。
    // 输出：
    [
      { "id": "install-pnpm", "score": 4.721, "matchedTerms": ["corepack","pnpm"] },
      { "id": "setup-node",   "score": 2.105, "matchedTerms": ["pnpm"] }
    ]

在这个例子中，标题字段的高 boost 让 "install pnpm" 这个片段即使正文较短也排在前面；而 "corepack" 出现两次的正文贡献受 `k1` 饱和限制，不会无限放大。

## 性能、质量与可观测性指标

1. **查询 P95 延迟**：单查询从分词到返回前 100 名的耗时。在 M2 Mac 上处理 1 万片段应低于 5 毫秒；超过 20 毫秒说明倒排列表过长或排序未剪枝。

2. **索引构建时间**：从文件读取到可查询状态的总时间。应与片段数线性相关；若出现超线性增长，检查是否对每个词项都记录了全量位置信息。

3. **召回率 Recall@k**：对一组带人工标注的问题，前 k 个结果包含正确答案的比例。本地知识库目标 Recall@10 不低于 0.75，否则应检查字段权重或分词。

4. **平均倒数排名 MRR**：对每个问题取第一个正确答案排名的倒数求平均。MRR 低于 0.4 通常意味着标题权重不足或 IDF 截断过狠。

5. **零结果查询比例**：查询分词后没有任何词项命中索引的比例。持续高于 5% 说明分词器与文档词汇表不一致，例如代码驼峰命名未被拆分。

6. **得分分布熵**：记录每次查询结果前 10 的得分标准差。标准差过小说明区分度不足，可能是字段权重过于平均或查询词均为高频词。

## 失败模式、诊断证据与恢复动作

1. **IDF 负分导致总分异常**
   诊断：查询包含 "the"、"如何" 等高频词，结果得分出现负数或极小的正值。
   恢复：对 IDF 设置 `idf_floor`，并在分词层默认过滤停用词。

2. **字段权重为 0 导致字段失效**
   诊断：查询明确出现在标题的问题，返回结果中标题字段的 `matchedTerms` 为空。
   恢复：在配置加载阶段用 JSON Schema 校验 `boost > 0`，加载失败即报错。

3. **字段长度偏差压制短片段**
   诊断：短标题片段在查询精确命中标题时排名低于长正文片段。
   恢复：降低正文字段的 `b` 值，或对标题字段使用更小的 `avgdl` 做独立归一化。

4. **分词器无法匹配代码标识符**
   诊断：查询 `userProfile` 无法命中文档中的 `user_profile`。
   恢复：在分词前增加标识符规范化流水线，把驼峰、下划线、连字符统一为同一种形式。

5. **索引与文件系统不同步**
   诊断：返回结果中包含已删除文件的 `id`，或新文件搜索不到。
   恢复：维护 `indexVersion` 与文件内容哈希；启动时比对哈希，不一致则重建索引。

6. **`k1` 过大造成词频堆砌占优**
   诊断：某片段因为查询词重复 10 次，排在语义更相关但词频低的片段之上。
   恢复：把 `k1` 降到 `0.8` 附近，并引入 BM25F 或二阶段交叉编码器重排。

## 问答测试样例

1. 正向：问 "如何安装 pnpm？" 期望返回 `install-pnpm`，且前 3 名中包含该 ID。
2. 正向：问 "corepack enable 命令" 期望 `install-pnpm` 的 `body` 字段命中 "corepack" 并排名首位。
3. 边界：问 "p" 单个字符，要求返回空数组；因为分词器最小词长为 2，避免爆炸式召回。
4. 边界：问 "pnpm pnpm pnpm pnpm pnpm" 重复 5 次，要求首结果仍为 `install-pnpm`，但得分与查询 1 次时相比增幅受 `k1` 限制，不应超过 1.5 倍。
5. 无证据：问 "Kubernetes ingress controller TLS 配置" 而知识库只有前端内容，要求返回空列表并附带 `reason: "no_matching_term"`。
6. 无证据：问空字符串 `""`，要求校验失败并抛出 `ValidationError: query must be non-empty`。

## 维护、版本、来源与相邻主题

索引文件应附带版本号，例如 `indexVersion: "bm25-v2"`，并在反序列化时拒绝不兼容的旧格式。来源字段记录每个片段对应的原始文件路径、起始行号和最后修改时间，便于调试。BM25 排序与以下主题相邻：倒排索引构建负责提供 `df` 和 `tf`；查询扩展负责在 BM25 之前改写查询词；向量检索负责在 BM25 之后按语义补充候选；重排模型负责在 BM25 结果上做精排。BM25 本身不依赖外部 API，但分词器、停用词表和字段配置应纳入版本控制，与代码同步发布。

## 结论

事实：BM25 的核心计算只依赖词频、逆文档频率、字段长度、平均长度和字段权重五个可量化输入。推论：在本地文件知识库这种规模可控、字段边界清晰的场景下，字段隔离归一化与启动时全量建索引通常能在延迟和准确率之间取得较好平衡。未知：对于具体业务，`k1`、`b` 和字段权重的最优组合无法仅凭默认值确定，必须通过带标注的查询集做离线评估才能确认。
