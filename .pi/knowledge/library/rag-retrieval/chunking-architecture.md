# 分块策略：在上下文完整性与检索成本之间建立可替换边界

## 摘要与问题边界

分块策略（Chunking Strategy）是检索增强生成（RAG）系统中 ingestion 与 retrieval 之间的核心边界。它决定原始文档如何被切分为可嵌入、可召回、可组装的片段，同时直接影响上下文完整性、嵌入语义保真度和每次请求的成本。作为架构设计者，应当把分块视为一组可替换接口和明确责任的契约，而不是一上来就选定固定长度或递归字符切分。本文从架构视角出发，先建立概念模型、责任边界和接口抽象，再讨论具体实现取舍、实施流程、失败模式与可观测性，并给出一个贴近 TypeScript / Web / 本地文件知识库的配置示例。

## 核心概念与数据模型

1. **源文档（Source Document）**：被切分的最小可寻址单元，如一个 Markdown 文件、一个 PDF 页面、一个 API 返回的 HTML 片段或一段数据库记录。它在系统中必须具有稳定标识、版本指纹和来源 URI。

2. **片段（Chunk）**：源文档经过切分后得到的、可独立嵌入和召回的文本单元。一个片段在逻辑上包含 `content`、`chunk_id`、`source_id`、`start_offset`、`end_offset`、`header_chain`、`semantic_tag` 等字段。

3. **片段规范（ChunkSpec）**：定义片段应满足的全局约束，包括最大长度（按 token / 字符 / 句子）、最小长度、是否允许跨段落、是否保留 Markdown 标题链、是否启用层次化父子关系。ChunkSpec 是可替换接口的输入，不依赖具体切分器。

4. **边界标记（Boundary Marker）**：语义或结构上的断点，例如 Markdown 标题、空行、代码块结束符、表格行边界、HTML 标签闭合点。边界策略决定切分时哪些标记具有“不可穿越”的优先级。

5. **重叠策略（OverlapPolicy）**：控制相邻片段之间共享内容的数量与方式。常见形式包括固定 token 滑动窗口、整句重叠、段落级回退和基于标题链的元数据继承。重叠的目的是降低边界信息损失，但会直接增加索引体积和冗余召回。

6. **语义上下文层（Context Layer）**：附着在片段上的、用于帮助 LLM 还原上下文的元数据，例如从根标题到当前段落的层级路径、前一片段摘要、所属章节标签。上下文层不参与向量相似度计算，但参与最终 prompt 组装。

7. **版本与来源指纹（Provenance）**：每个片段必须能追溯到其在源文档中的位置与版本。当源文档更新时，系统通过 fingerprint 判断哪些片段需要删除、新增或保持不变，避免整个索引重建。

## 设计决策与取舍

### 片段粒度的单位选择

选择 token、字符还是句子作为长度单位，决定了片段在不同模型和 tokenizer 下的稳定性。以 token 为单位能精准控制嵌入模型和 LLM 的上下文窗口，但会导致同样配置在不同 tokenizer 下产生不同边界。以字符为单位对设计者和调试者更直观，却可能与模型的实际输入长度脱节。建议把长度单位封装为 `LengthMetric` 接口，让 ChunkSpec 与具体 tokenizer 解耦。

### 语义边界 vs 固定窗口

固定窗口切分实现简单、长度稳定，但容易在代码块、表格、列表或论证中途截断，造成召回片段语义不完整。基于语义边界（标题、段落、句子）的切分能保留更多上下文，但片段长度分布不均匀，可能产生超短或超长片段。实践中，可采用“先语义边界、后长度兜底”的混合策略：优先在边界处切分，若剩余文本超过最大长度，再在其内部按固定窗口二次切分。

### 重叠与冗余预算

重叠能够缓解边界截断问题，却会增加索引存储、嵌入计算和召回噪音。重叠策略必须在 ChunkSpec 中显式声明预算：例如“相邻片段共享不超过最大长度的 20%，且共享单元为完整句子”。当源文档频繁包含短列表或表格时，重叠可能导致同一条记录被重复索引多次，需要在重排序或去重阶段处理。

### 元数据继承与定位信息

片段元数据不是装饰，而是检索后重新拼合上下文的依据。标题链、章节号、文件名、行号范围都应在切分时注入，而不是在 prompt 组装阶段再临时解析。需要区分“用于过滤的结构化元数据”和“用于还原上下文的文本化元数据”：前者写入向量库 payload，后者作为 `context_prefix` 拼接在 content 前供 LLM 理解。

### 层次化分块与扁平索引

对于长文档，可维护两层 chunk：父 chunk（章节级）用于粗召回，子 chunk（段落级）用于精召回。父子关系通过 `parent_chunk_id` 关联。层次化结构能提高长距离依赖的保留能力，但会增加索引复杂度、写入延迟和一致性维护成本。扁平索引更简单，适合短文档或高更新频率场景。

### 静态预算 vs 动态预算

静态预算指所有文档使用同一 ChunkSpec，部署简单但无法适配不同体裁。动态预算根据文档类型、查询历史或模型上下文余量自动调整最大长度。动态策略需要额外的分类器或规则引擎，并引入运行时决策复杂度。建议在系统早期采用静态预算加文档类型覆盖（override）机制，待可观测数据充分后再演进为动态预算。

## 可执行的实施流程

1. **定义 ChunkSpec 契约**：将最大长度、长度单位、边界优先级、重叠策略、元数据继承规则写入版本化的配置 schema，作为切分器与嵌入器之间的接口。

2. **选择并封装 tokenizer / parser**：将 tokenizer 包装为 `TokenCounter` 接口，将 Markdown / HTML / 代码解析器包装为 `BoundaryDetector` 接口，避免具体库直接污染分块逻辑。

3. **加载源文档并计算指纹**：读取本地文件或 Web 抓取内容，计算 `source_id` 和 `version_hash`，用于后续增量更新和来源追溯。

4. **识别结构边界**：解析标题层级、代码块、表格、列表、段落，生成带优先级和类型的边界标记列表。

5. **执行一级语义切分**：按高优先级边界把文档划分为可变长度的“语义块”，确保不穿越代码块或表格。

6. **执行二级长度兜底切分**：对超过最大长度的语义块，在次级边界（句子、短语）处继续切分，生成最终片段。

7. **应用 OverlapPolicy**：在相邻片段之间按策略复制完整句子或固定 token，并更新偏移量和元数据。

8. **注入上下文层元数据**：为每个片段附加标题链、行号范围、前后片段引用、来源 URI。

9. **嵌入并写入索引**：调用嵌入模型得到向量，连同 payload 写入向量库；记录每个 chunk 的 embedding id 与 source fingerprint。

10. **评估与回滚**：在离线评估集上测量边界保留率、长度分布、召回指标和上下文成本，根据结果调整 ChunkSpec 并重新发布版本。

## YAML 示例：本地 Markdown 知识库配置

> chunking:
>   version: "2.1.0"
>   default:
>     length_metric: "token"
>     max_length: 256
>     min_length: 32
>     boundary_priority: ["h2", "h3", "paragraph", "sentence"]
>     protect_blocks: ["code", "table", "blockquote"]
>     overlap_policy:
>       type: "sentence"
>       max_overlap_tokens: 40
>     metadata:
>       inherit_header_chain: true
>       include_line_numbers: true
>       include_source_uri: true
>   overrides:
>     - glob: "docs/api/*.md"
>       max_length: 512
>       boundary_priority: ["h2", "code_block", "paragraph"]
>     - glob: "docs/faq/*.md"
>       max_length: 128
>       overlap_policy:
>         type: "none"

输入：一组本地 Markdown 文件，按 glob 匹配对应规则。处理：先根据 `boundary_priority` 和 `protect_blocks` 识别不可穿越的结构边界，再按 `max_length` 进行兜底切分，应用 `overlap_policy` 并继承标题链。输出：每个 Markdown 文件生成若干 chunk 记录，包含 `chunk_id`、`content`、`header_chain`、`source_uri`、`start_line`、`end_line` 和向量，写入本地或远程向量库。

## 性能、质量与可观测性指标

1. **片段长度分布**：统计每个 chunk 的 token / 字符数，绘制 P50 / P95 / P99。测量方法：在切分完成后对全部 chunk 采样并调用 `TokenCounter`，输出直方图。

2. **边界保留率（Boundary Preservation Rate）**：被切分点命中在语义边界（段落、标题、代码块结束）的比例。测量方法：人工标注或在解析阶段标记合法边界，计算切分点与合法边界的重合度。

3. **上下文覆盖率（Context Coverage）**：单次查询所需的关键信息能否在召回的片段中完整出现。测量方法：构造 golden answer 评估集，检查答案所需的事实是否被覆盖。

4. **召回质量指标（MRR / NDCG@k）**：在固定测试查询集上比较不同分块策略的召回排名。测量方法：使用标准检索管道，对比 top-k 中 relevant chunk 的比例和排名。

5. **每次请求的上下文成本**：平均每个查询消耗的 token 数（召回片段内容 + 重叠 + 元数据前缀）。测量方法：在 prompt 组装阶段记录 `context_tokens_used`，按查询聚合。

6. **端到端检索延迟**：从查询到返回召回结果的 P95 延迟。测量方法：在检索中间件埋点，区分向量搜索、重排序和元数据拼接耗时。

## 失败模式、诊断证据与恢复动作

1. **孤儿片段**：切分后某一片段只包含半句话或无意义词组，导致嵌入语义丢失。诊断证据：大量 chunk 长度低于 `min_length`，且向量相似度查询结果随机。恢复：回退到更高优先级的边界或合并相邻短片段。

2. **代码块 / 表格被拦腰截断**：片段开头是代码行中间或表格单元格，导致 LLM 无法理解结构。诊断证据：chunk 内容以非闭合 fence 标记、表格分隔线不完整或 `<td>` 未闭合。恢复：将 `protect_blocks` 加入不可穿越边界列表，并重新切分受影响的 source。

3. **重叠爆炸**：短列表或 FAQ 条目导致相邻片段重复度过高，召回结果充斥冗余。诊断证据：不同 chunk_id 的片段内容 Jaccard 相似度超过 0.7，且 top-k 召回中出现大量重复 source。恢复：对短体裁关闭重叠或改用元数据继承替代内容复制。

4. **语义漂移**：过小的片段将完整论证拆散，单个片段无法承载独立语义，检索时召回片段与查询相关但无法回答问题。诊断证据：高召回率但低答案覆盖率，片段标题链显示论证被切断。恢复：提高最大长度、优先按章节边界切分，或启用父 chunk 摘要。

5. **元数据与源文档版本不一致**：源文档更新后，chunk 仍携带旧标题链或行号，导致 LLM 引用错误。诊断证据：`version_hash` 不匹配，但 chunk 的 `updated_at` 早于 source 最新修改时间。恢复：基于 fingerprint 的增量删除与重建，定期运行一致性校验任务。

## 问答测试样例

1. **正向问题**：分块策略中 ChunkSpec 的作用是什么？
   **期望回答**：ChunkSpec 是分块器与嵌入器之间的契约，定义最大长度、长度单位、边界优先级、重叠策略和元数据继承规则，使具体切分算法可替换。

2. **正向问题**：为什么要在片段上附加标题链而不是只在 prompt 阶段拼接？
   **期望回答**：标题链属于上下文层元数据，能在召回后帮助 LLM 还原片段在原文中的位置与层级，避免在 prompt 组装阶段重复解析源文档。

3. **边界问题**：当一段代码块长度超过 `max_length` 时，分块器应如何处理？
   **期望回答**：代码块属于 `protect_blocks`，不应被普通段落边界策略穿越；应在代码块内部按次级安全边界（如函数定义、逻辑空行）切分，并标注片段属于同一代码块。

4. **边界问题**：动态预算与静态预算各自的适用条件是什么？
   **期望回答**：静态预算部署简单，适合早期或文档类型单一的场景；动态预算适合文档体裁差异大、上下文成本敏感且已有充分评估数据的系统。

5. **无证据拒答条件**：请给出某个具体 LLM 在不同分块大小下的绝对准确率排名。
   **拒答条件**：无法回答，因为准确率取决于具体任务、数据集、嵌入模型和 LLM 版本，本知识库未包含此类实验数据。

6. **无证据拒答条件**：分块重叠比例是否越高越好？
   **拒答条件**：不能简单断言越高越好。重叠会提升边界信息保留，但也会增加索引体积、冗余召回和上下文成本；最佳比例需通过评估集测量后确定。

## 维护、版本、来源与相邻主题

分块策略的维护应独立于嵌入模型和 LLM 的迭代。每次修改 ChunkSpec 都视为一次 schema 版本升级，旧版本 chunk 应保留或按版本号隔离，直到新策略完成离线评估。来源追溯要求每个 chunk 保留 `source_id`、`version_hash`、`start_offset`、`end_offset`，以便在文档更新时做增量重建。与相邻主题的关系如下：上游是文档解析与清洗（负责生成结构良好的源文档），下游是嵌入、向量索引与检索排序（依赖 chunk 的语义独立性和元数据完整性）。分块策略还与提示工程、上下文窗口管理、成本估算和可观测性深度耦合，但不应直接依赖具体 LLM 的内部 tokenizer 行为，除非通过显式接口封装。

## 结论：事实、推论与未知

**事实**：分块策略是 RAG 架构中 ingestion 与 retrieval 之间的关键边界；片段的长度、边界、重叠和元数据共同决定召回质量与上下文成本；ChunkSpec、BoundaryDetector、OverlapPolicy、LengthMetric 等接口抽象可以让具体实现可替换；每个 chunk 必须携带来源指纹和定位信息以支持增量更新。

**推论**：在大多数本地 Markdown / Web 知识库场景中，“先语义边界、后长度兜底”的混合策略，加上句子级重叠和标题链继承，能在上下文完整性与成本之间取得较好平衡；层次化分块适合长文档，但应推迟到评估数据表明扁平索引确实不足时再说。

**未知**：具体最佳 `max_length` 和重叠比例无法先验确定，必须通过目标查询集、嵌入模型和下游 LLM 的联合评估得出；不同语言、代码库、表格结构的边界保留率上限也需在真实数据上测量；动态预算的决策模型和训练数据构建方法仍属开放工程问题。
