# 分块策略：在上下文完整、片段大小与检索成本之间保持可验证平衡

## 摘要与问题边界

分块策略决定本地文件知识库、Web 文档或内部 Wiki 在送入向量索引与 LLM 上下文窗口之前，被切分为多少个文本单元及其边界位置。其目标是在单次检索中保留足够的语义上下文，同时控制每次请求占用的 token 数与检索成本。本文的边界限定在：基于文本的分块（不含多模态）、面向 TypeScript/Web 技术栈的本地文件知识库、以观察延迟、稳定性和故障恢复为主的运维视角。本文不覆盖模型训练、多模态编码器或跨语言翻译对齐。

## 核心概念与数据模型

1. **语义单元**：分块不是机械地截断字符串，而是保留一段自包含的最小语义。例如，一个完整的 TypeScript 接口声明或一个函数实现应整体保留；将其腰斩会导致后续 LLM 无法判断参数类型或返回值。

2. **边界锚点**：每个块必须记录原始文档坐标（文件路径、行号、字节偏移、父章节标题），使命中结果能够回源定位，也为重排序和调试提供可验证证据。

3. **重叠窗口**：相邻块之间保留固定长度的公共文本，避免跨边界的查询（如"上一段提到的配置"）在交界处丢失上下文。重叠量通常按目标块大小的 10%–25% 设置。

4. **元数据层**：块内容之外，需携带来源标签、版本号、语言、编码格式、分块器标识与运行时间戳。元数据不参与向量计算，但参与过滤与归因。

5. **容量与成本单元**：以 token 或字符数为计费与上下文占用单位。评估指标不是"块越小越好"，而是"单位有效信息量的延迟与成本"。

6. **检索-生成耦合协议**：检索器返回 k 个块后，必须将这些块按原始顺序或相关性排序后拼接，并确保拼接后的总长度加上系统提示不超过上下文窗口。超过时需触发压缩或截断策略。

## 设计决策与取舍

### 固定大小分块与语义边界分块

固定大小分块实现简单、可预测，但容易切断代码函数、列表或表格。语义边界分块按段落、标题、函数或 Markdown 段落切分，上下文损失小，但会导致块大小分布极不均匀，可能产生远超平均水平的"长尾大块"。建议策略：先按语义边界粗切，再对超大块进行重叠二次切分。

### 重叠与去重

重叠提升边界召回率，但会增加索引体积和冗余检索成本。运维上应监控：索引中字符总量 / 原始文本总量 的比值。该比值超过 1.4 时，说明重叠设置过高，应下调或改用摘要元数据替代原文重叠。

### 粒度与检索次数

小块提升匹配精度，但需要检索更多块才能覆盖完整答案，增加延迟和上下文费用。运维可观察的边界是：单次问题返回 3–5 个块时，答案完整率是否显著高于返回 1–2 个块；若超过 7 个块仍无提升，则粒度已失真或需重排序。

### 版本稳定性与索引一致性

本地文件知识库会随代码迭代变化。同一文档的多次分块版本必须保持版本锚点一致，否则检索器可能返回已删除章节的旧块。推荐用文件内容哈希或 Git blob 作为版本标识，并在索引更新时保留旧版本直到新版本完成校验。

### 压缩与重排序

检索后常对块进行重排序或摘要压缩。压缩可降低上下文成本，但会丢失具体参数、路径或错误日志。运维应要求：压缩后的块必须保留原始块 ID，以便在 LLM 输出出现错误时回查原始文本。

## 可执行的实施流程

1. 收集原始文件清单，记录每个文件的绝对路径、编码、最后修改时间和内容哈希，建立来源登记表。

2. 选择语义边界解析器：Markdown 按标题/段落、TypeScript 按函数/接口/类、JSON 按键路径。对无法识别的混合文档，降级为固定大小窗口。

3. 设置目标块大小（如 512 tokens）与最大块大小（如 1024 tokens），并配置 10%–20% 的重叠字符数。

4. 运行分块器，生成块记录，每个记录包含 chunk_id、source_path、start_line、end_line、version_hash、language、content 和 parent_headers。

5. 对生成的块集合进行容量校验：计算总 token 数、最大块 token、空块数量、长度分布 P50/P95/P99。

6. 将校验通过的块送入嵌入模型，生成向量并写入索引；写入前再次校验 source_path 与 version_hash 是否对应。

7. 部署检索接口，记录每次查询的检索延迟、返回块数、命中分数、原始总长度和拼接后长度。

8. 建立回滚检查点：保留上一版本的索引快照和分块元数据；当新版本索引出现检索质量下降或延迟异常时，可在分钟级切换回旧版本。

## TypeScript 本地文件知识库分块示例

以下是一个面向本地 Markdown 与 TypeScript 文件的轻量分块函数。输入是经过读取的文件内容与元数据；处理阶段按 Markdown 标题和代码边界切分，并保留行号与父标题；输出是块记录数组，可直接送入嵌入与索引。

```typescript
interface FileMeta {
  path: string;
  version: string; // 内容哈希或 Git 版本
  mtime: number;
  encoding: string;
}

interface Chunk {
  chunkId: string;
  sourcePath: string;
  version: string;
  parentHeaders: string[];
  startLine: number;
  endLine: number;
  content: string;
}

function chunkLocalFile(
  text: string,
  meta: FileMeta,
  targetTokens: number = 512,
  overlapChars: number = 80
): Chunk[] {
  const segments = splitBySemanticBoundaries(text, targetTokens);
  const chunks: Chunk[] = [];
  let prevTail = "";
  for (let i = 0; i < segments.length; i++) {
    const seg = segments[i];
    const content = (prevTail + seg.body).trim();
    chunks.push({
      chunkId: `${meta.path}#${i}`,
      sourcePath: meta.path,
      version: meta.version,
      parentHeaders: seg.headers,
      startLine: seg.startLine,
      endLine: seg.endLine,
      content,
    });
    prevTail = seg.body.slice(-overlapChars);
  }
  return chunks;
}
```

输入是单个文件的原始文本与来源元数据；处理依据语义边界和重叠参数生成自包含块；输出数组可被索引系统消费，并在检索命中时通过 sourcePath 和行号定位原文。

## 性能、质量与可观测性指标

1. **检索延迟 P95**：从查询发起到返回 k 个块的时间。应在测试集上运行至少 100 次，记录 cold start 与 warm cache 两种状态。边界：P95 超过 800ms 时应触发告警。

2. **上下文占用率**：每次请求中拼接块的总 token 数占上下文窗口的比例。目标控制在 40%–60%，留出系统提示与生成空间。超过 80% 视为高危。

3. **块命中率**：在标注测试集上，正确答案所需的证据被包含在返回 top-k 块中的比例。建议 top-5 命中率不低于 0.75。

4. **索引膨胀率**：索引总字符量除以原始文件总字符量。正常范围 1.1–1.3；超过 1.5 表示重叠或元数据冗余过高。

5. **来源一致性**：检索返回块的 version_hash 与当前文件系统版本不一致的比例。应低于 0.1%，否则说明索引更新滞后或文件同步失败。

## 失败模式、诊断证据与恢复动作

1. **边界切断**：LLM 输出引用不存在的参数或函数签名。诊断证据：命中块的起止行号位于函数或列表中部；恢复：改用语义边界解析器，对代码文件按 AST 边界切分。

2. **上下文耗尽**：请求返回 504 或超时，且拼接后长度接近上下文上限。诊断证据：上下文占用率持续高于 80%；恢复：降低最大块大小、启用检索后摘要压缩、或提高 top-k 重排序阈值。

3. **版本漂移**：检索结果包含已删除文件或旧版本内容。诊断证据：命中块 version_hash 与当前文件哈希不一致的比例升高；恢复：回滚到上一索引快照，修复文件同步与版本锚点逻辑。

4. **长尾大块阻塞**：少数块大小显著超过 P99，导致单次请求 token 暴增。诊断证据：块长度分布 P99 超过目标大小的 2 倍；恢复：对超大块按子边界二次切分，并记录二次切分后的 parent_headers 链。

5. **空块与噪声块**：索引中存在大量空字符串或仅包含标点的块，影响检索质量。诊断证据：空块数量 > 总块数 1% 或低分命中块占比 > 30%；恢复：在分块后增加清洗过滤步骤，移除空块并设置最小有效长度阈值。

## 问答测试样例

1. 正向问题：如何为本地 TypeScript 文件选择分块边界？可回答：按函数、接口、类声明切分，并在块中保留 startLine、endLine、sourcePath 与 version。

2. 正向问题：重叠窗口的作用是什么？可回答：保留相邻块之间的公共上下文，降低跨边界查询的信息丢失，但会增加索引体积。

3. 边界问题：当块长度分布 P99 是目标大小的 2.5 倍时应如何处理？可回答：启用二次切分，同时记录父标题链与原始块 ID，避免回源断裂。

4. 边界问题：上下文占用率 85% 时是否应继续增大最大块？可回答：不应，优先降低最大块或启用压缩，否则将挤压生成空间并提升超时风险。

## 维护、版本、来源和相邻主题关系

分块策略的维护周期应与文件版本发布周期绑定。每次文档或代码变更后，需重新跑分块、校验、嵌入、索引四步流水线。建议将分块器版本、嵌入模型版本、索引格式版本均写入索引元数据，避免不同版本混用导致检索异常。

来源信息必须保留到块级别，包括文件路径、行号、版本哈希和分块时间。这些字段是后续归因、审计和故障恢复的基础。

相邻主题包括：向量索引构建、嵌入模型选择、重排序策略、上下文窗口管理、RAG 评估框架。分块策略位于它们的上游：分块输出的质量与边界直接影响后续所有环节的可观测性和稳定性。与提示工程的关系是：分块提供事实边界，提示工程决定如何使用这些事实。

## 结论

事实：分块策略将原始文档切分为带来源坐标的语义单元，通过边界锚点、重叠窗口和元数据层支持可验证的检索与回源。合理的分块能够控制单次请求的上下文占用率与索引体积。

推论：在 TypeScript/Web 本地文件知识库中，按函数/接口/类声明等语义边界切分，配合 10%–20% 的重叠和版本哈希校验，可在运维层面获得较稳定的 P95 延迟与命中率。

未知：不同嵌入模型对特定重叠比例和块大小的敏感度、混合文档（Markdown 与代码混排）的最优解析顺序、以及极端长文档（单文件超过 10 万行）下的分块与索引成本曲线，需要依赖项目内部评测集进一步实验。
