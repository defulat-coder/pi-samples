# RAG 检索引用与证据：可追溯结论的架构设计

## 摘要与问题边界

在检索增强生成系统中，"引用与证据"关注的是：模型产出的每个可验证结论，都必须能够回指到具体的来源文件、片段以及版本信息。这一概念不负责评估结论本身是否为真，也不处理版权归属或用户访问权限；它的边界是"证明结论曾经可以从哪些来源的哪些版本中推导出来"。超出边界的问题——例如来源本身的权威性、多来源之间的语义冲突裁决、以及法律意义上的引用合规性——需要由相邻模块处理，不能混入证据层。设计者需要在一开始明确：引用系统是一个可追溯性基础设施，而非一个事实核查系统。

## 核心概念与数据模型

1. **来源单元（SourceUnit）**：可被引用的最小知识实体，通常对应一个文件、一个文档段落或一个数据库记录。每个 SourceUnit 必须拥有一个稳定标识符，在内容不变时保持不变，在内容变化时生成新标识符。在本地文件知识库场景中，标识符可以由相对路径和内容哈希拼接而成，例如 `docs/api/auth.md@sha256:abc123`。

2. **版本定位器（VersionLocator）**：精确描述来源单元在某一时刻的状态，至少包含存储路径、版本哈希和捕获时间戳。版本定位器不依赖文件系统的当前状态，因此即使文件被后续修改，历史结论仍然可以被复核。版本定位器必须是不可变的；如果需要更新，应生成新的 VersionLocator 而不是修改旧的。

3. **片段锚点（FragmentAnchor）**：在 SourceUnit 内部的精确定位信息。可采用行号范围、字符偏移、语义块标识符或三者的组合。行号便于人类阅读，字符偏移适合程序校验，语义块标识符则能在文件小幅重排后仍保持指向能力。单一锚点方案通常不够，建议采用"主锚点 + 备用锚点"结构。

4. **证据包（EvidenceBundle）**：回答中某个具体主张所依赖的全部来源引用的集合。一个 EvidenceBundle 不只包含文本片段，还包含片段与主张之间的角色标注，例如"直接支持"、"提供背景"、"限定范围"或"存在冲突"。没有角色标注的 Bundle 无法支撑复杂的推理场景。

5. **引用断言（CitationClaim）**：从模型生成的一个原子结论到一个或多个 EvidenceBundle 的映射。CitationClaim 需要携带置信度分数和生成时刻的时间戳。置信度不应只由模型自行决定，而应结合检索得分、片段相关性和来源时效性共同计算。

6. **验证接口（Verifier）**：一个可替换的组件，负责在生成之后或用户查询时检查 CitationClaim 是否仍然成立。Verifier 只回答"该引用当前是否可解析"和"被引片段是否与生成时一致"，不判断结论是否正确。接口必须被设计为可插拔，以便在不同存储后端之间切换。

## 设计决策与取舍

### 稳定标识与人类可读路径的分离

内容哈希能够提供稳定的引用目标，但对人类阅读者不友好。设计时应将内部标识与人类可读路径分离：内部使用哈希标识版本，外部展示相对路径加简短哈希前缀。例外情况是历史归档场景，此时路径可能已被重命名，展示路径应通过来源注册表解析，而不是直接使用文件系统路径。

### 精确片段与上下文窗口的两层模型

只给出精确片段会导致上下文丢失，只给出大段落又会降低可验证性。推荐两层模型：核心证据区是精确片段，上下文扩展区是包含核心片段的更大范围。引用展示时默认显示核心证据，允许用户展开上下文。边界问题是，上下文扩展区的范围必须由策略固定，不能由模型动态决定，否则引用边界会变得模糊。

### 同步验证与异步校验的分工

对所有引用进行实时验证会显著增加响应延迟。决策是：生成阶段只做轻量存在性检查，完整验证放入异步管线，结果通过事件流或 Webhook 异步返回。只有当用户明确要求"当前是否仍然成立"时，才触发同步强验证。这一分工的代价是，用户在刚收到回答时可能看到的是基于历史版本的证据状态。

### 单一来源与多来源聚合的显式标注

复杂回答往往需要综合多个来源。设计时必须要求模型在每次综合处显式标注所依赖的来源组合，不能隐含合并。如果一个结论由三个来源共同支撑，CitationClaim 中必须列出三个 EvidenceBundle 及其各自的角色。例外是通用背景知识：如果系统明确判定某陈述属于基础常识，可以标记为 "common_knowledge" 并跳过来源绑定，但这一判定本身需要审计日志。

### 强引用与弱引用的区分

强引用要求被引用的 SourceUnit 和片段在当前版本中仍然存在且语义一致；弱引用允许目标已被删除或修改，但仍保留历史证据价值。设计时应同时支持两种引用类型，并在展示层用不同视觉样式区分。弱引用在用于法律、医疗或安全敏感场景时应触发额外警告。

## 可执行的实施流程

1. 建立来源注册表，为每个 SourceUnit 分配稳定标识符，并记录其所有历史 VersionLocator。
2. 定义片段抽取策略，确定片段最小长度、最大长度、重叠策略以及锚点类型组合。
3. 实现版本冻结机制，在回答生成前锁定所引 SourceUnit 的版本快照，避免生成过程中来源发生变化。
4. 设计证据存储格式，要求 CitationClaim 和 EvidenceBundle 可序列化为 JSON，并支持按回答 ID 和主张 ID 索引。
5. 开发引用生成协议，规定模型输出中引用标记的语法、位置和必须携带的元数据字段。
6. 集成验证管线，将 Verifier 接入生成后处理流程，对输出中的每个引用执行存在性和一致性检查。
7. 构建可观测层，记录每次引用的解析结果、延迟、失败原因和版本差异。
8. 制定回退策略，当引用验证失败时，明确是降级为弱引用、移除引用并提示用户，还是直接拒答。

## 代码示例：本地 TypeScript 知识库中的证据模型

```
interface VersionLocator {
  sourceId: string;
  path: string;
  contentHash: string;
  capturedAt: string;
}

interface FragmentAnchor {
  type: "line" | "offset" | "semantic";
  start: number;
  end?: number;
  blockId?: string;
}

interface EvidenceBundle {
  locator: VersionLocator;
  anchor: FragmentAnchor;
  role: "direct" | "background" | "qualifier" | "conflict";
  excerpt: string;
}

interface CitationClaim {
  claimId: string;
  conclusion: string;
  confidence: number;
  generatedAt: string;
  bundles: EvidenceBundle[];
}

interface Verifier {
  verify(claim: CitationClaim): Promise<{
    resolvable: boolean;
    consistent: boolean;
    currentLocator?: VersionLocator;
    mismatch?: string;
  }>;
}
```

输入是一个模型生成的 CitationClaim，包含结论、置信度和一组 EvidenceBundle。处理阶段由 Verifier 根据 sourceId 和 contentHash 查找当前存储，比对应引用片段的锚点和摘录内容。输出是验证结果，包含是否可解析、是否与生成时一致，以及若不一致时的新版本定位器和差异说明。该接口不判断结论真假，只确认来源当前是否仍支撑该结论。

## 性能、质量和可观测性指标

1. **引用覆盖率**：有至少一个 CitationClaim 支撑的主张数占总主张数的比例。通过解析模型输出中的主张边界并匹配引用标记来测量。目标通常应高于 0.85，通用背景知识声明除外。

2. **引用可解析率**：被 Verifier 判定为 resolvable 的引用占总引用数的比例。该指标直接反映标识符和锚点机制是否稳定。低于 0.95 时应触发锚点策略审查。

3. **片段精确度**：EvidenceBundle 中被用户或评估者判定为相关的片段比例。可通过人工标注或合成问答对自动测量，要求片段内容与问题语义相关。

4. **版本一致性**：回答生成后一段时间内，引用仍然 consistent 的比例。该指标揭示知识库更新频率与回答缓存策略是否匹配。下降过快说明缓存 TTL 设置过长或来源变更过于频繁。

5. **端到端引用延迟**：从模型输出完成到所有引用完成异步验证的中位时间。该指标帮助判断验证管线是否需要水平扩展。

## 失败模式、诊断证据与恢复动作

1. **片段漂移**：文件内容更新后，原有行号或字符偏移失效，导致引用无法解析。诊断证据是 Verifier 返回 resolvable 为 false 且 currentLocator 与原始 locator 的 contentHash 不一致。恢复动作是启动语义重锚定，通过内容匹配找到新位置，并生成新的 CitationClaim。

2. **引用幻觉**：模型输出了看似规范但实际上不存在的引用标识符。诊断证据是 sourceId 或 contentHash 在注册表中无记录。恢复动作是拒绝该回答并要求模型重新生成，同时将失败样本加入训练或提示示例。

3. **版本冲突**：用户看到的回答基于旧版本，但当前知识库已发生关键更新。诊断证据是 versionConsistency 指标下降或用户反馈"信息已过时"。恢复动作是在展示层附加版本提示，并提供"以当前版本重新验证"的入口。

4. **证据不足**：模型对高置信结论只提供了弱证据或背景证据。诊断证据是 CitationClaim 中所有 bundle 的 role 都不是 direct，但 confidence 高于阈值。恢复动作是强制降低输出置信度，或要求模型补充直接证据后再生成。

5. **循环引用**：多个来源片段互相引用，形成证据闭环但没有外部锚点。诊断证据是通过依赖图分析发现引用链中没有 SourceUnit 指向原始外部来源。恢复动作是设定引用深度上限，并要求链中至少有一个来源被标记为 primary。

## 问答测试样例

1. **正向问题**："本项目的认证接口使用什么协议？" 期望回答引用 `docs/api/auth.md@sha256:abc123` 第 12 至 18 行的直接证据，并给出协议名称。

2. **正向问题**："列出所有支持的部署方式。" 期望回答聚合 `docs/deploy/docker.md` 和 `docs/deploy/k8s.md` 两个来源，每个部署方式都有独立 CitationClaim。

3. **边界问题**："如果我把 `docs/api/auth.md` 重命名为 `docs/api/login.md`，原来的引用还能解析吗？" 期望回答说明注册表维护 sourceId 到路径的映射，因此内部引用仍可解析，但展示路径会更新。

4. **边界问题**："一段只出现在上下文扩展区但未在核心证据区的内容，能否单独支撑一个结论？" 期望回答是不能，上下文扩展区只提供背景，核心证据区才产生 direct 角色的 CitationClaim。

5. **无证据拒答条件**："请预测项目三年后的架构方向。" 当知识库中不存在关于未来规划的来源时，模型应拒绝给出具体结论，或明确标注为"无来源支撑的观点"。

6. **无证据拒答条件**："给出某位贡献者的私人联系方式。" 即使文件中有相关信息，若该信息被标记为非公开，系统应拒绝引用并说明访问策略限制，而不是生成无法验证的回答。

## 维护、版本、来源与相邻主题的关系

引用与证据层需要与向量检索、重排序、提示工程和评估体系协同，但不应互相耦合。向量检索负责召回候选片段，重排序负责排序，证据层负责将最终被选中的片段固定为可追溯的引用。提示工程负责教导模型正确输出引用标记，评估体系负责判断引用质量。来源更新应通过事件总线通知证据层，触发异步重新验证。版本策略上，每个 SourceUnit 的每次内容变更都应生成新的 VersionLocator，旧版本保留至少一个可配置的保留周期，以支撑历史回答的复核需求。来源注册表应独立于文件系统，避免重命名或移动操作破坏历史引用。

## 结论

**事实**：每个可验证结论都可以被绑定到具体的 SourceUnit、FragmentAnchor 和 VersionLocator；Verifier 接口是可替换的；引用覆盖率、可解析率、片段精确度、版本一致性和引用延迟是五项核心可观测指标。

**推论**：通过将稳定标识与人类可读路径分离、采用精确片段加上下文扩展的两层模型、以及区分强引用与弱引用，可以在不牺牲响应延迟的前提下实现高度可追溯的 RAG 输出。异步验证管线是平衡实时性与可验证性的合理架构选择。

**未知**：多来源冲突时的自动裁决策略、跨语言知识库的统一锚点方案、以及在极端高频更新场景下版本注册表的存储成本上限，仍需要结合具体业务场景进一步验证。
