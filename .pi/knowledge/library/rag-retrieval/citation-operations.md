# RAG 检索引用与证据链：可回指、可验证、可恢复的设计

## 摘要与问题边界

在检索增强生成（RAG）系统中，回答结论必须能够回指到具体文件、片段和版本信息。这不仅是结果可信度的要求，更是运维团队在观察性能、稳定性和故障恢复时的核心抓手。本文聚焦的边界是：从查询进入检索层，到模型生成最终回答，再到引用证据被验证、记录和审计的全过程；不包括大模型训练、通用提示工程或前端交互设计。关键判断是：一个“正确”回答如果无法证明其来源，在运维视角下应视为不可验证输出，不能用于高风险的自动化决策或事后追溯。

## 核心概念与数据模型

1. **来源文件（Source File）**：指被摄入知识库的原始文档，必须具备全局唯一标识符 `source_id` 和版本指纹 `version_hash`。同一个文件的不同版本应被视为不同来源，而不是覆盖旧数据。
2. **片段锚点（Chunk Anchor）**：每个文本片段在原始文件中的精确位置，包括起始行号、结束行号、段落 ID 或分块序号。锚点不能只在向量索引中隐式存在，必须在返回结果中显式携带。
3. **证据引用（Evidence Citation）**：回答中每个事实性陈述到具体片段锚点的映射。一个引用至少包含 `source_id`、`version_hash`、`chunk_id` 和 `span`（片段内范围）。
4. **版本指纹（Version Fingerprint）**：通常采用 SHA-256 或 Git commit hash，用于在文件更新后判断索引与回答是否仍基于同一版本。版本不一致是运维中最常见的隐蔽错误。
5. **检索上下文（Retrieval Context）**：记录每次查询使用的索引名称、嵌入模型、top-k 数量、相似度阈值和重排策略。这些信息决定了引用是否可被复现。
6. **置信度与覆盖度（Confidence and Coverage）**：引用覆盖率衡量回答中有多少事实被证据支持；未覆盖部分应标记为“模型生成”或“无证据”。覆盖率低于阈值时应触发告警或拒绝输出。

## 设计决策与取舍

### 引用粒度：句子级还是段落级
句子级引用精确但成本高，模型容易产生碎片化输出；段落级引用更易生成，但可能把无关信息纳入证据。边界判断：当片段长度超过 512 个 token 时，应要求模型在引用内给出 span 子范围，否则允许段落级引用。

### 版本固定：实时索引还是快照
实时索引能反映最新文档，但会导致同一问题在不同时刻得到不同证据；快照版本保证可复现，却需要显式切换机制。取舍：生产环境应采用“快照优先、实时更新走灰度”策略，每次查询绑定到具体索引版本。

### 引用格式：内联引用还是脚注
内联引用适合人工快速核对，脚注适合批量审计。例外：当回答被其他系统消费时，必须同时提供结构化 JSON 和可读文本两种格式，不能只依赖文本中的括号编号。

### 无证据时的策略：拒绝还是生成
完全拒绝会降低用户体验，但生成无证据内容会引入幻觉风险。判断：对事实性问题强制拒答；对创意性或概括性问题允许低置信度生成，但必须在输出中明确区分“有证据”与“无证据”部分。

### 存储成本：保留完整片段还是仅引用 ID
保留完整片段便于离线审计，但增加存储；仅保留 ID 节省空间，却依赖索引长期可用。取舍：至少保留片段原文的哈希和 160 个字符的摘要，并在 30 天内保留完整片段用于故障回溯。

## 可执行实施流程

1. 为每个来源文件分配 `source_id` 和 `version_hash`，并在文件变更时生成新版本，禁止原地更新。
2. 将文件切分为固定大小或语义边界片段，为每个片段生成 `chunk_id` 和锚点信息。
3. 同时构建向量索引和倒排索引，确保检索结果既能按语义召回，也能按关键词召回。
4. 在检索层记录每次查询的 `retrieval_context`，包括索引版本、模型名称、top-k 和阈值。
5. 在系统提示中明确要求模型对任何事实性结论输出引用，未引用内容使用 `unverified` 标签。
6. 在生成后解析模型输出，抽取引用编号，并验证其是否存在于本次检索返回的片段集合中。
7. 将最终回答、引用列表、检索上下文和模型输出哈希写入审计日志，保留至少 90 天。
8. 运行引用覆盖率检查，计算被引用片段数与事实陈述数的比例，低于 0.8 时标记为低风险。
9. 配置告警：当版本指纹不一致、引用解析失败率超过 1% 或检索延迟 P99 超过 2 秒时触发。
10. 建立回滚机制：当新版本索引出现引用错误率上升时，可在 5 分钟内切换回上一快照。

## 性能、质量和可观测性指标

1. **检索延迟 P50/P99**：使用 OpenTelemetry 或类似工具在检索函数入口和出口打点，P99 超过 2 秒视为容量或索引异常。
2. **引用覆盖率**：计算回答中事实陈述数与成功引用数之比，目标大于 0.9；可通过规则解析或辅助模型评估。
3. **引用准确率**：抽样人工检查引用是否真正支持对应陈述，每周至少检查 100 条。
4. **版本一致性检查通过率**：对比回答中的 `version_hash` 与当前索引中同 `source_id` 的最新版本，一致率应高于 99.5%。
5. **幻觉率**：通过无证据输出比例和引用验证失败率综合衡量，目标低于 1%。
6. **恢复时间（MTTR）**：从引用错误告警触发到回滚完成的时间，目标小于 5 分钟。

## 失败模式与恢复

1. **引用幻觉**：模型输出 `[1]` 但检索结果中不存在该片段。诊断证据是引用解析失败日志；恢复动作是降低模型温度、收紧提示，并过滤未验证引用。
2. **版本漂移**：文件已更新，但索引仍返回旧版本。诊断证据是 `version_hash` 与文件系统不一致；恢复动作是重新触发索引任务并切换快照。
3. **检索遗漏**：相关片段相似度低于阈值未被召回。诊断证据是同一问题在 top-k 提高后得到更好答案；恢复动作是调整阈值、重排模型或补充同义词。
4. **输出格式不合法**：模型未按约定 JSON 输出，导致引用解析失败。诊断证据是解析错误日志；恢复动作是增强 few-shot 示例并加入输出模式校验。
5. **索引损坏**：向量索引与元数据索引不一致，导致 `chunk_id` 无法对应原文。诊断证据是索引一致性检查失败；恢复动作是从上一个健康快照重建索引。
6. **审计日志缺失**：引用数据未写入日志，导致无法事后回溯。诊断证据是日志采样为空；恢复动作是检查写入队列和 retention 策略。

## 问答测试样例

**正向问题**
- 问：“本地知识库引用必须包含哪些字段？”
- 期望：回答包含 source_id、version_hash、chunk_id，并引用 `docs/rag-citation.md` 第 88 至 95 行。

**边界问题：多版本冲突**
- 问：“2024 年和 2025 年的配置要求有什么不同？”
- 期望：回答分别引用两个版本的文件，并标注各自的 version_hash。

**边界问题：片段跨文件**
- 问：“如何同时配置索引和提示？”
- 期望：回答引用多个文件的片段，并说明每个引用对应的子主题。

**边界问题：同义查询**
- 问：“怎么设置 RAG 里的来源追踪？”
- 期望：即使查询未出现“引用”一词，也能召回相关片段并给出正确引用。

**无证据拒答**
- 问：“如何配置 PostgreSQL 主从复制？”
- 条件：知识库中没有 PostgreSQL 相关内容。
- 期望：回答明确说明“当前知识库未找到相关证据，无法回答”，而不是给出通用答案。

**无证据拒答：超出范围**
- 问：“明天北京天气如何？”
- 期望：拒绝回答，因为知识库不包含实时天气数据，且无法提供文件级证据。

## 维护、版本、来源与相邻主题关系

维护重点是定期运行引用一致性检查，清理失效快照，并保留至少两个版本的索引以便回滚。版本管理应与文件系统或 Git 仓库同步，避免在索引层单独维护版本号。来源审计要求每次回答都能追溯到具体文件和生成时间戳，不能仅依赖会话 ID。

本主题与相邻主题的关系如下：
- **数据摄入与分块**：决定片段锚点的质量，是引用准确的基础。
- **索引管理**：决定检索结果和版本一致性，直接影响引用可复现性。
- **提示工程**：决定模型输出引用的格式和覆盖率。
- **评估与对齐**：决定引用准确率和幻觉率的测量标准。
- **可观测性**：决定日志、指标和告警的完整性。

## 结论

事实：在 RAG 系统中，每个回答结论都可以被强制要求回指到文件、片段和版本信息；引用结构化字段包括 `source_id`、`version_hash`、`chunk_id` 和 `anchor`；检索上下文必须被记录以便复现。

推论：当运维团队能够持续观察检索延迟、引用覆盖率、版本一致性和幻觉率时，系统的稳定性和可恢复性会显著高于仅依赖端到端测试的基线；无证据时应优先拒答高风险事实性问题。

未知：不同嵌入模型和重排策略对引用准确率的具体影响需要针对每个知识库单独评估；模型在超长上下文中的引用边界稳定性尚未有统一结论，需通过持续实验验证。
