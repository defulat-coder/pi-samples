# 混合检索：字面通道与语义通道的融合架构

## 摘要与问题边界

混合检索不是把两种算法拼在一起，而是为“用户表达意图”与“文档实际措辞”之间的鸿沟设计一条可演进的桥接层。单独的字面检索擅长精确术语、版本号、配置键和命令片段，但容易漏掉同义改写、意图泛化和跨段落推理；单独的语义检索擅长概念对齐，却在专有名词、短标识符和最新引入的术语上频繁产生幻觉或低置信度。架构视角下，核心问题是如何把两条通道的结果纳入同一个可审计、可替换、可回滚的融合框架，而不是在工程实现初期就锁定某个向量库或 BM25 引擎。

责任边界需要提前画清楚：查询路由层只决定“用哪些通道”，不解释内容；字面索引层只负责 token 到文档的命中，不推断语义；向量索引层只负责嵌入空间中的近似近邻，不做事实校验；融合层只负责分数归一化与排序，不生成最终答案；生成层只在拿到带来源的候选片段后才开始推理。任何一层都不应跨越边界去做下一层的工作。

## 核心概念与数据模型

1. **字面通道（Lexical Channel）**：基于稀疏表示，典型实现包括倒排索引、BM25、TF-IDF 或精确前缀匹配。它的强项是命中文档中确实出现的字符串，例如 `pnpm-lock.yaml`、`packageManager`、`SessionManager.inMemory()` 这类项目级专有名词。
2. **语义通道（Semantic Channel）**：基于密集向量，通过嵌入模型把查询和文档块映射到同一向量空间，使用近似最近邻（ANN）召回。它适用于查询词与文档词不完全一致但意图相近的场景，例如“会话生命周期”与 `SessionManager` 的映射。
3. **证据片段（Evidence Chunk）**：混合检索的最小返回单元，必须包含原始文本、来源文件路径、块边界、所属通道、原始分数和归一化分数。没有来源的候选不能进入融合层。
4. **融合层（Fusion Layer）**：将两个通道的分数转换到可比空间，并加权合并。常见策略包括 Reciprocal Rank Fusion（RRF）、线性加权、Min-Max 归一化后再加权。融合层必须暴露参数接口，便于 A/B 测试和回滚。
5. **查询路由（Query Router）**：决定一次查询激活哪些通道，并可触发查询改写。路由策略可以是静态规则（例如含版本号或文件路径时强制激活字面通道）、模型分类器或启发式规则。路由器的输出是可审计的：它必须记录选择了哪些通道以及理由。
6. **重排序与截断（Rerank & Cutoff）**：在融合后的候选列表上，用轻量级交叉编码器或规则进行二次排序，然后按上下文预算截断。截断不是简单取 top-k，而是兼顾多样性、来源覆盖和去重。

## 设计决策与取舍

### 通道独立还是共享索引
让两个通道共享同一个分块和元数据层，但各自维护独立的索引文件。这样可以在不破坏字面索引的情况下升级向量模型，也可以单独重建 BM25 索引而不重新计算 embedding。代价是写入路径需要双写一致性，通常用异步任务队列和版本标记来缓和。

### 分数归一化策略
BM25 分数与余弦相似度不在同一量纲，不能直接相加。RRF 用排名倒数，避免对原始分数分布敏感；线性加权需要先归一化，适合分数分布稳定的场景。项目初期建议先用 RRF，因为它对单通道异常高分更鲁棒，但会损失头部精确区分度。

### 嵌入模型版本锁定
嵌入模型的版本一旦变更，整个向量空间可能漂移。必须在配置中显式声明模型名称、版本、维度、池化策略和最大序列长度。模型升级应视为一次“向量索引重建事件”，而不是简单的依赖补丁。

### 查询改写由谁负责
改写可以提高语义通道召回，但会增加延迟并引入不可控的语义偏移。建议把改写放在可选的预处理阶段，并记录改写前后的查询。对于精确匹配型查询，应允许路由层跳过改写，直接走字面通道。

### 上下文预算分配
需要为每个通道设定最大返回数，避免语义通道在长尾文档中淹没字面通道的精确命中。同时设定跨通道去重阈值，防止同一证据片段因措辞相近被重复计入上下文。

## 可执行的实施流程

1. 定义证据块边界：决定按段落、固定 token 数还是语义边界切分，并为每个块标注文件路径、行号范围和版本。
2. 建立文档预处理流水线：清洗、去重、提取代码注释和文档标题，生成统一格式的中间文件。
3. 构建双索引管道：一条生成 BM25 或倒排索引，另一条生成向量索引；两者共用元数据但独立存储。
4. 选择并冻结嵌入模型：记录模型标识、维度、序列长度和输出归一化方式，纳入版本控制。
5. 实现查询路由器：基于规则、关键词分类或轻量模型，决定激活哪些通道，并生成查询改写副本。
6. 实现双通道并行召回：对字面通道执行 token 查询，对语义通道执行向量 ANN，各自返回候选证据块。
7. 实现融合与归一化：将两通道排名转换为统一分数，按权重合并，去重，进入重排序。
8. 建立观测与反馈闭环：记录每次查询的路由选择、通道召回、融合结果和用户后续行为，用于评估和调整参数。

## 本地文件知识库示例

示例场景：用户查询 “pnpm workspace 怎么设置 private field”。输入是原始字符串，处理过程如下：字面通道命中 `pnpm-workspace.yaml` 和 `package.json` 中确实出现 `private` 与 `workspace` 字样的文档块；语义通道命中讨论 monorepo 包作用域和 npm 发布范围的段落，即使文中没有出现完全一致的 “private field” 短语。融合层把两通道候选按 RRF 公式合并，其中字面通道候选因头部排名靠前获得较高倒数排名分，语义通道候选补充了概念说明。输出是一个按最终分数排序的候选列表，每个条目包含：来源文件路径、块起始行号、所属通道、原始分数、归一化分数和摘要文本。

对应的配置结构可以用以下伪描述表达：根对象包含 lexicalChannel（指定索引目录与 topK）、semanticChannel（指定模型版本、维度、索引目录与 topK）、fusion（strategy 为 RRF，k 取 60）、rerank（启用交叉编码器与上下文预算 4000 tokens）、observability（记录每次查询的事件 ID 与通道命中率）。输入端点接收 `{ query, sessionId, projectCwd }`，处理层并行访问两个通道，输出端点返回 `{ queryId, rankedChunks, routingDecision, latencyMs }`。这个示例说明：输入是用户意图，处理是通道独立召回与融合，输出是可审计的带来源候选。

## 性能、质量与可观测性指标

1. **双通道端到端召回延迟 P99**：从请求到融合截断完成的时间，建议按通道分别记录，以便定位慢路径。
2. **字面命中率与语义命中率**：对已知查询集，统计仅字面通道、仅语义通道、双通道同时命中的比例，识别通道覆盖盲区。
3. **融合后 top-k 答案相关性**：用 LLM 或人工评分，对 top-5 候选按“是否回答查询”打分，目标是高于任一单通道的 top-k。
4. **跨通道去重覆盖率**：统计被识别为重复的候选比例，避免上下文被重复证据浪费。
5. **查询路由准确率**：对标注数据集，检查路由器是否正确选择了通道组合。精确术语查询不应被错误路由到纯语义通道。
6. **上下文利用率**：最终送入生成层的 token 数与预算上限之比，过高说明截断失效，过低说明召回不足。

## 失败模式

1. **嵌入模型漂移**：升级或重新训练模型后，向量索引与查询向量不再对齐，导致语义通道召回率骤降。诊断证据是语义命中率在模型更新前后出现断崖式下降。恢复动作是回滚模型版本并重建索引。
2. **分数空间不匹配**：错误地直接将 BM25 与余弦相似度相加，使某一通道因量纲优势垄断排序。诊断证据是融合结果中某一通道来源占比异常接近 100%。恢复动作是切换到 RRF 或正确的归一化策略。
3. **查询路由误判**：含精确文件名或版本号的查询被路由到语义通道，导致无法命中。诊断证据是“文件路径查询”的命中率低于阈值。恢复动作是增加路由规则，强制含路径或版本号的查询优先走字面通道。
4. **上下文截断丢证据**：融合后候选过多，关键证据在重排序或截断中被排除。诊断证据是用户反馈“答案正确但遗漏了某条文档”。恢复动作是引入多样性约束，确保每个来源至少保留一个候选。
5. **索引不同步**：字面索引已更新但向量索引尚未重建，导致同一文档在两通道中呈现不同版本。诊断证据是同一来源路径在两通道中的内容摘要冲突。恢复动作是引入索引版本标记，在融合前过滤版本不一致的候选。

## 问答测试样例

1. 正向问题：“Pi Agent 如何通过 AgentSession 创建会话？”期望双通道共同命中：字面通道命中 `AgentSession` 和 `createAgentSession`，语义通道命中会话生命周期与事件订阅相关段落。
2. 正向问题：“pnpm workspace 的 `package.json` 里 `private` 字段有什么用？”期望字面通道精确命中 `private` 和 `workspace`，语义通道补充 monorepo 发布策略。
3. 边界问题：“为什么我的查询路由把 `SessionManager.inMemory()` 送到了语义通道？”这是诊断类问题，期望命中路由规则、日志格式和配置项，而非生成代码。
4. 边界问题：“请比较 RRF 和线性加权在短查询下的差异。”期望命中融合策略设计决策，包含具体参数和边界条件。
5. 无证据拒答：“这个项目的 CI 流水线用的是什么工具？”如果知识库中没有 CI 配置或文档，应明确回答没有证据，而不是猜测 GitHub Actions。
6. 无证据拒答：“Pi SDK 下一版本会支持哪些新模型？”如果知识库没有版本计划或路线图，应回答无法验证，不推断未来功能。

## 维护、版本、来源与相邻主题

混合检索需要持续维护三个版本线：文档内容版本、索引构建版本和融合配置版本。文档更新后，应触发双索引重建任务，并在元数据中标记 `contentVersion` 和 `indexVersion`。融合配置参数（RRF 常数、通道权重、上下文预算）应纳入配置版本，与模型发布记录一起审计。

来源管理要求每条候选都能追溯到原始文件路径和版本。项目中 `.pi/knowledge` 与 `.pi/skills` 是官方与自定义知识来源，混合检索架构不应假设它们自动加载，而应显式把 `cwd` 下的这些目录作为资源加载输入。

相邻主题包括：纯语义检索（Dense Retrieval）、纯字面检索（Lexical Retrieval）、重排序（Reranking）、查询改写（Query Rewriting）和检索增强生成（RAG）。混合检索是这些主题的集成层，而不是替代层。它与 Agent 工具调用的边界在于：混合检索返回带来源的候选，Agent 负责决定如何引用、验证和呈现。

## 结论

事实：混合检索通过独立维护字面通道与语义通道，再用融合层统一排序，可以在多数真实查询上同时降低漏召回和误召回。分数归一化、查询路由、索引版本和来源可追溯是架构落地的四项硬性约束。

推论：采用 RRF 作为初始融合策略，并为精确术语查询保留路由规则，是本项目级知识库中较稳健的起点。当查询词与文档措辞高度一致时，字面通道应占主导；当查询表达意图而非具体术语时，语义通道应起补充作用。

未知：具体的最优权重和 RRF 常数取决于项目文档的术语密度和嵌入模型的向量分布，无法在未测量前预设；不同 ANN 算法在高维代码向量上的召回-延迟曲线也需要项目自有数据验证。这些参数应通过在线实验和离线评估共同确定，而不是作为常量写死。
