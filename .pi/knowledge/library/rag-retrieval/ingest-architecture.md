# 语料摄取：将 Markdown、结构化记录与来源元数据转换为可检索概念的架构方法

## 摘要与问题边界

语料摄取不是简单的“把文件导入向量数据库”，而是知识库与外部来源之间的责任边界层。它处理三类输入：Markdown 文档、结构化记录（如 ADR、JSON Schema、YAML 配置项）以及来源元数据（文件路径、修改时间、作者、版本、标签）。输出是携带来源证明的可检索概念，使检索器能按标题、术语、实体和关系召回内容，也使 Agent 在引用时有明确的出处。本文不讨论爬虫抓取、权限系统或排序模型，只关注本地文件知识库中从原始语料到索引概念的转换架构。

## 核心概念与数据模型

1. 来源记录（SourceRecord）：标识一份原始材料的不可变入口，包含规范 URI、MIME 类型、最后修改时间、内容哈希和发现来源。URI 必须稳定，建议使用 `file://` 加仓库相对路径，并辅以 git blob 哈希作为次级标识。
2. 逻辑块（LogicalChunk）：以标题层级、列表边界或表格边界为锚点的自包含信息单元。每个块保留父标题链（breadcrumbs），使检索结果可还原上下文。
3. 概念记录（ConceptRecord）：从块中抽出的术语、实体或关系，包含规范标签、别名、定义、作用域和类型。一个块可产出多个概念，一个概念也可由多个块共同支撑。
4. 来源元数据（SourceMetadata）：从文件前置 matter、sidecar 文件或版本控制中解析的附加信息，例如标题、作者、版本、标签、置信度、提取策略和许可证。
5. 索引视图（IndexView）：概念在检索层的多模态表示，包括稀疏词项倒排、稠密向量嵌入、结构化 facet 和可选的知识图谱边。摄取层只负责生成这些视图，不负责排序。
6. 摄取管线（IngestionPipeline）：由发现、校验、解析、归一化、切分、抽取、索引和审计八个阶段组成的可替换流程。每个阶段输入输出均为显式接口，允许单独替换实现。

## 设计决策与取舍

**来源边界：文件系统优先，API 作为扩展。** 本地文件知识库的核心优势是可重复、可版本化，便于在 CI 中做差异校验。API 来源引入网络、鉴权和异步问题，应抽象为 `SourceProvider` 接口，默认实现为本地文件，API 实现仅作为可选插件。

**解析深度：Markdown 用语法树，纯文本用流。** Markdown 需要保留标题、表格、代码块和链接，因此使用 AST 解析；纯文本笔记则按段落流切分。代价是 AST 解析更慢，但能避免列表项被无情截断。

**切分策略：语义边界优先，Token 上限兜底。** 切分不以固定字符数为唯一标准，而是按 H2/H3 标题和列表/表格边界生成逻辑块，再检查 Token 是否超过 512。超长块按句子边界二次切分，保留父标题链。

**索引形态：概念索引为主，全文索引为辅。** 概念索引支持 Agent 做结构化推理，全文索引捕获精确短语和代码片段。两者共存，但概念记录是主要召回对象。

**元数据冲突：frontmatter 优先于 sidecar。** 允许嵌入式 frontmatter 和同名 sidecar 文件并存。冲突时，frontmatter 覆盖 sidecar，因为嵌入式数据与内容同生共死，更易维护。

## 可执行的实施流程

1. 发现：通过 glob 枚举允许的目录，按 MIME 类型和文件后缀过滤，记录每份文件的 mtime 和 sha256。
2. 校验：校验 frontmatter 或 JSON Schema，标记非法文件到隔离队列，避免污染下游。
3. 解析：Markdown 用 remark/unified 生成 AST；YAML/JSON 记录用 schema 校验；提取标题、标签和作者。
4. 归一化：将相对链接转换为规范 URI，剥离脚本、iframe 和不可序列化内容，统一日期和作者格式。
5. 切分：按标题层级和结构边界生成逻辑块，为每个块生成 breadcrumbs，并保留原始块在文件中的字符偏移。
6. 抽取：基于规则、模板和可选 NER 提取概念，记录抽取方法和置信度。
7. 索引：向向量库写入嵌入，向倒排索引写入词项，向 facet 存储写入结构化字段，同时写入来源反向索引。
8. 审计：生成摄取清单，统计阶段耗时、错误数、概念数，运行 QA 测试样例，输出质量报告。

## 示例：输入、处理与输出

以下示例描述一份本地 Markdown 文档在摄取流程中的形态变化，无具体实现细节。

来源记录：
- uri：`file:///docs/adr/0001-ingestion.md`
- mtime：`2025-03-10T09:14:00Z`
- sha256：`a1b2c3…`
- 内容类型：`text/markdown`

原始内容包含 frontmatter：标题、作者、版本、标签，以及一个 H2 章节“核心概念”和一个无序列表。

处理动作：
1. 解析 frontmatter 生成 SourceMetadata，校验必填字段。
2. 按 H2 切分得到逻辑块“核心概念”。
3. 从列表项中提取概念“LogicalChunk”，记录别名“逻辑块”“语义单元”。

输出概念：
- label：`LogicalChunk`
- aliases：`逻辑块`、`语义单元`
- definition：以标题或结构边界为锚点的自包含信息单元
- provenance：`file:///docs/adr/0001-ingestion.md#核心概念`
- chunkContext：`ADR 0001 > 核心概念`
- confidence：0.95
- extractor：heading-list-rule

## 性能、质量与可观测性指标

1. 单文件摄取延迟：从发现到索引写入的端到端时间，按 P50 和 P99 分阶段记录。测量方法是在每个阶段出口记录耗时，并汇总到摄取清单。
2. 逻辑块完整率：被切分后仍保留标题链和表格/list 完整性的块占比。通过审计脚本检查每个块是否包含断裂表格或孤立列表项。
3. 概念覆盖率：已命名实体中附带定义的比例。用 QA 测试样例和人工标注的术语表对比计算。
4. 检索精度@K：对固定测试问题，返回前 K 个概念中相关概念的比例。需要维护一份与来源绑定的 golden set。
5. 错误隔离率：校验失败、解析失败或索引失败的文件被正确隔离且未进入主索引的比例。通过清单中的状态字段统计。

## 失败模式、诊断证据与恢复动作

1. 解析失败：YAML frontmatter 语法非法或缺少必填字段。证据是解析器报错行号和 schema 验证报告。恢复动作：将文件移入隔离队列，记录错误，通知作者，允许通过 sidecar 手动补全。
2. 表格被截断：切分器把表格拆到多个块，导致行单元格丢失。证据是逻辑块中出现未闭合的表格标签或行数校验失败。恢复动作：启用表格感知边界，强制表格作为一个整体块，超长表格按行拆分时保留表头。
3. 元数据漂移：文件被重命名或移动，但索引中仍保留旧 URI。证据是 mtime 异常或 git 状态显示路径变化，而来源反向索引指向不存在的路径。恢复动作：用内容哈希作为主键，并在重命名时生成重定向记录。
4. 概念冲突：同一术语在不同文档中有不同定义。证据是 duplicate label 告警，附带来源列表。恢复动作：按来源优先级合并（如 ADR > 设计文档 > 博客），并在概念中保留多源定义和置信度。
5. 索引写入失败：向量库或倒排索引因网络/容量问题写入部分成功。证据是写入计数与预期计数不一致，或异常日志。恢复动作：写入死信队列，按指数退避重试，必要时切换只读模式并告警。

## 维护、版本、来源与相邻主题关系

来源记录使用 git commit 与内容哈希共同定位，确保历史版本可回滚。管线本身通过 schema 版本管理，schema 升级时必须有迁移策略：旧版本索引可保留为只读，或按新 schema 重新摄取。维护周期包括增量摄取（基于 mtime 和哈希差异）、全量重跑（schema 变更后）和定期死信清理。

每个概念必须链接到来源 URI、逻辑块和抽取方法，形成可验证的引用链。摄取层不处理权限、排序和对话管理：权限由上游网关负责，排序由检索层负责，对话由 Agent 运行时负责。下游消费者包括 Web 检索界面、本地测试脚本和评估流水线。相邻主题“嵌入模型”是摄取层的下游消费者，而不是摄取层本身。

## 结论

事实：语料摄取的核心产出是携带来源证明的可检索概念；管线的八个阶段和六个核心数据模型是架构边界本身，不依赖于具体实现。

推论：以语义边界而非纯 Token 切分能提升上下文完整性；概念索引与全文索引并存比单一索引更适合 Agent 引用；frontmatter 优先策略能降低元数据漂移风险。

未知：在不同领域知识库中，最优逻辑块大小和表格拆分阈值仍需通过 golden set 实验确定；大规模仓库中 schema 迁移的端到端成本取决于具体存储引擎和文件数量，当前项目未验证。
