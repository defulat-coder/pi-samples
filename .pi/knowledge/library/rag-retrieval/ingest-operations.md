# 语料摄取：从 Markdown 与结构化记录构建可检索概念的验证与运维

## 摘要与问题边界

语料摄取是把 Markdown 文档、结构化记录与来源元数据转化为可检索概念的过程，不是简单的文件搬运。本文从验证与运维视角出发，关注单次成功之外的稳定性、延迟、容量边界和故障恢复。讨论范围限定在本地文件型知识库、TypeScript/Web 服务边界，以及向向量索引与图谱索引的转换；不涉及外部爬取、多租户隔离、实时协作编辑等未被项目验证过的场景。

核心问题边界可归纳为三条：第一，输入侧必须接受格式异构的原始文件，并保证语义单元不被人为截断；第二，处理侧必须保留来源链路与版本指纹，使每次检索结果都能回溯到原始段落；第三，输出侧必须生成可被下游检索器按标题、标签、术语和正文召回的概念对象，同时暴露可观测的进度、错误与质量指标。

## 核心概念与数据模型

1. **原始文档（Raw Document）**：指磁盘上的 Markdown 文件、JSON 记录文件或 YAML 配置文件。其唯一标识采用相对路径加内容哈希，例如 `docs/api/auth.md#a1b2c3`，避免重命名导致索引失效。

2. **语义块（Semantic Chunk）**：将原始文档按标题层级、代码块边界或自然段落切分后的最小检索单元。每个块必须记录起始行号、结束行号、父级标题路径和所属文档标识，保证召回后能定位原文。

3. **概念节点（Concept Node）**：从语义块中提取的、带有显式标签与术语的检索对象。一个概念节点可包含多个语义块引用，但每个语义块在同一版本内只能属于一个逻辑概念节点，防止重复召回。

4. **来源元数据（Provenance Metadata）**：包括文档路径、Git 提交哈希、文件修改时间、切分策略版本、提取器版本和校验签名。校验签名采用 SHA-256 对块的原始文本与元数据联合计算，用于后续比对。

5. **索引记录（Index Record）**：概念节点经向量化或图谱化后的输出形态，包含向量嵌入、稀疏关键词、关系边和目标集合。索引记录必须携带与概念节点一致的来源指纹。

6. **摄取任务（Ingestion Job）**：一次完整的摄取运行，包含扫描、解析、切分、提取、索引和验证六个阶段。任务级别记录开始时间、结束时间、处理字节数、失败项列表和最终校验报告。

## 设计决策与取舍

### 1. 切分策略：按标题层级还是固定长度
按标题层级切分能保留上下文，但块大小差异大；固定长度切分便于批处理，却容易截断代码示例或列表。项目采用混合策略：优先在标题边界处切分，若单块超过 800 个字符再在句子边界处二次切分。代价是需要维护两套边界规则，单元测试覆盖成本上升。

### 2. 元数据存储：内联还是旁路
内联把元数据写进索引字段，查询时无需二次查找；旁路把元数据存入独立键值存储，索引更轻。项目选择旁路存储，原因是来源元数据体积可能超过向量字段，且图谱关系需要单独版本化。代价是每次召回都要额外一次查找，延迟增加约 5 到 15 毫秒。

### 3. 嵌入生成：同步批量还是异步队列
同步批量实现简单，适合万级文档以下场景；异步队列能处理大容量，但增加运维复杂度。项目采用本地文件型知识库默认同步批量，超过一万个语义块时自动切换到异步队列。切换阈值以实际压测为准，不是理论推导。

### 4. 错误处理：严格中止还是部分失败
严格中止保证索引一致性，但任何小错误都会阻塞更新；部分失败允许继续处理健康文件，但需记录失败项并在后续重试。项目采用部分失败策略，每次任务结束时生成失败清单，运维人员可在不重建全量索引的情况下单独修复。

### 5. 版本管理：全量重建还是增量差异
全量重建逻辑简单，可消除历史脏数据；增量差异节省时间与计算资源，但要求精确比对内容哈希。项目采用增量差异作为默认路径，仅在切分策略版本升级时触发全量重建。这意味着旧版切分策略产生的索引会被整体替换，而不是逐步演进。

## 可执行的实施流程

1. 扫描文件系统，枚举目标目录下的 `.md`、`.mdx`、`.json` 和 `.yaml` 文件，生成原始文档清单，并记录每个文件的绝对路径、大小和修改时间。

2. 对每份原始文档计算内容哈希，与上一次摄取任务的哈希表比对，标记新增、变更和删除的文件。

3. 根据文件扩展名选择解析器：Markdown 使用标题层级与代码块边界解析；JSON 使用数组元素或对象字段作为语义块；YAML 使用映射键路径作为语义块入口。

4. 执行切分，输出语义块集合，每个块包含原始文本、行号范围、父级标题路径和块级哈希。

5. 对语义块执行概念提取：识别术语、标签、关系引用和摘要句，生成概念节点并建立与语义块的引用关系。

6. 将概念节点送入嵌入模型生成向量，同时构建稀疏关键词索引和图谱关系边，输出索引记录。

7. 把索引记录写入目标索引库，并把来源元数据写入旁路存储，确保两者使用相同的指纹键。

8. 运行验证查询：抽取一组已知正向样例和边界样例，检查召回结果是否包含预期概念节点，并验证来源指纹是否可解析。

9. 生成摄取任务报告，包含处理文档数、语义块数、失败项列表、平均嵌入延迟、索引写入延迟和校验签名列表。

10. 若失败项数量超过阈值，触发告警并进入人工审阅流程；否则标记任务成功，并更新任务日志。

## 本地文件知识库的摄取示例

以下示例展示一份 Markdown 文件如何被转换为可检索概念。

输入文件 `docs/auth/session.md`：

```
## 会话生命周期

createAgentSession 接受 ModelRuntime 与工具集合，返回一个 AgentSession 实例。

### 订阅事件

在调用 session.prompt() 之前必须先订阅 message_update 与 tool 事件。
```

处理配置：

```yaml
ingestion:
  sourceDir: "./docs"
  include: ["*.md"]
  chunking:
    strategy: "heading"
    maxChunkSize: 800
  extractors:
    terms: ["AgentSession", "ModelRuntime", "createAgentSession"]
    tags: ["session", "events"]
  provenance:
    gitCommit: "HEAD"
    splitterVersion: "1.2.0"
```

输出概念节点：

```json
{
  "conceptId": "auth-session-lifecycle",
  "terms": ["AgentSession", "ModelRuntime", "createAgentSession"],
  "tags": ["session", "events"],
  "chunks": [
    {
      "docPath": "docs/auth/session.md",
      "startLine": 1,
      "endLine": 3,
      "hash": "sha256:a1b2..."
    }
  ],
  "provenance": {
    "gitCommit": "8f3e2d",
    "splitterVersion": "1.2.0"
  }
}
```

输入是原始 Markdown 与配置；处理阶段完成解析、切分、术语提取和指纹计算；输出是带有来源链路的可检索概念节点，可被下游向量索引或图谱索引直接消费。

## 性能、质量和可观测性指标

1. **端到端摄取延迟**：从任务启动到验证查询通过的总时间。测量方法是在 CI 中运行完整摄取任务，记录时间戳差值，并保存到任务日志。目标值取决于语料规模，万级语义块应控制在十分钟以内。

2. **每块嵌入延迟**：单个语义块从文本到向量嵌入的时间。测量方法是嵌入模型调用前后打时间戳，排除网络排队。若平均值超过 200 毫秒，应检查批次大小或模型后端负载。

3. **召回准确率**：在已知正向样例上，预期概念节点是否出现在前 K 个结果中。测量方法是在每次摄取后运行固定测试集，统计命中比例。若低于 95%，优先检查切分边界是否破坏了术语上下文。

4. **失败项比例**：处理失败的文档数或语义块数占总数的比例。测量方法是在任务报告中聚合失败清单。若超过 1%，应暂停自动触发并人工介入。

5. **来源指纹可解析率**：召回结果中概念节点能成功解析回原始文档的比例。测量方法是在验证查询阶段抽样检查，目标是 100%，任何低于该值的情况都视为索引或元数据存储不一致。

## 失败模式、诊断证据与恢复动作

1. **切分截断术语**：代码块或长列表被错误切分，导致术语失去上下文。诊断证据是召回结果包含不完整的句子或孤立的代码片段。恢复动作是调整切分策略版本，触发全量重建，并更新边界规则单元测试。

2. **哈希冲突导致增量跳过**：文件内容已变但哈希巧合相同，极少数情况下会发生。诊断证据是检索内容陈旧但文件修改时间已更新。恢复动作是切换到内容加文件大小的联合哈希，或定期触发全量重建。

3. **嵌入模型超时**：大容量批次导致嵌入接口响应超时。诊断证据是每块嵌入延迟骤升且失败项集中在最后一批。恢复动作是缩小批次大小、启用异步队列，或降级到本地备用模型。

4. **旁路元数据索引不一致**：索引记录写入成功但来源元数据写入失败。诊断证据是来源指纹可解析率低于 100%。恢复动作是比对索引键与元数据键，重新写入缺失的元数据，并引入写入事务或两阶段提交。

5. **配置文件语法错误导致解析器崩溃**：YAML 配置中出现非法缩进或重复键。诊断证据是解析阶段抛出异常且整个文件被标记失败。恢复动作是修复配置文件，对解析器增加异常捕获，并把失败文件加入重试清单而非中止任务。

## 维护、版本、来源与相邻主题的关系

维护工作的核心是保证摄取流水线的可重复性。每次切分策略、提取器或嵌入模型版本变更，都要更新 `splitterVersion` 或 `extractorVersion`，并触发一次全量重建。任务日志与失败清单应保留至少最近二十次运行，便于回溯异常来源。

来源管理依赖 Git 提交哈希与文件修改时间，但不依赖外部爬取服务。所有来源证据必须能在本地文件系统中验证，避免引入不可复现的网络状态。

与相邻主题的关系：语料摄取上游是文档编写与知识库组织，下游是检索排序与 Agent 引用生成。摄取层不负责回答质量调优，也不负责多轮对话状态管理。它的边界是把原始文件可靠地转换为可检索概念，并为每次召回提供可验证的来源链路。

## 结论

事实：语料摄取必须处理 Markdown、JSON 和 YAML 三种本地文件格式；切分后必须保留行号、父级标题路径和内容哈希；来源元数据与索引记录必须共享同一指纹键；项目明确采用部分失败策略与增量差异重建。

推论：按标题层级优先的混合切分策略在本地文件型知识库中更利于召回准确率；旁路存储元数据会以可接受的延迟换取版本化灵活性；异步队列切换阈值应通过实际压测而非理论值确定。

未知：不同嵌入模型对代码块与中文术语的切分敏感度差异尚未量化；大规模增量场景下哈希冲突的实际发生频率缺乏运行数据；旁路存储在极端写入失败时的最终一致性保证需要进一步压测验证。
