# 字面检索：面向确定性召回的文档边界与可替换接口

## 摘要与问题边界

字面检索是一种以可验证词项匹配为核心的召回机制。它把标题、标签、正文和中文关键词当作可解释的证据源，而不是把相关性交给稠密向量或语言模型的隐式近似。对于 TypeScript/Web 与本地文件知识库这类边界清晰、来源可控的场景，字面检索负责回答“哪些文档明确包含这些词”，并只在有证据时返回结果；没有证据时必须能够明确拒答，而不是用概率生成“看起来相关”的答案。

本方案的定位是架构层面的召回基础设施。它先定义文档单元、字段权重、分词接口和倒排索引等可替换边界，再决定具体实现。语义检索可以作为相邻能力与之并行，但不应替代字面检索的确定性职责。

## 核心概念与数据模型

1. **文档单元（Chunk）**：知识库的最小召回单位。每个 chunk 必须包含 `title`、`tags`、`body`、`keywords`、`source_path`、`content_hash`、`version` 和 `created_at`。标题与标签是人工或半人工标注的强信号，正文是原始文本，中文关键词是面向检索显式维护的等价词集合。

2. **词项（Term）**：经过分词与规范化后的最小匹配单元。对中文来说，词项由分词器产出；对英文和数字，按空白与标点切分并统一小写。词项不保留原始大小写，也不保留全角半角差异。

3. **倒排索引（Inverted Index）**：每个词项维护一个 posting 列表，记录 `(chunk_id, field, term_frequency, positions)`。字段内出现位置用于支持短语查询与邻近排序。

4. **字段权重（Field Weight）**：`title` 权重最高，其次是 `tags` 与 `keywords`，`body` 最低。权重决定初始得分，但不决定命中与否。同一词在标题命中不应自动压过所有正文命中，必须保留可调试的得分分布。

5. **查询解析（Query Parse）**：支持 `field:value` 前缀、双引号短语、`AND`/`OR` 布尔组合。不支持模糊前缀、拼写纠错或语义扩展，这类能力由外部服务提供。

6. **召回与排序边界（Recall & Rank Boundary）**：字面检索只召回包含全部强制词项的 chunk；排序由加权得分与位置 proximity 共同决定。超出 top-k 的结果可以截断，但必须在日志中记录截断位置，以便后续评估。

## 设计决策与取舍

### 分词器是可替换接口，不是内置黑盒

默认分词器只承担“把字符串拆成词项”的职责，不耦合业务规则。接口形如 `tokenize(text: string): Term[]`。如果需要中文领域词典、停用词或特殊符号处理，通过插件实现，而不是修改核心引擎。这保证了在浏览器端与 Node 端可以采用不同实现，而索引格式保持一致。

### 索引持久化选择 JSONL 而非数据库

本地文件知识库本身以文件为中心，索引也存储为按行分隔的 JSONL，便于版本控制和 diff。唯一需要保证的是写入原子性：先写到临时文件，再重命名覆盖。对于查询并发较高的场景，可以在内存中加载倒排索引，文件仅作为冷启动来源。

### 字段权重采用静态加权，而非学习排序

静态加权的好处是可解释、可审计。设计者在配置文件中直接声明 `title:10`、`tags:8`、`keywords:7`、`body:3`。初期不学模型，因为训练数据不足，且模型权重会掩盖字面证据。只有当黄金评测集超过数千条且稳定后，才允许在静态得分基础上叠加轻量学习模型。

### 查询解析拒绝模糊意图

字面检索不猜测用户意图。查询“日志”只匹配“日志”这个词，不匹配“记录”“tracing”等近义词。如果系统要支持同义词扩展，必须由 `keywords` 字段显式维护等价词，而不是由检索引擎在线推断。这一取舍把“语义扩展”与“确定性召回”明确分开。

### 与向量检索并行而非嵌套

在 RAG 架构中，字面检索和向量检索可以并行执行，最后由上层合并。不要把字面检索当作向量检索的预过滤，因为那样会丢失“无证据拒答”的能力。并行结果各自带证据来源，上层策略决定最终选择。

## 可执行的实施流程

1. 定义 chunk schema 与配置：确定字段列表、权重、分词器、停用词、是否保留位置信息。
2. 文档解析：读取 Markdown 或源码注释，按标题层级切分 chunk，提取 frontmatter 中的 `tags` 与 `keywords`。
3. 分词实现：实现或接入 `Tokenizer`，对每个字段分别产出词项，中文词项保留位置。
4. 构建倒排索引：遍历所有 chunk，生成 `term → posting[]`，同时保留每个 chunk 的 `content_hash` 与 `source_path`。
5. 实现查询解析器：支持前缀字段、短语、布尔 `AND`/`OR`，默认所有词项为 `AND`。
6. 实现检索引擎：按 posting 列表求交，计算加权得分与位置 proximity，返回 top-k 结果及命中片段。
7. 暴露 Web API：提供 `/search?query=&limit=&fields=`，返回 SSE 或 JSON，包含 `chunk_id`、`score`、`matched_terms`、`snippet`。
8. 接入可观测性：记录每次查询的解析耗时、召回数、截断数、未命中词项和最终返回结果。
9. 建立黄金评测集：用结构化问答样例定期回归，监控精确召回率与拒答准确率。
10. 版本化索引：在索引文件中写入 `schema_version`， schema 变更时触发全量重建。

## 示例：本地文件知识库的字面索引

下面是一份贴近 TypeScript/Web 项目的索引配置与索引片段。输入是仓库中的 Markdown 笔记；处理流程按 schema 分词、加权并生成倒排表；输出是带证据的召回列表。

```json
{
  "schema": {
    "version": "1",
    "fields": [
      { "name": "title", "weight": 10, "tokenize": true },
      { "name": "tags", "weight": 8, "tokenize": true, "split": "|" },
      { "name": "keywords", "weight": 7, "tokenize": false, "split": "," },
      { "name": "body", "weight": 3, "tokenize": true }
    ],
    "tokenizer": { "provider": "local-segment", "stopwords": ["的","了"] }
  },
  "index": {
    "term": "字面检索",
    "postings": [
      { "chunk_id": "c-rag-001", "field": "title", "tf": 1, "positions": [0] },
      { "chunk_id": "c-rag-001", "field": "body", "tf": 2, "positions": [12, 87] }
    ]
  }
}
```

输入是一段标题为“字面检索：面向确定性召回的文档边界”的文档。处理时，引擎把标题和正文分词，发现“字面检索”在标题出现一次、在正文出现两次，于是写入 posting。当用户查询 `字面检索` 时，引擎返回 `c-rag-001`，得分高于只有正文命中的 chunk。输出 JSON 中还会附带 `matched_terms: ["字面检索"]`、`snippet: "标题命中：字面检索：面向..."`，以及原始 `source_path`，以便用户点击打开本地文件。

## 性能、质量与可观测性指标

1. **首字节延迟 p99**：从请求到达 `/search` 到返回第一条结果的时间。目标在本地方案中低于 50 ms。使用日志采样测量。
2. **精确召回率 P@k**：在 top-k 结果中，被标注为“相关”的 chunk 比例。由黄金评测集定期计算。
3. **未命中词比例**：查询中包含但索引不存在的词项数。若超过 20%，说明分词策略或语料覆盖有问题。
4. **索引覆盖率**：有 `title` 和至少一个 `tag` 或 `keyword` 的 chunk 比例。目标高于 95%，否则标题/标签召回会失效。
5. **拒答准确率**：对于无证据查询，系统返回空结果的比例。应接近 100%，避免用正文近似生成答案。
6. **得分分布熵**：top 结果得分是否过于集中。如果第一名得分是第二名的十倍以上，说明权重可能失衡。

## 失败模式、诊断证据与恢复动作

1. **分词过度切分**：中文词“机器学习”被切成“机器”和“学习”，导致查询“机器”返回不相关结果。诊断证据：命中片段中没有完整词“机器学习”，`matched_terms` 只显示单字。恢复：接入领域词典，或启用双引号短语查询。
2. **字段权重失衡**：标题命中被放大，正文中的关键步骤被压到第二页。诊断证据：得分分布熵异常，body 字段命中得分低于阈值。恢复：调低 title 权重或提高 body 权重，重新评估。
3. **同形异义污染**：英文词“bug”在昆虫学笔记与调试笔记中都被命中。诊断证据：返回结果来自多个不相关标签。恢复：在 `tags` 中强制区分领域，或在查询中要求 `tags:debug`。
4. **索引与文件不同步**：源文件已更新，但索引仍指向旧版本。诊断证据：`content_hash` 与文件当前哈希不一致。恢复：每次保存文件时触发增量重索引，或按固定周期全量重建。
5. **查询特殊字符注入**：用户输入 `title:"foo` 或 `body: *` 导致解析器异常。诊断证据：解析错误日志。恢复：解析器统一转义引号，非法语法返回 400 并附带错误信息。
6. **停用词过度剔除**：把“的”作为停用词，但业务中“的”出现在固定术语里。诊断证据：查询含“的”的返回结果为空。恢复：停用词表按字段可配置，关键词字段不启用停用词。

## 问答测试样例

1. **正向**：问“字面检索的核心原则是什么？” 预期返回标题包含“字面检索”的 chunk，因为标题和正文都命中。
2. **多字段 AND**：问 `title:字面检索 tags:RAG`。预期只返回同时满足标题命中和标签为“RAG”的 chunk；如果文档没有该标签，必须空结果。
3. **短语边界**：问 `"确定性召回"`。预期只返回包含该完整短语连续出现的 chunk，分词切分后位置必须连续。
4. **无证据拒答**：问“图神经网络在检索中的优势”。如果索引中没有“图神经网络”，必须返回空结果，并不得用正文生成答案。
5. **关键词等价**：问“keyword search”。如果 `keywords` 字段显式包含“keyword search”等价于“字面检索”，则返回相关 chunk；否则空结果。
6. **大小写与全半角**：问“RAG”与“ｒａｇ”应返回相同结果，因为规范化后词项一致；如果未规范化则视为失败。
7. **标签缺失边界**：问 `tags:向量检索`。若文档只有正文提到“向量检索”但没有该标签，必须不返回，以证明标签字段边界生效。

## 维护、版本、来源和与相邻主题的关系

索引 schema 必须携带版本号。任何字段权重、分词器或 posting 格式变更都要升级 `schema_version`，并触发全量重建。来源信息保留 `source_path` 与 `content_hash`，不依赖外部 git 系统；在本地文件知识库中，可用文件系统修改时间作为辅助校验。

与相邻主题的关系：向量检索负责语义近似与泛化，字面检索负责确定性证据；两者在混合检索中由上层合并，而不是互相替代。关键词扩展与同义词表属于治理层面，应由知识库维护者显式维护，而不是检索引擎自动推断。评估体系与字面检索紧密相邻，黄金集与拒答样例必须随 schema 同步更新。

## 结论

**事实**：字面检索通过标题、标签、正文和中文关键词的显式匹配实现可验证召回；分词器、字段权重、索引格式和查询解析器都可以作为可替换接口独立演进。

**推论**：在边界清晰、来源可控的本地文件与 Web 知识库中，优先使用字面检索作为基础召回层，能够显著降低无证据生成答案的风险；只有当语义检索拥有稳定、可审计的评测链路时，才适合与其并行使用。

**未知**：不同中文分词器在工程代码与业务文档上的切分一致性仍未被系统量化；同形异义、领域新词和关键词衰减的长期维护成本，需要更多项目级数据才能给出通用阈值。
