# 字面检索：用标题、标签、正文与中文关键词建立确定性召回

## 摘要与问题边界

字面检索是一种以字符、分词或短语的精确命中为前提的召回机制。它的核心承诺是：只要目标文档在标题、标签、正文或关键词中出现过某个表达式，就能通过对应的查询被找到。这种机制不依赖向量相似度，也不做语义改写，因此召回结果具有可解释、可复现、可审计的特点。本文讨论的范围是面向本地文件型知识库、Web 前端展示以及 TypeScript 服务端的字面检索系统；不包含稠密向量检索、大模型生成式回答，也不把近似最近邻当作主要召回路径。

## 核心概念与数据模型

1. **文档（Document）**：知识库的最小管理单元，包含稳定标识 `docId`、文件路径 `path`、最后修改时间 `mtime` 和版本戳 `version`。同一个物理文件在重命名或迁移后必须被视为新文档，否则会出现索引与内容错位。
2. **标题（Title）**：通常取自文件名、一级标题或人工维护的显示名。标题命中权重最高，默认采用前缀匹配；例如查询“健康检查”应命中标题“健康检查配置指南”，但不应命中正文中偶尔出现“健康检查”四字的无关段落。
3. **标签（Tag）**：受控词表中的短词，匹配方式必须是精确相等。标签设计用于快速横向筛选，例如 `observability`、`k8s`、`frontend`。大小写、全半角、连字符差异都应在索引前完成归一化。
4. **关键词（Keywords）**：人工或半自动提取的中文术语集合，例如“Pod 就绪探针”“滚动发布”。关键词支持精确匹配和部分同义词扩展，但扩展表必须显式维护，不能由模型自由改写。
5. **正文（Body）**：原始 Markdown 文本经过去除标记、段落切分后的内容块。每个块保存 `chunkId`、`offset`、`length`，用于结果高亮和来源定位。正文默认使用子串匹配，权重最低。
6. **倒排索引（Inverted Index）**：以归一化后的词元为键、以文档或块 ID 列表为值的映射。每个 postings 条目还需记录字段来源和出现频次，以便后续按字段权重打分和布尔过滤。

## 设计决策与取舍

### 精确、前缀与子串的优先级
标题使用前缀匹配，可兼顾“Docker 网络”命中“Docker 网络模型”；标签与关键词使用精确匹配，避免“日志”命中“日志收集器”造成误召回；正文使用子串匹配，保证任意片段均可被定位，但会引入大量低相关结果。三者的优先级顺序是：标签 > 关键词 > 标题 > 正文。

### 中文分词策略
中文没有天然空格，必须在字典分词与 n-gram 之间做选择。工程上采用“项目术语字典 + 二元覆盖”的混合方案：字典中的术语必须被完整切出，未知文本退化为 n-gram。这样既能保证“服务网格”作为一个整体被召回，也能覆盖新造词。

### 字段权重的可配置性
默认权重为标签 10、关键词 8、标题 5、正文 1。权重不是模型学得，而是运维可编辑的配置项。当业务发现某类查询大量依赖正文子串时，才考虑上调正文权重；否则应保持低权重，抑制噪声。

### 索引存储介质
小型知识库（< 1 万文档）可直接把倒排索引加载到内存，查询延迟稳定在亚毫秒级。中大型知识库使用 LevelDB 或 SQLite 持久化，启动时做一致性校验。内存方案重启重建成本较低，但进程崩溃会丢失未持久化状态；持久化方案需要处理索引文件损坏后的恢复。

### 确定性召回与排序的边界
字面检索的第一目标是“不错过”，第二目标才是“排得准”。因此排序分数仅作为同义词命中数、字段权重和词频的线性组合，不引入学习排序模型。任何返回结果都必须满足至少一个词元命中，空命中直接返回空列表，不得由后端编造答案。

## 可执行的实施流程

1. 采集本地 Markdown 文件，解析文件路径、一级标题、YAML 元数据中的 `tags` 和 `keywords`，以及正文文本。
2. 对文本做归一化：统一全半角、转小写、移除多余空白和 Markdown 标记，保留中文、英文、数字及常用连字符。
3. 加载项目术语字典，对标题、标签、关键词和正文分别分词，生成归一化后的词元列表。
4. 构建倒排索引，每个 postings 记录 `docId`、`field`、`chunkId`、`termFrequency`，并按字段分桶。
5. 对索引做冒烟测试：使用 20 个已知正向查询和 10 个已知负向查询验证命中与未命中是否符合预期。
6. 暴露 HTTP 查询接口，支持按字段过滤、布尔组合（AND/OR/NOT）和 `limit` 限制，接口层设置请求超时。
7. 接入可观测性：记录每次查询耗时、命中文档数、是否空结果、命中的字段分布。
8. 部署文件监听器或定时任务，在源文件 `mtime` 变化时触发增量索引更新；每日执行一次全量重建作为兜底。

## 示例：本地文件知识库的输入、处理与输出

| 阶段 | 内容 |
|---|---|
| 输入 | 文件 `docs/k8s-probe.md`，标题为“Kubernetes 健康检查与就绪探针”，标签 `["k8s", "observability"]`，关键词 `["健康检查", "就绪探针", "Probe"]`，正文讲解 `livenessProbe` 和 `readinessProbe` 的配置。 |
| 处理 | 系统归一化标题后按字典切出“Kubernetes”“健康检查”“就绪探针”；标签精确映射为 `k8s`、`observability`；关键词写入倒排表；正文子串索引保留原始文本偏移。 |
| 输出 | 查询“健康检查”返回该文档，命中年段为标题与关键词，得分高于仅正文中出现“健康检查”的其他文档；查询“就绪”若配置为精确或前缀模式且未收录该缩写，则可能返回空结果。 |

## 性能、质量和可观测性指标

1. **P99 查询延迟**：在持续 1 分钟的混合查询负载下，使用 Prometheus 或本地 histogram 统计。目标值为内存索引 < 5 ms，持久化索引 < 50 ms。
2. **Recall@K**：针对人工标注的 100 条 golden query，检查前 K 条结果是否包含所有应召回文档。K 通常取 5 和 10，目标 recall@10 ≥ 0.90。
3. **误召回率**：随机抽取 200 条非空结果，人工判断结果与查询词元是否真实相关。目标误召回率 < 5%。
4. **索引新鲜度**：`max(source_mtime) - last_index_mtime`。 freshness > 5 分钟时触发告警。
5. **空结果率**：按查询长度和命中的字段分组统计。短查询空结果率高说明分词或字典有问题；长查询空结果率高说明布尔组合过于严格。

## 失败模式、诊断证据与恢复动作

| 失败模式 | 诊断证据 | 恢复动作 |
|---|---|---|
| 索引过期 | 搜索结果展示已删除或旧路径文件；freshness 指标 > 阈值 | 触发全量重建；校验 `mtime` 变化监听是否失效 |
| 术语未收录 | 用已知关键词查询返回空，但用更长子串查询可命中 | 把术语加入项目字典，执行增量重索引 |
| 子串洪水 | 单次查询返回上千条结果，且 top 结果与查询主题弱相关 | 收紧匹配模式，从子串改为前缀或精确；提高最小命中词元数 |
| 查询超时 | P99 延迟突增，超时错误日志增多 | 设置 `limit` 上限、增加查询超时、缓存高频查询 |
| 索引文件损坏 | 启动时报 checksum 失败或序列化异常 | 删除损坏索引，从源文件全量重建；启用双副本索引滚动更新 |

## 问答测试样例

1. 正向：查询“Kubernetes 健康检查”，期望命中标题含“Kubernetes 健康检查与就绪探针”的文档。
2. 正向：查询标签“observability”，期望返回所有带该标签的文档，且不混入仅正文中出现的文档。
3. 边界：查询“K8s 探针”，若未配置“K8s → Kubernetes”同义词扩展，系统应返回空或提示无命中。
4. 边界：查询单个中文助词“的”，因低于最小词元长度，结果必须为空。
5. 无证据拒答：查询“RabbitMQ 集群拆分脑”，若语料中从未出现 RabbitMQ 相关内容，系统应返回空列表，不得编造答案。
6. 无证据拒答：查询“TypeScript 编译器 API 性能”，若“编译器 API”未在字典中且正文中未出现连续子串，系统应返回空或仅匹配“TypeScript”“性能”但分数低于阈值。

## 维护、版本、来源与相邻主题的关系

索引格式必须与代码版本一起维护，任何字段权重、分词器或归一化规则变更都应视为 schema 升级。推荐在索引元数据中写入 `schemaVersion`、`sourceGitCommit` 和 `buildTimestamp`，便于在回滚时识别索引是否兼容。来源侧建议保留原始 Markdown 文件，不删除，只通过 `mtime` 判断是否需要更新。字面检索与稠密向量检索是互补关系：前者负责高召回、可解释；后者负责语义泛化。生产系统中常把字面检索作为第一路召回，再用向量重排或交叉编码器进行精排， hybrids 方案需要在评估阶段分别标注两路的贡献比例。

## 结论

事实：字面检索依赖精确、前缀或子串命中，倒排索引是其核心数据结构，字段权重和分词字典直接决定召回边界。推论：只要术语被正确切分和索引，就能实现稳定且低延迟的确定性召回；若项目术语变化频繁，则需要持续维护字典和同义词表。未知：具体业务中的真实查询分布、用户是否接受空结果、以及本地硬件在最大语料规模下的内存上限，都需要在部署后通过实际观测数据进一步确认。
