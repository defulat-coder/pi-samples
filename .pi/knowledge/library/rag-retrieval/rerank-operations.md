# RAG 重排序：小候选集下的相关性提升与延迟控制

## 摘要与问题边界

重排序（Reranking）位于 RAG 检索阶段之后、提示词组装之前，对第一阶段已经召回的小规模候选集逐对（查询，候选）进行更精细的相关性打分，并据此重新排序或截断。它解决的是“召回足够但排序不准”的问题，而不是“召回不足”。本文从验证与运维视角出发，讨论如何在 TypeScript/Web 服务与本地 Markdown 文件知识库环境中控制额外延迟、捕获失败、设计降级，并留下可审计的证据链。适用范围：第一阶段候选集通常在 10–100 条之间、端到端响应可接受数百毫秒级额外开销；不适用于需要毫秒级延迟或全局重排海量候选的场景。重排序不是必要组件，而是链路中的可选质量门，失败时必须能无损回退到第一阶段排序。

## 核心概念与数据模型

1. QueryContext：包含原始查询、查询扩展结果、会话 ID、时间戳和请求 trace_id，是重排序调用的输入锚点。
2. CandidateSlice：第一阶段返回的 Top-K 候选集合，每条记录保存片段 ID、文本、来源文件路径、初始分数和文本长度，禁止在重排序前丢弃这些元数据。
3. RerankScore：重排序模型输出的标量分数，常见取值区间 [0,1] 或 (−∞,+∞)；必须与 InitialScore 分开存储，避免不同分布直接比较。
4. FusionWeight：融合两阶段分数的系数或方法，例如 min-max 归一化后的线性加权、RRF（Reciprocal Rank Fusion）等；权重变更属于配置版本事件。
5. LatencyBudget：分配给重排序步骤的耗时上限，通常取整条 RAG 链路 P95 延迟的 30%–50%；超过即触发降级。
6. FallbackSignal：重排序失败或超时时返回的显式标记，如 `timeout`、`model_error`、`nan_score`、`skipped`，供下游决定使用原始排序还是返回错误。
7. CacheEntry：缓存键由查询哈希、候选 ID 列表指纹、模型版本和索引版本联合生成；缓存值保存分数数组与过期时间。
8. ObservabilityEvent：每次调用记录输入候选数、输出分数统计量、模型版本、耗时、token 数、异常类型和回退动作。

## 设计决策与取舍

### 候选集大小 K 的选取
K 过小（<5）时，重排序的边际收益低，且模型容易放大单条噪声；K 过大（>200）时，延迟和上下文成本会侵蚀第一阶段的收益。推荐按延迟预算反推：若单对平均耗时为 t、预算为 L，则 K ≈ L / t × 0.7，保留 30% 余量；同时设置硬上限，避免异常查询把大候选集全部送进模型。

### 同步与异步重排
同步重排实现简单但阻塞响应；异步重排可用于热点查询预热或写入缓存。首次查询通常必须同步，否则用户体验下降；高复现查询可结合缓存。异步任务必须拥有独立的超时和错误处理，不能污染主请求的降级路径。

### 自托管与外部 API
自托管小型交叉编码器可控延迟与数据隐私，但需要 GPU/CPU 容量规划；外部 API 降低维护负担，但引入网络抖动和限流。本地文件知识库若含敏感内容，倾向自托管。无论哪种方式，都必须在服务内实现本地降级，不能假设外部模型永远可用。

### 分数融合策略
直接用重排序分数替换初始分数会丢失召回信号；简单线性插值可能因分布差异而扭曲。建议对两阶段分数分别 min-max 归一化后再加权；缺失重排序分数的候选退化为初始分数并标记。对检索来源差异较大的候选，可考虑分来源归一化，避免某一检索通道的分数被压制。

### 降级路径
任何重排序失败都不应导致整体链路失败。单个候选异常时标记为 null；整体失败时切到无重排序路径，并在响应中附加 `rerank_skipped=true`，确保审计可见。降级不是静默行为，必须被指标和日志显式记录。

### 缓存一致性与失效
缓存键若只含查询文本，索引或模型更新后会返回过期分数。必须包含候选集合指纹与索引版本；TTL 建议不超过索引刷新周期的一半。缓存只应缓存分数，不缓存候选文本，因为文本可能先于索引更新被修改。

### 重排序与提示词内排序的边界
重排序决定哪些片段进入最终提示词，但不负责提示词内部示例的排列；如果提示词对片段顺序敏感，则重排序输出还需经过一次与提示词模板适配的裁剪。

## 可执行实施流程

1. 在检索阶段固定第一阶段输出的最大候选数 K，并把候选写入结构化日志，字段包括 `candidate_ids`、`initial_scores`、`source_paths`、`text_lengths`。
2. 根据当前部署模型的平均耗时与整条链路 P95 延迟预算，计算最大允许 K；超过预算时先按初始分数截断。
3. 在 TypeScript 服务中定义 `RerankerClient` 接口，包含 `rerank(query, candidates)`、`healthCheck()`、`fallbackToInitial()`。
4. 为每个候选构造模型输入：查询文本 + 分隔符 + 候选片段文本；超过模型最大长度时按句子边界截断，并记录 `truncated=true`。
5. 调用重排序模型，获取分数后立刻校验数值范围与 NaN；异常分数用 `null` 占位。
6. 将有效重排序分数与第一阶段分数归一化，并按配置权重融合，生成最终 Top-N；全部缺失时直接使用第一阶段排序。
7. 把重排序事件写入可观测流，字段包括 `duration_ms`、`model_version`、`input_tokens`、`score_mean`、`fallback_signal`。
8. 在 API 层设置超时与断路器：单次超时触发降级；连续失败达到阈值打开断路器并告警。
9. 建立每日对账任务：对比重排序路径与无重排序路径的 Top-1/Top-5 差异率，差异率超过 20% 时触发人工评估。
10. 模型或索引更新后，先用固定测试集比较 NDCG@10、P95 延迟和失败率，通过后再切换流量。

## 代码示例：本地 Markdown 知识库的重排序输入/处理/输出

```typescript
// packages/pi-agent/src/rerank/reranker.ts
interface Candidate {
  id: string;
  text: string;
  source: string;        // e.g. ".pi/knowledge/rag.md"
  initialScore: number;
  textLength: number;
}

interface RerankResult {
  id: string;
  rerankScore: number | null;
  finalScore: number;
  truncated: boolean;
}

async function rerankCandidates(
  query: string,
  candidates: Candidate[],
  latencyBudgetMs: number
): Promise<RerankResult[]> {
  const maxK = estimateMaxK(latencyBudgetMs);
  const slice = candidates.slice(0, maxK);

  const start = performance.now();
  const scores = await crossEncoder.scorePairs(
    query,
    slice.map(c => c.text),
    { timeoutMs: latencyBudgetMs * 0.8 }
  );
  const duration = performance.now() - start;

  return fuseScores(slice, scores, duration);
}
```

输入：用户查询字符串和来自第一阶段检索的候选列表，每条候选携带本地 Markdown 文件路径和初始分数。处理：服务先按延迟预算估算可承受的候选数，再调用交叉编码器逐对打分并设置子超时；返回分数经过范围校验后与初始分数融合。输出：`RerankResult` 数组，包含重排序分数、最终融合分数以及是否发生截断，供后续提示词组装使用。

## 性能、质量与可观测性指标

- 重排序 P95/P99 延迟：使用 `duration_ms` 直方图测量，目标不超过 RAG 总响应 P95 的 40%。
- 相关性增益 ΔNDCG@10：在固定标注测试集上对比“仅第一阶段”与“重排序后”，若连续两周为负则回滚。
- 候选覆盖率：实际进入重排序的候选数 / 第一阶段返回数，低于预期 K 说明截断或过滤异常。
- 失败率与降级率：`fallback_signal` 非空事件占比，细分为超时、模型错误、数值异常、限流。
- 缓存命中率：`cache_hit=true` 请求占比；过高可能 TTL 太长导致索引更新未生效，过低说明缓存键设计或复现率不足。
- 每次调用字符/token 成本：记录输入总字符数，用于容量规划和成本预警。
- Top-K 重叠度：对比重排序前后 Top-5 的 Jaccard 相似度，过高说明模型未改变排序，过低则要检查是否过拟合。

## 失败模式、诊断证据与恢复动作

1. 模型调用超时：证据是 `duration_ms` 接近 `latencyBudgetMs` 且 `fallback_signal=timeout`。恢复动作是减小 K、切换更轻量模型或启用异步预热。
2. 分数分布塌陷：证据是输出分数标准差小于 0.01。恢复动作是检查模型是否对截断文本过拟合，加入温度缩放或重新归一化。
3. 上下文长度溢出：证据是 `truncated=true` 且长文本候选的 `rerankScore` 为 null。恢复动作是按句子边界截断、改用支持长上下文的模型，或对长文档先分段再检索。
4. 模型版本回退导致 NDCG 下降：证据是每日对账中 `ndcg_delta < -0.05`。恢复动作是立即切回上一版本并冻结新模型部署。
5. 缓存命中但候选集合已变更：证据是 `cache_hit=true` 而当前索引指纹与缓存键指纹不一致。恢复动作是让缓存键包含索引版本号并缩短 TTL。
6. 外部 API 限流：证据是返回 429 且 `fallback_rate` 突增。恢复动作是打开本地降级路径、增加指数退避，并扩容自托管实例。
7. 索引漂移导致重排序输入质量差：证据是覆盖率正常但 ΔNDCG 持续下降，同时第一阶段召回分数整体偏低。恢复动作是检查向量索引或分块策略，而非直接调整重排序模型。

## 问答测试样例

- 正向问题：在 50 条候选集上启用重排序后，NDCG@10 从 0.61 提升到 0.73，P95 延迟从 420 ms 增加到 890 ms。是否应继续运行？答：应继续，但需把延迟预算和 K 调优纳入 backlog，因为相关性提升显著且延迟仍在可接受范围。
- 边界问题：候选集只有 3 条时是否还调用重排序？答：不建议；样本太少，模型分数不稳定，直接走无重排序路径并记录 `rerank_skipped=low_k`。
- 边界问题：重排序模型对某条候选返回 NaN，下游该怎么处理？答：将该候选 `rerankScore` 标记为 null，融合时退化为仅使用 `initialScore`，记录异常并在 1 小时内告警。
- 无证据拒答：重排序模型内部使用了哪些训练数据？答：运维视角不掌握训练数据细节，如需知道需查看模型卡片或训练记录，当前系统未存储该信息。
- 无证据拒答：重排序是否一定能击败 BM25？答：不能断言；需用固定测试集测量 NDCG 和召回率，不同语料表现不同。
- 正向问题：如何验证缓存没有返回过期分数？答：对比缓存命中的分数与重新计算的分数差异，并确保缓存键包含 `model_version` 与 `index_version` 两个字段。
- 边界问题：重排序分数全部集中在 0.5 附近，是否说明模型失效？答：不一定，可能是输入查询与候选差异过小；需结合分布标准差、ΔNDCG 和人工抽样综合判断。

## 维护、版本、来源与相邻主题关系

- 版本控制：重排序模型、分词器、prompt 模板和融合权重都应纳入版本管理；每次升级先 5% 灰度，观察 24 小时再全量。
- 来源与上下文：重排序依赖第一阶段检索和文本分块，输出影响提示词构建与生成；它是检索层与生成层之间的可选质量门。
- 日志保留：原始重排序事件保留 30 天用于故障复盘；聚合指标保留 90 天。
- 相邻主题：与查询扩展相关——重排序不能修复查询本身缺失同义词；与混合检索相关——融合阶段要区分“检索融合”与“重排序融合”；与评估相关——必须建立离线标注集，否则无法判断重排序是否有效。
- 与本地文件知识库结合：候选 `source` 字段指向本地 Markdown 路径，便于 Inspector 点击溯源；失败时可直接定位到具体文件版本。
- 容量规划：根据峰值 QPS、单请求平均 token 数和模型并发能力，计算所需实例数；建议预留 30% 余量应对查询尖峰。

## 结论

事实：重排序是在小候选集上用一个更强的模型重新打分，从而提高最终排序相关性；它引入额外延迟和新的失败点，因此必须提供显式降级路径。推论：在 TypeScript/Web 后端、本地文件知识库场景下，把 K 控制在延迟预算反推值以内、保留初始分数作为 fallback、并做归一化融合，是运维上最稳健的方案。未知：给定业务语料的最佳重排序模型、最优融合权重以及长期用户满意度收益，必须通过持续 A/B 测试和人工评估确定，不能仅凭离线指标推断。
