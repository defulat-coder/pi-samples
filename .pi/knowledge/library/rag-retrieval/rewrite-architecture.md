# RAG 查询改写：在语义扩展与意图守恒之间建立可替换接口

## 摘要与问题边界

查询改写是 RAG 检索阶段之前的一层有界变换。输入是用户的自然语言请求 Q0，输出是一组面向检索器的检索表达式 R。它的核心职责不是给出答案，而是把潜在同义词、实体别名、技术缩写和显式约束转换为检索器可理解的形式，同时保持用户真正意图不变。

该层必须被设计为可替换接口。项目术语表、领域同义词表、规则引擎或轻量模型可以独立演进，编排器只依赖稳定的改写契约。问题边界如下：

- 查询改写是检索准备，不是语义路由。不能根据关键字把消息分发到不同工具。
- 它不能改变用户的硬约束，例如 “只搜索 docs 目录” 或 “排除 node_modules”。
- 它不负责最终排序，排序由下游 ranker、embedding 或混合检索完成。
- 当输入存在歧义且缺乏知识库证据时，应优先透传原查询或返回澄清请求，而不是静默改写。

## 核心概念与数据模型

1. 原始查询 Q0：包含表面文本、检测到的 locale、会话上下文、显式否定词和作用域。它不只是字符串，而是一个带有约束签名和意图线索的结构。
2. 意图签名 I：描述查询的类别，如信息查找、导航、比较、操作配置。意图签名在改写过程中必须保持不变，改写结果应能被反向映射回同一意图。
3. 实体字典 E：领域内的规范实体、缩写和别名。例如 “pi-coding-agent” 对应 “@earendil-works/pi-coding-agent”，“AgentSession” 对应会话运行时。每个条目需记录来源、可变性和置信度。
4. 同义词层 S：结构化的同义集合，包含方向性强度、领域范围和反例。某些术语被标记为不可改写，例如 “AGENTS.md” 作为文件名必须原样保留。
5. 约束解析 C：从查询中提取的过滤条件，包括文件类型、版本号、目录、作者、时间范围。约束分为硬约束和软偏好两类。
6. 改写结果 R：包含原始查询、若干扩展变体、每条变体的来源标签、置信度、回退指针和追踪 ID。每个变体都携带可审计的 provenance，便于失败时定位。

## 设计决策与取舍

### 接口优先，而非实现内嵌

应定义 `QueryRewriter` 接口，核心方法为 `rewrite(query, context)`，返回稳定的 `RewriteResult` 结构。这样规则引擎、轻量模型或混合策略可以在不修改编排器的情况下替换。代价是接口契约必须稳定；一旦 `R` 的字段发生破坏性变更，所有消费者都需要同步升级。

### 同义词来源必须分层

来源优先级应为：项目术语表优先，领域同义词表次之，通用同义词表再次，模型生成仅作候补。越高层来源越可控，越低层来源覆盖率越高。使用 LLM 生成同义词时，必须要求来源归因，否则容易引入未经验证的扩展，造成检索污染。

### 硬约束与软偏好必须区分

硬约束是过滤条件，例如 “只搜索 docs 目录”“版本必须是 v10”。如果同义词扩展与硬约束冲突，必须中止该扩展并回退到原查询。软偏好是排序增强，例如 “优先最新文档”，可以变成 ranking boost，而不是查询改写。

### 单查询改写与多查询改写的边界

当查询包含比较意图、多实体或明显歧义时，可生成多查询变体。对于精确的技术查找，例如 “AgentSession 的 dispose 方法”，应保持单查询改写。经验边界是：当识别出的核心实体超过三个或意图为比较类时，才启用多查询，且变体数量上限应明确。

### 置信度与回退机制

每个改写变体必须输出置信度。当最高置信度低于阈值、硬约束被覆盖或意图签名发生漂移时，系统应回退到原查询并记录原因。回退不是失败，而是保护用户意图的主动设计。

## 可执行的实施流程

1. 输入归一化：去除无关噪声，保留代码术语的大小写，识别 locale，使用领域字典进行分词。
2. 意图签名提取：判断查询是查找、导航、比较还是操作配置，记录否定词和作用域。
3. 实体链接：将查询中的术语映射到本地文件知识库中的规范实体，标记来源和置信度。
4. 约束解析：提取显式过滤条件，如目录、版本、文件后缀；识别隐式时间或范围表达。
5. 同义词扩展：按来源优先级展开同义词，应用不可改写术语列表和反例模式。
6. 查询变体组合：生成原始查询、扩展后的查询以及可选的多查询变体，每个变体附带 provenance。
7. 评分与置信度：通过嵌入距离、约束覆盖率和来源可信度计算每个变体的置信度。
8. 治理与回退：执行最大变体数、拒绝列表、硬约束检查和回退策略。
9. 追踪输出：记录输入、规则命中、输出变体、置信度和回退原因，用于后续可观测性。

## 贴近本地文件知识库的配置示例

以下是一个面向 TypeScript Web 项目、基于本地文件知识库的改写器配置：

    rewriter:
      version: "2.1.0"
      interface: "QueryRewriter"
      domain: "pi-coding-agent"
      sources:
        - id: "project-glossary"
          path: ".pi/knowledge/glossary.json"
          priority: 1
        - id: "skill-terms"
          path: ".pi/skills/*/terms.yaml"
          priority: 2
        - id: "general-synonyms"
          path: "data/synonyms.tsv"
          priority: 3
      nonNegotiableTerms:
        - "node_modules"
        - "AGENTS.md"
        - "pi-coding-agent"
      hardConstraints:
        directory:
          token: "docs/"
          target: "path"
        version:
          token: "v10.30.3"
          target: "semantic_version"
      expansion:
        maxVariants: 3
        maxSynonymsPerEntity: 4
        requireSourceAttribution: true
      fallback:
        minConfidence: 0.7
        action: "pass_through"

输入是用户查询和当前会话上下文；处理阶段加载分层来源，将 “pi-coding-agent” 链接到项目术语，把 “session” 扩展为 “AgentSession” 或 “session lifecycle”，但保留 “AGENTS.md” 和 “node_modules” 原样；输出是 `RewriteResult`，包含原始查询、若干检索变体、每条来源和置信度。

## 性能、质量与可观测性指标

1. 意图保持率：通过原始查询与改写后变体的嵌入余弦相似度衡量，每月抽样人工复核一次。
2. 召回增益：在带标注的测试集上比较启用与未启用改写时 top-k 命中的提升比例。
3. 精确率损失：统计 top-10 结果中因同义词扩展引入的伪阳性文档比例。
4. 改写覆盖率：记录有多少比例的查询至少获得了一个非完全相同的改写变体。
5. 端点延迟：记录改写步骤的 p50 和 p99 耗时，并细分到每个来源和规则。
6. 回退率：统计因置信度不足或硬约束冲突而回退到原查询的比例。

## 失败模式、诊断证据与恢复动作

1. 同义词污染：top 结果包含大量与主题无关的文档。证据是同义词命中了反例模式。恢复：将该词加入反例列表并降低对应来源权重。
2. 约束被改写覆盖：用户要求 “排除 node_modules”，但改写后的变体丢失了否定词。证据是约束解析日志中该约束未命中。恢复：拒绝该变体，触发回退。
3. 意图漂移：原查询关注 “AgentSession 生命周期”，改写后变成 “用户登录会话”。证据是嵌入相似度低于阈值。恢复：人工审查并收紧意图签名检查。
4. 实体链接错误：例如 “pi” 被链接到数学常数而非项目 SDK。证据是规范实体 ID 与上下文标签不匹配。恢复：增加上下文消歧提示，或要求用户确认。
5. 过度扩展：生成了过多语义接近的变体，导致返回重复 chunk。证据是变体去重率升高。恢复：降低变体上限，启用结果去重。
6. 无来源的模型生成：LLM 在没有项目术语支持的情况下发明了同义词。证据是来源字段缺失。恢复：要求所有扩展必须带来源，否则阻断。

## 问答测试样例

1. 正向：用户问 “如何在本地文件知识库中配置 TypeScript 的 pi-agent session？”应扩展 “pi-agent” 到 “pi-coding-agent” 和 “AgentSession”，并保留 “TypeScript” 与 “本地文件知识库”。
2. 正向：用户问 “pnpm lock 文件与 npm 有什么区别？”应扩展 “lock” 到 “lockfile”，保持比较意图，且不引入 “mutex” 或 “thread lock”。
3. 边界：用户问 “pi 的 agent 是什么？”实体 “pi” 存在歧义。应输出低置信度变体并附 provenance，或请求澄清。
4. 边界：用户问 “只搜索 docs 目录下的 API 设计。”应将 “docs/” 作为硬约束附加到每个变体，若无法附加则回退。
5. 无证据拒答：用户问 “2027 年的 pi 计划是什么？”知识库中没有未来计划，应透传原查询并标记低置信度，不编造答案。
6. 无证据拒答：用户问 “xyz 框架的报错怎么解决？”若 “xyz” 不在任何术语表中，应禁止模型发明同义词，直接返回原查询。

## 维护、版本、来源与相邻主题关系

查询改写器本身应与编排器、检索器和排序器解耦。术语表和约束规则应使用语义版本管理，并在升级时运行回归测试集。来源必须可追溯，包括项目术语表、技能包、通用词表和模型生成记录。与相邻主题的关系如下：

- 与 embedding 模型的关系：改写扩展检索语法，embedding 负责语义匹配；二者不能互相替代。
- 与重排序的关系：改写提升召回，重排序提升精确率；软偏好可直接交给重排序层。
- 与混合检索的关系：改写结果可以分别送入向量索引、关键字索引和本地文件路径索引。
- 与知识库索引的关系：索引必须包含规范实体和别名，否则改写后的查询无法命中。

## 结论

事实是：查询改写是 RAG 管线中可替换的检索准备层，能够在不回答用户的情况下扩展同义词、实体和约束，从而提升召回。

推论是：当来源分层、硬约束严格、置信度阈值合理时，LLM 生成的同义词扩展可以带来可度量的召回增益；如果缺少控制，则容易造成意图漂移和检索污染。

未知是：每个具体领域的最优扩展数量、用户长期查询意图的漂移速度、以及 LLM 生成同义词在冷启动项目中的稳定边界，仍需要通过项目级 A/B 测试和持续审计来验证。
