# RAG 查询改写：在保留意图的前提下扩展同义词、实体与约束

## 摘要与问题边界

查询改写是 RAG 管线中位于用户输入与检索器之间的预处理层。它的任务不是生成最终答案，也不是替代重排序模型，而是在原始查询进入向量数据库或混合搜索引擎之前，通过受控的词汇扩展、实体归一化和约束显式化，提高召回率并降低语义鸿沟。问题边界必须明确限定：它只处理同一意图下的表达变体，不回答超出输入的问题，不进行多轮对话的状态推理，也不对检索结果做摘要。核心风险在于，任何扩展一旦越过原意的边界，就会引入噪声甚至事实错误，因此改写系统必须内置意图漂移检测与回退机制。

## 核心概念与数据模型

1. **OriginalQuery（原始查询）**：包含原始字符串、语言标签、会话标识、客户端版本和时间戳。它是不可变的真相来源，所有改写结果都必须能够回溯到该对象。
2. **IntentSignature（意图签名）**：从查询中抽取的动作动词、主题域、目标文档类型、时间约束、地理约束和必填字段集合。它用于判断扩展是否仍然服务于同一任务。
3. **EntitySlot（实体槽位）**：包含规范标识符、表面形式集合、实体类型、置信度和来源知识库版本。例如 “Node.js” 应链接到技术实体而非普通名词。
4. **SynonymExpansion（同义词扩展）**：记录原始词项、候选扩展、方向（双向、上位、下位）和来源。方向字段尤其关键，因为“电脑”的上位词“电子设备”可能过度泛化。
5. **ConstraintClause（约束子句）**：由字段、操作符、值和否定标志组成，同时标记是硬性过滤还是软性加权。例如 “不含 React” 应映射为 must_not。
6. **RewrittenQueryBundle（改写查询包）**：包含若干候选查询，每个候选附带扩展依据、意图漂移分数和原始查询引用。当最大漂移分数超过阈值时，系统应直接返回原始查询作为唯一候选。

## 设计决策与取舍

### 同义词扩展的覆盖率与语义漂移

同义词表不能无限扩张。建议采用领域可控词表加向量相似度的双层策略：先以精确匹配的同义词对做召回，再用嵌入模型补充候选，但仅当余弦相似度高于 0.75 时才保留。纯 LLM 生成的扩展词虽然覆盖率高，却容易引入隐式假设，因此只作为补充来源。

### 实体链接的精确召回权衡

实体归一化优先保证精确率而非召回率。当置信度低于 0.6 时，应保留原始字面表达，而不是强行链接到知识库中的近似条目。这样做虽然会漏掉部分别名，却能避免把“苹果”水果链接成公司。

### 约束条件是强化检索还是后置过滤

数值、枚举、时间等约束应优先映射为底层搜索引擎的过滤语法；无法直接映射的约束则作为后置过滤。若约束过于严格导致零结果，可降级为软性加权，而不是直接丢弃约束。

### 单查询改写 versus 多查询分解

当查询中的实体数量不超过 3 个、同义词候选不超过 5 组时，使用单查询改写即可。若查询包含多个并列子意图，则拆分为多个候选查询并行检索，最后合并结果。分解虽然增加检索次数，但能降低单个查询的语义冲突。

### LLM 参与深度与延迟成本

简单查询使用规则加嵌入完成改写；仅当歧义分数高于 0.6 或包含复杂否定结构时才调用 LLM。LLM 改写必须服从与规则改写相同的漂移验证，且 P99 延迟预算应控制在 300 毫秒以内，否则应降级为规则路径。

## 可执行的实施流程

1. **输入校验与规范化**：去除首尾空白，统一 Unicode 规范化形式 NFC，检测语言，拒绝空字符串或超过 2000 字符的输入，校验允许的字符集合。
2. **意图解析与分词**：将查询切分为动作、主题、约束片段，输出 IntentSignature。动作动词用于判断是否需要返回教程、文档还是配置示例。
3. **实体抽取与链接**：对照本地实体知识库和别名表进行匹配，输出 EntitySlot 列表。未命中实体保留为字面词项，不编造规范 ID。
4. **受控同义词扩展**：仅对名词和形容词扩展，使用词表和向量相似度双重过滤，记录每个扩展的方向和来源。
5. **约束抽取与校验**：识别日期、数值、布尔和枚举约束，验证操作符是否被底层搜索引擎支持，标记软硬性，拒绝无法解析的表达式。
6. **候选查询组装**：将实体、同义词和约束组合成候选查询，限制每个词项的扩展数量，避免组合爆炸。
7. **意图漂移验证**：用句子嵌入模型计算改写后查询与原始查询的余弦相似度。若低于 0.82，则标记为漂移并回退到原始查询。
8. **执行与可观测性输出**：调用检索器，记录输入、中间结果、最终候选和漂移分数，通过事件流对外暴露，以便后续评估与 A/B 测试。

## 性能、质量和可观测性指标

1. **检索召回率提升**：以原始查询为基线，测量改写后 top-10 召回率是否提升，计算相对增益百分比。应在标注好的查询文档对上离线评估。
2. **意图漂移拒绝率**：统计因漂移分数低于阈值而被回退到原始查询的请求比例。目标不是零，而是维持在一个稳定区间，例如 5% 到 10%。
3. **阶段延迟 P50 与 P99**：分别测量输入校验、实体链接、同义词扩展、约束解析和漂移验证的耗时，定位瓶颈。
4. **实体链接精确率与回退率**：定期抽样人工校验 EntitySlot 的正确性，并监控未命中实体的回退比例，防止知识库覆盖不足。
5. **约束违反率**：在检索返回的前 K 篇文档中，检查不满足硬性约束的文档比例，验证约束映射是否正确。

## 失败模式、诊断证据与恢复动作

### 同义词污染

典型证据是改写后查询的漂移分数骤降，同时点击率和相关性评分下降。例如把“Java”扩展为“咖啡”会引入无关文档。恢复动作包括收紧相似度阈值、引入词性过滤，以及为高频歧义词设置阻止列表。

### 实体误链接

当实体置信度处于 0.5 到 0.7 之间，且上下文Embedding与多个候选实体都接近时，容易发生误链接。应在低置信度时保留字面词，并通过上下文会话嵌入辅助消歧，而不是默认选择最高置信度。

### 约束遗漏

如果检索结果中反复出现违反时间或版本要求的文档，说明约束没有正确映射为过滤条件。恢复动作包括引入专门的日期与数值解析器，并在检索后做二次过滤验证。

### 过度扩展导致检索噪声

当单个词项被扩展出超过 5 个近义词，或同义词方向以上位词为主时，检索结果的主题会发散。应限制每词扩展数量，并默认禁用宽泛上位词扩展。

### LLM 改写改变原意

LLM 可能把“不含 React 的框架”改写成“React 替代品推荐”，意图发生偏移。证据包括改写句与原始句Embedding相似度低于阈值，以及用户随后重新输入更精确的查询。恢复动作是启用漂移护栏，并把失败样本加入人工反馈训练集。

## 维护、版本、来源与相邻主题关系

查询改写模块需要独立版本管理，包括知识库版本、同义词表版本、实体目录版本和配置 Schema 版本。同义词来源应可追溯，优先来自搜索日志中的用户改写行为、人工编纂的领域词表和公开的层级本体。实体知识库建议每季度同步一次，并在 Schema 变更时发布兼容性说明。与相邻主题的关系如下：查询分解负责把复杂意图拆成子查询；混合检索负责在向量、关键词和结构化过滤之间分配权重；重排序负责在召回后精排；而查询改写只负责在进入检索器之前提升查询表达质量。它们之间通过定义清晰的 DTO 边界进行解耦。

## 结论

事实层面，受控的查询改写确实能够提升 RAG 系统的召回率，尤其是在用户使用了非标准术语或省略了约束条件时；意图漂移验证和实体置信度门控是避免改写失控的必要机制。推论层面，结合规则与轻量 LLM 的混合改写路径，在保持低延迟的同时，能够处理大部分中低复杂度查询；多查询分解对于长查询的降噪效果优于单查询的过度扩展。未知层面，不同领域下最优的同义词相似度阈值尚无统一答案；用户在线 reformulation 信号是否足以自动修正改写策略仍需持续实验；改写对下游生成模型事实准确性的长期影响也还没有被充分量化。
