# RAG 查询改写：在扩展语义与保持原意之间的验证与运维

## 摘要与问题边界

查询改写是 RAG 检索阶段的前置环节，目标是把用户输入扩展为包含同义词、相关实体和隐含约束的查询集合，同时严格保留原始意图。运维视角下，这项工作不是一次性的 NLP 调优，而是一个需要持续观测召回率、精确率、延迟和一致性的生产子系统。其边界非常清晰：当改写导致检索结果偏离用户真实问题时，即使单个查询看起来成功，也应当判定为故障。本主题只讨论检索前的查询侧改写，不包含向量索引构建、重排序和生成后处理。

## 核心概念与数据模型

1. **原始查询（Raw Query）**：用户实际输入的文本，是后续所有改写的不可变基线。任何改写版本都必须能够回溯到原始查询。

2. **意图签名（Intent Signature）**：用结构化方式记录查询的核心动作、目标对象和约束类型。例如 `{action: find, target: error_log, constraint: last_24h}`，用于在改写后做一致性校验。

3. **语义扩展集（Semantic Expansion Set）**：由同义词、近义词、领域术语和相关实体构成的候选集合，通常附带与原始词的相似度分数和来源标签。

4. **约束保持规则（Constraint Guard）**：显式记录必须保留的时间、版本、路径、权限、数值范围等条件。约束丢失是改写阶段最严重的故障类型之一。

5. **改写置信度（Rewrite Confidence）**：量化当前改写可靠性的分数，通常综合语义相似度、约束完整度和历史表现计算得出。

6. **结果对齐证据（Evidence Alignment）**：记录改写后检索结果与原始意图匹配程度的可验证痕迹，包括命中文档ID、匹配片段和偏移校验标记。

## 设计决策与取舍

### 在线改写与离线预改写的取舍

在线改写根据实时输入动态生成扩展查询，灵活性高，但会引入额外延迟，适合长尾和个性化查询。离线预改写把常见查询提前生成多组扩展版本，延迟低，但无法覆盖新词和突发需求。生产系统中通常采用混合策略：高频查询走离线缓存，长尾查询走在线服务，并在缓存未命中时触发后台更新。

### 同义词表与 LLM 生成的取舍

同义词表基于规则，可解释、可控、延迟低，但覆盖范围有限，容易过时。LLM 生成覆盖广、能理解上下文，但可能产生幻觉扩展，且成本更高。推荐的做法是：同义词表负责精确约束词，LLM 负责上下文相关的语义扩展，并通过过滤层拦截不可信结果。

### 单轮改写与多轮改写的取舍

单轮改写实现简单、延迟稳定，适合明确、结构化的查询。多轮改写能逐步澄清模糊意图，但会放大延迟和错误累积。只有在对话式检索场景中才启用多轮，并设置最大轮数和每轮置信度阈值。

### 约束硬保留与软保留的取舍

硬保留指在改写中绝对不允许删除或修改约束词，例如版本号、文件名、状态码。软保留允许在语义等价时做近义替换，例如把“最近一周”扩展为“过去 7 天”。所有约束必须在规则配置中明确标注保留级别。

### 扩展激进度的阈值设定

扩展过少会漏召回，扩展过多会引入噪声。通常设定语义相似度下限、候选扩展数量和结果截断阈值，并通过 A/B 实验验证不同阈值对业务指标的影响。

## 可执行的实施流程

1. 建立原始查询的意图基线，输出稳定的意图签名格式，作为后续校验的参照。

2. 梳理业务领域的同义词、缩写、别名和上下位实体，形成可版本化的知识表。

3. 定义约束保持规则，明确哪些词属于硬保留、软保留或可替换。

4. 实现查询改写服务，支持规则扩展、LLM 扩展和混合模式，并为每次改写输出置信度。

5. 将改写服务接入检索链路，确保原始查询和改写版本可并行召回，便于对比。

6. 设置对照实验，比较改写前后在相同测试集上的召回率、精确率和平均倒数排名。

7. 部署可观测性，记录改写延迟、改写版本分布、约束丢失事件和意图偏移告警。

8. 建立回滚与熔断机制，当改写服务超时、置信度低于阈值或意图偏移告警触发时，自动降级为原始查询检索。

## TypeScript 配置与处理示例

以下 JSON 描述一个本地文件知识库场景的查询改写配置：

```json
{
  "rewritePolicy": "hybrid",
  "hardConstraints": ["version", "filename", "statusCode"],
  "softConstraints": ["timeRange", "environment"],
  "expansion": {
    "maxCandidates": 5,
    "similarityThreshold": 0.78,
    "sources": ["rule_table", "domain_llm"]
  },
  "fallback": {
    "onTimeout": "original_query",
    "onLowConfidence": "original_query",
    "confidenceThreshold": 0.65
  }
}
```

输入为 `"React 18 useEffect 在严格模式下的重复执行问题"`，处理阶段提取意图签名 `{framework: React, version: 18, hook: useEffect, mode: StrictMode, issue: double_invoke}`，随后从同义词表扩展出 `{StrictMode: 严格模式}`, 从 LLM 生成相关实体 `{useEffect: effect_cleanup, concurrent_render}`。输出改写查询集合包含原始查询和三个扩展版本，每个版本标注置信度和来源。

## 性能、质量与可观测性指标

1. **改写延迟 P99**：测量从接收原始查询到返回改写集合的耗时，目标通常低于 100 毫秒，超过则触发告警并记录采样。

2. **召回率变化**：在固定测试集上比较启用改写前后的召回率，要求有统计显著的提升或至少不下降。

3. **精确率变化**：监控改写引入的噪声是否导致前 K 结果中不相关文档比例上升。

4. **意图偏移率**：通过规则或人工抽检，统计改写后检索结果与原始意图不符的查询占比，目标控制在 2% 以下。

5. **服务可用性**：改写服务的成功响应比例，结合熔断和降级策略，目标不低于 99.9%。

## 失败模式、诊断证据与恢复动作

1. **过度扩展**：把“Python 异步”扩展出“Java 多线程”等同义词，导致检索结果混入无关语言。诊断证据是扩展候选与原始词相似度低于阈值且无领域关联。恢复动作是降低扩展激进度和补充负例词表。

2. **意图漂移**：用户查询“Docker 日志”被改写成“Kubernetes 日志”，改变了核心对象。诊断证据是意图签名中目标对象发生变化。恢复动作是强化硬保留规则并加入对象锁定机制。

3. **约束丢失**：原始查询限定“v2.1”，改写后版本号被省略，导致返回旧版本文档。诊断证据是约束保持规则校验失败。恢复动作是把版本号加入硬保留列表并增加后置校验。

4. **同义词冲突**：某个术语在不同上下文中含义相反，例如“branch”在 Git 和银行领域完全不同。诊断证据是同一扩展词在多领域测试集中产生正负两种结果。恢复动作是按业务上下文路由到不同的同义词表。

5. **服务超时**：LLM 扩展接口响应缓慢，拖慢整条检索链路。诊断证据是 P99 延迟突增且超时错误率上升。恢复动作是触发熔断，降级为原始查询或规则扩展。

## 问答测试样例

1. **正向**：用户问“如何用 TypeScript 配置 ESLint 9 flat config”，期望改写保留 `ESLint 9` 和 `flat config`，并扩展出 `eslint.config.mjs` 和 `FlatCompat`。若版本号丢失则判定失败。

2. **正向**：用户问“Next.js App Router 中 Suspense 的 loading 行为”，期望扩展出 `loading.js` 和 `streaming`，同时保持 `App Router` 不被替换为 `Pages Router`。

3. **边界**：用户问“React 性能优化”，查询高度模糊。期望系统输出多个低置信度改写版本并提示需要澄清，而不是武断选择一个方向。

4. **边界**：用户问“2024 年 Q3 的 Node.js LTS 版本”，时间约束必须硬保留，若改写成“最新 LTS”则判定为约束丢失。

5. **无证据拒答**：用户问“这个项目上周修复了哪些 bug”，但知识库中没有按周组织的变更记录。系统应拒答或返回未命中，而不是编造 bug 列表。

6. **无证据拒答**：用户问“pi-coding-agent 的私有 API 细节”，若项目中无相关文档，应明确说明未找到相关资料，避免基于猜测生成扩展查询。

## 维护、版本、来源与相邻主题的关系

查询改写的同义词表和约束规则应当与代码一起版本管理，每次变更都需要在测试集上跑回归。来源标注必须清晰，区分人工维护、LLM 生成和自动挖掘。查询改写与 Dense Retrieval 相邻，后者负责语义编码，前者负责输入侧扩展；与 Hybrid Search 相邻，后者决定如何融合多种检索结果；与 Re-rank 相邻，重排序负责改写后的精排，但不负责扩展语义。与 Prompt Engineering 的区别在于：查询改写发生在检索阶段，而不是生成阶段的提示构建。

## 结论

事实：查询改写能够提升 RAG 系统的召回能力；约束保留是改写正确性的底线；可观测性是运维该系统的前提。

推论：在工程实践中，混合使用规则表和 LLM 生成通常比单一策略更稳定；设定置信度阈值和熔断降级是控制故障影响面的有效手段。

未知：不同业务场景下最优的扩展阈值和改写轮数仍需通过 A/B 实验确定；LLM 生成扩展的长期漂移趋势尚未形成统一量化标准。
