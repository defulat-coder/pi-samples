# 向量检索：在语义相似边界处引入嵌入模型与版本治理

## 摘要与问题边界

向量检索解决的是“语义相似”而非“字符串相等”的问题。当用户查询与目标文档在措辞、语言或抽象层级上不一致，但所表达的概念相近时，才应当引入 embedding 向量。它的边界非常清晰：精确文件名、ID、路径、配置键等可确定性匹配的内容，应交给关键词索引、哈希表或关系查询；只有需要理解同义改写、跨语言映射、概念关联或上下文含义时，向量检索才成为必要组件。同时，向量空间的坐标本身没有可解释意义，检索结果必须绑定到生成该向量的嵌入模型及其版本号，否则无法保证长期一致性。

## 核心概念与数据模型

1. **文档切片（Chunk）与语义单元**：向量不是为整篇文档生成，而是为段落、句子或固定 token 窗口生成。切片边界若落在句子中间，会破坏语义完整性；若切片过大，会在查询时被无关段落稀释相似度。通常以 200–500 个 token 为窗口，并保留前后重叠（overlap）以维持上下文。

2. **嵌入模型与版本（Embedding Model & Version）**：这是向量检索的核心依赖。每个向量必须携带模型名称、版本号、输出维度、池化策略（如 mean pooling、CLS pooling）以及归一化方式。不同模型生成的向量处于不同空间，不可混用；同一模型的不同版本通常也需要视为异构空间。

3. **向量索引结构**：生产环境几乎不会使用暴力扫描，而是采用近似最近邻（ANN）结构，如 HNSW、IVF 或 PQ。HNSW 在召回率和延迟之间表现均衡，但内存消耗高；IVF 适合内存受限且可容忍稍低召回率的场景；PQ 压缩显著但会损失精度。

4. **相似度度量**：余弦相似度（cosine）适用于归一化向量，关注方向而非绝对尺度；点积（dot product）在归一化后等价于余弦，但允许保留幅度信息；欧氏距离（L2）在向量未归一化时更直观。度量的选择必须与训练模型时的目标函数一致。

5. **混合检索与重排序**：向量检索通常与 BM25、关键词检索或稀疏向量并行执行，再通过线性加权或 learned ranker 融合。融合阶段必须保留各分支的原始分数和来源标签，以便后续审计。

6. **元数据与过滤谓词**：向量库中的每条记录都应保留标量字段，如来源文件路径、创建时间、模型版本、切片索引、权限标签。查询时先做标量过滤，再在过滤后的子集上执行 ANN，否则会在整个向量空间中搜索无权限访问的内容。

7. **向量空间版本治理**：当嵌入模型升级时，旧向量无法直接与新向量比较。必须制定迁移策略：保留旧版本索引直到新索引重建完成，或显式标记每条记录的模型版本并在查询时只搜索同版本向量。

## 设计决策与取舍

**何时使用 embedding，何时拒绝**。若 80% 的查询是精确文件名、配置项 ID、版本号或命令路径，则优先构建倒排索引和 Trie 前缀树，而非向量索引。embedding 的引入应基于查询日志中“语义失败”的比例，即关键词命中为空但人工判断存在相关文档的请求占比。

**稠密向量与稀疏向量**。稠密向量（如 768 维或 1536 维）适合概念层面的相似；稀疏向量（如 SPLADE、BM25 向量化）适合保留精确术语权重。对于本地文件知识库，建议同时维护两套索引，并通过融合层让两类结果竞争。

**托管服务与自托管**。托管向量数据库（如 Pinecone、Weaviate Cloud、Qdrant Cloud）减少运维负担，但模型版本和租户隔离仍由自己控制。自托管（如 pgvector、Milvus、Qdrant）便于在私有环境保留完整审计日志，但需要负责分片、备份和 ANN 参数调优。

**单一模型与多模型**。单一模型简化版本治理，但无法覆盖代码、自然语言、表格、图像等不同模态。若引入多模型，则每个查询必须先经路由层判断其模态，再进入对应模型和索引，且每条结果必须标注模型来源。

**实时索引与批量重建**。embedding 计算通常比标量索引慢一个数量级，因此不适合每条写入都同步生成向量。更可靠的做法是：写入队列化，异步生成 embedding，更新索引时采用 copy-on-write 或 dual-index 切换，避免查询看到半新半旧的向量空间。

**固定阈值与动态 Top-K**。固定相似度阈值容易被模型版本升级打破；动态 Top-K 更稳定，但可能返回大量低质量结果。建议同时输出原始分数、归一化分数和阈值命中率，由上层应用根据业务场景决定截断。

## 可执行的实施流程

1. 收集三个月查询日志，标记“语义失败”样本，确认向量检索的必要性。
2. 选择嵌入模型，锁定版本号、维度、池化方式和归一化策略，并写入配置清单。
3. 设计文档切片策略：窗口大小、重叠量、边界规则（优先按段落和代码块边界切分）。
4. 定义向量库 schema：向量字段、标量元数据字段、模型版本字段、权限字段。
5. 搭建 ANN 索引，选择 HNSW 或 IVF，设定 ef_construction、M、nlist 等参数并记录。
6. 实现异步 embedding 管道：写入 → 队列 → 模型调用 → 归一化 → 索引更新。
7. 构建查询管道：查询重写 → 标量过滤 → ANN 检索 → 混合融合 → 重排序 → 输出溯源。
8. 建立可观测性：记录查询向量、模型版本、候选分数、最终返回文档、延迟和阈值命中率。
9. 制定模型版本迁移 SOP：旧索引冻结 → 新模型重建 → 影子验证 → 流量切换 → 旧索引归档。
10. 建立 QA 测试集：正向问题、边界问题、无证据问题，每季度运行并监控指标回归。

## 代码示例：记录模型版本的索引与查询

```typescript
// 输入：一段本地 Markdown 文件切片
const chunk = {
  id: "adr-0001:chunk-3",
  text: "当查询意图依赖同义词或跨语言映射时，应使用向量检索。",
  source: "docs/adr/0001-rag-boundary.md",
  model: "text-embedding-multilingual-v3",
  version: "2024-06-01",
  dim: 1024,
  normalized: true,
};

// 处理：调用模型生成向量，携带模型与版本元数据
const vector = await embed(chunk.text, {
  model: chunk.model,
  version: chunk.version,
});
await vectorStore.upsert({
  id: chunk.id,
  vector,
  payload: {
    source: chunk.source,
    model: chunk.model,
    version: chunk.version,
    dim: chunk.dim,
  },
});

// 输出：查询时强制限定同版本向量，并返回溯源信息
const results = await vectorStore.search({
  queryVector,
  filter: { version: "2024-06-01" }, // 关键：版本隔离
  topK: 10,
});
// 返回结果包含 id、score、source、model、version
```

该示例的核心在于：向量不是裸坐标，而是与模型版本绑定。查询过滤条件必须包含版本号，否则不同模型产生的向量会被错误比较。

## 性能、质量与可观测性指标

1. **召回率（Recall@K）**：在测试集中，前 K 个结果包含人工标注相关文档的比例。通过标注 200 条语义问题及其对应文档测量，目标值通常 ≥ 85%。

2. **精确率（Precision@K）**：前 K 个结果中真正相关文档的比例。与召回率结合绘制 PR 曲线，以确定最佳 K 和阈值。

3. **P99 查询延迟**：从查询文本到返回结果的时间，托管服务通常可控制在 200ms 内，自托管 HNSW 在 10 万级文档上通常低于 100ms。

4. **索引吞吐量**：每秒可完成 embedding 并写入索引的文档切片数。取决于模型推理速度和批量大小，通常需要监控队列长度以识别积压。

5. **模型版本覆盖率**：存量向量中属于当前查询所用模型版本的比例。低于 100% 意味着仍存在旧版本索引，查询结果可能出现跨版本污染。

6. **阈值命中率与空结果率**：查询命中相似度阈值的比例，以及空结果比例。空结果率过高说明模型与知识库不匹配或阈值过严。

## 失败模式、诊断证据与恢复动作

**模型版本漂移**：查询使用新模型向量，但索引中仍大量存在旧版本向量。诊断证据：结果中混杂不同 `version` 标签，或覆盖率低于 100%。恢复动作：冻结旧索引，用新模型重建全量索引，切换前完成影子对比。

**切片粒度错误**：相关文档被切成过长片段，导致查询语义被无关内容淹没；或切得过碎，丢失上下文。诊断证据：高召回但低精确，或相关片段得分被同一文档的不相关片段拉高。恢复动作：调整窗口大小和重叠量，重新生成切片并重建索引。

**向量空间污染**：训练或微调数据与知识库领域不一致，导致相似度计算偏离业务语义。诊断证据：人工判断相关的结果得分低，而无关结果得分高。恢复动作：更换或微调领域适配模型，重新 embedding，并对比 PR 曲线。

**近似算法召回下降**：ANN 参数（如 HNSW 的 `ef` 或 IVF 的 `nprobe`）设置过低，导致近邻被遗漏。诊断证据：暴力扫描的 Recall@10 明显高于 ANN 的 Recall@10。恢复动作：提高 `ef`/`nprobe`，或重建索引时增大 `ef_construction`。

**元数据过滤导致空结果**：标量过滤条件过于严格，先过滤掉候选再执行 ANN，结果为空。诊断证据：去掉过滤后检索正常。恢复动作：将过滤谓词与向量搜索结合，使用支持 pre-filtering 的向量库，或调整权限模型。

## 问答测试样例

1. **正向问题**：哪些文档讨论了“在语义不匹配时引入 embedding 而不是关键词搜索”？预期召回 `docs/adr/0001-rag-boundary.md` 相关切片。

2. **边界问题**：`docs/adr/0001-rag-boundary.md` 的文件路径是什么？应拒绝使用向量检索，返回文件系统或关键词索引结果，因为路径是精确匹配。

3. **跨语言问题**：查询“向量检索应记录哪些元数据”用中文，文档原文为英文。应召回英文切片，因为语义相似不依赖语言。

4. **无证据拒答**：查询“Pi 支持哪些语言”在知识库中没有任何文档。应返回空结果，不编造答案。

5. **版本敏感问题**：若测试集中包含旧模型 `v2023-12-01` 的向量，查询使用 `v2024-06-01`，结果必须只来自新版本，旧版本切片不得出现。

6. **阈值边界问题**：查询“量子计算在 RAG 中的应用”与知识库内容仅有弱相关。若最高相似度低于 0.65，应返回空或提示“无足够相关文档”，而不是硬凑结果。

## 维护、版本、来源与相邻主题关系

维护向量检索系统的关键不是优化单次查询，而是管理向量空间的长期一致性。每次嵌入模型升级、切片策略变更或归一化方式调整，都应视为一次新的索引版本。建议将模型版本、维度、池化策略、训练数据来源和许可证信息写入 `EMBEDDING_REGISTRY` 文件，作为配置审计的一部分。

与相邻主题的关系：关键词检索（BM25、Trie、倒排）负责精确匹配和 high-idf 术语；图检索负责实体关系和多跳推理；重排序模型负责在候选集合上做精细排序；大语言模型负责基于检索结果生成最终答案。向量检索位于“语义匹配”这一层，它不应替代其他层，而应通过统一 ID 与它们关联。

## 结论

**事实**：向量检索依赖嵌入模型将文本映射到稠密向量空间；不同模型或版本的向量不可直接比较；相似度度量、切片策略、ANN 参数和元数据过滤都会显著影响结果。

**推论**：对于本地文件知识库，最稳健的设计是：切片按语义边界生成，每条向量强制绑定模型版本，查询时通过版本过滤隔离，并维护混合检索与重排序作为补充。

**未知**：特定业务领域的最优切片窗口、多模态混合检索的融合权重、以及模型版本生命周期（何时必须强制重建而非双索引共存）需通过持续实验和 A/B 测试确定。
