# 面向运维与验证的向量检索实践

## 摘要与问题边界

当用户查询与知识库片段字面表达不一致但语义相近时，才应引入 embedding 向量检索。它不能替代关键词搜索，而是补充“同义、近义、上下文相关”的召回。本实践聚焦 RAG 中“查询向量化 → 近似最近邻（ANN）召回 → 结果过滤与重排”的链路，并强制记录 embedding 模型名称、版本号与向量维度。模型版本未记录时，无法解释召回结果是否来自同一向量空间，更无法在召回异常时定位模型变更。运维与验证的核心是：不要只看一次成功请求，而要持续收集成功、失败、延迟、容量与恢复证据。

## 核心概念与数据模型

1. 向量单元：每个被检索片段对应一个 d 维浮点向量，由固定模型在固定版本下生成。向量必须携带 model_name、model_version、dimension、generated_at。缺少这些字段时，运维人员无法判断两个向量是否来自同一向量空间，更无法在召回异常时定位模型变更。
2. 查询向量：用户问题经同一模型同一版本编码，禁止跨版本比较，否则相似度无意义。生产环境应把模型版本作为查询上下文的一部分，与索引分片严格对齐。
3. 索引分片：按集合与模型版本分片。升级模型时新建分片，保留旧版本用于回滚与 A/B 对比。分片名建议包含版本号，例如 kb_v2024-01-01。
4. 相似度函数：选择余弦相似度、内积或欧氏距离，并显式声明。不同函数的阈值不可混用。例如余弦 0.75 与内积 0.75 在归一化与否的情况下代表不同置信度。
5. 候选与过滤：ANN 先返回候选 Top-K，再按阈值、权限、时间窗、来源标签过滤。K 应大于最终展示数，为重排与容缺失留余量。若过滤后为空，应在日志中记录过滤原因。
6. 距离分布：记录每次查询结果的相似度分布。分布突增或突降往往先于用户投诉，是稳定性指标。当分布均值偏离历史基线超过 2σ 时，应触发模型或索引健康检查。
7. 来源锚定：每个向量绑定原始文本块 ID、源文件路径、分块参数。召回失败时必须能追溯到生成步骤，避免把“检索不到”误判为“业务问题”。

## 设计决策与取舍

### 1. 模型与版本锁定
生产索引一旦建立，embedding 版本必须冻结。升级模型时，先离线重建新索引，在影子流量中对比召回率与延迟，再切换。任何版本切换都要记录蓝绿集合名称与切换时间点。

### 2. 相似度函数与阈值
余弦适合长短不一文本；内积在未归一化且重视信息密度时可用；欧氏距离直观但阈值解释性弱。阈值应通过评估集确定，并在不同业务场景下设置不同阈值。

### 3. 实时与批量索引
实时写入适合频繁更新，但增加碎片和合并开销；批量重建延迟低但新内容可见性差。通常采用“批量重建 + 小批量增量”，并在低峰期合并分片。

### 4. 本地与托管服务
本地库可控、可离线运行，但容量与恢复需自行保障；托管服务把网络延迟、配额、模型版本黑盒化。本地方案需实现备份、副本与版本隔离，至少保留两个副本。

### 5. Top-K 与阈值
仅 Top-K 在语义模糊时易引入无关结果；仅阈值可能返回空。生产采用 Top-K 兜底、阈值过滤、重排截断的三层策略。阈值过低时直接返回空也比返回噪声更安全。

### 6. 重排序取舍
在 Top-K 后用交叉编码器或规则重排可提升精度，但增加延迟。若 P95 已接近上限，应放弃重排或仅对高置信查询启用。

## 可执行的实施流程

1. 定义语义单元：明确最小检索粒度，避免 chunk 过大稀释语义或过小丢失上下文。常见做法按段落或代码块切分，代码块不可与普通文本混切。
2. 固定模型与版本：在配置中写死 model_name、model_version、revision，任何变更都通过 PR 与回归测试。上线前把模型元数据写入索引的 schema 头。
3. 设计向量 schema：记录 source_id、file_path、chunk_index、chunk_size、permission_tags、indexed_at。字段缺失会导致失败排查无法定位原始片段。
4. 批量生成并校验：对全部片段生成向量，校验维度一致性、NaN/Inf 与空向量比例，写入分片。校验不通过时禁止上线。
5. 建立索引与分区：按模型版本创建独立集合，配置距离度量与索引参数，记录构建耗时与索引大小。建议用模型版本命名集合，便于灰度。
6. 实现检索路径：查询 → 同模型编码 → ANN 召回 → 阈值过滤 → 元数据过滤 → 重排 → 返回带来源的 Top-N。每一步都要记录耗时和结果数。
7. 接入可观测性：打印 embedding_latency、ann_latency、recall_count、filter_drop_count、result_distance_distribution。指标应与服务日志使用同一 trace id。
8. 设置告警与演练：P95 检索延迟 < 500 ms、ANN 召回率相对暴力检索 > 90%、版本不一致报警；定期注入故障并验证回滚。告警阈值应随流量规模定期复核。

## 本地文件知识库 JSON 示例

    {
      "schema_version": "v1",
      "embedding": {
        "model": "text-embedding-3-small",
        "version": "2024-01-01",
        "dimension": 1536,
        "metric": "cosine"
      },
      "chunks": [
        {
          "id": "chunk-042",
          "source": "docs/runbook/rollback.md",
          "chunk_index": 3,
          "chunk_size": 512,
          "overlap": 64,
          "text": "当向量检索返回空时，优先检查模型版本与索引分片是否一致。",
          "vector": [0.021, -0.005, 0.018],
          "indexed_at": "2024-06-12T09:23:00Z"
        }
      ],
      "last_verified_at": "2024-06-12T10:00:00Z"
    }

输入：原始 Markdown 文件、分块参数、embedding 模型配置。处理：按 chunk_size 与 overlap 切分，调用模型生成向量，写入 JSON 并附带模型与版本。输出：可被本地向量检索加载的索引条目，包含足够元数据用于失败溯源。

## 性能、质量与可观测性指标

1. 端到端检索延迟：P50、P95、P99；区分 embedding、ANN、过滤、重排各阶段。通过日志或 APM 在每次请求后上报。
2. ANN 召回率：用评估集对比 ANN Top-K 与暴力检索 Top-K 重叠率，目标 > 90%。每周用固定评估集回归一次。
3. 结果相关性：通过标注集计算 MRR 或 NDCG@K，低于阈值则检查模型、阈值或分块。人工标注不少于 100 条核心问题。
4. 距离分布漂移：记录每批次相似度均值，与基线比较，偏移超过 2σ 告警。基线应在系统稳定后采集至少一周。
5. embedding 生成失败率：统计超时、空向量、NaN/Inf、维度错误，超过 0.1% 触发降级。失败请求要单独记录，便于重放。
6. 版本一致性：索引向量版本与在线查询编码版本不一致率必须为零。每次请求前校验，若不一致直接拒绝检索。

## 失败模式、诊断证据与恢复动作

1. 模型版本漂移：日志出现 model_version mismatch，相似度普遍低于基线。恢复：切回旧模型索引，新版本重建完成前不切换。切换前必须对比 A/B 指标。
2. 索引文件损坏：加载报错或返回结果数异常下降。恢复：从备份副本加载；备份不可用时触发离线重建，期间关键词检索兜底。重建期间禁用自动切换。
3. ANN 召回坍塌：评估集 recall@10 从 92% 跌至 55%。恢复：回退到已知良好的参数快照，必要时切换暴力检索或增大候选集。同时检查最近是否修改了索引参数。
4. embedding 服务异常：P99 延迟突增，出现空向量或 NaN。恢复：启用缓存查询向量 fallback；返回“检索暂不可用”，修复后重放失败请求。不要返回无来源的低置信结果。
5. 阈值过紧或过松：过紧返回结果长期为零，过松低相似度结果占比升高。恢复：基于评估集重新校准阈值，使用分场景阈值。变更阈值后需观察 24 小时。
6. 索引过期：命中来源文件已删除或更新，但 indexed_at 早于修改时间。恢复：标记脏分片，触发增量重建，并附加知识库版本提示。用户可见结果应显示“基于 2024-06-12 版本”。

## 问答测试样例

1. 正向：如何回退向量索引？→ 召回 chunk-042，来源 docs/runbook/rollback.md，答案包含模型版本与索引分片检查。系统应优先召回该片段并给出可验证的来源路径。
2. 正向：embedding 模型升级要注意什么？→ 冻结生产版本、离线重建、A/B 对比、保留旧索引。不应只回答“升级模型”，而要给出新旧索引切换流程。
3. 边界：余弦相似度 0.75 一定相关吗？→ 不一定，需结合模型、版本、评估集阈值与上下文；不同模型间不可比较。若评估集显示 0.75 召回率仅 60%，则该阈值不可靠。
4. 边界：Top-K=10 但返回为空？→ 可能阈值过紧、模型版本不匹配、ANN 坍塌、索引损坏，列出排查指标。建议先检查 model_version 与 filter_drop_count。
5. 拒答：这个向量库支持 GPU 吗？→ 未在文档中找到关于 GPU 部署的可验证信息，无法回答。不要根据模型名称推断硬件支持。
6. 拒答：用哪个 embedding 模型最好？→ 未找到基准对比数据，无法给出通用最优模型，应依据评估集、延迟与成本选择。没有项目评估集时，任何推荐都缺乏证据。

## 维护、版本、来源与相邻主题

- 版本管理：模型或分块策略变更视为索引 schema 升级，旧索引保留到新版本验证完成。建议在集合名中嵌入版本，并保留至少一个发布周期。同时保留生成该索引时使用的配置文件与依赖版本。
- 来源记录：所有向量必须能回到原始文本、文件路径与生成时间。定期扫描 indexed_at 与文件 mtime 的差异，发现过期立即重建。过期检测应通过文件 mtime 自动触发，而不是等用户投诉。
- 相邻关系：向量检索与关键词检索互补；与重排序、混合检索、查询改写相邻。建议关键词兜底再叠加向量召回。评估集和故障演练同样服务于相邻主题。
- 评估：效果无法通过单次成功判断，需建立持续评估集，定期回归。新增文档或模型版本后必须重新跑评估。

## 结论

事实：向量检索通过 embedding 将语义相似问题转化为距离计算；模型与版本不一致会直接导致相似度不可比；本地文件知识库必须记录来源、分块参数与生成时间；单次成功请求不能证明系统稳定。

推论：在模型版本冻结、索引分片隔离、持续评估与分层过滤的前提下，向量检索可稳定扩展 RAG 的语义召回能力；但延迟与容量随规模增长，需要参数调优与分区。

未知：具体业务的最优 embedding 模型、最佳分块大小、阈值和 ANN 参数无法预先确定，必须在项目评估集与真实流量上验证；不同模型的向量空间偏移幅度也无法仅凭文档推断。未知还包括用户真实查询分布与评估集之间的偏差对长期效果的影响。
