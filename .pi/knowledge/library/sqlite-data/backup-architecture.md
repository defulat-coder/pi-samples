# SQLite 本地数据备份恢复：WAL、快照、导出与完整性验证的架构设计

## 摘要与问题边界

本文讨论以 SQLite 为中心的本地数据系统在浏览器、桌面或边缘节点中的备份与恢复架构。范围限定在单文件或本地文件组，不涉及分布式事务、云端主从复制或对象存储的多活一致性。核心问题不是“如何复制一份文件”，而是如何在 WAL、快照、逻辑导出和恢复之间划分责任，并建立可替换、可验证的接口，使长期演进中的存储后端、校验算法和恢复策略能够独立升级。

## 核心概念与数据模型

1. **WAL 三元组**：在 `journal_mode=WAL` 下，运行时的持久化单元由主数据库文件、`-wal` 日志文件和 `-shm` 共享内存文件共同组成。任何只复制主数据库而不包含 `-wal` 的备份，都可能丢失已提交事务，恢复后出现“页面错位”或“ malformed disk image”。

2. **检查点状态**：WAL 检查点将日志页回写主库。`PRAGMA wal_checkpoint(PASSIVE)` 允许并发写入，`FULL` 会阻塞新写，直到完成。备份策略应明确检查点类型，并在检查点前后记录日志帧号，以便判断捕获的是哪一个一致状态。

3. **快照与恢复点**：一次快照生成一个不可变的恢复点（Restore Point, RP），包含数据库文件、可选的 WAL 段、清单文件和校验摘要。恢复时先写入临时目录，验证通过后再原子替换当前数据库。

4. **逻辑导出**：使用 `sqlite3` 转储或应用级 JSON 导出得到的 SQL/JSON 文件。它是可读的迁移辅助，但可能无法完整保留 FTS5 外部内容、自定义扩展或版本元数据。逻辑导出不应作为唯一恢复手段，除非已证明与原库等价。

5. **备份状态机**：状态包括 `pending`、`checkpointing`、`capturing`、`verifying`、`verified`、`failed`、`expired`。每次状态转移必须写入单调递增的序列号，失败时保留日志和临时产物，禁止原地回写。

6. **可替换接口**：`SnapshotProvider` 负责物理捕获；`IntegrityVerifier` 负责页级与应用级校验；`RestoreOrchestrator` 负责在临时目录重建并切换；`SchemaValidator` 负责版本兼容。各接口通过稳定契约交互，避免实现细节泄漏到上层业务。

## 设计决策与取舍

### WAL 检查点策略

优先在应用空闲窗口执行 `PRAGMA wal_checkpoint(FULL)`，确保捕获时主库包含全部已提交数据。若业务无法容忍写停顿，则改用 `PASSIVE` 并同时捕获 `-wal` 文件，但此时恢复脚本必须能够重放这些日志。例外：当存在长时间未提交的事务时，`FULL` 检查点可能失败，应降级为快照 `-wal` 或标记本次备份为“可能包含未提交数据”。

### 二进制快照与逻辑导出

二进制快照是权威恢复源；逻辑导出是审计、迁移和跨版本同步的辅助。边界在于：FTS5 索引、自定义虚拟表、SQLite 扩展配置不会出现在逻辑导出中，因此导出后重建必须作为显式步骤。两者不应互相替代，而应通过清单记录它们之间的派生关系。

### 校验算法组合

使用 `xxhash64` 进行快速传输/本地完整性校验，使用 `SHA-256` 进行防篡改与来源证明。决策理由：备份文件通常很大，需要低成本比对；而清单摘要需要抵抗意外修改。若安全密钥不可用，则 `SHA-256` 仍可作为校验和，但不再提供签名级别的不可否认性。

### 在线备份与离线备份

在浏览器或受限运行时，使用 SQLite 的 `backup` API 或 `VACUUM INTO` 比直接复制打开中的文件更安全；在 Node 或 Electron 中，可以借助文件锁或 `sqlite3` 在线备份 API。取舍：在线备份延长备份时间但保持应用可用；离线备份简单，但会阻塞用户。对于本地知识库，推荐在线备份并在 UI 上显示进度。

### 版本与迁移边界

备份清单中必须记录 `schemaVersion`（应用模式版本）、`sqliteVersion`（运行库版本）和 `fileFormat`（文件格式号）。恢复时，如果备份的 `schemaVersion` 高于当前代码支持，则直接拒绝；如果低于当前，则进入迁移路径。该判断由 `SchemaValidator` 完成，迁移脚本应可替换，避免在恢复核心中写死升级逻辑。

## 可执行的实施流程

1. 在业务低峰或收到显式命令时进入备份窗口，暂停非必要写入。
2. 执行 `PRAGMA wal_checkpoint(FULL)` 或 `PASSIVE`，并记录检查点前后的日志帧号。
3. 运行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`，确认主库无页面损坏与外键违规。
4. 在写保护或锁保护下捕获主库、`-wal` 和 `-shm`（若使用 WAL），或使用 SQLite 备份 API 写入临时副本。
5. 计算每个文件的 `xxhash64` 和清单整体 `SHA-256`，并将结果写入清单文件。
6. 将临时恢复点移动到不可变目录，命名中嵌入时间戳与序列号，禁止覆盖。
7. 在隔离的临时目录中执行一次完整恢复：重建数据库、运行完整性检查、执行应用级采样断言。
8. 将验证通过的恢复点注册到恢复点注册表，标记状态为 `verified`，并清理失败的临时产物。
9. 定期运行自动恢复演练，演练结果写入可观测日志，失败时触发告警。
10. 达到保留期限后，将过期恢复点归档或删除，并更新注册表。

## 示例：备份清单与处理边界

以 TypeScript/Web/本地文件知识库为例，备份工具接收一次捕获目录，生成清单记录。

- 输入：目录 `data/` 包含 `knowledge.db`、`knowledge.db-wal`、`knowledge.db-shm`。
- 处理：调用 `PRAGMA integrity_check`；计算 `knowledge.db` 与 `knowledge.db-wal` 的 `xxhash64`；用整个记录计算 `SHA-256` 摘要。
- 输出：清单记录，字段包括 `backupId` = `rp-2025-11-21-001`，`source` = `file:///data/knowledge.db`，`schemaVersion` = `7`，`sqliteVersion` = `3.46.0`，`mode` = `wal-snapshot`，`files` 列表中每个条目含 `name`、`size`、`xxhash64`，`manifestHash` 为全记录 `SHA-256` 十六进制值。该清单在恢复时首先被校验，任何字段缺失或哈希不匹配都导致恢复中止。

## 性能、质量与可观测性指标

1. **备份耗时**：从进入备份窗口到清单写入完成的时间，使用单调时钟测量，按 `p50` 和 `p99` 分位上报。
2. **RPO（恢复点目标）**：当前时间与最新已验证恢复点的时间差，必须低于业务约定的阈值。
3. **完整性验证通过率**：通过的恢复点数量除以总尝试数量，按日聚合。
4. **校验和冲突率**：恢复或演练时发现的校验和不匹配次数，每次冲突都要记录文件名和字节偏移。
5. **存储放大率**：备份总大小与线上数据库大小之比，用于评估保留策略。
6. **写停顿时长**：检查点或锁持有期间阻塞用户写入的时间，在 UI 中显示并设置告警阈值。

## 失败模式、诊断证据与恢复动作

1. **缺少 WAL 文件**：恢复时 `integrity_check` 报告 “database disk image is malformed”。应重新检查源目录，确认 `-wal` 文件存在，必要时执行检查点后重新捕获。
2. **清单哈希不匹配**：恢复工具报 `manifestHash` 与计算值不一致。诊断证据是清单中某个文件大小与磁盘大小不同。恢复动作：标记该恢复点不可信，回退到上一个已验证恢复点，并审计存储链路。
3. **检查点长时间阻塞**：`wal_checkpoint(FULL)` 超过超时阈值。证据是事务帧号不再增长。动作：取消备份，改用 `PASSIVE` 加 `-wal` 捕获，或提示用户结束长事务。
4. **热备份撕裂页**：直接复制打开文件时出现页面校验和错误。证据是恢复后的 `integrity_check` 报告特定页偏移损坏。动作：放弃文件级复制，改用 SQLite 备份 API 或 `VACUUM INTO`。
5. **存储截断**：备份文件大小小于清单记录。证据是读取时提前到达 EOF。动作：验证拷贝前后的文件大小，使用原子重命名，失败时重试。
6. **应用级不变量破坏**：恢复后业务查询返回异常，如空集合或重复主键。证据是应用断言失败。动作：回滚到前一个恢复点，触发领域修复流程，不尝试“就地修复”当前数据库。

## 问答测试样例

1. **正向**：在 WAL 模式下为什么必须同时捕获主数据库和 `-wal`？
   答：因为已提交事务可能尚未回写到主库，`-wal` 是这些事务的权威来源，遗漏它会导致恢复丢失数据或页损坏。

2. **边界**：恢复时能否直接覆盖当前数据库文件？
   答：不应直接覆盖。正确做法是先恢复到临时目录，验证完整性、版本和应用断言后，再原子切换或重命名。

3. **正向**：`xxhash64` 和 `SHA-256` 在备份清单中分别承担什么职责？
   答：`xxhash64` 用于快速文件级完整性校验，`SHA-256` 用于清单整体与来源证明；两者互补，不互相替代。

4. **边界**：如果 `PRAGMA wal_checkpoint(FULL)` 因长事务失败，备份是否应继续？
   答：默认不应继续，除非策略明确允许降级为 `PASSIVE` 并保留 `-wal` 文件；降级必须在清单中显式记录。

5. **无证据时的拒答**：这个方案能否保证 100% 不丢失数据？
   答：不能。具体可靠性取决于存储介质、保留策略和演练频率，没有绝对保证。

6. **无证据时的拒答**：File System Access API 在所有浏览器上的快照性能如何？
   答：未知，需要针对目标运行时使用真实数据量实测；不能从 SQLite 行为直接推断。

## 维护、版本、来源与相邻主题

维护工作包括：定期执行恢复演练并审计日志、更新 SQLite 运行时后重新验证文件格式兼容性、轮换签名密钥、检查保留策略是否导致存储超限。备份清单自身具有独立的版本字段，新增字段时应保持旧版本的读取能力，必要时通过升级脚本转换。主要来源包括 SQLite 文件格式、WAL 模式与检查点机制、`PRAGMA integrity_check`、SQLite 备份 API 以及 `VACUUM INTO` 语义。相邻主题包括：本地优先同步（与同步合并策略区分）、静态加密（备份文件是否加密不在本文讨论）、文件系统访问 API、数据库模式迁移、以及只读副本/审计日志。

## 结论

- **事实**：WAL 模式下必须将主库、`-wal` 和 `-shm` 视为一个整体；`PRAGMA integrity_check` 是验证页级完整性的核心手段；不可变的恢复点与清单摘要是可验证恢复的基础。
- **推论**：将快照作为权威恢复源、逻辑导出作为辅助、恢复前在临时目录验证，能够在单用户本地知识库场景中实现可接受的 RPO 与回滚能力；可替换接口使得存储后端和校验算法可以独立演进。
- **未知**：具体浏览器 File System Access API 在真实数据量下的吞吐与配额行为；用户本地存储介质的长期故障率；SQLite 未来版本对文件格式与扩展语义的兼容性细节，需要项目级实测与版本兼容性矩阵持续更新。
