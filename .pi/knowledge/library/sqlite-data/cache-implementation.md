# SQLite 本地查询缓存：稳定读取复用与变更精确失效的实现

## 摘要与问题边界

本方案在 SQLite 与本地文件/浏览器存储的边界上，为读多写少的查询建立一层结果缓存，核心目标是在数据未变更时复用稳定读取结果，在写入提交后按表级依赖精确使缓存失效。输入包括：规范化后的 SQL 文本、绑定参数数组、当前数据库 schema 版本号、事务边界标识、写操作影响的表名集合。输出包括：命中时的反序列化结果、未命中时的新执行结果、失效事件记录、以及每次查询的命中/未命中决策日志。主要错误类型为：读到已失效结果（脏读）、不同查询因缓存键冲突而互相覆盖、事务内写入后的读取仍命中缓存、存储溢出导致缓存丢失、schema 版本漂移导致键空间污染。不适用场景包括：写入密集型工作负载、对实时一致性有强要求的金融或库存扣减逻辑、以及单条结果集过大（例如超过 50 MB）的查询。

## 核心概念与数据模型

1. **查询签名（Query Signature）**：缓存键由三部分拼接后做哈希生成——去除注释与多余空白后的 SQL 文本、绑定参数值的 JSON 序列化、当前 schema 版本号。绑定参数必须按顺序参与，不能使用默认参数占位符，否则同名不同值的参数会产生相同签名。
2. **缓存条目（Cache Entry）**：包含原始结果字节或结构化克隆对象、创建时间戳、依赖表集合、生成时的事务 ID、以及 SHA-256 校验和。校验和用于在读取持久化存储时检测位翻转或序列化损坏。
3. **依赖反向索引（Dependency Index）**：维护 `tableName → Set<cacheKey>` 的多对多映射。当某张表发生变更时，只需遍历该集合即可定位所有待失效条目，无需扫描全部缓存。
4. **失效令牌（Invalidation Token）**：每次写事务成功提交后，生成单调递增的整数写入 `_cache_invalidation_log` 表。读路径在命中缓存后，必须确认条目的生成令牌不小于最近一次涉及其依赖表的失效令牌；否则视为过期。
5. **一致性窗口（Consistency Window）**：定义为从写入提交到所有相关缓存条目被删除或标记为无效之间的最大时间。同步失效方案该窗口接近 0 ms；异步失效方案允许存在数十到数百毫秒的窗口，必须在文档中显式声明。
6. **TTL 与显式失效并列**：TTL 仅作为兜底清理机制，不能替代写时失效。显式失效保证正确性，TTL 保证缓存不会无限膨胀。
7. **事务上下文（Transaction Context）**：同一条事务内的写入操作，必须使该事务后续读取无法命中任何早于本次写入生成的缓存条目。实现上为每个事务维护一个本地写入表集合，读取时若依赖表与该集合相交则跳过缓存。

## 设计决策与取舍

**缓存键粒度：表级失效还是行级失效**。表级实现简单，只需在 SQL 执行前通过 EXPLAIN 或正则提取表名；缺点是任何行的变更都会使依赖该表的大量缓存失效。行级失效精确，但需要解析 WHERE 子句、处理 JOIN 与子查询，并维护主键到缓存键的映射，实现复杂度高、易出错。对于本地数据知识库场景，推荐表级失效作为默认策略，仅在热点单表上可选行级失效。

**存储后端：内存、IndexedDB 还是本地文件**。内存缓存命中延迟最低，但进程退出即丢失，适合高频小结果。IndexedDB 可跨会话持久化，但所有值需结构化克隆或序列化，大对象写入会阻塞主线程。本地文件缓存适合 Node.js 或 Electron 主进程，需要自行处理并发锁。Web 场景建议分层：内存 LRU 作为一级，IndexedDB 作为二级。

**序列化格式：JSON、MessagePack 还是结构化克隆**。JSON 通用但无法直接表示 `Date`、`Uint8Array`、`undefined`，需要 reviver 转换。MessagePack 体积小、速度快，但引入额外依赖。在浏览器主线程与 Worker 之间传输时，优先使用结构化克隆（`postMessage` 直接传对象），避免序列化开销。

**失效时机：同步还是异步**。同步失效在写事务提交后立即执行，保证一致性窗口最小，但会增加写路径延迟，且如果在失效过程中崩溃，可能留下脏缓存。异步失效将失效任务放入微任务队列或后台 Worker，写延迟低，但需要在读取路径做版本校验以覆盖窗口期内的脏读风险。

**并发模型：单线程主线程还是 Worker 隔离**。SQLite 在浏览器中通常通过 WebAssembly 运行于主线程或 Dedicated Worker。若数据库在 Worker 中，缓存也应位于 Worker 中，主线程只通过消息协议请求结果，避免跨线程同步状态的复杂性。Node.js 场景下，可考虑在数据库连接所在的线程内实现缓存。

## 可执行的实施流程

1. **查询审计**：列出应用中所有 SELECT 查询，标记读取频率高、结果稳定、不涉及随机函数或用户特定临时状态的候选。排除使用 `RANDOM()`、`LAST_INSERT_ROWID()` 依赖、以及每次查询参数均不同的高维度查询。
2. **键规范化实现**：建立 `normalizeSQL(sql)` 函数，移除 `--` 与 `/* */` 注释、折叠多余空白、统一关键字大小写。绑定参数按顺序序列化为字符串后参与 HMAC-SHA-256 计算，schema 版本作为 salt。
3. **依赖提取**：执行查询前，先通过 SQLite 的 `EXPLAIN QUERY PLAN` 解析出访问的表名；对于复杂视图，递归解析视图定义并汇总底层基表。将 `queryKey → tableSet` 写入依赖索引。
4. **读取路径实现**：拦截 `executeQuery(sql, params)`，先生成签名并检查内存缓存；命中后验证 TTL、校验和、以及依赖表的最新失效令牌；全部通过则返回反序列化结果，否则进入未命中路径。
5. **未命中处理**：实际执行 SQL，将结果序列化，计算校验和，写入缓存条目，并在依赖索引中为每个依赖表注册该缓存键。
6. **写入监听**：拦截所有 `INSERT`、`UPDATE`、`DELETE`、`REPLACE` 以及 `DROP TABLE`、`ALTER TABLE` 语句。写事务提交成功后，收集其影响的所有表名。
7. **失效执行**：根据影响表名查询依赖索引，删除或标记所有相关缓存键为无效，并向 `_cache_invalidation_log` 写入新的失效令牌。若使用异步失效，读取路径在窗口期内通过令牌比较拦截脏缓存。
8. **事务内特殊处理**：为每个打开的事务分配唯一 ID 和本地写入表集合。事务内的读取若发现依赖表出现在该集合中，即使全局缓存存在也不得命中。
9. **验证套件编写**：包含命中测试、未命中测试、写入后同步失效测试、事务回滚不触发失效测试、TTL 到期测试、schema 升级后旧缓存不可见测试。
10. **灰度与回退**：提供功能开关 `queryCache.enabled`，以及每个查询的 opt-out 标记。上线初期可仅对低风险查询开启，并保留通过环境变量一键关闭的能力。

## TypeScript/Web 本地文件知识库配置示例

缓存配置可声明为一组运行时参数：命名空间 `namespace` 取应用标识符加数据库文件 SHA-256 前 8 位，用于隔离多个数据库实例的键空间；键模板 `keyTemplate` 固定为 `hmac-sha256(normalizedSQL + "|" + paramDigest + "|" + schemaVersion)`；依赖索引表名 `dependencyTable` 设为 `_query_cache_deps`，用于记录 queryKey 到 tableName 的多对多关系；结果存储桶 `resultStore` 在浏览器中使用 IndexedDB 的 objectStore `queryCacheResults`，在 Node.js 中使用 OPFS 或单文件 JSONL；最大年龄 `maxAgeMs` 默认 300000，表示无失效事件时缓存最长存活 5 分钟；最大条目数 `maxEntries` 默认 1000，超出时按 LRU 淘汰；写入后失效模式 `invalidationMode` 可选 `sync` 或 `async`，默认为 `sync`；事务内缓存策略 `txnCachePolicy` 固定为 `never`，即同一事务内写入后的读取禁止命中缓存。输入为上述配置与一条 SELECT 查询；处理为生成签名、检查缓存、验证依赖表令牌、必要时执行并写回；输出为结果对象、命中标志、以及本次决策的追踪日志。

## 性能、质量和可观测性指标

1. **缓存命中率**：`hitCount / (hitCount + missCount)`，按查询模板分组。目标读多写少场景应高于 80%。
2. **命中延迟 p99**：从调用查询到返回缓存结果的耗时。内存缓存应低于 1 ms；IndexedDB 缓存应在 5–20 ms 之间。
3. **失效延迟**：写入事务提交到相关缓存条目不可见的时间。同步失效应接近 0 ms；异步失效应在 50 ms 内收敛。
4. **存储占用**：缓存条目总字节数与条目数量。设置硬上限并通过 LRU 或 TTL 兜底。
5. **脏读事件数**：在读取路径若发现命中的缓存条目已被标记为无效，但尚未删除，应计数为 near-miss 或 dirty-read-avoided。长期非零说明失效路径有延迟。
6. **缓存重建时间**：未命中后执行原始 SQL 并序列化写入缓存的端到端耗时，用于评估缓存引入的额外开销。

## 失败模式

1. **缓存未失效**：写入后仍能读到旧结果。诊断证据：命中日志中的 `entryCreatedAt` 晚于写入提交时间，或失效令牌小于最新值。恢复动作：立即清空该表关联的全部缓存，检查依赖索引是否正确注册。
2. **缓存键冲突**：不同语义查询因规范化过度或参数摘要碰撞产生相同签名。诊断证据：命中结果与未命中结果不一致。恢复动作：调整键模板，加入 SQL 原始长度或 schema 版本，清理冲突键。
3. **序列化/反序列化错误**：结果包含不可克隆对象（如函数或循环引用）。诊断证据：缓存写入或读取抛出 `DataCloneError` 或 `SyntaxError`。恢复动作：对结果做深度规范化，剔除不可序列化字段，或在写入前做防御性克隆。
4. **存储溢出**：IndexedDB 配额耗尽或 OPFS 文件系统满。诊断证据：`QuotaExceededError`。恢复动作：紧急按 LRU 淘汰 50% 条目，或降级为仅内存缓存。
5. **事务隔离破坏**：事务内写入后同事务读取命中了写入前缓存。诊断证据：事务内读取返回非当前事务写入值。恢复动作：确保事务 ID 写入上下文，读取时校验 `entryTxnId !== currentTxnId` 且依赖表不与事务写入表相交。
6. **Schema 版本漂移**：数据库升级后旧缓存键未失效。诊断证据：查询结果列数或类型与新 schema 不符。恢复动作：升级时递增 `schemaVersion`，使旧键自然失效，并清空依赖索引。

## 问答测试样例

1. **正向问题**：当同一条 SELECT 在 10 秒内被调用两次且期间无写入，第二次是否命中缓存？预期：命中，返回与第一次按位等价的结果。
2. **边界问题**：`UPDATE users SET name='x' WHERE id=1` 后，依赖 `users` 表和 `users` 与 `orders` JOIN 的缓存是否都失效？预期：是，因为依赖索引按表名反向映射。
3. **边界问题**：事务内执行更新后立即查询同一张表，是否命中缓存？预期：否，必须返回当前事务写入后的新值。
4. **边界问题**：缓存 TTL 到期但数据未变更，是否自动重新执行查询？预期：是，TTL 仅作为兜底清理机制，到期后必须回源。
5. **边界问题**：两个并发读取同时未命中同一查询，是否会执行两次原始 SQL？预期：可能，取决于是否实现请求合并；未实现合并时允许双重回源，但结果必须一致。
6. **拒答条件**：当没有变更日志或 `_cache_invalidation_log` 记录时，能否回答“某条缓存是否已失效”？预期：不能，必须回答缺乏证据，拒绝猜测失效状态。

## 维护、版本、来源与相邻主题关系

缓存方案必须与数据库 schema 版本绑定。每次执行 `ALTER TABLE`、`CREATE INDEX`、`DROP VIEW` 等变更后，应将 `schemaVersion` 单调递增，并使全部缓存条目失效。依赖索引表 `_query_cache_deps` 和失效日志表 `_cache_invalidation_log` 属于缓存内部表，不应被业务查询直接引用。来源上，键生成与失效策略参考了 SQLite 的 `EXPLAIN QUERY PLAN` 输出语义、Web Storage 的配额模型，以及本地优先软件中常见的读取缓存模式。相邻主题包括：SQLite WAL 模式（影响并发读写可见性）、OPFS 与 Origin Private File System（提供浏览器端持久化）、IndexedDB 的存储配额与事务语义、以及结构化克隆算法（决定哪些结果类型可直接缓存）。与事务日志复制或事件溯源不同，本方案是结果级缓存而非变更流，失效由写操作触发而非由订阅事件驱动。

## 结论

**事实**：SQLite 本地查询缓存可以显著降低读多写少场景下的重复查询开销；通过表级依赖反向索引能够在写事务提交后定位并删除相关缓存条目；同一事务内写入后的读取必须禁用缓存以维持隔离性；TTL 只能作为兜底，不能替代显式失效。

**推论**：在浏览器环境中，将缓存放在与数据库 Worker 同一线程内，并采用同步失效加异步持久化的混合策略，能够在一致性与延迟之间取得较好平衡；键生成使用规范化 SQL、绑定参数摘要和 schema 版本的组合，可将冲突概率控制在可接受范围。

**未知**：特定应用场景下行级失效相比表级失效能否带来足够的命中率提升以抵消实现复杂度；SQLite WASM 在不同浏览器中的实际 I/O 吞吐与 IndexedDB 写入延迟对缓存整体收益的精确量化；在极端高并发写入场景下，异步失效窗口内读取路径的校验开销是否会抵消缓存带来的延迟收益。
