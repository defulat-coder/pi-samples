# SQLite 本地知识库中的一致性：事实、派生统计与模型解释的责任切分

## 摘要与问题边界

在基于 SQLite 的本地数据知识库中，"一致性"不是指分布式事务的强一致性，而是指三类信息在时间、语义和可验证性上的对齐：数据库事实、派生统计和模型生成的自然语言解释。数据库事实是行级记录，派生统计是经过聚合或转换后的数值/结构，模型解释则是大语言模型根据前两类内容生成的可读叙述。当用户提问时，如果系统把模型解释当作事实返回，或者把派生统计的采样误差隐藏为确定性结论，就会产生架构层面的可信度崩塌。

本文的边界限定在单进程、本地文件、以 SQLite 为主要持久化载体的 TypeScript/Web 应用场景。我们不讨论多节点复制、网络分区或跨设备同步。核心问题是如何在代码、Schema 和接口层面为这三类信息划定不可混淆的所有权边界，使得替换统计引擎、替换模型提供者或替换 SQLite 实现时，不会破坏"什么可以被断言为真"这一契约。

## 核心概念与数据模型

1. **事实表（Fact Table）**：以不可变事件或原始记录形式存在的数据行，例如一次文件扫描结果、一次用户编辑、一次向量索引构建日志。事实表只描述"发生了什么"，不解释原因，也不预先聚合。其主键通常是时间戳与唯一事件标识的组合，便于按时间顺序重建状态。

2. **派生视图（Derived View）**：通过 SQL 查询、窗口函数、聚合或 TypeScript 计算从事实表生成的结果。派生视图必须显式声明依赖的事实表、计算版本和有效时间戳。它代表"在特定计算版本和特定快照下的统计结果"，而不是永恒真理。

3. **解释片段（Explanation Fragment）**：由模型根据事实和派生统计生成的自然语言段落。解释片段必须携带生成模型标识、提示版本、温度参数、生成时间以及所引用的数据快照标识。解释片段本身不是数据源，而是对数据源的阐释。

4. **来源溯源层（Provenance Layer）**：一张独立的 SQLite 表或 JSONL 日志，记录每一次回答的完整血缘：用户问题、检索到的行 ID、使用的派生视图版本、模型调用参数、输出文本。溯源层是审计、回滚和争议解决的唯一权威。

5. **可替换接口（Replaceable Port）**：事实存储、统计计算、解释生成三者通过 TypeScript 接口隔离。例如，`FactStore`、`Aggregator`、`Explainer` 三个接口各自独立，SQLite 只是 `FactStore` 的一种实现，本地文件是另一种，`Aggregator` 可以在 SQL 内执行，也可以在 Worker 线程内执行。

6. **一致性契约（Consistency Contract）**：由项目定义的显式规则集合，例如"同一快照下，解释片段引用的统计值必须与派生视图的返回值一致"、"事实表的写入顺序必须与文件系统修改事件的时间戳单调非减"。契约是可测试的，而不是口头约定。

## 设计决策与取舍

### 事实表优先 vs. 视图优先

事实表优先意味着所有用户可见的"答案"最终都必须能追溯到原始行。其代价是存储增长较快，查询需要聚合。视图优先则把预计算结果当作主要数据源，查询快但丢失了原始粒度。对于本地知识库，推荐事实表优先，因为本地存储成本相对可控，而可审计性和回滚能力对长期演进更有价值。只有在事实表行数超过百万且聚合查询频繁时，才引入物化视图，并且物化视图必须标记为派生视图而非事实。

### 解释生成在线 vs. 离线

在线解释在每次查询时调用模型，灵活但成本高、延迟大。离线解释把常见问题的解释预生成并缓存到 SQLite 中，查询快但需要处理过期问题。建议采用混合策略：高频、稳定的问题走离线解释缓存，缓存条目携带事实快照哈希；新颖或复杂问题走在线生成。离线缓存本身也是派生数据，必须受一致性契约约束。

### 严格 Schema vs. 灵活文档

SQLite 是关系型数据库，但本地知识库经常需要存储半结构化的元数据。建议在核心事实表使用严格 Schema，在扩展元数据列使用 JSON 字符串，并通过 `json1` 扩展或应用层校验约束其结构。不要把模型的自由输出直接写入严格 Schema 的列中，否则模型幻觉会变成 Schema 级污染。

### 版本化在 Schema 内 vs. 在应用层

为每一张事实表增加 `schema_version` 和 `ingestion_version` 列，可以在 SQLite 层面保留历史版本信息。但复杂的版本迁移逻辑应放在应用层，避免在数据库中嵌入过多的条件分支。边界是：Schema 负责"这是哪一版数据"，应用层负责"如何把这版数据转换到当前语义"。

### 同步阻塞写入 vs. 异步事件溯源

如果 Web 应用运行在主线程，SQLite 的同步写入会阻塞 UI。可以把文件系统事件先写入内存队列，再由 Worker 线程批量写入 SQLite。这种异步架构的事实表必须包含一个"收到事件时间"和"持久化时间"两个字段，以便诊断队列延迟和乱序问题。

## 可执行实施流程

1. **定义三类信息的接口契约**：在 TypeScript 中声明 `FactStore`、`Aggregator`、`Explainer` 三个接口，明确输入输出、错误类型和必须返回的来源元数据。接口不依赖具体实现，SQLite 只是 `FactStore` 的候选实现之一。

2. **设计事实表 Schema**：为每一类原始事件创建独立的事实表，包含事件 ID、事件发生时间、数据内容、来源文件路径、校验和、Schema 版本。禁止在事实表中存储解释性文字或聚合结论。

3. **建立派生视图注册表**：把所有派生统计查询登记到一张元数据表中，包含视图名称、SQL 文本或计算函数引用、依赖的事实表列表、版本号、作者和最后验证时间。视图必须通过单元测试后才能注册。

4. **实现来源溯源记录器**：在每次生成回答时，向溯源表写入一条记录，包含问题哈希、检索到的事实 ID 列表、使用的派生视图版本、模型调用 ID、生成文本哈希、时间戳。溯源记录是后续可观测性和争议解决的基础。

5. **构建解释片段生成管线**：`Explainer` 的实现必须把模型输出拆分为多个片段，每个片段标注其引用的来源类型（事实/派生/混合）和具体标识符。禁止生成没有来源引用的断言。

6. **编写一致性测试套件**：测试应覆盖三类场景：事实与派生视图数值一致、派生视图与解释片段引用一致、同一张事实表在不同快照下结果单调。测试直接操作 SQLite 文件和接口，不通过 UI。

7. **部署本地可观测性仪表板**：在 Web 应用中增加一个仅开发者可见的"Inspector"面板，显示最近一次回答的溯源链、事实行数、派生视图版本、模型调用延迟和缓存命中状态。该面板读取与生产相同的数据库表。

8. **制定回滚与重生成策略**：当发现模型解释存在事实错误时，不修改原始事实表，而是通过更新派生视图版本或提示版本，触发解释片段的重生成，并保留旧版本解释作为历史记录。

## TypeScript 与 SQLite 本地知识库的示例

```typescript
interface FactRecord {
  eventId: string;
  occurredAt: number;
  sourcePath: string;
  payload: string; // JSON
  schemaVersion: number;
}

interface DerivedView<T> {
  name: string;
  version: number;
  dependencies: string[];
  compute: (db: Database) => T;
}

interface ExplanationFragment {
  text: string;
  modelId: string;
  promptVersion: number;
  snapshotHash: string;
  citations: Array<{ type: 'fact' | 'derived'; id: string }>;
}

class SQLiteFactStore implements FactStore<FactRecord> {
  private db: Database;
  insert(record: FactRecord) {
    this.db.prepare(`
      INSERT INTO facts (event_id, occurred_at, source_path, payload, schema_version)
      VALUES (?, ?, ?, ?, ?)
    `).run(record.eventId, record.occurredAt, record.sourcePath, record.payload, record.schemaVersion);
  }
}
```

输入是一组文件系统事件，例如 `{ path: '/docs/adr/0001.md', mtime: 1720000000, hash: 'abc...' }`。处理流程先把这些事件写入 `facts` 表，再通过 `DerivedView` 计算"最近 30 天修改过的 ADR 数量"，最后由 `Explainer` 生成"本项目有 7 份近期架构决策记录"这句话。输出是带引用的解释片段，其中 `citations` 指向派生视图名称和版本，而不是模糊的"根据知识库"。

## 性能、质量与可观测性指标

1. **事实写入吞吐量**：每秒可持久化的事件数。测量方法是在隔离测试数据库中批量插入 10 万条模拟事件，记录总耗时和 CPU 占用。该指标决定文件系统监听器是否需要背压。

2. **派生视图刷新延迟**：从事实表更新到派生视图结果可见的时间间隔。测量方法是在写入事实表后立即可选相关视图，记录返回最新值所需时间。对于本地应用，应控制在 100 毫秒以内。

3. **解释片段引用完整率**：生成的解释片段中，所有数字性断言都有明确引用的比例。通过离线评测集人工或规则检查，目标值应高于 99%。

4. **来源溯源覆盖率**：用户回答是否 100% 写入溯源表。通过定期审计查询 `SELECT COUNT(*) FROM answers WHERE provenance_id IS NULL` 来验证。

5. **缓存命中率与新鲜度**：离线解释缓存的命中比例，以及命中条目的快照哈希与当前事实表快照哈希的偏差时间。高命中率但高偏差时间意味着缓存策略需要收紧。

## 失败模式、诊断证据与恢复动作

1. **模型解释与数据库事实不一致**：用户收到"项目有 12 个组件"的解释，但 `facts` 表中实际只有 10 个。诊断证据是溯源表中解释片段引用的派生视图版本与实际查询结果不符。恢复动作是冻结该解释缓存版本，重新生成并标记旧版本为失效。

2. **派生视图依赖缺失**：视图 `recent_adr_count` 查询的 `facts` 表在迁移后被重命名，但视图注册表未更新。诊断证据是视图查询返回 `no such table` 或空结果。恢复动作是在注册表中版本化视图依赖，并在单元测试中校验所有依赖表存在。

3. **事实表 Schema 版本漂移**：新代码写入 `schemaVersion: 3` 的记录，但旧解释仍按 `schemaVersion: 2` 解析 `payload`。诊断证据是解析失败率上升或字段缺失。恢复动作是引入 `schemaVersion` 白名单，拒绝未注册版本的写入。

4. **异步队列导致的事件乱序**：文件系统先发生删除后发生创建，但写入 SQLite 时顺序颠倒，导致派生视图短暂显示文件不存在。诊断证据是 `occurred_at` 与 `persisted_at` 差值异常大，且事件顺序与文件系统日志不符。恢复动作是在消费者端按 `sourcePath + occurred_at` 排序后再批量写入。

5. **模型幻觉被当作事实写入**：解释管线错误地把模型输出中的数字提取出来，反向写入了事实表。诊断证据是事实表中出现没有对应原始事件来源的行。恢复动作是事实表写入接口只接受带有 `sourcePath` 或 `eventId` 的记录，禁止从解释输出反向写入。

## 问答测试样例

1. **正向问题**："本项目有多少份 ADR 文档？" 预期回答引用派生视图 `adr_count_v2` 和事实表行 ID，给出具体数字。通过条件是回答中的数字与当前视图查询结果一致。

2. **正向问题**："请总结最近一个月的代码变更。" 预期回答基于 `git_commit_facts` 表，通过 `monthly_commit_summary_v1` 视图聚合，并列出变更文件数区间。通过条件是摘要不 invent 未在事实表中出现的文件名。

3. **边界问题**："如果我现在创建一份新 ADR，计数会变成多少？" 系统应回答当前数字，并说明新 ADR 尚未被持久化到事实表，因此不在统计范围内。通过条件是区分当前事实与未来可能状态。

4. **边界问题**："模型 A 和模型 B 对同一份文档的解释哪个更准确？" 系统应返回两个解释片段的来源信息（模型 ID、提示版本、引用快照），但不主动裁决"哪个更准确"，除非有明确的人工标注事实支持。通过条件是不把模型比较变成主观判断。

5. **无证据拒答**："这个项目的核心作者是谁？" 如果事实表只包含文件元数据而不包含 Git 作者信息，系统应拒绝回答，并指出缺失的数据源。通过条件是不基于文件名猜测作者。

6. **无证据拒答**："请预测下个月的 bug 数量。" 如果数据库中没有历史 bug 记录或预测模型未注册，系统应说明无法预测，并区分"缺少事实"与"缺少模型"。通过条件是不进行无依据外推。

## 维护、版本、来源与相邻主题关系

维护工作的核心是保持三类信息边界的清晰。每次 Schema 变更都需要同时更新事实表、派生视图注册表和解释管线中的版本映射。建议为每个主要组件维护独立的语义化版本：SQLite Schema 版本、派生视图包版本、解释提示模板版本、来源溯源协议版本。

来源管理方面，所有事实表数据应记录原始文件路径和校验和，以便在 SQLite 文件损坏时从原始文件重新构建。派生视图的 SQL 或函数代码应纳入版本控制系统。解释片段的生成参数和模型版本应写入溯源表，而不是只存在于服务器日志中。

与相邻主题的关系：本主题与"SQLite 事务与并发"相邻但不重叠，后者关注锁和隔离级别，本文关注语义一致性；与"RAG 检索增强生成"相邻，但本文强调检索结果必须区分事实与解释；与"本地文件索引"相邻，但本文把文件索引当作事实表的一种输入，而非最终答案。

## 结论

**事实**：SQLite 表中的行级记录、文件系统事件、校验和和来源路径是系统内唯一可被直接断言为真的数据。派生视图是事实经过版本化计算后的结果，其真实性受计算逻辑和输入快照约束。解释片段是模型输出，必须携带来源引用，不能作为事实本身。

**推论**：在本地单进程架构中，通过 `FactStore`、`Aggregator`、`Explainer` 三个可替换接口，以及独立的来源溯源层，可以在不引入分布式事务的前提下实现足够的设计一致性。事实表优先策略在长期演进中优于视图优先策略，因为可审计性和回滚能力更难事后补建。

**未知**：当模型提供者更新其基础模型时，解释片段的语义稳定性无法完全保证，只能通过对齐提示版本和采样参数来降低漂移；当用户直接修改 SQLite 文件绕过应用层时，校验和与 Schema 版本只能检测异常，无法自动恢复语义正确性。这些边界外的风险需要额外的人工流程或文件级权限控制来管理。
