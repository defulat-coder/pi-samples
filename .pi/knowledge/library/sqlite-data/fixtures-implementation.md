# SQLite 本地数据测试夹具构建指南：以确定性样本覆盖边界状态、空集、异常与时间窗口

## 摘要与问题边界

测试夹具不是“几条假数据”，而是把 SQLite 数据库的某一状态固化为可重复输入、可验证输出、可断言错误形态的契约。在本地数据场景下，夹具必须同时处理内存数据库、临时文件数据库、WAL 模式、并发读取锁、空表、NULL、外键孤儿、时间窗口边界、整数溢出、唯一索引冲突等状态。本文只讨论实现视角：先给出输入、输出、错误、生命周期和验证步骤，再进入 TypeScript 代码；不讨论生产环境迁移或云端同步策略。

## 核心概念与数据模型

1. **夹具合同（Fixture Contract）**：一份不可变约定，包括 schema 快照、种子数据、时间锚点、预期输出、允许的错误代码。合同编号与数据库 schema 版本一一对应，schema 变更后合同必须重新生成。
2. **种子数据分类**：canonical（典型业务场景）、boundary（边界值）、empty（空表或空结果集）、stress（批量、长字符串、大整数）、lifecycle（插入-更新-删除-软删除序列）。每一类对应一个独立夹具文件，避免互相污染。
3. **确定性身份生成器**：所有主键、外键、时间戳均来自固定种子的伪随机生成器或手工编排，避免测试运行之间出现不同 ID。类型使用 `bigint` 或固定长度字符串，不依赖系统时间。
4. **时间锚点（Temporal Anchor）**：每个夹具固定一个 UTC 纪元点，例如 `2024-06-15T00:00:00.000Z`。所有相对时间窗口（“最近 7 天”“上季度”）都围绕该锚点计算，而不是 `Date.now()`。
5. **错误合同（Error Contract）**：区分 SQLite 返回码（`SQLITE_CONSTRAINT_FOREIGNKEY`、`SQLITE_CONSTRAINT_UNIQUE`）、better-sqlite3 抛出的异常对象、以及测试框架的断言失败。合同明确哪些错误是预期内、哪些必须中断测试。
6. **本地夹具包结构**：每个夹具包含一个 `.sqlite` 文件（或生成脚本）、一个 `manifest.json`、一个 `schema-checksum.txt`。如果使用 WAL 模式，测试结束时必须执行 `PRAGMA wal_checkpoint(TRUNCATE)` 或单独丢弃 `-wal` 文件。
7. **验证清单（Manifest）**：记录输入 SQL、参数、预期结果集、预期错误、断言顺序。验证脚本读取清单并与实际执行结果逐项比对。
8. **版本锁**：schema 版本、夹具版本、验证脚本版本三元组必须同时变更。不允许只更新 schema 而不更新夹具。

## 设计决策与取舍

### 内存数据库 vs 临时文件数据库

内存数据库速度快，但无法保存跨进程状态，适合单元测试；临时文件数据库能模拟真实 `journal_mode` 和 WAL 行为，适合集成测试。本方案默认使用临时文件，每个测试用例拥有独立目录，测试结束后整体删除。

### 手工构造 vs 程序化生成

边界状态必须手工编排，例如 `NULL`、空字符串、`0`、最大长度字符串、跨时间窗口的临界日期；典型业务数据可通过工厂函数生成。工厂函数必须接受固定种子，禁止默认随机。

### 固定时间 vs 时间旅行工具

禁止在夹具中调用 `new Date()`。所有时间相关字段在生成时写入绝对 UTC 字符串；测试中通过 `Date` 的 stub 或注入的时钟对象锚定到合同纪元点。时间窗口的边界值精确到毫秒，避免整点四舍五入差异。

### 每个测试隔离 vs 共享只读夹具

写入型测试必须一人一库；只读查询测试可共享同一夹具，但共享前必须计算文件校验和。任何写入都会复制夹具到临时目录，原夹具只读。

### 外部验证脚本 vs 测试框架内断言

核心验证使用独立脚本，按清单逐条执行 SQL 并比对结果；测试框架只负责调用脚本和报告失败。这样夹具可在不同测试框架之间复用。

### 校验和 vs 按需生成

提交生成的 `.sqlite` 和 `manifest.json` 到版本控制，并用 `schema-checksum.txt` 在 CI 中校验。代价是仓库体积增加；收益是消除生成环境差异导致的测试漂移。

## 可执行的实施流程

1. 梳理 schema：导出所有表、列、索引、外键、检查约束、默认值，标注可为空的列和带检查约束的列。
2. 建立边界状态映射表：列出每个表的边界状态，包括空表、全 NULL 行、空字符串、0、极值、孤儿外键、违反唯一索引的候选行。
3. 定义时间锚点：为项目选择一个固定纪元，所有时间窗口、软删除、创建时间、更新时间都围绕该点生成。
4. 编写夹具工厂：使用固定种子生成主键、外键、时间戳；对边界状态使用手工覆盖，确保生成结果可预期。
5. 生成夹具包：为每个测试用例输出 `.sqlite`、`.json` manifest、`.txt` 校验和，文件命名包含 schema 版本和夹具版本。
6. 运行验证脚本：按 manifest 中的输入 SQL 执行，比对结果集行数、列顺序、字段类型、错误代码；差异必须显式记录。
7. 集成到 CI：在干净临时目录中运行，禁止复用上次测试残留文件；测试前断言校验和匹配。
8. 收集指标：记录生成耗时、夹具体积、断言数量、时间漂移、稳定性率；设定阈值，超限报警。
9. 定期审计：每次 schema 变更后重新生成全部夹具；删除超过两个版本未使用的旧夹具。

## 夹具示例：本地知识库条目表

以下是一份面向 TypeScript / Web / 本地文件知识库的夹具清单片段，使用无代码围栏的纯文本排版展示。

> fixture: journal_v3_20240615
> schema_version: 2024-06-12
> anchor_time: 2024-06-15T00:00:00.000Z
>
> 输入：
> 表 journal 包含字段 id、title、body、created_at、updated_at、deleted_at。
> 种子行 A：id=1001，created_at=2024-06-14T23:59:59.000Z，deleted_at=null。
> 种子行 B：id=1002，created_at=2024-06-08T12:00:00.000Z，deleted_at=2024-06-14T00:00:00.000Z。
> 种子行 C：id=1003，created_at=null，deleted_at=null。
> 表 journal 同时存在一条空表状态，用于空结果测试。
>
> 处理：
> 查询“最近 7 天且未删除的条目”使用参数 anchor_time 减去 7 天作为窗口起点。
> 结果排序按 created_at 降序，deleted_at 为 null 为保留条件。
>
> 输出：
> 期望结果集仅包含行 A，因为行 B 已软删除，行 C 缺少 created_at 被排除，空表状态返回空数组。
> 错误场景：尝试插入一条指向不存在的 tag_id 的关联行，应抛出 SQLITE_CONSTRAINT_FOREIGNKEY。

## 性能、质量、可观测性指标

1. **夹具生成耗时**：从工厂函数到完整 `.sqlite` 生成的时间。测量方式：CI 中统计生成命令耗时，单夹具超过 2 秒需优化。
2. **单个夹具体积**：`.sqlite` 文件字节数。测量方式：在 PR 中对比体积增长，超过 50 KB 需拆分或压缩。
3. **断言覆盖率**：manifest 中预期输出与错误断言占全部查询分支的比例。测量方式：以 schema 中的列和约束为维度，计算被覆盖的边界状态百分比。
4. **时间漂移**：在 stub 时钟与实际 UTC 之间跑同样查询，结果差异数量。测量方式：连续运行 10 次，统计结果集不一致次数。
5. **稳定性率**：同一测试无代码变更情况下连续 100 次运行的失败率。测量方式：CI  nightly 任务重复执行，失败率必须为零。
6. **错误恢复次数**：失败模式中因夹具过旧、锁竞争、校验和失败导致的重试或重新生成次数。测量方式：日志中按错误标签统计。

## 失败模式

1. **Schema 漂移**：应用代码变更了列名或类型，但夹具仍使用旧 schema。诊断证据：验证脚本报告 `SQLITE_ERROR: no such column` 或 `SQLITE_MISMATCH`；`schema-checksum.txt` 与当前 schema 不匹配。恢复动作：重新导出 schema、重新生成全部夹具、更新版本号。
2. **时间窗口漂移**：测试或夹具工厂中误用本地时间或 `Date.now()`。诊断证据：在 anchor_time 前后一毫秒的结果不同，跨时区 CI 节点出现差异。恢复动作：统一使用 UTC 字符串；删除任何未注入的时钟调用。
3. **文件锁竞争**：多个测试共享同一临时文件或复制时机太晚。诊断证据：错误码 `SQLITE_BUSY` 或 `SQLITE_LOCKED`；测试日志显示并发读取。恢复动作：每个测试用例独立临时目录；写入前复制夹具，避免共享。
4. **WAL 残留**：WAL 模式下测试中断导致 `-wal` 文件与主数据库不一致。诊断证据：文件校验和通过但查询结果异常；日志出现 `database disk image is malformed`。恢复动作：测试结束时强制 `wal_checkpoint(TRUNCATE)`，并在 setup 中删除残留 WAL 文件。
5. **生成器非确定性**：工厂函数默认使用随机或依赖未初始化状态。诊断证据：连续两次生成的 `.sqlite` 校验和不同；相同测试间歇性失败。恢复动作：固定伪随机种子；显式排序所有 INSERT 语句。
6. **错误断言泄漏**：预期错误未写入合同，导致异常被测试框架吞掉。诊断证据：错误代码与 SQL 返回码不一致；测试绿但业务逻辑错误。恢复动作：在 manifest 中为每个预期错误声明 `expected_error_code`，验证脚本必须显式捕获并校验。

## 问答测试样例

1. 正向问题：在 `journal_v3_20240615` 夹具中，查询“最近 7 天且未删除的条目”返回什么？答案：仅返回行 A，按 `created_at` 降序排列。
2. 边界问题：当表 `journal` 为空时，同一查询返回什么？答案：返回空数组，错误码为无错误。
3. 边界问题：行 C 的 `created_at` 为 null，它会被包含在结果中吗？答案：不会，因为窗口过滤条件要求 `created_at` 非空且大于窗口起点。
4. 无证据拒答：如果我把 `anchor_time` 改成 2025 年，结果会是什么？答案：夹具合同中没有这个版本，无法回答；必须重新生成夹具。
5. 正向问题：如何验证夹具与当前 schema 一致？答案：比较 `schema-checksum.txt` 与从当前 schema 计算出的校验和。
6. 边界问题：尝试插入 tag_id 不存在的关联行时会发生什么？答案：抛出 `SQLITE_CONSTRAINT_FOREIGNKEY`，错误码在 manifest 中已声明。

## 维护、版本、来源和与相邻主题的关系

夹具与数据库迁移脚本必须同版本号管理；迁移脚本升级后，夹具必须重新生成。夹具的来源包括：schema 导出、业务规则文档、历史 bug 报告中的边界案例。版本控制建议只保留当前主版本和上一个兼容版本的夹具，超过两个版本后删除。与相邻主题的关系：与“迁移测试”共享 schema 导出逻辑；与“端到端测试”共享临时文件目录管理；与“属性测试”互补，后者负责发现未知边界，前者负责固化已知边界。

## 结论

事实：SQLite 本地数据的测试夹具必须是一份可重复、可校验、版本化的合同；边界状态、空集、异常和时间窗口需要显式定义，而不是依赖运行时环境。推论：在 TypeScript 实现中，优先使用固定种子的工厂函数、UTC 时间锚点、独立临时目录和外部验证脚本，可以显著降低测试漂移和锁竞争。未知：在特定文件系统或并发读取压力下，WAL 模式的精确超时行为和 better-sqlite3 的异常对象字段可能因平台而异，需要在目标运行环境中实测后写入错误合同。
