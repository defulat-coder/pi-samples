# SQLite 本地数据迁移脚本：在旧数据、回滚与开发重建之间的架构约束

摘要：在基于 SQLite 的本地数据系统中，迁移脚本不是“把表结构改对”的一次性 SQL，而是连接旧数据、当前应用版本与未来回滚能力的确定性转换器。本文的边界限定在单文件 SQLite 场景——例如浏览器 WebAssembly 版本、Electron/Tauri 本地文件、Node 端 CLI 工具——重点讨论如何在开发迭代中保留旧数据、如何在失败时安全回滚、如何在新成员加入时重建一致的开发环境。我们不讨论远程数据库的多节点复制，也不讨论 ORM 的自动同步；这里把迁移脚本视为架构中的一个可替换接口，先定义其责任边界，再选择具体实现。

## 核心概念与数据模型

1. 版本向量
   用三元组 (schema_major, schema_minor, patch) 描述数据库模式版本，并在数据库内部维护一张 `schema_migrations` 表。该表记录已应用的迁移标识、应用时间、校验和，是迁移器判断“当前在哪里、下一步到哪”的唯一权威来源。

2. 迁移单元
   每个迁移是一个不可变单元，包含：唯一标识 `migration_id`、源版本 `from_version`、目标版本 `to_version`、正向脚本 `up`、逆向脚本 `down`、前置条件断言 `precondition`、内容校验和。迁移单元一旦发布，不得原地修改；修正应通过追加新迁移完成。

3. 状态机
   数据库在迁移过程中处于以下状态之一：未应用 `unapplied`、已应用 `applied`、失败 `failed`、部分应用 `partial`。状态转换由事务边界保证，任何异常都必须落到 `failed` 或 `partial`，并留下日志。

4. 兼容性层
   应用代码不直接读取旧表名或旧列，而是通过视图或类型化的只读适配器访问数据。迁移脚本负责把旧模式映射到这个兼容性层，应用代码只依赖兼容性层的稳定契约。

5. 影子副本
   对于删除列、拆分表、重命名主键等破坏性变更，迁移器先在单独表或临时文件中构建“影子副本”，验证行数与校验和后再执行切换，避免在原表上直接破坏旧数据。

6. 可重复重建
   空数据库加上基线脚本与全部迁移序列，必须能逐位复现到生产库的等效模式。开发环境重建依赖“基线 + 种子数据 + 迁移”三条路径，而不是依赖某个开发者的本地备份。

## 设计决策与取舍

### 显式版本表 vs 文件哈希校验
显式版本表是迁移器的入口契约，文件哈希仅作为防篡改验证。边界是：版本表用于决定下一步，哈希用于审计；不要把文件哈希当作版本号使用，因为同一个 SQL 文件在不同换行符下哈希会变。

### up/down 成对 vs forward-only
成对迁移支持回滚，但要求 `down` 脚本必须语义可逆，成本显著增加。forward-only 更简单，却依赖快照恢复来回退。判断标准是：用户数据一旦写入就不可逆，因此任何涉及数据转换的迁移都应同时提供 `down`，而仅新增索引或空表可只提供 `up`。

### 事务粒度
单事务全量迁移保证原子性，但在大表上会长时间持有写锁。分块迁移通过批量提交降低锁竞争，但会暴露中间状态。边界：本地 SQLite 在 WAL 模式下支持并发读，因此中小型数据可单事务；超过百万行时必须分块，并在兼容性层屏蔽中间状态。

### 破坏性变更采用重命名列还是新建表迁移
SQLite 对 `ALTER TABLE` 支持有限，很多变更需要“新建表—复制数据—删除旧表”。新建表迁移更冗长，但能通过影子副本保留旧数据、支持回滚；直接重命名列脚本短，却容易丢失旧列数据。建议：涉及数据类型的收缩、主键调整、列拆分时，一律走新建表路径。

### 开发、测试、生产分支策略
迁移序列必须是线性的；不允许多个开发者同时修改同一段版本号。实践中用时间戳或单调递增整数命名迁移文件，避免分支合并时的版本冲突。测试环境应执行“基线 + 全迁移”，而开发环境允许“清空并重建”以验证种子脚本。

### 迁移器与应用启动顺序
迁移器必须在应用业务逻辑之前运行，且应阻塞启动直到完成或失败。边界例外：只读模式启动可跳过迁移，但必须在日志中声明；任何写操作必须先完成迁移。

## 可执行的实施流程

1. 启动时检查 `schema_migrations` 表是否存在；不存在则创建，并写入基线版本。
2. 读取当前版本号和最近一次迁移的校验和。
3. 扫描迁移目录，按版本排序生成待执行列表。
4. 对每一个待执行迁移，先执行 `precondition` 断言，例如检查旧列存在、行数非零。
5. 开启事务，执行 `up` 脚本；若涉及大表，则按主键分块提交。
6. 成功后在 `schema_migrations` 插入记录，包含迁移标识、目标版本、校验和、应用时间。
7. 失败时回滚当前事务；若已分块提交，则标记为 `partial` 并触发 `down` 补偿脚本。
8. 开发环境重建时，删除本地 `.db`、重新创建基线、加载种子数据、应用全部迁移，并校验最终校验和与 CI 产物一致。

## 贴近 TypeScript/Web/本地文件的示例

输入：一名开发者新增 `user_profiles.display_name` 列。迁移清单片段如下，以 JSON 表示：

    {
      "migration_id": "20250815_add_display_name",
      "from_version": "0003",
      "to_version": "0004",
      "up": "ALTER TABLE user_profiles ADD COLUMN display_name TEXT;",
      "down": "ALTER TABLE user_profiles DROP COLUMN display_name;",
      "precondition": "SELECT 1 FROM pragma_table_info('user_profiles') WHERE name='name'",
      "checksum": "sha256:a1b2c3..."
    }

处理：迁移器在事务中先执行 `precondition`，确认旧列 `name` 存在后执行 `up`，插入列，最后在 `schema_migrations` 记录该迁移并校验文件哈希。

输出：数据库版本变为 `0004`，`user_profiles` 表新增可为空的 `display_name` 列，应用代码通过兼容性视图读取 `COALESCE(display_name, name)`，旧数据不会被改写。

## 性能、质量与可观测性指标

1. 迁移耗时
   在 CI 与本地分别记录“空库到最新版本”的总时长。测量方式：迁移器在启动和结束时写入结构化日志，按迁移标识拆解。

2. 回滚成功率
   统计 `down` 脚本在测试流水线中的执行成功比例。低于 100% 必须阻塞发布，因为这意味着无法从失败中恢复。

3. 校验和冲突次数
   记录已记录校验和与磁盘文件校验和不一致的频率。非零即视为异常，提示迁移文件被意外修改。

4. 孤立行比例
   破坏性迁移后，对比影子副本与原表的行数；比例偏差说明转换逻辑有遗漏。

5. 种子脚本幂等性
   在开发重建流程中连续执行两次种子脚本，比较最终行数与校验和；必须完全一致。

## 失败模式、诊断证据与恢复动作

1. 版本表缺失
   诊断证据：启动时查询 `schema_migrations` 抛出 `no such table`。恢复：进入初始化模式，执行基线脚本，然后按顺序应用全部迁移。

2. 校验和不一致
   诊断证据：磁盘迁移文件哈希与 `schema_migrations` 记录不匹配。恢复：禁止继续迁移，告警并人工审查；不得自动“修复”文件。

3. 前置条件失败
   诊断证据：`precondition` 返回空集或假。恢复：跳过该迁移并标记 `failed`，由开发者确认是否缺少前置迁移或数据异常。

4. 破坏性数据丢失
   诊断证据：影子副本与原表行数不一致，或下游查询返回预期外的空集。恢复：若仍在事务内则回滚；若已分块提交，则执行 `down` 补偿并重新加载备份。

5. 并发写冲突
   诊断证据：SQLite 返回 `database is locked` 或 WAL 检查点失败。恢复：迁移器在启动时获取独占写锁，超时后退出并让上层重试；本地应用应避免多实例同时启动迁移。

## 问答测试样例

1. 正向问题：如何在 SQLite 中新增一列并保留旧数据？
   答：追加 `ALTER TABLE ADD COLUMN` 迁移，前置条件确认表存在；由于新增列默认空值，旧行不会被删除。

2. 边界问题：迁移目录为空时迁移器应做什么？
   答：校验当前版本号与基线一致后直接返回，不得报错。

3. 边界问题：down 脚本必须撤销 up 的全部副作用吗？
   答：在涉及不可逆用户数据转换时，`down` 只能保证模式回退，不能保证数据内容完全复原；该限制需在文档中声明。

4. 无证据拒答：如何配置 PostgreSQL 流复制？
   答：本文档只覆盖本地 SQLite 文件，不提供 PostgreSQL 流复制配置。

5. 无证据拒答：ORM 自动迁移与手动迁移脚本哪个更好？
   答：未在项目中给出具体约束，无法判断优劣；本文只提供手动迁移脚本的架构边界。

6. 边界问题：开发环境重建时用户自己的测试数据怎么办？
   答：重建流程只保证种子数据与迁移后的模式一致；个人测试数据不在版本控制之内，需开发者自行导出。

## 维护、版本、来源与相邻主题

迁移脚本的版本号应与应用代码版本解耦：模式版本独立递增，应用可向后兼容多个模式版本。迁移文件纳入源码管理，与 `schema_migrations` 表一一对应。相邻主题包括：SQLite WAL 与并发控制、本地文件加密、ORM 的 schema 同步、备份与快照策略、版本化迁移测试框架。本文不替代这些主题，而是定义迁移脚本与它们之间的接口：迁移脚本向 ORM 提供稳定模式，向备份策略提供版本号，向测试框架提供 `up/down` 入口。

## 结论

事实：SQLite 本地数据库的迁移脚本是一个可替换的转换接口，其正确性由版本表、事务边界、校验和和 `up/down` 单元共同保证。
推论：在本地迭代中，只有先把迁移器设计为独立于业务代码的组件，才能在不破坏旧数据的前提下安全回滚并重建开发环境。
未知：具体项目的用户数据恢复策略、最大可容忍锁持有时间、以及多平台文件锁定行为，仍需在目标环境中通过测量确定。
