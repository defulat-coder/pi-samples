# TypeScript 工程中的错误建模：从验证到运维的四种失效类

## 摘要与问题边界

在 TypeScript 服务里，错误常常被压缩成“成功”或“失败”两个布尔值。对需要观察性能、稳定性和故障恢复的工程师来说，这种压缩会丢失关键证据：一次调用失败是因为用户输入错误、服务自身能力不足、上游依赖抖动，还是程序内部出现了不可恢复的不变量破坏？本文把错误建模从“catch 一个异常”提升到“为每次调用建立完整的证据记录”，核心关注四类错误：用户错误、能力错误、上游错误和不可恢复故障。讨论范围限定在 Node.js/TypeScript 后端、本地文件知识库、Web API 与分布式依赖调用场景；前端表单校验、浏览器网络抖动等客户端问题不在本主题范围内。

## 核心概念与数据模型

1. **用户错误**：请求本身不符合业务规则，例如参数缺失、格式错误、违反唯一性约束。HTTP 层通常对应 400、404、422 等状态。责任方为调用方或最终用户，服务端不应重试，恢复动作是用户修正输入。证据应记录：请求体摘要、校验失败路径、业务错误码。
2. **能力错误**：调用方已经到达服务边界，但缺少权限、配额耗尽、功能开关未启用或订阅等级不足。典型 HTTP 状态为 401、403、429、402。责任方是授权/配额系统，不是用户输入错误，也不是服务 bug。恢复动作是开通权限、提升配额或调整功能开关。
3. **上游错误**：服务依赖的外部组件失败，包括数据库、向量检索、本地文件系统、第三方 HTTP 接口、消息队列等。表现为超时、部分返回、连接断开或返回 5xx/503。责任方是依赖，恢复动作包括重试、熔断、降级、排队。证据必须记录：上游名称、端点、超时配置、重试次数、每次尝试的返回码。
4. **不可恢复故障**：程序内部不变量被破坏，例如未捕获异常、panic、断言失败、数据校验在写入后失败、类型转换失败。HTTP 层通常表现为 500 或进程崩溃。责任方是工程实现，恢复动作是停止相关进程、发出高优先级告警、人工调查、回滚或重启，绝不应盲目重试。
5. **证据模型**：任何一次操作都必须至少记录 `{status, kind, latency_ms, retry_count, capacity_used, recovery_attempts, final_outcome}`。成功请求只记录延迟和容量；失败请求还要记录失败类别、重试序列和最终是否恢复。这样运维分析时不会只看一次成功请求就判定系统健康。
6. **分类决策树**：先判断请求是否到达业务逻辑；若未到达且输入非法，则用户错误。若到达边界但缺少授权或配额，则能力错误。若业务逻辑调用外部依赖失败，则上游错误。若程序自身出现未捕获异常或不变量破坏，则不可恢复故障。所有边界都应有明确的判断依据，而不是靠异常消息中的关键词猜测。

## 设计决策与取舍

### 用户错误与能力错误的责任边界
两者都不应由服务端重试，但恢复责任不同。用户错误需要用户修改输入；能力错误需要管理员或授权系统变更。把 401/403 错误误标为 500，会导致客户端或中间件进行错误重试，放大无效流量；把用户错误过度暴露细节，可能泄露内部数据结构。因此错误码必须稳定，错误信息必须安全。

### 上游错误重试与立即失败
上游错误通常允许重试，但重试会引入额外延迟和容量消耗。重试策略需要结合幂等性、超时预算、容量窗口。如果依赖是本地文件系统或只读缓存，重试成本较低；如果是写操作或非幂等第三方接口，重试可能产生副作用。因此重试前必须确认操作语义，并在日志中记录每次尝试。

### 不可恢复故障的停机与降级
当不可恢复故障出现时，服务面临“继续运行可能产生错误状态”与“立即失败影响可用性”的权衡。对于涉及资金、数据一致性或持久化写入的模块，优先选择 fail-stop，让进程退出并由编排器重启；对于只读查询模块，可以考虑返回部分降级结果并触发告警。核心原则是不能让破坏后的状态继续扩散。

### 日志级别与采样策略
用户错误通常用 INFO 或 WARN 记录，便于聚合但不触发告警；能力错误用 WARN 或 ERROR，提示授权/配额系统异常；上游错误用 ERROR，并关联依赖名称；不可恢复故障用 FATAL 或 CRITICAL，要求 100% 保留。为控制成本，用户错误可采样 1%，但故障必须全量保留，否则无法形成恢复证据链。

### 类型化错误与可读错误信息
在 TypeScript 中应定义带品牌的错误类或联合类型，如 `UserError | CapabilityError | UpstreamError | Fault`。内部携带完整上下文，但向客户端返回时只暴露 `{code, message, ref, retryable}`。这样既保证调试能力，又避免泄露堆栈或内部路径。

## 可执行的实施流程

1. 在 `packages/contracts` 或项目公共模块定义错误分类枚举：`UserError`、`CapabilityError`、`UpstreamError`、`Fault`，并给出统一基类。
2. 在 Web 框架入口层（Express/Fastify/Koa 中间件）捕获所有未处理异常，按分类规则映射 HTTP 状态码与指标标签。
3. 在边界层（数据库客户端、HTTP 调用、文件系统封装、子进程调用）使用 `Result<T, E>` 包装返回，显式把依赖失败标记为 `UpstreamError`。
4. 为每个请求生成 `requestId`/`correlationId`，在异步传播中通过 AsyncLocalStorage 或显式参数传递，确保错误链可追踪。
5. 对 `UpstreamError` 实施指数退避重试与熔断，记录每次尝试的延迟、返回码和重试序号。
6. 将错误证据写入结构化日志（JSON Lines），字段包括 `kind`、`latency_ms`、`retry_count`、`capacity_used`、`upstream_name`、`final_outcome`。
7. 向客户端返回统一错误体，包含业务错误码、安全消息、追踪引用和是否可重试标志。
8. 部署 SLO 看板，按类别展示错误率、延迟分位数、恢复成功率和容量饱和度，并设置告警阈值。
9. 定期进行故障注入：人为延迟上游、关闭本地文件句柄、注入错误码，验证分类和重试行为是否符合预期。

## 示例：知识库搜索调用的证据记录

```yaml
event: knowledge_search
request_id: req_7f3a9c
input:
  query: "TypeScript 错误建模"
  user: u_42
  max_results: 10
processing:
  validation_status: ok
  upstream_calls:
    - name: vector_db
      status: timeout
      latency_ms: 500
      retry_count: 1
    - name: vector_db
      status: success
      latency_ms: 150
      retry_count: 2
    - name: local_markdown_parser
      status: success
      latency_ms: 20
      retry_count: 0
  capacity_used:
    concurrent_queries: 3
    file_descriptors: 2
output:
  http_status: 200
  result_count: 5
  total_latency_ms: 670
  error_kind: none
  recovery_happened: true
```

输入是一个合法的知识库搜索请求。处理过程中，向量数据库首次调用超时，被归类为上游错误，服务在 100 毫秒和 200 毫秒两次退避后再次调用成功；本地 Markdown 解析器正常。输出是 200 成功，但日志记录了完整延迟、重试和容量证据。如果只看最终 HTTP 200，会忽略向量数据库的稳定性风险；只有保留每次尝试的证据，才能判断上游是否需要扩容或熔断。

## 性能、质量与可观测性指标

1. **分类错误率**：按 `kind` 维度统计每分钟错误数与总请求数之比。测量来源是结构化日志或 Prometheus 指标。
2. **分位延迟**：按错误类别统计 p50、p95、p99 延迟。用户错误应极低；上游错误受重试影响会出现长尾。
3. **重试与熔断状态**：记录 `retry_count` 和 `circuit_breaker_state`。上游重试次数突增或熔断频繁打开，说明依赖或阈值配置异常。
4. **容量饱和度**：并发查询数、连接池使用、文件描述符数、队列深度。这些解释为何上游错误会连锁放大。
5. **恢复成功率**：首次失败但最终成功的请求比例。需要从同一 `requestId` 的日志序列中计算，不能只看最终结果。
6. **证据完整率**：错误事件中包含全部必填字段的比例。缺失字段会导致事后无法定位根因。

## 失败模式、诊断证据与恢复动作

1. **用户错误被标为上游错误**：错误分类规则把 400 参数错误映射为 500，导致重试风暴。诊断证据：大量 `retry_count > 0` 且 HTTP 状态为 400 的日志。恢复：修正分类映射，并在入口层先做校验。
2. **能力错误返回 500**：401/403 被包装为 500，客户端或网关持续重试。诊断证据：5xx 错误中夹杂大量授权失败特征。恢复：将权限/配额错误显式映射为 403 或 429，并在响应中声明不可重试。
3. **上游超时被吞为不可恢复故障**：依赖超时未捕获，导致整个进程崩溃。诊断证据：崩溃日志中没有 `upstream_name` 或 `retry_count`。恢复：在依赖客户端捕获特定异常，统一包装为 `UpstreamError`。
4. **熔断阈值过低**：正常抖动触发熔断，导致大量请求被提前拒绝。诊断证据：`circuit_open` 事件数高于上游实际错误率，且依赖健康检查正常。恢复：使用百分位延迟和错误率组合阈值，避免固定计数。
5. **不可恢复故障未停服**：程序继续运行，写入损坏数据。诊断证据：下游消费到不一致状态，或数据校验在写入后失败。恢复：对关键模块启用 fail-stop，配合快照与回放机制。
6. **日志采样丢失恢复证据**：用户错误采样 1% 但上游错误也误用采样，导致无法证明一次成功是经过重试恢复的。诊断证据：只有最终成功日志，没有中间失败日志。恢复：上游错误和故障必须 100% 保留，采样策略按 `kind` 区分。

## 问答测试样例

1. 正向：本地 Markdown 解析器读取文件时抛出 `ENOENT`，应如何分类？回答：如果文件路径由用户输入决定，则归为用户错误；如果路径由系统配置决定，则归为上游错误。判断依据是路径是否经过业务校验。
2. 正向：403 与 401 有何区别？回答：两者都是能力错误，401 表示未通过认证，恢复动作是获取凭证；403 表示已通过认证但缺少权限，恢复动作是授权。
3. 边界：上游依赖返回 500 并经过三次重试仍失败，最终应返回什么？回答：服务应记录为上游错误，向客户端返回 503 或部分降级结果，绝不能返回 500 让客户端误以为是服务自身故障。
4. 边界：一次请求成功是否能证明系统健康？回答：不能。必须同时观察错误率、延迟分布、重试次数、容量饱和度和恢复成功率。
5. 拒答：当日志中只有一次成功请求且无其他证据时，能否判断“这次成功是否经历过上游失败”？回答：应拒绝判断，标记为未知，并补充分布式追踪或全量日志后再分析。
6. 边界：向量数据库偶发超时但重试后成功，这类调用是否应计入错误？回答：最终 HTTP 状态不计入错误，但上游延迟和重试计数必须计入稳定性指标，作为容量或熔断调整的依据。

## 维护、版本、来源与相邻主题

错误分类 schema 应随业务版本化，存放在 `packages/contracts` 或同等公共模块。新增依赖时，必须同步更新上游错误映射表；新增权限或配额时，必须同步更新能力错误码。维护证据主要依赖项目自身的结构化日志、SLO 看板和故障复盘记录。本主题与相邻主题的关系如下：与“结构化日志”相邻，因为错误证据需要统一日志格式；与“SLO/错误预算”相邻，因为不同类别错误对应不同的预算分配；与“熔断与重试”相邻，因为上游错误需要这两者的配合；与“分布式追踪”相邻，因为 `requestId` 是跨服务证据链的关键；与“类型安全”相邻，因为 TypeScript 的联合类型可以强制分类在编译期被处理。

## 结论

事实是：在 TypeScript 工程中，用户错误、能力错误、上游错误和不可恢复故障有明确的责任边界和运维动作，混淆它们会直接引发重试风暴、资源浪费或数据损坏。推论是：把每次调用的成功、失败、延迟、容量和恢复证据都记录下来，可以显著缩短故障定位时间，并避免只看一次成功请求就得出系统健康的错误结论。未知是：具体部署中的错误率、延迟分布和恢复成功率取决于实际工作负载、依赖版本和容量配置，任何分类策略都需要在真实流量和故障注入实验中持续验证，不能仅凭理论设计断定最优。
