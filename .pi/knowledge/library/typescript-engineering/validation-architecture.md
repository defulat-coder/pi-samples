# TypeScript 工程实践：边界输入校验与内部类型收窄

## 摘要与问题边界

输入校验不是“对所有数据做一遍判断”，而是在进程、主机、模块或信任域之间的边界处，对进入系统的字节流施加结构性与语义性约束，并将通过约束的数据转换为内部已收窄类型。内部逻辑不再重复执行宽松的运行时检查，而是依赖类型系统保证前提成立。本主题覆盖 HTTP 请求体、查询参数、文件内容、环境变量、子进程消息、工具函数参数以及本地知识库检索条件等入口；不覆盖业务规则引擎内部的复杂因果推断，也不替代数据库层完整性约束。

## 核心概念与数据模型

1. **边界（Boundary）**。任何数据从不可控空间进入可控代码的路径。在 TypeScript 工程中，边界至少包括：HTTP 路由处理器、CLI 参数解析器、文件系统读取器、环境变量加载器、Web Worker 消息端口、外部命令返回流以及插件/工具调用入口。同一进程内由本团队维护的函数调用通常不构成边界，除非该函数被设计为跨包公共 API。

2. **校验器（Validator）**。将未知输入映射为已知类型并产生结构化错误的函数。它应当是纯函数：不依赖全局状态、不触发副作用、对同一输入总是返回同一结果。返回类型建议采用 `Result<T, ValidationError[]>` 模式，避免用异常控制正常分支。

3. **已收窄类型（Narrowed Type）**。通过 branded type、模板字面量类型、判别联合或精确元组表示的、比通用原始类型更强的类型。例如 `EmailAddress`、`NonEmptyString`、`SemanticVersion`、`AbsolutePath`。内部函数签名应使用这些类型，而不是 `string` 或 `any`。

4. **校验契约（Validation Contract）**。边界与内部逻辑之间的正式约定，通常体现为 schema 文件、类型定义与测试矩阵。它明确三点：接受哪些形状、拒绝哪些形状、错误如何编码。契约一旦发布，就属于公共 API 的向后兼容范围。

5. **可替换接口（Replaceable Port）**。将校验逻辑抽象为可注入的端口，而不是散落在每个 handler 中。例如定义 `Parser<T>` 接口，由 Zod 实现、io-ts 实现或手写实现替换，业务代码只依赖端口。这样可以在不修改内部逻辑的前提下切换校验库或升级 schema。

6. **失效隔离（Failure Isolation）**。当校验失败时，错误应被限制在边界适配器内，不应污染内部状态、事务或持久化存储。必要时使用只读副本或一次性数据结构，确保拒绝的请求不会留下半初始化对象。

## 设计决策与取舍

**校验层位置：边界优先，业务不变式后置**。将所有检查推到最外层可降低内部逻辑的防御性代码，但某些规则必须依赖业务上下文，例如“同一用户的并发预约不能超过限额”。这类不变式应在校验通过后由业务聚合根执行，而不是在 JSON schema 层表达。

**静态类型无法替代运行时校验**。TypeScript 在编译后擦除类型，因此任何来自 I/O 的数据都必须经过运行时校验，即使 source 是 TypeScript 客户端发送。不能因为两端共享 `.d.ts` 就省略边界校验；网络层、序列化层或中间代理都可能破坏类型假设。

**校验库选择：形状优先，领域规则手写**。Zod、Valibot、arktype 等库适合处理结构、可选字段、联合类型与类型推断；但涉及业务语义（如“该 projectId 是否存在于本工作区”）时，应通过 repository 查询或领域服务校验，避免把数据库逻辑塞进 schema。

**错误反馈粒度：外部 API 粗粒度，内部工具细粒度**。对公网暴露的接口，错误信息应避免泄露字段存在性或内部枚举值，可返回统一格式如 `{ error: 'INVALID_INPUT' }`。对本地开发工具或团队内部 API，可返回字段级诊断，以提升调试效率。

**向后兼容：只增不减，显式弃用**。边界契约新增可选字段是安全的；删除字段、收紧约束或改变错误编码都属于破坏性变更，应通过版本化路径或内容协商处理。建议在 schema 中保留 `deprecated` 标记，并在日志中统计命中次数。

## 可执行的实施流程

1. 枚举所有数据入口，绘制“信任边界图”，标注每个入口的数据来源、序列化格式与调用频率。
2. 在共享包中定义领域模型类型，优先使用 branded type 表达 `Email`、`UUID`、`Path` 等概念，避免内部函数接收裸 `string`。
3. 为每个入口编写校验 schema，schema 的输出类型必须与领域模型类型一致，必要时通过 `transform` 完成从原始值到 branded type 的转换。
4. 将校验器封装为 `Parser<T>` 端口实现，注入到边界 handler，避免在 handler 中直接引用具体库。
5. 在边界 handler 中执行校验，失败时立即返回 400/Bad Request 或等价的本地错误码，不将未经验证的值传给下游。
6. 内部函数签名只接受已收窄类型，并在单元测试中通过类型级断言确保调用点不会传入裸原始值。
7. 构建三层测试矩阵：合法输入正向通过、边界输入精确拒绝、畸形输入触发 schema 错误。每次新增字段时同步补充对应用例。
8. 在生产环境记录校验延迟、拒绝率与错误类别，设置“未处理异常进入内部逻辑”的告警。

## 输入、处理与输出示例

```json
{
  "input": {
    "rawQuery": "  TypeScript validation  ",
    "maxResults": "10",
    "includeDraft": "true",
    "workspaceId": "ws_9fA2bC"
  },
  "boundaryValidation": {
    "trim": true,
    "maxResults": { "coerce": "number", "min": 1, "max": 100 },
    "includeDraft": { "coerce": "boolean" },
    "workspaceId": { "pattern": "^ws_[A-Za-z0-9]{6}$" }
  },
  "output": {
    "query": "TypeScript validation",
    "maxResults": 10,
    "includeDraft": true,
    "workspaceId": "ws_9fA2bC"
  }
}
```

输入层接收字符串与未知格式；边界校验负责裁剪空白、强制类型转换、范围限制与正则匹配；输出层将已验证的值交给内部知识库检索函数，该函数签名使用 branded type `WorkspaceId` 与 `BoundedInteger<1, 100>`，不再重复检查格式。

## 性能、质量和可观测性指标

1. **校验覆盖率**。测量方法：统计所有数据入口中已配置 schema 的入口比例，目标 100%。未覆盖入口应在 CI 中阻断合并。
2. **单次校验 P99 延迟**。通过边界 handler 的 Span 测量从字节到 narrowed 对象的耗时；复杂 schema 应控制在 1ms 以内。
3. **误拒率**。分析日志中重复出现的合法请求被拒绝的模式，计算每周误拒数占请求总数比例，目标低于 0.1%。
4. **内部未处理异常率**。在内部服务入口设置 panic/error 拦截，统计因“断言失败”或“不可能分支”触发错误的数量，若大于零说明边界校验或类型收窄存在漏洞。
5. **类型收窄率**。在类型检查报告中统计 branded type 或精确联合的使用比例，目标核心领域对象中裸 string/number 字段占比低于 10%。

## 失败模式、诊断证据与恢复动作

1. **类型擦除导致运行时越界**。诊断：日志显示 `Cannot read properties of undefined` 且堆栈起始于内部函数而非边界。恢复：为对应入口补全 schema，并在调用链最前端增加解析步骤。
2. **校验器未覆盖新增字段**。诊断：新字段在下游被使用但 schema 仍标记为 unknown 或缺失。恢复：将未知字段默认拒绝，启用 `strict`/`strip` 策略，并建立 schema 变更检查清单。
3. **错误消息泄露内部结构**。诊断：错误响应包含数据库列名或内部枚举值。恢复：在边界适配器中对错误码表做映射，生产环境只返回公开错误标识。
4. **过度校验造成拒绝合法输入**。诊断：客服或监控显示特定客户端版本请求被批量拒绝。恢复：回滚 schema 收紧变更，使用灰度统计评估影响面。
5. **校验与内部类型不同步**。诊断：TypeScript 编译通过但运行时 schema 抛出类型错误，或反之。恢复：将 schema 的输出类型直接导出为领域类型，启用 `satisfies` 检查，并在 CI 中运行类型与 schema 一致性测试。

## 问答测试样例

1. 正向：用户提交合法查询 `maxResults=20`，系统是否返回不超过 20 条结果？预期：通过校验，内部检索函数接收 `BoundedInteger<1,100>` 类型值 20。
2. 边界：`maxResults=0` 应如何处理？预期：边界校验拒绝，返回统一错误码，不进入内部逻辑。
3. 边界：查询字符串仅包含空格，是否视为空查询？预期：先裁剪后校验，若裁剪后为空则拒绝或按业务规则处理为空查询。
4. 边界：`workspaceId` 格式正确但对应的工作区已删除，应由哪一层拒绝？预期：边界只验证格式，业务层通过 repository 查询后返回 404 或业务错误。
5. 无证据：能否断言 Zod 在所有场景下都比 io-ts 快？预期：拒绝回答，除非提供针对本工程负载的基准测试数据。
6. 无证据：输入校验能否完全防止 SQL 注入？预期：拒绝绝对化回答；输入校验可降低风险，参数化查询与最小权限才是最终防线。

## 维护、版本、来源与相邻主题

输入校验 schema 应与 API 版本同步演进，建议采用 OpenAPI 或自定义契约文件作为单一来源。每次修改 schema 必须同步更新类型定义、测试用例与错误码文档。相邻主题包括：序列化/反序列化负责字节到数据结构，输入校验负责数据结构到领域类型，业务不变式负责领域类型到合法状态，认证授权负责身份与权限，可观测性负责验证效果验证。它们共同构成边界防御体系，但不应相互替代。

## 结论

事实：TypeScript 类型在运行时被擦除；所有外部输入都必须经过运行时校验；内部函数使用 branded type 或精确联合可以减少防御性代码。推论：将校验器抽象为可替换端口、把校验失败隔离在边界处，是长期维护成本最低的架构选择。未知：具体项目的最佳校验库、字段级错误信息策略以及 schema 版本化节奏，取决于实际流量特征、合规要求与团队能力，需要本地基准测试与代码审查确认，不能由通用模板直接决定。
