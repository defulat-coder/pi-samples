# Web 流式交互中的断线重连：可恢复性、已完成 Turn 与不可重放流的边界划分

## 摘要与问题边界

在基于 Server-Sent Events（SSE）或 WebSocket 的长连接流式交互中，客户端与服务器之间的任何一次网络抖动都可能导致连接中断。断线重连不是简单的“自动再连一次”，而是一个需要区分三种状态的架构问题：可恢复的连接断开、已经完整结束的 turn，以及不可重放的流。错误地将已完成 turn 当作可恢复流，会导致重复生成；把不可重放流当作可恢复流，则会让客户端永远等待一段已经丢失的数据。本文从架构视角出发，先建立概念边界和可替换接口，再推导具体实现，目标读者是负责协议边界、状态持久化和长期演进的系统设计人员。

## 核心概念与数据模型

1. **Turn（一轮交互）**：一次从用户请求到服务端最终响应完成的完整语义单元。一个 turn 可以包含多个流式片段（chunks），但 turn 的结束由服务端显式标记，而不是由连接是否断开决定。

2. **Stream（流）**：turn 内部的传输层数据通道，负责按顺序推送 chunks。流的生命周期短于或等于 turn；一个 turn 可能因为重连而切换多个流。

3. **Connection（连接）**：传输层 TCP/WebSocket/SSE 会话，只承载流，不拥有 turn 的语义。连接断开不等于 turn 失败。

4. **Resumable Token（恢复令牌）**：服务端为每个 turn 颁发的单调递增序列标识与已确认偏移量。客户端重连时携带该令牌，服务端据此判断哪些 chunks 可以重发、哪些已经确认。

5. **Replay Window（重放窗口）**：服务端在内存或外部存储中保留的已生成但未确认 chunk 的有限时间窗口。超出窗口的流被定义为不可重放。

6. **Completed Marker（完成标记）**：turn 结束时服务端发送的不可变的最终标记，包含校验和与版本号。客户端收到该标记即认为 turn 结束，无需再恢复。

## 设计决策与取舍

### 恢复状态应该放在服务端还是客户端

将恢复状态放在服务端可以简化客户端逻辑，避免在不可靠的浏览器环境中维护复杂状态；但代价是服务端需要为每个活跃 turn 维护会话上下文，增加内存和存储成本。将状态放在客户端可以降低服务端负担，但客户端需要安全地保存大量历史 chunks，且在跨设备场景下不可用。推荐采用服务端主导的轻量令牌加客户端仅缓存最近一个 `last_acked_offset` 的折中方案。

### 重放窗口的长度

窗口越长，可恢复性越好，但存储和一致性成本越高。过短的窗口会把本可恢复的短暂断线变成不可重放。建议以业务可容忍的最大等待时间作为上限，而不是以 chunk 数量作为唯一指标，因为不同模型的生成速率差异很大。一般设置为 60 到 300 秒，并允许按租户调整。

### 重连后是否重置拥塞控制

SSE 基于 HTTP，重连时会复用或新建 TCP 连接，可能触发慢启动。WebSocket 重连则需要新的握手。若业务对延迟敏感，应在协议层之外维护一个应用级心跳，使重连决策不依赖传输层超时，避免在弱网环境下频繁触发 TCP 重传退避。

### 不可重放流的用户体验

当恢复令牌过期或服务端缓存已释放时，必须向客户端明确返回不可重放错误，而不是静默 fallback 到从头生成。因为重新生成会破坏 turn 的幂等性，可能导致用户看到不一致的回答。正确做法是返回 `410 Gone` 语义的错误码，并建议用户重新发起一次新的 turn。

### 心跳与空闲超时

空闲连接容易被 NAT、负载均衡器或移动网络代理切断。心跳间隔必须小于任何中间件的空闲超时。建议服务端发送间隔 15 秒、客户端超时 30 秒的心跳，同时记录心跳丢失事件用于后续诊断。

## 可执行的实施流程

1. 客户端在发起 turn 前从服务端申请一个全局唯一的 `turn_id` 和初始 `stream_token`。
2. 服务端为该 turn 初始化内存缓冲区、单调递增 `chunk_seq` 计数器和 `acked_offset`。
3. 客户端打开 SSE 或 WebSocket 连接，并在请求头或首帧中携带 `turn_id` 与 `last_acked_offset`。
4. 服务端鉴权后校验 `turn_id` 是否存在、是否已结束、是否在重放窗口内。
5. 若 turn 未结束且在窗口内，服务端从 `last_acked_offset + 1` 开始重放缓冲区中的历史 chunks。
6. 客户端收到每个 chunk 后更新本地 `last_acked_offset`，并周期性向服务端发送确认。
7. 服务端在收到确认后释放已确认 chunk 的缓冲区空间，但保留 turn 结束前的最小恢复上下文。
8. turn 正常结束时，服务端发送 `completed_marker`，客户端收到后清理本地恢复状态。
9. 若连接断开，客户端等待指数退避后使用相同的 `turn_id` 和 `last_acked_offset` 重连。
10. 若服务端返回不可重放错误，客户端终止恢复流程并提示用户重新发起 turn。

## 示例：TypeScript 与本地文件知识库的恢复令牌

```json
{
  "turn_id": "turn_20240815_7a3f",
  "stream_token": "st_2k9m",
  "last_acked_offset": 12,
  "completed": false,
  "replay_window_expires_at": "2024-08-15T09:05:00Z"
}
```

输入：客户端在断开 45 秒后携带上述 JSON 重连。处理：服务端检查 `turn_20240815_7a3f` 仍存在，且当前时间早于 `replay_window_expires_at`，于是从第 13 个 chunk 开始推送。输出：客户端补齐缺失内容，直到收到 `completed_marker` 后结束。

## 性能、质量和可观测性指标

1. **重连成功率**：重连后成功补全 turn 的次数占总断线次数的比例，从服务端日志按 `turn_id` 聚合计算。
2. **重放窗口命中率**：重连请求落在重放窗口内的比例，用于调整窗口长度。
3. **重复 chunk 率**：客户端收到重复 chunk 的比例，应接近零，通过 chunk 去重计数测量。
4. ** turn 完成延迟 P99**：从用户发起请求到收到 `completed_marker` 的尾部延迟，排除用户主动取消的场景。
5. **不可重放率**：因窗口过期或状态丢失导致无法恢复的 turn 比例，需按错误码细分。
6. **心跳 false positive 率**：心跳超时但实际网络仍可用的比例，用于校准心跳间隔。

## 失败模式、诊断证据与恢复动作

1. **短暂断线但重放窗口未命中**
   诊断证据：服务端日志显示 `turn_id` 存在但 `replay_window_expires_at` 已过期。
   恢复动作：返回不可重放错误，客户端提示用户重新发起 turn。

2. **客户端确认丢失导致服务端重复推送**
   诊断证据：同一 `chunk_seq` 被多次推送到同一个 `turn_id`。
   恢复动作：客户端按 `chunk_seq` 去重，服务端保留幂等推送语义。

3. **已完成 turn 被误触发重连**
   诊断证据：服务端已记录 `completed_marker` 为 true，但客户端仍发送恢复请求。
   恢复动作：服务端直接返回完成标记，客户端关闭恢复流程。

4. **负载均衡器导致会话粘附失效**
   诊断证据：重连后 `turn_id` 在新节点上不存在。
   恢复动作：将 turn 状态存储到 Redis 等共享存储，或启用 sticky session 并监控节点一致性。

5. **心跳与中间件空闲超时冲突**
   诊断证据：连接在固定时间间隔被切断，如 60 秒、120 秒。
   恢复动作：缩短心跳间隔，或在服务端配置 keep-alive 参数。

## 问答测试样例

1. **正向问题**：当连接断开 20 秒后恢复，客户端应该携带什么信息？
   回答：`turn_id` 和 `last_acked_offset`，服务端据此判断是否在重放窗口内并重放缺失 chunks。

2. **边界问题**：如果 turn 已经结束但客户端未收到完成标记，重连会发生什么？
   回答：服务端返回 `completed_marker`，客户端标记 turn 完成，不再恢复。

3. **边界问题**：重放窗口设置为 0 是否可行？
   回答：技术上可行，但等同于禁用恢复，所有断线都会变成不可重放，仅适用于对一致性要求极高且可接受重新生成的场景。

4. **无证据拒答**：断线重连是否需要客户端保存完整的 chunk 历史？
   回答：不需要，客户端只需保存 `last_acked_offset`，完整历史由服务端在重放窗口内维护。

5. **无证据拒答**：是否可以用新的 `turn_id` 恢复旧的 turn？
   回答：不可以，`turn_id` 是 turn 的全局唯一标识，更换 `turn_id` 会创建新的语义单元。

6. **正向问题**：如何区分可恢复断线和已完成 turn？
   回答：服务端通过 `completed_marker` 和重放窗口共同判断；已完成 turn 返回完成标记，可恢复断线返回缺失 chunks。

## 维护、版本、来源与相邻主题关系

本文档应与流式协议规范、会话管理文档和错误码表同步维护。每次修改恢复令牌结构或重放窗口默认值时，必须更新版本号并在 API 变更日志中标注。断线重连与会话管理、消息幂等、背压控制和离线队列是相邻主题；它依赖会话管理识别用户身份，依赖消息幂等避免重复生成，依赖背压控制防止重放时淹没客户端，与离线队列的区别在于断线重连只处理同一个 turn 内的临时中断，不处理跨 turn 的异步投递。

## 结论

**事实**：断线重连必须区分可恢复断线、已完成 turn 和不可重放流；`turn_id`、`last_acked_offset`、`completed_marker` 和重放窗口是四种核心机制。

**推论**：将恢复状态主要放在服务端、客户端仅保存最小确认偏移，是在 Web 浏览器环境下较均衡的架构选择。

**未知**：在极端弱网或频繁切换网络接口的移动设备上，最优的心跳间隔和最大重连次数需要结合实际用户数据进一步验证；不同负载均衡器的空闲超时分布也会影响推荐参数。
