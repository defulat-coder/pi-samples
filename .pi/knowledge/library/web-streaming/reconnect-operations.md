# Web 流式交互中的断线重连：可恢复断开、已完成 Turn 与不可重放流的运维判定

## 摘要与问题边界

断线重连不是“网络恢复后自动再试一次”的兜底逻辑。在 Web 流式交互里，一次 TCP 断开可能对应三种完全不同的语义：服务端仍在生成内容但传输层中断的可恢复断开；服务端已经发出结束标记、客户端只是没来得及接收的已完成 Turn；以及服务端无法按原样重新生成内容的不可重放流。运维视角的核心任务是建立证据链，把“连接是否恢复”与“业务结果是否正确”分开度量，避免因为一次偶发成功请求就认定系统可靠。

本文只讨论浏览器到服务端、基于 SSE、WebSocket 或 HTTP 流式响应的长连接恢复机制，不涉及分布式事务两阶段提交、数据库主从切换或 CDN 边缘缓存刷新。重点放在如何区分可恢复与不可恢复状态、如何在重连后保持消息顺序、以及如何留下可验证的恢复证据。

## 核心概念与数据模型

1. **会话三元组**：持久 `session_id`、临时 `transport_id` 与 `turn_id` 必须解耦。`session_id` 标识用户对话上下文，`transport_id` 标识一次具体网络连接，`turn_id` 标识一次完整的请求-响应回合。
2. **分片序号**：每个数据块携带单调递增的 `seq`，空分片可作为心跳占位。客户端记录 `highest_received_seq` 与 `last_ack_seq`，二者之差即为未确认窗口。
3. **完成标记**：Turn 结束由显式 `EOS` 或 `turn_completed=true` 标记，而不是由连接关闭推断。连接关闭可能发生在服务端已发送 EOS 之后，也可能发生在生成中途。
4. **可恢复性判定**：服务端收到重连请求后，检查 `turn_id` 是否存在、对应 `seq` 是否仍在重放窗口内、以及生成过程是否仍处于可继续状态，返回 `recoverable`、`completed` 或 `non_replayable`。
5. **重放日志**：按 `turn_id` 和 `seq` 索引的追加式缓存，保留时长必须小于等于协议声明的恢复窗口，并受内存与磁盘预算限制。
6. **观测证据链**：一次可验证的重连必须同时包含客户端断连事件、服务端连接释放事件、重连握手事件和首包恢复事件，缺少任意一环都不能算作成功恢复。

## 设计决策与取舍

### 服务端保留状态还是无状态化

有状态服务端保存生成器对象与重放日志，恢复路径短，但单节点故障时需要状态迁移或 sticky session。无状态服务端要求模型输出可完全确定地按相同输入重新生成，或者依赖外部缓存，否则无法恢复。多数 Web 流式场景采用“短时有状态 + 可配置窗口”的折中。

### 重放全量还是仅补增量

全量重放从 Turn 起始重新推送，客户端逻辑简单，但浪费带宽且可能导致重复渲染。增量恢复从 `last_ack_seq+1` 开始，要求客户端能区分已渲染、已确认、仅收到未确认三种状态，并在渲染层做去重。建议默认增量恢复，同时保留全量回退路径。

### 幂等键的生成策略

如果模型输出具有随机性，必须使用服务端生成的 `turn_id` 作为唯一标识，而不是把用户消息哈希作为幂等键。后者会导致不同会话中相同提问被错误映射到同一次生成结果，或旧上下文被新请求污染。幂等键只用于重试同一 Turn，不用于跨会话复用结果。

### 传输层与心跳设计

SSE 在 HTTP/2 上更容易穿透企业代理，WebSocket 握手次数少但可能被防火墙静默切断。无论哪种传输，都必须配置应用层心跳，周期应小于代理空闲超时的一半。心跳缺失时，服务端要释放生成器，避免僵尸资源占用。

### 退避策略与窗口对齐

客户端退避采用指数退避加抖动，最大间隔必须小于服务端重放窗口。若服务端窗口为 30 秒，而客户端最大退避为 60 秒，则任何超过 30 秒的断连都会变成不可恢复，退避策略形同虚设。

## 可执行的实施流程

1. 在会话建立时分配全局唯一且稳定的 `session_id`，与具体传输连接分离。
2. 协议层要求每个数据块都携带 `turn_id`、`seq`、`timestamp` 和可选的 `chunk_hash`。
3. 客户端维护两个游标：`highest_received_seq` 表示已收到的最大序号，`last_ack_seq` 表示已向服务端确认的最大序号。
4. 服务端为每个活跃 Turn 维护一个固定大小的重放窗口，并记录最近一次客户端确认时间。
5. 启用应用层心跳：客户端在静默周期内发送 `ping`，服务端超时未收到则主动关闭连接并回收资源。
6. 断连检测需要区分网络错误、服务端主动关闭、浏览器后台冻结与代理静默切断。
7. 重连握手携带 `session_id`、`turn_id`、`last_ack_seq`，服务端返回恢复状态与下一个起始 `seq`。
8. 恢复成功后，服务端从 `last_ack_seq+1` 开始推送；若 Turn 已完成则返回完整输出摘要；若已超时则返回 `non_replayable` 并触发新 Turn。

## 本地配置与消息格式示例

以下是一个项目级 YAML 配置片段，用于定义本地知识库中保存的断线重连协议参数。该配置会被 API 在启动时加载，并在握手阶段返回给客户端。

    recovery:
      transport: "sse"
      heartbeat_interval_ms: 15000
      replay_window_ms: 30000
      max_reconnect_backoff_ms: 25000
      session_cookie_name: "pi_session"
      chunk_schema:
        required: ["turn_id", "seq", "payload", "eos"]
        ack_field: "last_ack_seq"
        completion_field: "eos"

输入为客户端初次握手时提交的 JSON：`{"session_id":"s_7a3f","turn_id":"t_91b2","last_ack_seq":42}`。服务端在接收到该输入后，查找 `turn_id` 对应的重放日志，判断 `seq=43` 是否在窗口内。处理过程中会更新 `last_seen_at` 时间戳并生成新的 `transport_id`。输出为恢复响应：`{"status":"recoverable","resume_from":43,"transport_id":"tr_x9k1"}`，随后服务端从 43 开始补发后续分片。如果 `turn_id` 已结束且 EOS 已发出，则输出 `{"status":"completed","turn_id":"t_91b2","summary_hash":"a1b2..."}`。客户端应使用摘要校验本地内容是否完整。

## 性能、质量和可观测性指标

1. **恢复成功率**：在恢复窗口内发生的断连中，最终成功续传的比例。通过服务端 `recoverable` 响应数除以断连事件总数计算。
2. **断连到首包延迟**：从客户端触发重连到收到第一个恢复分片的中位时间与 P99。需要在客户端记录 `reconnect_start_at` 与 `first_recovered_chunk_at`。
3. **重放窗口命中率**：请求恢复的 `seq` 范围落在重放日志内的比例，低于阈值说明窗口过短或资源回收过早。
4. **服务端每会话资源占用**：包括生成器对象内存、重放日志条目数和磁盘 IOPS，应在压力测试中按并发会话数绘制基线。
5. **客户端虚假重连率**：无实际服务端状态丢失却触发重连的比例，可通过比对客户端 `reconnect` 事件与服务端 `connection_lost` 事件来识别。
6. **最终一致性偏差率**：Turn 结束后客户端渲染内容与服务器端 `summary_hash` 不匹配的比例，是判断重连是否真正正确的金标准。

## 失败模式、诊断证据与恢复动作

1. **半开连接**。证据：服务端日志持续出现 `write timeout` 且客户端无后续 `seq` 到达，但服务端认为连接仍活跃。恢复动作：启用 TCP keepalive 与应用层心跳，服务端在写超时后主动释放生成器。
2. **重放窗口过期**。证据：客户端重连请求返回 `410 recovery_expired`，服务端重放日志已无该 `turn_id`。恢复动作：向用户返回“该轮回复已无法续接”，引导发起新 Turn。
3. **幂等键误用**。证据：相同 `turn_id` 关联的上下文哈希不匹配，或客户端收到与之前语义矛盾的后续内容。恢复动作：握手时校验 `context_hash`，不一致则拒绝恢复。
4. **客户端缓存污染**。证据：客户端请求的 `last_ack_seq` 大于服务端已发送的最大 `seq`。恢复动作：服务端返回 `seq_out_of_range`，客户端清空本地缓存并重新初始化该 Turn。
5. **浏览器后台冻结**。证据：`visibilitychange` 事件记录页面进入 `hidden`，随后心跳间隔显著拉长超过阈值。恢复动作：页面重新可见时主动刷新 `transport_id` 并重连，不要依赖被节流的心跳。
6. **代理静默切断长连接**。证据：应用层心跳正常，但超过代理空闲超时后无数据收发，抓包显示连接被 RST。恢复动作：采用 HTTP/2 ping 帧或降低心跳间隔至代理超时的一半以下。

## 问答测试样例

1. 正向问题：客户端持有 `session_id`、`turn_id` 和 `last_ack_seq`，服务端重放窗口未过期，应返回什么恢复状态？预期答案：`recoverable`，并从 `last_ack_seq+1` 开始推送。
2. 边界问题：服务端已发送 EOS，但客户端未收到最后一个分片，重连后如何处理？预期答案：服务端返回 `completed` 状态及完整内容摘要，不应重新进入生成状态。
3. 边界问题：`last_ack_seq` 等于服务端当前最大 `seq`，且 EOS 尚未发出，重连后应收到什么？预期答案：先收到 EOS 或继续等待后续生成，不应重复已确认分片。
4. 无证据拒答条件：仅客户端感觉“卡顿”，没有断连事件也没有服务端超时日志，能否确认需要重连？预期答案：不能，必须等待心跳超时或收到明确的网络错误码。
5. 边界问题：移动端从 WiFi 切换到蜂窝网络导致 IP 变化，是否可恢复？预期答案：可以，只要 `session_id` 和 `turn_id` 保持不变且传输层不绑定 IP。
6. 正向问题：如何验证一次成功恢复后内容没有丢失或重复？预期答案：客户端重新组装内容并计算哈希，与服务端返回的 `summary_hash` 比对，一致方可认为恢复正确。

## 维护、版本、来源与相邻主题关系

断线重连协议应在握手阶段进行版本协商，当 `seq` 语义、完成标记或重放窗口默认值发生变化时，必须升级协议次要版本。本文内容基于项目内部实现约定与本地压力测试数据，不引用未经验证的外部系统状态。相邻主题包括：限流与背压控制、负载均衡下的会话亲和性、身份令牌刷新、消息全局排序、以及端到端 exactly-once 语义。这些主题与断线重连存在接口依赖，但各自有独立的边界条件，不应混为一谈。

## 结论

事实：断线重连必须区分可恢复断开、已完成 Turn 和不可重放流；`turn_id`、`seq` 与 `last_ack_seq` 是区分的最小数据单元；恢复成功应以客户端最终内容哈希与服务端摘要一致为最终判据。

推论：在移动网络与企业代理环境下，应用层心跳周期设置为代理空闲超时的一半以下，可显著降低半开连接与静默切断导致的恢复失败；增量恢复比重放全量更节省带宽，但要求客户端维护更复杂的状态机。

未知：不同浏览器在后台冻结时对 `setTimeout` 与 WebSocket 心跳的节流策略差异尚未形成统一基线；长连接在 HTTP/3  over QUIC 上的迁移行为对本协议的最优窗口时长影响仍待实测。
