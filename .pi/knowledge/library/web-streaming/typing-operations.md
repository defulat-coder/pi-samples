# Web 流式交互中的输入状态：回答生成、工具执行与等待重试的全链路状态语义

## 摘要与问题边界

输入状态在 Web 流式交互中不是“用户是否正在打字”这一单一信号，而是会话生命周期内服务端对外暴露的、可被客户端订阅并用于故障定位的进度语义。它必须覆盖大模型回答生成、工具调用请求、工具执行挂起、重试等待以及最终完成或失败的全过程。本主题的边界限定在以 Server-Sent Events（SSE）或 JSON Lines 流为传输层、Agent 会话为处理单元、客户端仅消费不推导服务端内部状态的架构。超出边界的内容包括：用户侧的输入法组合状态、浏览器焦点状态、非流式的一次性 HTTP 响应，以及无需暴露给客户端的模型内部推理token。

验证与运维视角的核心诉求是：任何一次状态转换都必须留下可审计证据，避免工程师只看到一次成功请求就得出系统健康的结论。成功、失败、延迟、容量和恢复证据需要被同时记录，状态协议本身要支持重放、幂等和跨会话恢复。

## 核心概念与数据模型

1. **输入状态是一个生命周期信号，而不是 UI 动画标签**。它的作用是告诉客户端“服务端当前在做什么”，而不是为了让按钮转动。因此状态值必须能够映射到可观测事件，例如 `tool_execution_start`、`tool_execution_end`、`retry_scheduled`。

2. **状态空间由八个互斥值构成**：`idle`、`receiving`、`generating`、`tool_calling`、`tool_executing`、`retrying`、`error`、`completed`。互斥意味着同一时刻客户端只能看到一个主状态，服务端内部可以存在子状态，但对外推送时必须先聚合。

3. **状态转换必须由明确的事件触发**。`generating` 到 `tool_calling` 的转换只能由模型输出中包含的工具调用请求触发；`tool_calling` 到 `tool_executing` 的转换只能由客户端或服务端确认工具参数有效后触发；`retrying` 必须由可重试错误且未达到最大重试次数触发。

4. **状态与消息增量（delta）是两条独立通道**。文本增量、思考增量、工具调用增量属于内容通道；状态变更属于控制通道。控制通道必须携带序列号 `state_seq`，内容通道必须携带 `delta_seq`，两者都基于同一个单调递增的全局 `stream_seq`，以便客户端在重连时按序恢复。

5. **状态持久化用于会话恢复，而非实时同步**。服务端将每个状态转换写入会话存储，存储粒度到“最近一次已确认推送的 `stream_seq`”即可。恢复时从该序列号之后重放事件，而不是重算模型输出。

6. **状态与可观测性事件的映射是一对多**。一个 `tool_executing` 状态可能对应多个内部事件：工具开始执行、执行进度心跳、执行完成。对外只推送状态变化，但内部日志必须保留全部事件，用于后续排查。

## 设计决策与取舍

### 粗粒度状态与细粒度心跳的平衡
细粒度状态有利于调试，但会增加 SSE 流量和客户端重绘频率。建议状态推送只在主状态转换时发生；在同一个 `tool_executing` 阶段内，使用独立的 `progress` 心跳事件补充进度，心跳不改变主状态。这样可以避免状态枚举膨胀，同时保留长时间工具执行的可见性。

### 客户端推断与服务端显式推送
不允许客户端根据文本增量推断当前处于 `generating` 还是 `tool_calling`。所有状态必须由服务端显式推送。这一决策增加了服务端实现复杂度，但消除了因客户端推断不一致导致的“状态漂移”类故障。客户端的状态机只负责渲染，不负责状态计算。

### 状态超时与心跳机制
每个非终态都必须有超时上限。`tool_executing` 的超时应区分工具类型：本地命令 30 秒、网络请求 60 秒、大文件处理 300 秒。超时未收到进度心跳则强制迁移到 `retrying` 或 `error`。心跳间隔建议 5 秒，超过两个心跳周期未收到则客户端可认为连接异常。

### 错误状态的重试归属
并非所有错误都进入 `retrying`。可重试错误包括网络抖动、模型服务瞬时不可用、工具依赖临时超时；不可重试错误包括参数校验失败、权限拒绝、模型输出格式非法。`retrying` 状态必须在事件载荷中说明 `retry_count`、`max_retries` 和 `next_retry_at`，否则客户端无法判断剩余等待时间。

### 并发工具调用的状态聚合
当模型一次请求多个工具调用时，服务端不能为每个工具调用单独推送状态，否则客户端会看到混乱的状态抖动。统一进入 `tool_executing`，在全部工具结果返回或部分失败达到阈值后再做聚合决策。如果需要暴露单个工具进度，使用同一状态下的 `sub_task_progress` 数组，数组元素包含 `tool_call_id` 和 `progress`。

## 可执行的实施流程

1. 定义状态枚举和 JSON Schema，明确每个状态的有效载荷字段、必填项和迁移条件。
2. 在会话层建立统一事件总线，所有状态相关事件必须带有 `session_id`、`stream_seq`、`state_seq` 和 `timestamp`。
3. 实现服务端状态机，确保状态迁移函数为纯函数，输入为当前状态与事件，输出为新状态与副作用描述。
4. 在 SSE 推送层引入确认机制：关键状态变更要求客户端在 10 秒内回复 `ack`，否则服务端保留重放能力。
5. 客户端实现状态消费器，仅根据 `state_seq` 更新 UI，不根据内容增量推断状态。
6. 配置超时与心跳：非终态 5 秒心跳，工具执行按类型设置上限，重试等待使用指数退避。
7. 集成重试逻辑，重试前必须记录 `retry_scheduled` 事件，重试后记录 `retry_attempted` 事件。
8. 接入可观测性：每个状态转换输出结构化日志，并暴露 `/metrics` 端点供 Prometheus 抓取状态停留时长直方图。

## TypeScript 示例：状态机消费 SSE 事件

以下示例展示一个在浏览器端消费服务端状态流的最小化状态机。输入是从 SSE 流中解析出的 `AgentEvent` 对象；处理逻辑根据事件类型更新当前主状态；输出是渲染层可消费的 `SessionState`。此示例适用于本地文件知识库相关的工具调用场景，例如读取 `.pi/knowledge` 中的 Markdown 文件。

输入：服务端推送的事件包括 `state_update`、`text_delta`、`tool_execution_start`、`tool_execution_end`、`retry_scheduled`、`completed`。每个事件都携带 `stream_seq` 和 `state_seq`。

处理：状态机维护 `lastConfirmedSeq`，只处理大于等于该值的事件，忽略乱序和重复事件。当收到 `state_update` 时，直接替换当前状态；当收到 `tool_execution_start` 时，如果当前状态不是 `generating`，则记录异常并仍然进入 `tool_executing`，保证鲁棒性；当收到 `retry_scheduled` 时，迁移到 `retrying` 并记录下一次重试时间。

输出：渲染层读取 `SessionState` 中的 `phase`、`toolCalls`、`retryInfo` 和 `lastConfirmedSeq`，用于展示当前阶段、工具执行列表和恢复进度。`phase` 只能是 `idle | receiving | generating | tool_calling | tool_executing | retrying | error | completed` 中的一个。

## 性能、质量和可观测性指标

1. **状态转换延迟**：从事件产生到客户端收到 `state_update` 的时间差。测量方式是在服务端事件总线处记录 `event_emitted_at`，在客户端收到时计算差值，按状态类型分桶上报。
2. **重试次数分布**：统计每个会话中 `retry_scheduled` 的次数，按状态类型和错误码分组。异常信号是同一 `session_id` 在 1 分钟内重试超过 5 次。
3. **工具执行挂起时间**：`tool_executing` 状态的累计停留时长，减去实际工具执行时间得到等待与序列化开销。超过 P99 阈值 80% 时需要扩容工具执行器。
4. **客户端状态偏差**：通过客户端周期性上报 `lastConfirmedSeq` 与服务端 `lastEmittedSeq` 对比，差值大于 0 表示存在未确认或丢失的状态推送。
5. **会话恢复成功率**：连接断开后，客户端携带 `lastConfirmedSeq` 重连，服务端成功重放并达成最终一致的比例。低于 99.5% 视为可用性异常。

## 失败模式、诊断证据与恢复动作

1. **状态消息丢失**。诊断证据：客户端 `lastConfirmedSeq` 持续落后，UI 长期停留在 `generating`。恢复动作：客户端检测到两个心跳周期无状态更新后主动断开并重连，服务端从 `lastConfirmedSeq + 1` 重放事件。
2. **状态机卡住**。诊断证据：服务端日志显示同一状态持续超过最大超时时间，且无新事件进入。恢复动作：由外部看守进程强制迁移到 `error` 并关闭会话，避免资源无限占用。
3. **工具执行超时**。诊断证据：`tool_execution_start` 与 `tool_execution_end` 之间的时间差超过类型上限，伴随进度心跳缺失。恢复动作：标记该工具调用失败，根据错误类型决定是否进入 `retrying`；若不可重试则进入 `error`。
4. **重试风暴**。诊断证据：同一上游依赖在短窗口内触发大量 `retry_scheduled`，错误码多为 503 或超时。恢复动作：实施熔断，暂停新请求进入 `retrying`，返回 `error` 并附带 `upstream_unavailable` 原因。
5. **客户端状态漂移**。诊断证据：客户端上报的状态与服务端记录不一致，常发生在客户端根据内容增量自行推断状态时。恢复动作：强制客户端以服务端最后一次 `state_update` 为准刷新，移除客户端推断逻辑。

## 问答测试样例

1. 正向问题：当模型输出包含工具调用请求时，状态应如何迁移？答案：从 `generating` 迁移到 `tool_calling`，并等待参数确认后再进入 `tool_executing`。
2. 正向问题：工具执行期间客户端应如何获知进度？答案：通过不改变主状态的 `progress` 心跳事件或 `sub_task_progress` 数组。
3. 边界问题：如果工具执行超时但错误可重试，状态是 `retrying` 还是 `error`？答案：`retrying`，且事件必须携带 `retry_count` 和 `next_retry_at`。
4. 边界问题：多个工具并发执行时，其中一个失败、一个成功，主状态是什么？答案：只要还有工具未完成，主状态保持 `tool_executing`；全部结束后根据失败比例聚合为 `completed` 或 `error`。
5. 无证据拒答：如果服务端没有推送 `state_update`，客户端能否自行推断处于 `generating`？答案：不能，必须有服务端显式事件证据。
6. 无证据拒答：如果日志中只有客户端 UI 截图，能否判定状态机正确？答案：不能，需要服务端事件序列和 `stream_seq` 一致性校验。

## 维护、版本、来源与相邻主题

输入状态协议应独立版本化，建议采用 `state_protocol_version` 字段，当前版本为 `1.0.0`。版本升级时必须保证旧客户端至少能识别八个主状态，新增字段不得破坏旧字段解析。来源可追溯至 SSE 事件流规范与 Agent 会话事件协议。相邻主题包括“消息增量协议”“工具调用格式”“会话重连与恢复”“可观测性埋点”。输入状态与这些主题的关系是：消息增量协议负责内容顺序，工具调用格式负责触发条件，会话重连负责状态持久化，可观测性负责证据记录。

## 结论

事实：输入状态必须由服务端显式推送，包含八个互斥主状态，且每个状态转换都应有对应的可观测事件。推论：在运维实践中，如果状态通道与内容通道分离并引入序列号确认机制，可以显著降低客户端状态漂移和重连不一致的概率。未知：在不同浏览器网络环境下，SSE 重连时的状态重放延迟分布尚未有大规模生产数据验证；同时，极端高并发场景下状态聚合对服务端内存占用的影响也需要进一步基准测试。
